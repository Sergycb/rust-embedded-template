# Сопровождение шаблона

Этот файл — только про сам репозиторий шаблона: как устроен каскад выбора чипа,
откуда берутся плейсхолдеры и раскладка памяти, чем и как проверять изменения.
В сгенерированные проекты он не копируется (`ignore` в `cargo-generate.toml`),
поэтому всё, что должно жить в проекте пользователя, — в `AGENTS.md` и
`docs/**`, а не здесь.

Работаете в этом репозитории — читайте оба: `AGENTS.md` и `docs/**` описывают
архитектуру и конвенции, которые шаблон раздаёт проектам (`CLAUDE.md` здесь —
только импорт `AGENTS.md` плюс специфика Claude Code, см. раздел ниже про то,
что едет в проект пользователя), `MAINTAINING.md` — механику самой раздачи.

## Что здесь есть, чего нет в проектах пользователей

- `chip-select.rhai` — pre-хук: каскадный выбор чипа, `memory.x`, `write_size`,
  `ota`, `dual_core`, `bank_mode`, `erase_zero`, `watchdog_peripheral`,
  `cpu_freq_boost`, `cache`, `core_baseline`, `bank_switch`, `dual_bank_bit`, `dfu_bank`. Хуки
  cargo-generate в результат
  не копируются.
- `chip-data/` — сгенерированные таблицы, которые хук подключает через `import`
  (каталог в `ignore`; `import` находит его и так): `chips.rhai`, `packages.rhai`,
  `bank_mode.rhai`, `bank_switch.rhai`, `watchdog.rhai`, `cpu_freq_boost.rhai`,
  `rng.rhai` (линия и клок блока `RNG`: `rng_irq`, `rng_clock`, `rng_source`),
  `cache.rhai` (кэши чипа, теги через пробел: `icen`/`dcen` — биты `FLASH_ACR`, `icache` — блок `ICACHE`),
  `interfaces.rhai` (интерфейсы связи, выведенные в корпусе: `usart`, `fdcan`,
  `bxcan`, `eth`, `usb`, `otg` — по ним хук проверит ответ об интерфейсе) и
  `layout/<семейство>.rhai` — раскладка памяти, разложенная по первым двум символам
  суффикса (`f4`, `h7`, `wb`). Целиком раскладка — ~89 тысяч строк, а хуку нужна одна
  запись, поэтому он импортирует только файл своего семейства. Руками не правится.
- `post-script.rhai` — post-хук: сводка «что дальше» для пользователя. Команд
  не выполняет: `cargo update` оттуда убран (см. «Почему генерация из локального
  пути такая медленная»), поэтому и `--allow-commands` при генерации не нужен.
- `chip-data-gen/` — два инструмента мейнтейнера (каталог в `ignore`):
  - `cargo run --manifest-path chip-data-gen/Cargo.toml` — перегенерирует
    `chip-data/` целиком;
  - `cargo run --manifest-path chip-data-gen/Cargo.toml --bin template-check` —
    генерирует проект во временный каталог и прогоняет в нём весь набор
    проверок (см. «Порядок проверки» ниже).
- `.github/workflows/template.yml` — CI репозитория шаблона (см. «Что из этого
  делает CI» ниже); у сгенерированных проектов свой `ci.yml` рядом.
- `MAINTAINING.md` — этот файл.

Наоборот, едут — граница по тому же признаку «конвенции для кода в проекте
пользователя, а не про сопровождение шаблона»: `AGENTS.md` и `docs/**`
(рендерятся Liquid'ом, как и остальной шаблон: doc-блоки в `docs/modules/`
несут собственные `{%- if graph == "true" %}`, поэтому в `exclude` их
добавлять нельзя — там команды приезжают с настоящим чипом), и
`.claude/rules/*.md` (под git, правила по путям для домена/прошивки). А вот
рабочие файлы самого Claude Code внутри `.claude` — `settings.local.json`,
реестр агентов, расписания, mailbox и т.п. — не едут: они поимённо в `ignore`
`cargo-generate.toml`, каталог `.claude` целиком там больше не значится (см.
комментарий там же).

## Плейсхолдеры шаблона (`cargo-generate.toml`)

`{{chip}}`, `{{chip_feature}}`, `{{cpu}}`, `{{target}}`, `{{write_size}}`,
`{{page_size}}`, `{{swap_paged}}`, `{{state_erase_size}}`, `{{state_paged}}`, `{{config_erase_size}}`, `{{config_paged}}`, `{{boot_partitioned}}`, `{{config_store}}`,
`{{shared_flash}}`, `{{dual_core}}`, `{{bank_mode}}`, `{{erase_zero}}`,
`{{watchdog_peripheral}}`, `{{cpu_freq_boost}}`, `{{dfu_bank}}`, `{{bank_switch}}`, `{{dual_bank_bit}}`,
`{{rust_lib}}`, `{{newline}}` — плейсхолдеры, подставляемые
Liquid-рендером cargo-generate. Из них в `[placeholders]` объявлен только `ci`; вопросы про OTA, настройки,
граф, транспорт и протокол задаёт сам хук после выбора чипа (см. «Вопросы в хуке» ниже), а все остальные
выставляет `variable::set` в `[hooks].pre`-скрипте
`chip-select.rhai` — каскадный посимвольный выбор STM32 (семейство → линейка → дальше по
символу) по списку чипов, одновременно валидных и для `embassy-stm32`, и для
установленного локально `probe-rs`. Не `init`-хук: init-хуки выполняются ДО резолвинга
`--define`-значений с CLI в liquid-объект (проверено эмпирически — с `init`
`variable::is_set("chip_feature")` внутри hook не видит `--define chip_feature=...`,
попытка каскадного `variable::prompt` в неинтерактивном/`--silent` режиме падает с
`IO error: not a terminal`), `pre` — после, и объявлять сами эти плейсхолдеры в
`[placeholders]` тоже не нужно: `variable::set` работает независимо от декларации, а
`--define` по-прежнему читается через `variable::is_set`/`variable::get` внутри самого
hook.

### Значение в корневом workspace (`rust_lib`, `newline`)

Адрес rust-lib — одна переменная `rust_lib` (хук; умолчание —
`https://github.com/Sergycb/rust-lib`, форк — `--define rust_lib=…`, хранится
без `.git`). В `crates-cross/Cargo.toml` и документации она подставляется
обычным `{{rust_lib}}`. Корневой `Cargo.toml` и `deny.toml` так не могут: в
репозитории шаблона они рабочие (`cargo xtask lint`, `cargo deny check`), а
Liquid в корневом workspace живёт только в `#`-комментариях. Поэтому там пара:

```toml
# {%- comment %}
supervisor   = { git = "https://github.com/Sergycb/rust-lib.git" }
# {%- endcomment %}
#{{newline}}supervisor   = { git = "{{rust_lib}}.git" }
```

В шаблоне первая строка рабочая, вторая — комментарий; в проекте первой нет, а
`{{newline}}` (хук задаёт его как `"\n"`) отрывает строку от `#`, и она
становится рабочей. Адрес в `comment` и умолчание в хуке — одно и то же значение,
меняются вместе.

### `${{ ... }}` в файлах GitHub Actions обязано быть в `{% raw %}`

Выражения GitHub Actions начинаются с тех же двух скобок, что и Liquid, и
cargo-generate честно пытается их подставить. Наткнувшись на неизвестную переменную, он
**пропускает подстановку во всём файле целиком** — не в строке, а в файле. Проверено
эмпирически: в файле с голым `${{ secrets.TOKEN }}` рядом стоявший `{{target}}` тоже
приезжал в проект сырым.

Поэтому в `.github/workflows/*.yml` каждое такое выражение оборачивается:

```yaml
GH_TOKEN: {% raw %}${{ secrets.GITHUB_TOKEN }}{% endraw %}
```

Внутри `raw` Liquid ничего не трогает, а остальной файл рендерится как обычно (тот же
`{{target}}` рядом подставляется). Симптом нарушения — не ошибка генерации, а тихо
сломанный workflow у пользователя, поэтому проверка стоит в `template-check`
(`check_no_raw_placeholders`); она же умеет отличать легитимное `${{ ... }}` в готовом
проекте от пережившего генерацию плейсхолдера — см. `without_actions_expressions` там
же. GitLab этой проблемы лишён: он подставляет переменные через `$VAR`.

`ota` и `config` — два плейсхолдера, которые хук не просто читает, а перезаписывает.
Спрашиваются они строкой `yes`/`no` (тип `bool` не годится: `variable::get` в rhai
читает только строки и падает с «Variable ota not a String» — проверено), а хук
приводит ответ к `"true"`/`"false"`, на которые смотрят Liquid-условия. «Нет» —
окончательное: для `ota` это один образ на весь flash, `crates-cross/boot` и
разделы OTA в `crates-cross/bsp/src/flash.rs` уходят (файл целиком — если нет и общего замка под настройки), даже если схема в чип помещается; для `config` —
удаление `crates-cross/bsp/src/settings.rs`. «Да» в обоих случаях означает лишь «не возражаю»:
решает всё равно раскладка, и на чипе с крупными секторами ответ будет тем же
«нет», только с объяснением.

Порядок между ними не симметричен: раздел настроек решается ПЕРВЫМ, потому что
меняет всю OTA-схему — в хвосте он отрезает flash, а в резерве перед `ACTIVE` теснит
bootloader и `STATE`. Отсюда и второй набор цифр в `MEMORY_LAYOUT` (см. ниже). Ситуации
«OTA помещалась, пока не попросили раздел настроек» с тех пор, как раздел может лечь в
резерв перед `ACTIVE`, нет ни у одного чипа, и отдельного совета про неё хук больше не
печатает: не помещается схема с настройками — причина та же, что и без них.

`signed` (подпись OTA-образа) — не вопрос, а производная от итогового `ota`: есть OTA —
есть подпись, нет OTA (в том числе если схема не поместилась во flash) — нет и подписи.
`--define signed=...` на него не влияет. В шаблоне он управляет фичей `signed` у `domain` (проверка подписи — `domain::ota::boot`, ею пользуется `boot`), ключом в `crates-cross/boot`
(`boot/build.rs`, `OTA_PUBLIC_KEY_IN_IMAGE`, вызов `screen_update`), выбором
`Updater<_, _, true>` в `bsp::ota` и файлом `crates-cross/app/src/image.rs`
(`FW_VERSION` для `Mode::Signed`; без подписи его удаляет `post-script.rhai`). Подпись проверяет bootloader
(`domain::ota::boot::screen_update`), приложение — только длину, занятость и версию
(`domain::ota::update::apply_signed`), см. docs/ota.md.

`modbus_master` (Modbus master, клиентская половина; по умолчанию `no`) — той же формы:
строка `yes`/`no`, хук приводит ответ к `"true"`/`"false"`. Смысл он имеет только при
`protocol=modbus`: меню спрашивает его только тогда, а `--define modbus_master=yes` при другом
протоколе — ошибка (`no` принимается). Master не получают ни protobuf, ни CANopen. «true» оставляет `ports::ModbusClient`/`MasterError`,
`domain::modbus::master`, клиентские impl'ы транспортов `Rtu`/`Tcp`/`Udp` (в них же
слив `MAX_DRAIN` RTU и `master_error`) и их тесты; «false» вырезает всё это
Liquid-блоками `// {%- if modbus_master == "true" %}` … `// {%- endif %}` (в
комментариях, как и остальные условия в `crates-host`), а `domain/src/modbus/master.rs`
хук удаляет `file::delete` — только при `protocol=modbus` и «false» (без modbus каталог
`modbus` уходит целиком). `MAX_LOST_IN_A_ROW` в UDP master'у не принадлежит — им пользуется
и приём slave'а, поэтому остаётся в обоих вариантах. Тесты —
`modbus_master_*` в `chip-data-gen/tests/cascade.rs`, конфигурации
`modbus-master`/`modbus-uart` в `template-check`.

Четвёртый — `graph` (граф задач `supervisor`). Он выключается по размеру: раздел, в
который линкуется приложение (`ACTIVE` при OTA, иначе весь flash за вычетом настроек),
сравнивается с `GRAPH_MIN_PARTITION` — 32 KiB. Порог эмпирический, обе точки замерены
сборкой: на STM32L011F4 (16 KiB, Cortex-M0+) линкер не досчитывает двух сотен байт, на
STM32C011D6 (32 KiB, то же ядро) проект занимает 12.6 KiB из 32. Сам `supervisor`
стоит около полутора килобайт на Cortex-M4 и до пяти на Armv6-M, где крупнее и код, и
арифметика времени. Обе стороны решения закреплены тестом каскада
`graph_is_dropped_when_the_app_partition_is_too_small`; менять порог — вместе с ним.

Протоколу связи граф не нужен: при `graph=no` (и когда граф снят размером) узел
протокола и его `NET`/`USB` спавнит `tasks::spawn_all` (модули задач в
`crates-cross/app/src/tasks/` над `domain::{modbus,host,canopen,net,usb}::task`,
как `ota::task`). Транспорт протокола собирает `crates-cross/app/src/link.rs`, так что
`graph.rs` и модули задач строят один и тот же объект. Тест каскада —
`protocol_does_not_need_the_graph`, конфигурации `*-no-graph` в `template-check`.

В ветке ручной раскладки (`--define write_size=...`) размер раздела знает только
человек, поэтому ответ пользователя проходит как есть: не влезет — скажет линкер.

`--define chip_feature=...` сверяется со списком валидных чипов (`CHIPS.contains(suffix)`)
— опечатка ловится сразу при генерации, а не на `cargo build` в сгенерированном проекте.
Массив `CHIPS` из-за этого объявлен на верхнем уровне скрипта (не внутри `if`/`else`) —
он нужен обеим веткам. `chip`/`cpu`/`target` в конце скрипта выставляются только если ещё
не заданы (`if !variable::is_set(...)`) — их тоже можно переопределить отдельным
`--define`, независимо от `chip_feature` (см. таблицу `PACKAGE_CHOICES` ниже — override
`chip` заодно и пропускает её).

Все таблицы в `chip-data/` (список валидных чипов `CHIPS`, уточнение корпусировки
`PACKAGE_CHOICES`, банковая схема `BANK_MODE`, раскладка памяти `MEMORY_LAYOUT` и
остальные) пишет `chip-data-gen` — целиком, через соседний `chip-data.tmp` и подмену
каталога, чтобы файлы всегда были одного поколения и не оставалось файлов исчезнувших
семейств. Хук берёт их `import`'ом и копирует в одноимённые `const`, так что дальше по
скрипту они выглядят как раньше. Пишет их `chip-data-gen` — отдельный
standalone-крейт в корне репозитория, НЕ
член корневого `[workspace]` (свой `Cargo.toml` с пустым `[workspace]`) и НЕ часть
шаблона: он инструмент обслуживания САМОГО РЕПОЗИТОРИЯ, запускается мейнтейнером вручную
(`cargo run --manifest-path chip-data-gen/Cargo.toml`) при обновлении версии
`embassy-stm32` в `crates-cross/Cargo.toml` (обычный semver-пин на crates.io, сейчас `0.6.0` —
не путать с git-зависимостями на `main` из rust-lib, см. правило 2 ниже) или локальной
версии `probe-rs-tools`, и не
должен попадать в проекты пользователей шаблона — отсюда `ignore = ["chip-data-gen"]` в
`[template]` (не `exclude`: тот лишь отключил бы Liquid-подстановку, но файл всё равно
скопировался бы и упал с "invalid syntax" на буквальном `{{chip_feature}}` в исходнике
самого генератора; и без глоба `/**` — с ним cargo-generate директорию не распознаёт,
нужно имя каталога как есть, тоже проверено эмпирически). Он не может быть частью
`crates-host/xtask/`, хотя тот и выглядит подходящим местом по названию — `crates-host/xtask/` сам шаблонный
крейт и копируется в проекты пользователей, а этому инструменту там не место. Логика
`chip-data-gen`: чип-фичи `embassy-stm32` — из `cargo metadata` (полный список
объявленных features пакета, не только резолвящихся для этого воркспейса); валидные
идентификаторы probe-rs — из `probe-rs chip list`; итоговый список — пересечение (чип
исключается из каскада, если `embassy-stm32` его знает, а установленный `probe-rs` ещё
нет). Двухъядерные чипы (STM32H745/747/755/757, STM32WL54/55) кодируют выбор ядра
суффиксом прямо в чип-фиче embassy (`stm32h745zi-cm7`/`-cm4`) — probe-rs про этот
суффикс не знает (одна цель `STM32H745ZI` на оба ядра), поэтому `chip` вычисляется от
части ДО дефиса, а `cpu`/`target` для такого суффикса берутся не из таблицы по
семейству, а из отдельного `core_override()` в `chip-select.rhai` (там же и полный
список причин).

Для этих ~60 двухъядерных чипов каскад дополнительно выставляет переменную `dual_core`
(`"true"`/`"false"`, безусловно — без `--define`-override, см. `is_dual_core()` в конце
`chip-select.rhai`). Она выбирает ветку **прямо при генерации**, Liquid-условием
`{% if dual_core == "true" %}` в `crates-cross/bsp/src/board.rs` и `crates-cross/boot/src/main.rs`: в
проект попадает ровно одна реализация `init_peripherals()` — под двухъядерный чип
`embassy_stm32::init_primary(config, &SHARED_DATA)` (`SHARED_DATA` — локальная
`static MaybeUninit<SharedData>`, требуемая сигнатурой, никуда не публикуется), под
одноядерный обычный `init()`. Комментарий про AMP и option byte BCM4 тоже лежит внутри
двухъядерной ветки и в одноядерный проект не попадает.

Раньше здесь была Cargo-фича `dual-core` у `crates-cross/bsp`/`crates-cross/boot`, а в исходниках —
обе реализации под `#[cfg(feature = ...)]`. **Фичи больше нет** (убрана по решению
пользователя: в проект не должен попадать код для чужого класса чипа), не восстанавливать
без запроса. Свойство «рассинхрон шумит» при этом сохранилось: `init_primary` не
существует без настоящей `_dual-core` у `embassy-stm32` (её он включает сам для любой
`"...-cmN"` чип-фичи), поэтому ошибочный `--define dual_core=true` на одноядерном чипе
по-прежнему даёт ошибку компиляции, а не тихую сборку с чужим API.

**Осознанное ограничение** (не забытая деталь, зафиксировано по решению пользователя —
не расширять без отдельного запроса): код пишется только под ОДНО ядро — то, что
выбрано в каскаде (например `stm32h745zi-cm7` — CM7). Шаблон не генерирует для второго
ядра ни кода, ни отдельного образа, взаимодействие с ним не оркеструется. Это НЕ значит,
что второе ядро гарантированно бездействует — зависит от семейства:

- **STM32WL54/55**: CPU2 (CM0+) по умолчанию не стартует при сбросе, пока CPU1 (CM4) явно
  не выставит `PWR_CR4.C2BOOT` — сгенерированный код этого не делает, второе ядро реально
  остаётся выключенным.
- **STM32H745/747/755/757**: по умолчанию (option bytes BCM7=BCM4=1 у большинства ревизий)
  ОБА ядра стартуют при сбросе. CM4 стартует с адреса `BOOT_CM4_ADD0` (заводское значение —
  `0x08100000`, база Flash Bank2) — это ровно `dfu_origin` из `MEMORY_LAYOUT` для этих
  чипов (см. `chip-select.rhai`). После первого OTA-обновления там окажется валидный образ
  прошивки CM7, и CM4 начнёт параллельно исполнять его же поверх общей периферии/DMA —
  необслуживаемая гонка, а не бездействующее ядро. **Перед использованием обязательно
  проверьте/снимите BCM4** (или уведите `BOOT_CM4_ADDx` на пустую область) через
  `probe-rs`/STM32CubeProgrammer — шаблон это не делает и не может: это единоразовая
  настройка конкретной платы, а не то, что можно зашить в прошивку.

Полноценная symmetric/asymmetric AMP-поддержка потребовала бы: второй независимый
прошиваемый образ (свои `cpu`/`target`, свой `chip_feature` — второе ядро чипа) в рамках
одной генерации, `SharedData` по одинаковому адресу в обоих `memory.x` (а не локальная,
как сейчас), решение по оркестрации прошивки и `run` для двух образов и по OTA
двух прошивок в `crates-cross/boot` (сейчас рассчитан на одну). Это отдельная архитектурная
задача, не входит в шаблон.

Проверено ТОЛЬКО компиляцией (`cargo generate` → `cargo xtask build`/`lint cross` на
`stm32h745zi-cm7`), не на реальном железе — поведение второго ядра на конкретной плате
(включая факт того, включён ли у неё BCM4 из коробки) не проверялось. Однопроцессорные
чипы (в т.ч. остальные H7 — H743/H753 и т.п.) не затронуты — в их проекты попадает
одноядерная ветка, `Board::new()`/`main()` вызывают обычный `init()`, как раньше.

У чип-фич с суффиксом силиконовой градации, не обозначающим ядро (например `-a`/`-x` у
STM32L1xx — автомобильный температурный диапазон, не путать с `-cm7`/`-cm4` у
двухъядерных выше), просто взять часть ДО дефиса недостаточно: например для
`stm32l151c6-a` этот дефолт (`STM32L151C6`) существует и валиден, но не самый точный — у
probe-rs есть более специфичные `STM32L151C6TxA`/`STM32L151C6UxA` (16 KiB RAM против
10 KiB у общей цели — настоящая automotive-версия). Между собой такие цели различаются
только корпусировкой (`Tx`/`Ux`/`Hx`/`Yx`) — по `probe-rs chip info` они побайтово
идентичны (ядро, память), так что выбирать между ними незачем: `chip-data-gen` находит
все такие цели через `package_candidates()` и пишет их массивом в `PACKAGE_CHOICES`
(`chip-data/packages.rhai`), а
хук берёт первую (`PACKAGE_CHOICES[suffix][0]`) без вопроса — список из `BTreeSet`, поэтому
детерминирован. `CORE_MARKERS` в `chip-data-gen` (должен буквально совпадать со
списком в `core_override()`) исключает ядерные суффиксы из этого поиска — там
семантика другая (реально разные ядра, а не корпусировка одного и того же).

### Банковая схема (`bank_mode`, блок `BANK_MODE`)

У ~194 чипов (G4 cat3, L4+, F7, F4 dual-bank, L5, G0) `stm32-metapac` несёт НЕСКОЛЬКО
карт памяти — одно- и двухбанковую. Для них `build.rs` самого `embassy-stm32` ТРЕБУЕТ
фичу `single-bank`/`dual-bank` и без неё паникует («Chip supports single and dual bank
configuration. No Cargo feature to select one is enabled»), то есть сгенерированный
проект не собирается вовсе. `select_memory_config` повторяет его предикаты по именам
регионов (`BANK_1` без `BANK_2` → одобанковая) и предпочитает одобанковую: непрерывный
`ACTIVE`, а read-while-write, ради которого нужна двухбанковая, `crates-cross/boot` не
использует. Для одноконфигурационных чипов `bank_mode` — пустая строка, и `{% if %}` в
`crates-cross/Cargo.toml` фичу не выводит: лишняя фича так же фатальна («The 'single-bank'
feature is not supported on this dual bank chip»).

Предпочтение одобанковой стоит одного шага в прошивке: у G4 cat3, L4+, L5 и G0B/G0C с завода стоит
двухбанковый режим, и `bsp/src/banks.rs` (его же зовёт `boot` — `bsp::banks`) переключает
его при первом старте. Каким чипам, какой вариант регистров (`g0`/`g4`/`l4`/`l5`) и какой бит режима
(`g4:22`; у L4+/L5 бит зависит от объёма — `bank_switch_bits`) — блок
`BANK_SWITCH`: версия блока FLASH из метаданных через таблицу `FACTORY_DUAL_BANK` в
`chip-data-gen` — заводское значение option byte в метаданных нет, оно из документации. Каждый
вариант входит в набор `default_cases()` в `template-check` (`stm32g474re`,
`stm32g0b1rc`, `stm32l4r5zi`, `stm32l552ze`; список актуален на момент записи —
сверяйте с файлом), на плате — не проверен.

Второй банк за разрывом в адресах (`bank2_of` + проверка «вне цепочки» в
`compute_memory_layout`) — у 36 чипов с фиксированным dual: H742/743/745/747 и H7A3 с
1 MiB, U5F7/U5F9 с 2 MiB. С внутренней OTA там `DFU` в банке 2, раскладка несёт ключ
`dfu_bank_origin`, хук по нему выставляет `dfu_bank` и считает `__bootloader_dfu_*` от
начала банка, а `boot`/`bsp` пишут `DFU` через `Bank2Region` (почему не через цельный
`Flash` — docs/flash.md, «Банки flash»). Ветку проверяет `template-check`
(`stm32h743zg`, `dfu-bank`). Стыкующиеся банки — один непрерывный flash, `DFU` к банку
2 не привязан.

### Сторожевой таймер (`watchdog_peripheral`, блок `WATCHDOG`)

`bsp` объявляет поле `Peri<'static, peripherals::IWDG…>` и псевдоним
`wdg::BoardWatchdog = Iwdg<peripherals::IWDG…, HW_TIMEOUT_US>`, а имя типа в `embassy-stm32`
— ровно то, что стоит в метаданных: у 800 наборов из 891 это `IWDG`, у 91 — `IWDG1`
(H7), и у 32 из них рядом ещё `IWDG2` (двухъядерные H7: первый принадлежит ядру CM7,
второй CM4). Блок `WATCHDOG` перечисляет только исключения — 131 чип каскада, — а
остальным хук подставляет `IWDG`; полная таблица на 1479 строк повторяла бы одно и то
же слово рядом с уже сорока девятью тысячами сгенерированных.

Читается это не из `<chip>/metadata.rs`, в отличие от карты памяти: там лежат только
имя, семейство и `memory`, а перечень блоков — в общем файле, который тот включает
первой строкой (`include!("../metadata_0180.rs")`) и делит с десятками других чипов.
Отсюда две функции вместо одной: `parse_included_metadata` и `parse_watchdog_names`,
плюс кеш разобранных общих файлов.

Из того же общего файла берётся признак `CPU_FREQ_BOOST` (блок `CPU_FREQ_BOOST`,
переменная `cpu_freq_boost`): блок `PWR` версии `h7rm0468` — 25 чипов
H723/725/730/733/735. Им `bsp` получает `src/clocks.rs`, остальным хук его удаляет
(docs/clocks.md). Поэтому кеш хранит не список имён, а `SharedMetadata` — оба факта
файла разом.

Кэши (блок `CACHE`, переменная `cache`) выводятся так же, из метаданных: `icache` — есть блок
`ICACHE` в общем файле; `icen`/`dcen` — есть ли `set_icen`/`set_dcen` в файле регистров
`FLASH` его версии (`stm32-metapac/src/peripherals/flash_<версия>.rs`, `chip_caches`) — таблицы
семейств нет. Кэши ядра M7 в блок не входят: хук добавляет тег `scb`, когда выбранное каскадом
`cpu` — `cortex-m7` (так двухъядерный H745 получает его только в `-cm7`). Чипу без тегов хук
удаляет `crates-cross/bsp/src/cache.rs`; `board.rs`, `lib.rs` и `unstable-pac` в манифесте `bsp`
смотрят на ту же переменную. Тест — `caches_follow_the_metadata_and_the_core`.

Кэш данных ядра M7 (тег `scb_d`) включается только вместе с регионом `DMA_NC`: `chip-data-gen`
(`dma_nc_region`) отрезает до 32 KiB от конца RAM (`PANIC` уходит под регион) и кладёт в
запись раскладки `dma_nc_origin`/`dma_nc_length`. RAM у H7 — самая большая непрерывная
область (AXI-SRAM), а не DTCM с `0x20000000`; у остальных семейств — цепочка с `0x20000000`
(у WB более крупная SRAM2 — память радиостека CPU2); у ядра CM4 двухъядерных H7 — SRAM домена
D2 с `0x30000000`, мимо AXI-SRAM ядра CM7. `DMA_NC` не берётся из SRAM домена D2:
до неё не дотягивается IDMA SDMMC1; у H7 `SRAM4` в `0x38000000` целиком — `bdma_nc_*` (память BDMA).
Ядро M7 генератор берёт по семейству (`f7`/`h7`, не `-cm4`) — как `family_table` в хуке.
Хук выставляет `dma_nc_start`/`dma_nc_len` и `bdma_nc_*` (в `[env]` `crates-cross/.cargo/config.toml`),
удаляет `bsp/src/dma_nc.rs` там, где региона нет, дописывает `scb_d` в `cache` и вставляет в
`memory.x` приложения `SECTIONS { .dma_nc, .bdma_nc } INSERT AFTER .gnu.sgstubs;` (`INSERT AFTER
.uninit` не собирается под `flip-link`: проверено сборкой; инвариант «в `memory.x` нет SECTIONS»
в `memory_layout_invariants_hold_for_every_chip` сделан исключением для этих секций).
Тест — `every_m7_chip_gets_a_dma_region`. `DCACHE` (U5/H5) и предвыборка намеренно не включаются —
`docs/clocks.md`, «Кэши».

`core_baseline` ("true" для Cortex-M0/M0+/M23 по `cpu`) — ядра без `DWT.CYCCNT`, `CFSR` и
`DIV_0_TRP`: им нет `bsp::cycles` с `Board::cycles` и `ports::cycles`, а `bsp::fault` собирается
короче (`pc`/`lr`). Тест — `baseline_cores_are_marked`. `bsp::fault` остаётся у всех: обработчик
`HardFault` в нём ссылкой из `Board::new` держится в образе (в ELF есть `bsp::fault::__cortex_m_rt_HardFault`, `rust-nm`); на плате фолт не вызывался.

Когда блоков два, метаданные обоих ядер перечисляют оба — различить их там нечем, и
выбор делается по суффиксу ядра (`-cm4`), который каскад **уже** выбрал. Это не
эвристика по имени чипа: имя блока по-прежнему приходит из метаданных, по суффиксу
решается только который из двух. Настоящую эвристику по имени сюда заводить нельзя —
ровно на ней погорел признак `erase_zero` (см. ниже).

### Раскладка памяти (`write_size`, `ota`, блок `MEMORY_LAYOUT`)

`embassy-stm32` уже зависит (фича `metadata`) от `stm32-metapac`, а тот для каждого чипа
несёт `chips/<chip>/metadata.rs` — обычный Rust-файл с литералом `Metadata { memory: &[&[
MemoryRegion { address, size, settings: Some(FlashSettings { erase_size, write_size, ..
}) } ]] }`, читается текстом без сборки (`parse_chip_memory`). **Формат при этом не
один**: у одноконфигурационных чипов `stm32-data` печатает `memory: &[&[` одной строкой,
у многоконфигурационных — `memory: &[` и `&[` на следующей. Поэтому разбор идёт счётом
скобок (`split_memory_configs`), а не поиском литерала `memory: &[&[`, как раньше — на
том поиске ~194 чипа молча выпадали из генерации.

Отсюда `chip-data-gen` считает адреса/размеры (`compute_memory_layout` +
`compute_ota_partitions`) и пишет их в `MEMORY_LAYOUT`, а хук в конце — если для чипа
есть запись и `write_size` не задан через `--define` — выставляет `write_size`/`ota` и
пишет `memory.x` через `file::write` (во временную копию шаблона ДО рендера — то самое
"the template folder", о котором предупреждает документация `file::write`, не в
`crates-cross/*/memory.x` этого репозитория).

**`erase_zero` в записи — из `erase_value` того же `FlashSettings`**, а не из имени
чипа. Раньше хук считал признак как «фича начинается на `l0`/`l1`» — и мимо проходили
STM32WB10CC/WB15CC (`erase_value: 0` при другом префиксе, оба в каскаде): проект под
них получал `embassy-boot` без `flash-erase-zero` и неработающий раздел настроек, обе
поломки молчаливые. Эвристика по имени осталась одним последним рубежом в хуке — на
случай чипа, которого нет в таблице (сейчас таких нет), — и печатает предупреждение.
Стережёт это тест каскада `erase_zero_follows_the_metadata_not_the_chip_name`, где
рядом с `wb10cc`/`wb15cc` стоит `wb55rg` с обычным флешем: без него зелёным остался бы
и вариант «всё семейство WB стирается в ноль».

**`page_size` в записи есть, а в `memory.x` его нет** — и это не забытая строка.
`page_size` записи — физическая страница чипа (максимальный сектор стирания), а
плейсхолдер `{{page_size}}` — **страница обмена** `embassy-boot` (`PAGE_SIZE`), поле
`swap_page_size` набора цифр (`config_swap_page_size` во втором): она больше физической,
когда `swap_paged` = "true" (см. ниже). Нужна она не линкеру, а host-target тесту обмена
разделов: `swap()` кладёт `ACTIVE[i]` в `DFU[i + 1]`,
то есть прежний образ уезжает ровно на страницу, и без этого числа его негде искать.
Поэтому хук раздаёт его отдельной переменной, а `xtask` передаёт тесту. В ветках, где
раскладку пишет человек, переменная пустая — «неизвестен»; тест тогда сам себя
пропускает, а не ищет по выдуманному адресу.

**Наборов цифр в записи чипа два.** Второй, с префиксом `config_`, — раскладка того же
чипа с разделом настроек (`compute_config_partition`). Без OTA раздел — две последние
страницы flash (`config_origin`/`config_length`/`config_erase_size`), и `FLASH`
приложения короче на них. С OTA раздел считается двумя способами — в хвосте (тогда
`ACTIVE`/`DFU`/`BOOTLOADER_STATE` съезжают целиком: `compute_ota_partitions` считает их
ОТ размера доступного flash) и в мелких секторах резерва перед `ACTIVE`
(`place_settings_and_state`: bootloader, настройки, `STATE`), — и берётся тот, где
`ACTIVE` больше, при равенстве хвост. Где он оказался — `config_ota_settings_*`.
Хук выбирает набор одной строкой (`let key = if config { "config_" } else { "" }`) и
дальше берёт из него всё. Считать это в rhai нельзя: там пришлось бы повторить все
четыре проверки `assert_partitions` из `embassy-boot`. В резерв раздел встаёт, только
если bootloader'у перед ним остаётся `BOOTLOADER_TARGET` (32 KiB), а не `BOOTLOADER_MIN`:
выгоду для `ACTIVE` нельзя оплачивать бинарником bootloader'а — без этой границы на
равносекторных чипах раздел ужимал bootloader до 16 KiB ради одной-двух страниц. Цифры:
раздел возможен на 1429 чипах из 1479, из них на 1183 вместе с ним помещается OTA (на
остальных 20 из 1203 с OTA она не помещается и без раздела — `ACTIVE` меньше
`OTA_MIN_ACTIVE`); в резерв перед `ACTIVE` раздел лёг у 223 чипов F2/F4/F7, у остальных
он в хвосте.

**Файлы у `app` и `boot` разные.** У `app` `FLASH` = `ACTIVE` (приложение линкуется
именно туда), у `boot` `FLASH` = его собственная зона до `BOOTLOADER_STATE`. Раньше
писался один и тот же текст с `FLASH` от базы flash — и прошивка руками (`cargo flash -p boot --release`, затем
`cargo run -p app`) затирала бы bootloader образом приложения; OTA не работал ни на одном чипе.
Смещения `__bootloader_*` в обоих файлах считаются от литерала базы flash, а НЕ от
`ORIGIN(FLASH)`: их читает `embassy-boot`, работающий с флешем целиком, а `ORIGIN(FLASH)`
у `app` теперь означает начало `ACTIVE`.

**Выводятся ВСЕ регионы чипа**, а не только `FLASH`/`RAM`. `FLASH` и `RAM` — это
непрерывные цепочки от базовых адресов (их имена требует `link.x` у `cortex-m-rt`), а всё
остальное `extra_region_lines` отдаёт готовыми строками под своими именами из
`stm32-metapac`: ITCM, AXISRAM, CCMRAM, BKPSRAM, EEPROM, OTP и т.д. Раньше их не было
вовсе — на H723VE пользователь видел 128 KiB DTCM и не видел ни 320 KiB AXISRAM, ни
64 KiB ITCM, ни трёх SRAM. Две категории при этом выводятся ЗАКОММЕНТИРОВАННЫМИ, с
причиной прямо в строке:

- **окна внешних шин** (`EXTERNAL_BUS_PREFIXES` — `FMC_`, `SDRAM_`, `OCTOSPI_`, ...):
  памяти за ними нет, пока к плате не припаяна микросхема и не настроен контроллер.
  У всех них в метаданных стоит одинаковый размер 262144000 — это не память, а максимум
  адресного окна;
- **вторые окна того же блока** (`ALIAS_SUFFIX` — `CCMRAM_ICODE` при живом
  `CCMRAM_DCODE`, `SRAM2_ICODE` при живом `SRAM2`): физически это одна и та же память по
  двум адресам, и разместить данные в обоих окнах разом — молчаливое наложение, которого
  линкер не заметит.

Ограничения — четыре runtime-assert'а `assert_partitions` (`boot_loader.rs` из
`embassy-boot`; именно assert'ы, а не документация: нарушены — bootloader паникует на
старте, а не отказывается собираться):

1. `ACTIVE` кратен `PAGE_SIZE`;
2. `DFU` кратен `PAGE_SIZE`;
3. `DFU - ACTIVE >= PAGE_SIZE` — запас алгоритма swap;
4. `2 + 4 * (ACTIVE / PAGE_SIZE) <= BOOTLOADER_STATE / NorFlash::WRITE_SIZE`.

`PAGE_SIZE` здесь — **не** плейсхолдер `write_size`, а `max(ACTIVE::ERASE_SIZE,
DFU::ERASE_SIZE)`, который `embassy-boot` вычисляет сам; обе партиции живут поверх
цельного `Flash` (`crates-cross/boot/src/main.rs`), у которого `NorFlash::ERASE_SIZE =
MAX_ERASE_SIZE` всего чипа, — либо поверх `ErasePage<_, SWAP_PAGE_SIZE>`, если страницу
обмена расширили (абзац про `swap_paged` ниже). Плейсхолдер `write_size` — это const generic
`BootLoader::prepare::<_,_,_,N>`, размер буфера подкачки: обязан делить `PAGE_SIZE`, быть
кратным `NorFlash::WRITE_SIZE` и не меньше него — `NorFlash::WRITE_SIZE` чипа (4/8/32)
удовлетворяет всем трём, его и подставляем. Имя плейсхолдера осталось прежним ради
совместимости с проектами, задающими его через `--define`.

Четвёртый assert — причина, по которой `BOOTLOADER_STATE` нельзя делать «просто одним
сектором»: в нём лежит журнал прогресса swap, по слову на страницу `ACTIVE` в каждом из
четырёх проходов плюс два служебных. На L4 (1 MiB при секторе 2 KiB) это `(2 + 4*247) * 8`
байт — четыре сектора, а не один. Раньше здесь всегда стоял ровно один сектор, и **279 из
972 посчитанных раскладок роняли bootloader в панику при первом же старте** (среди них
l476rg — Nucleo-L476RG). Теперь размер `BOOTLOADER_STATE` подбирается под фактический
`ACTIVE`, а резерв при необходимости растёт на страницу (`BOOTLOADER_MIN` — сколько
обязано остаться под сам бинарник). Чтобы это не разъехалось снова, перед возвратом
раскладки вызывается `assert_embassy_boot_invariants` — те же четыре проверки, но на
этапе генерации.

`BOOTLOADER`/`BOOTLOADER_STATE` кратности `PAGE_SIZE` не подчиняются (в
`assert_partitions` их нет) и режутся по локальной границе сектора — на чипах с крупными
секторами (F4/F7/H7, до 128 KiB) целая страница под один отступ съела бы четверть чипа.
Но **пятая проверка** — уже не из `assert_partitions`, а из `Partition::new`
(`embassy-embedded-hal`): смещение и размер раздела кратны `ERASE_SIZE` флеша под ним,
иначе паника при построении раздела. Над цельным `Flash` (страница — `MAX_ERASE_SIZE`)
`STATE` в мелком секторе её не проходил, и у всех 223 чипов F2/F4/F7 с OTA и bootloader,
и приложение падали на первом старте. Теперь `STATE` живёт над `flash_page::ErasePage`
со страницей своего сектора — она лежит в записи полем `bootloader_state_erase_size`
(и `config_…` во втором наборе), хук раздаёт её плейсхолдером `state_erase_size`, а
`assert_embassy_boot_invariants` проверяет кратность всех трёх разделов своей странице.
`state_paged`/`config_paged` = "true", только если эта страница не равна физической
(`page_size`): тогда раздел оборачивается в `ErasePage`, иначе строится прямо над `Whole`, а
`const`-assert (`… == MAX_ERASE_SIZE`) держит равенство. `boot_partitioned` — строит ли
bootloader хоть один раздел над `BlockingPartition` (`STATE` со своей страницей или `ACTIVE`/`DFU`
со страницей обмена): только тогда ему нужны `FLASH_BYTES` и обёртки.
Сам сектор выбирает `place_state` — самый мелкий в резерве, как можно ближе к `ACTIVE`;
на чипах с равными секторами раскладка от этого не изменилась, на F4 `STATE` — 16 KiB в
секторе 3 вместо 64 KiB в секторе 4.
Краевой случай, ради которого `reserved_pages` растёт в цикле, — чипы, где уже первый
регион занимает целый `PAGE_SIZE` (H7 — 128 KiB с адреса 0, без мелких секторов в начале,
в отличие от F4): иначе `BOOTLOADER_STATE` съедал бы весь резерв.

**Страница обмена крупнее физической (`swap_paged`).** Подписанный `boot` весит ≈23 KiB,
а журнал из проверки 4 на чипе с мелкой страницей огромен: у L0 (страница 128 байт, ~640
страниц, слово 4) `STATE` — 10 KiB из блока в 32 KiB (`BOOTLOADER_TARGET`). Поэтому
`compute_ota_partitions` — обёртка над `compute_ota_at`, которая считает раскладку для
страницы обмена `S = p·2^k` (p — физическая, `S <= SWAP_PAGE_MAX` = 8 KiB) и берёт первую,
при которой журнал `(2 + 4*N) * WRITE_SIZE <= STATE_BUDGET` (2 KiB); `compute_ota_at`
считает всё — резерв, `ACTIVE`, `DFU`, сдвиг `ACTIVE` — в единицах `S`, а `STATE` по-прежнему
кладёт в физические сектора (`bootloader_state_erase_size`, отдельное число). Расширяется
только чип с равными секторами и без `DFU` в банке 2 за разрывом (`dfu_bank`): на
F2/F4/F7/H7 страница обмена и так крупнейший сектор, а банк 2 лежит в другом регионе
`Flash`. Не уложились на 8 KiB — остаётся физическая страница, а запас под код держит
`BOOTLOADER_MIN` (26 KiB; резерв растёт не менее чем на `MAX_EXTRA_RESERVED_BYTES` = 8 KiB
независимо от размера страницы). Запись несёт `swap_page_size` и `swap_paged` (и `config_…`
во втором наборе); хук выставляет `page_size` = `swap_page_size` и `swap_paged`; для `ota=no`,
`ota=external`, `dfu_bank` и ручной раскладки `swap_paged` = "false". Прошивка (`boot`,
`bsp::flash`) при "true" оборачивает `ACTIVE` и `DFU` в `flash_page::ErasePage<_, SWAP_PAGE_SIZE>`,
число — то же `{{page_size}}` (менять только вместе). `DFU` не короче `ACTIVE` + `S` и кратен
`S` (бывает на страницу длиннее, если остаток чётный). Инвариант «у каждого чипа с OTA зона
bootloader'а не меньше `BOOTLOADER_MIN`» стережёт `bootloader_zone_and_swap_page_hold_for_every_chip`.

### OTA на внешней флеши (`ota=external`, наборы `ext_*` и `ext_cfg_*`)

Третий и четвёртый наборы цифр в `MEMORY_LAYOUT` — `compute_external_ota`: внутри
только bootloader и `ACTIVE`, снаружи `STATE`, `DFU` и место под настройки, всё по
`ext_align`; `ext_cfg_*` — то же с настройками во внутреннем флеше (зона bootloader'а
или хвост). Почему так и какие числа — `docs/flash.md`. Проверки, которые
`assert_partitions` и `Partition::new` делают на плате, повторяет при генерации
`assert_external_invariants`.

Хук выбирает набор по ответу `ota` (`internal`/`external`/`no`; незнакомый ответ —
ошибка генерации) и `config`, пишет `memory.x` с символами-смещениями внешней флеши и
выставляет `ota_store` (на него смотрят `boot`, `bsp::flash`, `bsp::settings`,
`target-tests`, `xtask`) и `ext_page_size`.

**Вопросы в хуке.** Чип выбирается первым (каскад по символам или `--define chip_feature=...`),
а OTA, настройки, граф, транспорт и протокол спрашивает сам хук — в таком порядке, и
`variable::prompt` показывает только допустимое для чипа (`ask()`, блок «Вопросы» в
`chip-select.rhai`): граф, который не влезает в раздел приложения, и интерфейс без блока
у чипа не предлагаются, протоколы берутся из `PROTOCOL_INTERFACES` для выбранного
транспорта; OTA и настройки, не помещающиеся на чип, остаются в меню с пометкой «НЕ
ПОМЕЩАЕТСЯ» — их выбор включает ручную раскладку (хук ставит `write_size`, как при
`--define write_size=...`). Объявить эти вопросы в `[placeholders]` нельзя: `cargo-generate`
задал бы их сам до выбора чипа (и требует `prompt` у любого объявленного).
Транспорты — один список с отметками `transports:` (`TRANSPORT_ITEMS`): у хуков
`cargo-generate` только одиночный выбор, поэтому отметка `[x] `/`[ ] ` нарисована в
тексте пункта, и меню после каждого выбора показывается заново; первый пункт `готово`
— он же умолчание и ответ без терминала (тогда проект без транспортов). Пункт — вид,
по одному: `uart`, `can`, `ethernet` (пока транспорт `tcp`), `usb`, и только если у
чипа есть блок вида (`free_blocks()` — блоки всех его меток из `INTERFACES`). Имени
блока в пункте нет: транспорт получает первый свободный блок вида, а меняют его в
`resources.rs` — об этом и о назначенных блоках говорит `post-script.rhai`. Затем
`protocol:` — на каждый отмеченный транспорт, в порядке пунктов. Протокол в проекте пока один:
когда он выбран, следующему транспорту предлагаются только он и `none`, а виду, поверх
которого он не работает, вопрос не задаётся; `modbus_master` — один раз, при первом
Modbus. Через `--define` то же задаёт `links` (`parse_links()`, вместо пары
`interface` + `protocol`), и отсев чипов до каскада тогда считает блоки каждого вида.
Итог — переменная `links` (`вид:метка:блок:протокол:имя` через запятую; имя — блок
строчными, у `tcp`/`udp` — сам вид) и `has_*`. Файлы шаблона идут по `links`
циклом Liquid: у каждого транспорта своя группа в `resources.rs`, подмодуль драйвера
в `bsp` (`bsp::serial::<имя>`, `bsp::can::<имя>`, `bsp::usb::<имя>`), подмодуль
транспорта в `app` (`app::link::<имя>`, `app::usb::<имя>`), поле `Board` (или драйвер в
`bsp::Drivers`) и узел графа или модуль задачи без графа. `interface`,
`iface_periph` и производные от них считаются по основному транспорту (первый с
протоколом, иначе первый) и остались там, где речь об одном блоке (подсказки
`cargo xtask pins` в документации).
Сетевые службы — следом, только когда среди транспортов есть `tcp` или `udp`: список
с отметками `net_services:` (`NET_SERVICE_ITEMS`, тот же `checklist()`, что у
транспортов); `ssh` в нём только у чипа с RNG (`rng_irq`), иначе хук печатает, почему
его нет. Отмечен `ssh` — `ssh_auth:` (`password` — умолчание, `key`), при `key` — ввод
строки `ssh_key:` (`variable::prompt` с regex; пустой ввод — вход по паролю). Ключ из
ввода и из `--define` хук проверяет одинаково — `ssh_key_ok()`: тип, блоб ровно 68
символов base64, без кавычек и `\` (строка уедет в исходники).
Итог — `net_services` (`ssh,rest` в порядке пунктов, через `--define` — в порядке
списка), `ssh_auth`, `ssh_key`; пустые строки, когда не выбрано. Шаблон их пока не
читает: узлов служб ещё нет. Тесты — `net_services_*`, `ssh_*`,
`password_login_asks_no_key` в `cascade.rs`; обход путей отвечает на `ssh_key` заранее.
Без терминала `variable::prompt` отвечает «not a terminal», и `ask()` берёт умолчание:
OTA — `internal`, если схема помещается, иначе `no`; остальные — `no`/`none`/`yes`.
`--define` — режим для скриптов и **строгий**: опечатка и значение, невозможное для
чипа, — `throw` с объяснением, а не подстановка (иначе молча снятая защита, вроде
bootloader'а, всплыла бы на первом обновлении). Чип, заданный напрямую, не фильтруется
ответами; если же чип не задан, а через `--define` пришли ответы, список чипов в каскаде
сужается ими (`plan()` и `fits_answers()` — одно решение и для списка, и для выбранного
чипа). Тесты: `the_menus_come_in_order_and_offer_only_what_is_possible`, обход всех
путей по меню на характерных чипах (`every_path_through_the_menus_generates`; на каждом
пути заданы все переменные шаблона) и умолчания для каждого чипа
(`every_chip_generates_with_the_defaults`) в `tests/cascade.rs`. В
ветках с ручной раскладкой (`write_size` через `--define`, чип без раскладки)
`ext_page_size` — 4 KiB с предупреждением, как `state_erase_size` там же.

`bsp/src/external.rs` хук удаляет везде, кроме `ota=external`. Стерегут ветку тесты
каскада `external_ota_*` и три конфигурации `template-check`.

### Чипы без OTA (`ota = "false"`)

`compute_ota_partitions` возвращает `Err` с человекочитаемой причиной, когда схема не
помещается: ей нужно минимум 5 стираемых страниц (`BOOTLOADER` + `BOOTLOADER_STATE` +
`ACTIVE` + `DFU` на страницу больше `ACTIVE`). На STM32H723VE, например, 512 KiB одним
регионом с сектором 128 KiB — четыре страницы, валидной раскладки не существует ни при
каком дележе. Для таких чипов (276 из 1479 — либо flash меньше резерва под bootloader,
либо сектора слишком крупные) `memory.x` всё равно заполняется — одним
образом на весь flash, — а `crates-cross/boot` из проекта убирается: `members` в
`crates-cross/Cargo.toml` под `{% if ota == "true" %}`, `xtask` пропускает прошивку/линт boot
(`has_bootloader()`), а сам каталог сносит `file::delete("crates-cross/boot")` в хуке.

**Вторая причина отказа — `OTA_MIN_ACTIVE` в `chip-select.rhai`.** Раскладка может
сойтись, а под приложение остаться меньше, чем занимает пустая прошивка шаблона: у
чипов с 64 KiB flash это 15–16 KiB против примерно 17 KiB минимального образа на
Cortex-M0+. Такой проект генерировался и не собирался — замерено сборкой: `f030c8`
переполнял раздел на 848 байт, `c051c8` на 1904, `l051c8` на 272. Порог 24 KiB выбран
не на глаз: у 160 чипов под приложение выходит 16256 байт и меньше, а следующий по
величине раздел — сразу 40 KiB, так что любое значение внутри промежутка отсекает ровно
неработающие конфигурации. Стерегут это два теста каскада —
`ota_is_dropped_where_the_app_partition_is_too_small` и парный к нему
`ota_survives_where_the_app_partition_is_large_enough`: без второго порог мог бы снять
OTA у всех подряд незамеченным.

**Почему `file::delete`, а не `[conditional]` в `cargo-generate.toml`**: условия
`[conditional]` вычисляются только по значениям `[placeholders]` и переменных,
выставленных хуком через `variable::set`, НЕ видят — проверено эмпирически
(`[conditional.'ota != "true"']` каталог не убирал, то же условие по `ci` работало).
Порядок важен: после `file::delete` в этот каталог нельзя писать (`cargo generate` падает
с `os error 3`), поэтому в ветке без OTA пишется только `crates-cross/app/memory.x`.

`compute_memory_layout` возвращает `None` только когда считать не из чего: нет
непрерывной flash- или RAM-цепочки от базового адреса. Сейчас таких чипов нет ни одного,
и это не проза, а проверка: `chip-data-gen` падает с `ensure!`, если раскладок вышло
меньше, чем суффиксов, а хук — `abort`, если записи для чипа в `chip-data/layout/` нет
(разошлось правило семейства или каталог недоперегенерирован). Запасной ветки с
`memory.x`-плейсхолдером у хука больше нет; ручная раскладка — только через `--define
write_size=...`. `PANIC` выводится всегда,
когда есть раскладка, и это обязательство, а не удобство: паникёр release-профиля
(`panic-persist`) стоит у `app` и `boot` безусловно, и без символов `_panic_dump_*`
release-образ не линкуется. Размер — доля RAM (`PANIC_FRACTION`, зажатая между `PANIC_MIN`
и `PANIC_MAX`): 512 байт на чипе с 8 KiB и больше, 128 на двух килобайтах у STM32L011.
Фиксированные полкилобайта были бы на таких чипах четвертью всей памяти, поэтому регион им
просто не доставался — а с безусловным `panic-persist` это означало бы «шестнадцать чипов
генерируются в заведомо несобираемый проект». Других резервов в RAM нет: прежний `PERSIST`
(счётчик запусков) и символ `_hw_ram_start` (замер стека) ушли вместе со своими
потребителями. Ручной override — как и у `chip`/`cpu`/`target`: `--define write_size=...`
отключает автогенерацию memory.x целиком (адреса привязаны именно к вычисленному
`write_size`, доверять чужому нельзя) — тогда всё, как раньше, вручную.

Регрессионные тесты на всё перечисленное — `chip-data-gen/tests/cascade.rs`
(`memory_layout_invariants_hold_for_every_chip` проходит по всем чипам сразу) и юнит-тесты
в `chip-data-gen/src/main.rs`.

### Оценка RAM (`ram_estimate`, таблица `RAM_COST`)

Хук оценивает статическую RAM проекта (`.data` + `.bss` + `.uninit` release-образа
`app`) по таблице `RAM_COST` в `chip-select.rhai`: ядро, OTA, хранилище настроек, граф,
каждый транспорт `вид:протокол` вместе с его узлом и сетевой стек — один раз на
`tcp`/`udp`. Оценка плюс `STACK_RESERVE` сравнивается с регионом `RAM` раскладки
(`ram_length`): пункт списка транспортов, с которым не помещается, помечен
` — НЕ ПОМЕЩАЕТСЯ в RAM` (протокол там ещё не выбран — пункт стоит как худший
протокол своего вида), `--define links`/`interface` с ним — ошибка, а отсев чипов до
каскада по `links` такие чипы не показывает. Проект без транспортов не отвергается
никогда. С ручной раскладкой (`write_size`, невлезающие OTA или настройки) регион RAM
пишет человек — оценки нет (`ram_estimate` пуст).

Числа в таблице — замеренные. `cargo xtask build` печатает факт строкой `ram:`, хук —
оценку строкой `ram_estimate:`; `template-check` в полном прогоне сверяет их у каждого
случая и падает, если оценка ниже факта. Тогда таблицу перемеряют:

1. Факт по случаям — таблица в конце полного прогона `template-check` (столбцы «факт»
   и «оценка»).
2. Стоимость части — разность пары сборок на одном чипе «с ней / без неё», например
   `--define links=uart:modbus` против проекта без транспортов. Пару, которой нет
   среди случаев, собирают точечно: `cargo generate` с нужными `--define`, затем
   `cargo xtask build` в проекте, строка `ram:`.
3. Из нескольких чипов берётся наибольшая разность, база — по наибольшему из чипов:
   оценка обязана быть не ниже факта на любом.

`STACK_RESERVE` (1024 байта) — **не замерен**: глубину стека без платы не снять.
Он выбран: futures задач `embassy` и буферы транспортов лежат в `.bss`, на стеке —
только цепочка `poll`, кадры прерываний и форматирование паники, а под flip-link
переполнение — HardFault, а не тихая порча статиков. 2 KiB отвергли бы Modbus по UART
на STM32C011D6 (5760 байт RAM). Замерить можно на плате закраской стека: до `main`
(или первой строкой в нём) залить стек ниже текущего SP до `ORIGIN(RAM)` известным
словом (например `0xDEADBEEF`; под flip-link стек растёт вниз к началу RAM),
прогнать прошивку под нагрузкой всех узлов, затем остановить ядро и прочитать регион
через `probe-rs read` (или `read_memory` MCP `embedded-debugger`): самое низкое
перезаписанное слово — высшая отметка стека, от него до `_stack_start` — глубина. Наибольшая
по характерным проектам глубина с запасом и есть обоснованный `STACK_RESERVE`.

Новая часть проекта со статиками (узел, буфер, сетевая служба из `services`) — новая
строка таблицы и пара сборок под неё.


## Проверка изменений в шаблоне

Полный набор перед коммитом в репозитории шаблона — один список. CI шаблона
(`.github/workflows/template.yml`) гоняет из него подмножество, см. «Что из этого
делает CI»:

```
cargo xtask lint          # корневой workspace: fmt --check + clippy -D warnings
cargo xtask test host     # domain: cargo nextest

cargo fmt    --manifest-path chip-data-gen/Cargo.toml --check
cargo clippy --manifest-path chip-data-gen/Cargo.toml --all-targets -- -D warnings
cargo test   --manifest-path chip-data-gen/Cargo.toml --release

cargo run --manifest-path chip-data-gen/Cargo.toml --bin template-check
```

Последняя строка — полная генерация и сборка проектов (минуты; `--quick` — только
генерация), единственная проверка `crates-cross` и `chip-info`: ниже о ней.

Репозиторий шаблона нельзя собрать как обычный проект: `crates-cross/Cargo.toml`,
`crates-cross/.cargo/config.toml`, `crates-cross/bsp/src/board.rs` и `crates-cross/boot/src/main.rs` содержат
Liquid (`{{...}}` и `{% if %}`), а до рендера это ни валидный TOML, ни валидный Rust —
rust-analyzer ругается на них прямо в репозитории, и так и должно быть.

Раньше здесь была инструкция на страницу: найти все вхождения `grep`'ом, подставить
руками значения, выбрать по одной ветке каждого `{% if %}`, собрать, вернуть всё
обратно, не забыть проверить `git diff`. Теперь это делает инструмент:

Команда `template-check` — последняя строка списка выше. Он генерирует проект во временный каталог (`%TEMP%/rust-embedded-template-check/`,
там же общий кеш сборки — вторая конфигурация не пересобирает то, что от чипа не
зависит) под каждую конфигурацию набора `default_cases()` в
`chip-data-gen/src/bin/template-check.rs` — они задевают разные ветки генерации.
Список там и есть источник истины (число конфигураций растёт вместе с ветками, здесь
его не повторяем); для ориентира, что в него входит: одноядерный чип, он же с
`ota=no`; чип с выбором банковой схемы и чипы с переключением банков; чип, куда
OTA не помещается (единственный с `IWDG1` вместо `IWDG`); двухъядерный (`init_primary`
вместо `init`, единственный с `IWDG2`); чип с 2 KiB RAM на Cortex-M0+; раздел
настроек с OTA на равных и неравных секторах, без OTA, во внутренней EEPROM (L0/L1) и
на внешней флеши; подпись образа с графом задач и без него; чип, где стёртый флеш
читается нулями (`flash-erase-zero`); `ota=external` (H7, F4, L0); протоколы и
интерфейсы (`protocol`/`interface`): Modbus и protobuf поверх UART, CANopen на FDCAN
и bxCAN, Modbus TCP и protobuf UDP (стек `embassy-net`, узел NET), USB CDC
(устройство `embassy-usb` и узел USB). Дальше
проверяет, что не осталось ни одного
неподставленного плейсхолдера, что состав CI-файлов проекта совпадает с выбранным
`ci` (см. ниже про `--ci`), и прогоняет в сгенерированном проекте `cargo xtask
lint`, `test host`, `lint cross`, `build` — то есть ровно то, что README обещает
пользователю, — плюс `cargo xtask pins` (четырежды: без аргумента, с `RCC`, с
`I2C1 --snippet` и `--check`) и fmt/clippy для `chip-info`.

Отдельным шагом идёт **компиляция заготовок**: для каждого блока с выводами (у
STM32F407 их 38) берётся вывод `pins <БЛОК> --snippet`, всё складывается во
временный модуль `bsp` и прогоняется через clippy с `-D warnings`. Заготовку
человек вставляет в свой проект как есть, значит она обязана собираться, — а
проверялось до сих пор только то, что команда не упала. Цена этого пробела:
пять дефектов разом, каждый ронял вставленный код (дублирующиеся ключи там, где
два сигнала делят вектор; `Usb_otg_fsResources`, не проходящий
`non_camel_case_types`; несуществующий `adc::InterruptHandler` на большинстве
версий ADC; пустая `bind_interrupts!` у классического USB; недостающий импорт
`Peri`). Половина `assign_resources!` берётся ровно у одного блока — макрос
кладёт `split_resources` в корень крейта через `#[macro_export]`, и двух
вызовов в одном крейте не бывает; поэтому она на время проверки встаёт на место
`bsp/src/resources.rs`, а не рядом с первым макросом.

Последние шесть — единственная проверка `chip-info` вообще: его манифест до
генерации не резолвится (чип выбирается Cargo-фичей, а в ней Liquid), поэтому ни
`cargo xtask lint`, ни CI самого шаблона его не видят, и в репозитории шаблона
`cargo xtask pins` намеренно падает с объяснением вместо невнятной ошибки Liquid.
`cargo xtask lint` в сгенерированном проекте его тоже не трогает — иначе каждый
пользовательский CI тянул бы `stm32-metapac` ради инструмента, который на сборку
прошивки не влияет.

Исключение одно, и оно устроено так, чтобы правило выше осталось в силе: есть
отдельный джоб (`pins.yml` на GitHub, `pins:check` на GitLab), зовущий
`chip-info --check` по фильтру путей — при правке `crates-cross/bsp/src/**`,
самого `crates-host/chip-info/**` или `crates-cross/Cargo.toml`. Последние два не для
полноты: у `chip-info` своя запись в dependabot/renovate, и обновление
`stm32-metapac` меняет ровно те метаданные, по которым идёт проверка, а смена чипа
правит обе чип-фичи сразу. Метапак таким образом собирается не на каждый пуш, а
тогда, когда трогали проверяемое.

Зовётся `chip-info` напрямую, а не через `cargo xtask pins --check`: обёртка живёт в
корневом workspace, и её сборка потянула бы резолв `domain` с приватными
git-зависимостями, которых этому джобу не нужно.

**Файл `pins.yml` лежит и в репозитории шаблона** — в отличие от `template.yml`, он
не в `ignore`, потому что должен доехать до проектов. Поэтому первым шагом он
проверяет, подставлена ли чип-фича в манифесте `chip-info`, и в репозитории шаблона
завершается успехом, ничего не собирая: там этот манифест не резолвится вовсе. Уберёте
проверку — джоб покраснеет у мейнтейнера при первой же правке `bsp/src`.

Обязательной проверкой в branch protection этот джоб делать не стоит: он запускается
по фильтру путей, и PR, не трогающий распиновку, оставит обязательный статус висеть в
ожидании навсегда.

Флаги: `--quick` — только генерация и проверка плейсхолдеров (секунды вместо минут на
чип), `--ci gitlab|none` — другой CI-провайдер, `--define ключ=значение` (можно
несколько раз) — дополнительный ответ ко всем проверяемым конфигурациям, например
`--ci gitlab --define config=internal stm32f407ve`, `--keep` — не удалять проекты после
успеха, позиционные аргументы — свой список чип-фич.

`--ci` проверяет не только подстановку, но и состав: при `ci=github` в проекте есть
`.github/workflows/ci.yml` и нет `.gitlab-ci.yml` и `renovate.json`, при `gitlab` — наоборот,
при `none` нет ни того, ни другого (это делают `[conditional]` в `cargo-generate.toml`).
Обе ветки, кроме `github`, генерировались впервые: их прогоняет `template.yml` (по одному
чипу на ветку), а полный набор конфигураций живого проекта по-прежнему только `github` —
остальные проверяются мейнтейнером вручную с `--ci`.

Отдельная ценность прогона в том, что каждая конфигурация резолвит зависимости
заново: lock-файлов шаблон не раздаёт (см. ниже). Ломающие изменения незапиненных
git-зависимостей (`rust-lib`) видны только так: у самого шаблона `Cargo.lock` пинит
ревизии, поэтому локальные `cargo xtask lint`/`build` остаются зелёными, даже когда
свежий проект уже не собирается.

### Почему генерация из локального пути такая медленная

`cargo generate --path <каталог>` копирует каталог шаблона ЦЕЛИКОМ во временную
папку, и только потом читает `cargo-generate.toml`. Значит `ignore = ["target", ...]`
от копирования не спасает: он решает лишь, что попадёт в готовый проект. Всё, что
лежит в репозитории, — включая оба `target/` (в корне и в `crates-cross/`) с гигабайтами
артефактов — копируется при каждой генерации из локального пути.

Замерено на этом репозитории: генерация из каталога с 3 ГБ в `target/` — **169
секунд**, из облегчённой копии тех же исходников — **1 секунда**. А когда кеш
`template-check` ещё жил в `target/` и дорос до девяти гигабайтов, генерация сначала
надолго «зависала» без единого сообщения, а потом падала с «Недостаточно места на
диске (os error 112)».

Отсюда три решения, каждое со своей причиной:

- рабочие каталоги и общий кеш сборки `template-check` живут в
  `%TEMP%/rust-embedded-template-check/`, а не в `target/` — чтобы прогоны проверки
  не утяжеляли репозиторий;
- сам `template-check` генерирует не из репозитория, а из его копии, куда не
  попадают `target/` (на любом уровне), `.git/` и `chip-data-gen/`. Копия — около
  двух мегабайт, полный `--quick` по набору конфигураций укладывается в полминуты
  вместо пяти минут;
- руками шаблон удобнее брать через `--git` даже локально: `cargo generate --git
  "d:/Projects/rust embedded template"` клонирует только отслеживаемое в git, то есть
  без `target/` вовсе. Разница — секунда против трёх минут. Единственное «но»:
  клонируется закоммиченное, поэтому незакоммиченные правки шаблона так не
  проверить — для них и есть `template-check`.

### Lock-файлы шаблона

**Шаблон не раздаёт ни одного lock-файла** (`ignore` в `cargo-generate.toml`) —
каждый проект считает свои сам первой сборкой: корневой — `cargo xtask lint`/`test
host`, `crates-cross/Cargo.lock` — `cargo xtask build`, `crates-host/chip-info/` —
первым `cargo xtask pins`. Состав пакетов зависит от ответов при генерации: при
`ota=no` уходят `embassy-boot*`, при `config=internal` добавляются
`sequential-storage` и `embedded-storage-async`, при OTA — `salty`, а
протокол уносит или приносит целые крейты корневого workspace (`crates-host/proto`,
`crates-host/canopen`). Шаблонный lock подходил бы одному сочетанию, а остальным ронял
бы `cargo fetch --locked` (проверено вживую: проект без `crates-host/proto` на
шаблонном корневом lock падает с `cannot update the lock file`). Post-хук говорит о
lock-файлах прямо при генерации, а `--locked` в обоих CI проекта условный — строгий,
как только файл закоммичен.

Корневой `Cargo.lock` и `crates-host/chip-info/Cargo.lock` в самом репозитории шаблона
остаются — для его собственной сборки и CI; в проекты они не едут.

Цена решения, которую надо знать: свежесгенерированный проект резолвит `rust-lib`
(`supervisor`, `fsm`, `watchdog`) с текущего `main` вместо ревизий, проверенных
мейнтейнером. Если `main` уехал ломающим изменением — проект не соберётся с первого
раза. Риск принят сознательно: ни одна конфигурация не получает lock, который ей не
подходит, а поломка `main` всплывает и в `template-check` — каждая конфигурация
резолвит заново.

### Версии зависимостей: бот сюда не дотягивается

`.github/dependabot.yml` копируется в проекты и там работает, а в самом репозитории
шаблона из четырёх его записей живёт ровно одна — `github-actions`. Знать это надо,
чтобы не ждать обновлений, которые не придут:

- **`/crates-cross`** — Liquid внутри `members = ["app", {% if ota == "true" %}"boot",
  {% endif %}…]` ломает сам TOML: там падает даже `cargo metadata --no-deps`.
- **`/crates-host/chip-info`** — TOML валиден (Liquid стоит строкой в списке фич), но
  резолв падает: `stm32-metapac` не имеет фичи `{{chip_feature}}`. Именно резолв и
  делает бот, так что PR отсюда не появится. Живое доказательство, что не появлялся
  никогда: манифест объявлял `anyhow 1.0.100`, а его же lock давно держал 1.0.104.
- **Корневой** резолвится, но git-зависимости из приватного `rust-lib` бот обновлять
  не станет — доступа к репозиторию у него нет.
- **`chip-data-gen`** в списке отсутствует вовсе, и добавить его нельзя: файл уезжает
  в проекты пользователей, а этого каталога там нет (`ignore` в
  `cargo-generate.toml`) — запись указывала бы в пустоту и ломала бы бота уже у них.

Отсюда практика: версии во всех манифестах, кроме корневого, мейнтейнер поднимает
руками. Что отстало — видно так (имена берутся из самого манифеста, поэтому список не
надо поддерживать):

```bash
for manifest in crates-cross/Cargo.toml crates-host/xtask/Cargo.toml \
                crates-host/chip-info/Cargo.toml chip-data-gen/Cargo.toml; do
  grep -oE '^[a-z0-9_-]+ *= *(\{ *version *= *)?"[0-9][^"]*"' "$manifest" \
  | grep -vE '^(version|edition|rust-version|resolver|name) ' \
  | while read -r line; do
      name=${line%% *}
      cur=$(printf '%s' "$line" | grep -oE '"[^"]+"$' | tr -d '"')
      # User-Agent обязателен: без него crates.io отвечает отказом, и пустой
      # ответ выглядел бы как «версия неизвестна» для каждого крейта.
      new=$(curl -s --max-time 12 -H "User-Agent: template-maintainer" \
            "https://crates.io/api/v1/crates/$name" \
            | grep -o '"max_stable_version":"[^"]*"' | head -1 | cut -d'"' -f4)
      if [ -z "$new" ]; then
        echo "$manifest: $name — не удалось спросить crates.io"
      elif [ "$cur" != "$new" ]; then
        echo "$manifest: $name $cur -> $new"
      fi
    done
done
true   # чтобы статус не зависел от последнего сравнения
```

Одно ложное срабатывание в нём заложено и лечению не подлежит: сравнение
текстовое, поэтому `stm32-metapac = "21"` показывается как «21 -> 21.0.0». Это одна и
та же версия, записанная по-разному, и привязка к мажорной там намеренная — см.
следующий абзац.

Две оговорки, без которых механическое «поднять до последнего» ломает проект:

- **embassy — это набор.** `embassy-stm32`, `embassy-executor`, `embassy-sync`,
  `embassy-time`, `embassy-boot`, `embassy-boot-stm32` двигаются вместе; одиночный
  бамп даёт две несовместимые копии в графе.
- **Мажорная версия `stm32-metapac` в `chip-info` обязана совпадать с той, что тянет
  `embassy-stm32`** (об этом же говорит комментарий в `dependabot.yml`). Разъедутся —
  `cargo xtask pins` начнёт показывать данные другого поколения `stm32-data`, чем то,
  по которому собрана прошивка. Молча и правдоподобно.

Поднимать версии в манифесте стоит даже тогда, когда lock уже содержит свежие (так
бывает: semver-диапазон допускает патчи, и cargo подтягивает их сам). Бот сравнивает
манифест, а не lock, и отставший манифест молча прячет от него обновления.

Остальное проверяется командами из списка в начале раздела.

`chip-data-gen` не член ни одного `[workspace]`, поэтому в `cargo xtask lint` он не
попадает — его команды идут отдельными строками в том списке. `chip-info` тоже не член, но с
ним так не выйдет: до генерации его манифест не резолвится вовсе, и локально проверить
его нечем — только `template-check` (см. выше).

### Что из этого делает CI

`.github/workflows/template.yml` — CI самого репозитория (в проекты не копируется,
см. `[template].ignore`). Он гоняет на каждом пуше всё, что обходится без доступа к
приватному `rust-lib`: `cargo fmt --check` обоих манифестов, clippy и тесты
`chip-data-gen` (включая тесты каскада по всем чипам и проверку штампа версий) и
`template-check --quick` — генерацию под каждый чип набора с проверкой остаточных
плейсхолдеров.

Что CI сделать не может — собрать сгенерированный проект: `domain` тянет приватный
репозиторий, которого у Actions нет. Поэтому полный `template-check` (без `--quick`)
остаётся локальной командой, и прогонять его перед пушем всё равно нужно: именно он
ловит ломающие изменения `rust-lib` и ошибки, которые видны только компилятору.

Кстати о том, почему `--quick` в CI вообще работает без доступа к `rust-lib`:
генерация зависимости не резолвит вовсе. `cargo update` в post-хуке был и убран (см.
«Почему генерация из локального пути такая медленная»), а тот, что делает
`template-check`, идёт только в полном прогоне — то есть локально, где доступ есть.

### Тесты каскада

`chip-data-gen/tests/cascade.rs` — интеграционный тест на сам `chip-select.rhai`, не на
Rust-код генератора: гоняет реальный скрипт через движок `rhai` (dev-dependency) с
подменённым модулем `variable` (`is_set`/`get`/`set`/`prompt`) и `file`
(`write`/`delete`), без `cargo generate` и
без TTY. Таблицы из `chip-data/` разбираются один раз и подаются движку через
`StaticModuleResolver` под теми же путями, что пишет `import`, — так что выбор файла
семейства проверяется кодом самого хука. `variable::prompt` в моке сам ведёт каскад к заранее известной цели (выбирает
самый длинный вариант из choices, чьим префиксом является цель — не первый попавшийся,
иначе он ошибочно "останавливается" там, где чип совпадает с началом другого, того же
класса бага, что тест и должен ловить). `cascade_reaches_every_chip_without_hanging` и
`memory_layout_invariants_hold_for_every_chip` прогоняют так все чипы из `CHIPS`
(~1479 каждый) — ловят именно тот класс бага, который `--define chip_feature=...` в
принципе не может поймать (та ветка не создаёт ни одного `variable::prompt`, значит не
исполняет сам цикл каскада). Второй из них проверяет разом четыре уже случавшиеся
регрессии: `BOOTLOADER_STATE` с самого начала flash, одинаковый `memory.x` у app и boot
(app затирал bootloader), регионы OTA в проекте, который собирается без bootloader'а, и
незаполненный `crates-cross/target-tests/memory.x` (каскад его когда-то не писал вовсе, и
`cargo xtask test target` не линковался ни на одном чипе). В
`--release` — секунды на оба полных прогона (в dev-профиле
— единицы минут, интерпретация Rhai). Не в `cargo xtask lint`/CI (`chip-data-gen` не
член workspace, см. выше), гонять вручную при правке `chip-select.rhai`/`chip-data-gen`:
`cargo test --manifest-path chip-data-gen/Cargo.toml --release` (та же команда
запускает и юнит-тесты генератора из `chip-data-gen/src/main.rs`).

### Когда перегенерировать данные

Списки в `chip-data/` собраны из чип-фич конкретной версии `embassy-stm32` и из
`probe-rs chip list` конкретной установленной версии probe-rs. Обе версии записаны
штампом в начале `chip-data/chips.rhai`:

```
// Источник: embassy-stm32 0.6.0 (crates-cross/Cargo.toml), probe-rs 0.31.0
```

Тест `generated_blocks_match_the_declared_embassy_version` сверяет штамп с версией,
объявленной в `crates-cross/Cargo.toml`, и падает, если они разошлись. Это не формальность:
версию поднимает dependabot/renovate, молча, а списки при этом остались бы от старой —
расхождение вылезло бы уже у пользователя шаблона, при генерации. Увидели красный тест
— перегенерируйте:

```
cargo run --manifest-path chip-data-gen/Cargo.toml
```

Версию probe-rs тест не проверяет: она у каждого мейнтейнера своя и в репозитории не
объявлена. Штамп её фиксирует справочно — чтобы было видно, из какого набора целей
собран список.

**Осторожно с Liquid в манифестах.** Генератор резолвит зависимости через `cargo
metadata`, а для этого снимает из временной копии все `{% if %}`-блоки
(`strip_liquid`). Форму с управлением пробелами (`{%- if`) он раньше не понимал — и
после того, как условие такого вида появилось в `crates-cross/bsp/Cargo.toml`, генератор
перестал работать целиком, с невнятным «invalid key-value pair, expected key».
Заметно это только при запуске самого генератора, то есть раз в обновление
embassy-stm32, поэтому обе формы теперь под тестами
(`liquid_whitespace_control_is_stripped_too`, `every_template_manifest_strips_clean`).
Добавляете в манифест шаблона новую Liquid-конструкцию — прогоните
`cargo test --manifest-path chip-data-gen/Cargo.toml`.
