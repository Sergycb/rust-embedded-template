# Сопровождение шаблона

Этот файл — только про сам репозиторий шаблона: как устроен каскад выбора чипа,
откуда берутся плейсхолдеры и раскладка памяти, чем и как проверять изменения.
В сгенерированные проекты он не копируется (`ignore` в `cargo-generate.toml`),
поэтому всё, что должно жить в проекте пользователя, — в `AGENTS.md` и
`docs/**`, а не здесь.

Работаете в этом репозитории — читайте оба: `AGENTS.md` и `docs/**` описывают
архитектуру и конвенции, которые шаблон раздаёт проектам (`CLAUDE.md` здесь —
только импорт `AGENTS.md` плюс специфика Claude Code, см. раздел ниже про то,
что едет в проект пользователя), `MAINTAINING.md` — механику самой раздачи.

## Что здесь есть, чего нет в проектах пользователей

Полный список того, что не едет в проект, — `ignore` в `cargo-generate.toml` (и
`[conditional]` там же — файлы CI чужой платформы); хуки cargo-generate в результат
не копирует сам. Главное:

- `chip-select.rhai` — pre-хук: каскадный выбор чипа, вопросы о памяти и
  интерфейсах, `memory.x`, все переменные, которые видит Liquid (полный список —
  вызовы `variable::set` в `chip-select.rhai`), и основная часть удалений файлов
  под невыбранные ответы (`file::delete`).
- `chip-data/` — сгенерированные таблицы, которые хук подключает через `import`
  (каталог в `ignore`; `import` находит его и так): `chips.rhai`, `packages.rhai`,
  `bank_mode.rhai`, `bank_switch.rhai`, `watchdog.rhai`, `cpu_freq_boost.rhai`,
  `rng.rhai` (линия и клок блока `RNG`: `rng_irq`, `rng_clock`, `rng_source`),
  `cache.rhai` (кэши чипа, теги через пробел: `icen`/`dcen` — биты `FLASH_ACR`, `icache` — блок `ICACHE`),
  `reset.rhai` (флаги сброса `RCC`: `RESET` — версия регистров `RCC` чипа, `RESET_REGS` — регистр
  и пары `поле[,поле]:Причина` у версии),
  `interfaces.rhai` (интерфейсы связи, выведенные в корпусе: `usart`, `fdcan`,
  `bxcan`, `eth`, `usb`, `otg` — по ним хук проверит ответ об интерфейсе),
  `instances.rhai` (блоки чипа по метке интерфейса, в порядке выбора — из них хук
  назначает блок транспорту и шину внешней флеши) и
  `layout/<семейство>.rhai` — раскладка памяти, разложенная по первым двум символам
  суффикса (`f4`, `h7`, `wb`). Целиком раскладка — ~75 тысяч строк, а хуку нужна одна
  запись, поэтому он импортирует только файл своего семейства. Руками не правится.
- `post-script.rhai` — post-хук: удаляет `crates-cross/app/src/version.rs` без
  OTA и печатает сводку «что дальше». Команд не выполняет: `cargo update` оттуда убран
  (причина — комментарий в начале `post-script.rhai`), поэтому и `--allow-commands`
  при генерации не нужен.
- `chip-data-gen/` — два инструмента мейнтейнера (каталог в `ignore`):
  - `cargo run --manifest-path chip-data-gen/Cargo.toml` — перегенерирует
    `chip-data/` целиком;
  - `cargo run --manifest-path chip-data-gen/Cargo.toml --bin template-check` —
    генерирует проект во временный каталог и прогоняет в нём весь набор
    проверок (см. «Проверка изменений в шаблоне» ниже).
- `.github/workflows/template.yml` — CI репозитория шаблона (см. «Что из этого
  делает CI» ниже); у сгенерированных проектов свой `ci.yml` рядом.
- `MAINTAINING.md` — этот файл.

Наоборот, едут — граница по тому же признаку «конвенции для кода в проекте
пользователя, а не про сопровождение шаблона»: `AGENTS.md` и `docs/**`
(рендерятся Liquid'ом, как и остальной шаблон: doc-блоки в `docs/modules/`
несут собственные `{%- if graph == "true" %}`, поэтому в `exclude` их
добавлять нельзя — там команды приезжают с настоящим чипом), и
`.claude/rules/*.md` (под git, правила по путям для домена/прошивки). А вот
рабочие файлы самого Claude Code внутри `.claude` — `settings.local.json`,
реестр агентов, расписания, mailbox и т.п. — не едут: они поимённо в `ignore`
`cargo-generate.toml`, каталог `.claude` целиком там больше не значится (см.
комментарий там же). `CLAUDE.md` едет без Liquid-рендера (`exclude` в
`cargo-generate.toml`): в нём Liquid упомянут текстом.

## Плейсхолдеры шаблона (`cargo-generate.toml`)

Плейсхолдеры, подставляемые Liquid-рендером cargo-generate (`{{chip}}`, `{{target}}`,
`{{swap_buffer}}`, `{{rust_lib}}` и т.д.), — переменные pre-хука; полный список —
вызовы `variable::set` в `chip-select.rhai`. В `[placeholders]` объявлен один `ci` —
его cargo-generate задаёт сам, до хука. Остальные значения выставляет `variable::set` в
`[hooks].pre`-скрипте `chip-select.rhai` — каскадном посимвольном выборе STM32
(семейство → линейка → дальше по символу) по списку чипов, одновременно валидных и для
`embassy-stm32`, и для установленного локально `probe-rs`. Вопросы хук задаёт сам:
адрес rust-lib — до каскада, про OTA, настройки, граф, транспорт и протокол — после
выбора чипа (см. «Вопросы в хуке» ниже).

Хук — `pre`, а не `init`: init-хуки выполняются ДО того, как `--define`-значения с CLI
попадают в liquid-объект (проверено эмпирически — с `init`
`variable::is_set("chip_feature")` не видит `--define chip_feature=...`, а каскадный
`variable::prompt` в неинтерактивном/`--silent` режиме падает с
`IO error: not a terminal`). Объявлять эти переменные в `[placeholders]` не нужно:
`variable::set` работает без декларации, а `--define` хук читает через
`variable::is_set`/`variable::get`.

### Вопросы в хуке

Первым хук спрашивает адрес rust-lib (`rust_lib`, до каскада: без него
проект не собрать), потом выбирается чип (каскад по символам или `--define chip_feature=...`),
потом внешняя флеш, OTA, настройки, граф, транспорт и протокол — в таком порядке, и
последним — адрес hw-drivers (`hw_drivers`, только с внешней флешью). При этом
`variable::prompt` показывает только допустимое для чипа (`ask()`, блок «Вопросы» в
`chip-select.rhai`): граф, который не влезает в раздел приложения, и интерфейс без блока
у чипа не предлагаются, протоколы берутся из `PROTOCOL_INTERFACES` для выбранного
транспорта; OTA и настройки, не помещающиеся на чип, остаются в меню с пометкой
`DOES NOT FIT` — их выбор включает ручную раскладку (хук ставит `swap_buffer`, как при
`--define swap_buffer=...`). Объявить эти вопросы в `[placeholders]` нельзя: `cargo-generate`
задал бы их сам до выбора чипа (и требует `prompt` у любого объявленного).

#### Транспорты и протоколы

Транспорты — один список с отметками `transports:` (`TRANSPORT_ITEMS`): у хуков
`cargo-generate` только одиночный выбор, поэтому отметка `[x] `/`[ ] ` нарисована в
тексте пункта, и меню после каждого выбора показывается заново; первый пункт `done`
— он же умолчание и ответ без терминала (тогда проект без транспортов). С OTA
пункта `done` нет, пока ничего не отмечено (`checklist(…, need_one)`): образ приходит
по транспорту проекта, и сценарии `test host-target` (они есть только с protobuf) идут
тоже через него. Без
терминала тогда отмечается первый пункт; `--define interface=none` с OTA — ошибка
хука с подсказкой (`--define` не спрятать). Протокол при этом может быть `none`. OTA
к вопросу о транспортах уже решён окончательно: не поместившийся уходит в ручную
раскладку, а не снимается. Тексты
пунктов всех меню хука — только ASCII: `dialoguer` (меню `cargo-generate`) меряет
ширину пункта в байтах, и кириллический пункт, «переносящийся» по его счёту, при
каждой перерисовке стирает строки терминала над меню. Пункт — вид,
по одному: `uart`, `can`, `ethernet` (вид — `tcp` или `udp`, вопрос `ethernet:` сразу
за списком), `usb`, и только если у
чипа есть блок вида (`free_blocks()` — блоки всех его меток из `INTERFACES`). Имени
блока в пункте нет: транспорт получает первый свободный блок вида, а меняют его в
`resources.rs` — об этом и о назначенных блоках говорит `post-script.rhai`. Затем
`protocol:` — на каждый отмеченный транспорт, в порядке пунктов. Протокол в проекте пока один:
когда он выбран, следующему транспорту предлагаются только он и `none`, а виду, поверх
которого он не работает, вопрос не задаётся; `modbus_master` — один раз, при первом
Modbus. Через `--define` то же задаёт `links` (`parse_links()`, вместо пары
`interface` + `protocol`), и отсев чипов до каскада тогда считает блоки каждого вида.
Итог — переменная `links` (`вид:метка:блок:протокол:имя` через запятую; имя — блок
строчными, у `tcp`/`udp` — сам вид) и `has_*`. Файлы шаблона идут по `links`
циклом Liquid: у каждого транспорта своя группа в `resources.rs`, подмодуль драйвера
в `bsp` (`bsp::serial::<имя>`, `bsp::can::<имя>`, `bsp::usb::<имя>`), канал
протокола в `app` (конкретным типом в привязке графа или в модуле задачи), поле
`Board` и узел графа или модуль задачи без графа. `interface`,
`iface_periph` и производные от них считаются по основному транспорту (первый с
протоколом, иначе первый) и остались там, где речь об одном блоке (подсказки
`cargo xtask pins` в документации).

#### Сетевые службы

Сетевые службы — следом, только когда среди транспортов есть `tcp` или `udp`: список
с отметками `net_services:` (`NET_SERVICE_ITEMS`, тот же `checklist()`, что у
транспортов); `ssh` в нём только у чипа с RNG (`rng_irq`) и с разделом приложения не
меньше `SSH_MIN_PARTITION` (320 KiB: `sunset` с криптографией — около 165 KiB кода,
консоль `bareminal` — ещё около 27 KiB release),
иначе хук печатает, почему его нет. Вопроса о входе нет: консоль (SSH или `cli`)
пускает только по паролю; прежние `ssh_auth`/`ssh_key` в `--define` — ошибка.
Итог — `net_services` (`ssh,rest,mqtt` в порядке пунктов, через `--define` — в порядке
списка), `has_console` (`cli` или `ssh`) и `ssh_host_key`: `config` — ключ хоста плата создаёт
сама в разделе настроек (`domain::ssh::Stored`), `file` — вшит из `ssh-host-key.bin`
(`crate::net::ssh::HOST_KEY` в `app`; так и при `config` вместе с CANopen — раздел
настроек целиком его — и с настройками на внешней флеши: до драйвера проекта там
заглушка, и ключ менялся бы при каждом старте). Пустые
строки, когда не выбрано. Модули узлов невыбранных служб хук удаляет (`domain/src/http.rs`,
`ssh.rs`, `mqtt.rs` с их каталогами, `app/src/net.rs` без служб вовсе (модули служб в нём — Liquid),
`device.rs` без служб и protobuf); узел протокола `domain/src/server.rs` (Modbus slave) —
без Modbus. Сокеты стека считает `bsp::net::SOCKETS` из чисел генерации: DHCP-клиент,
сетевые транспорты (`net_sockets`), по сокету на копию пула REST (`http_connections` →
`HTTP_CONNECTIONS`), на SSH и на MQTT. Секреты
(`rest-token.txt`, `ssh-host-key.bin`, заготовка `mqtt.toml`) создаёт `cargo xtask`
(`secrets.rs`). Пароль консоли `post-script.rhai` пишет константой в
`crates-cross/app/src/console_password.rs`; файлов `console-password.*` нет.
Тесты — `net_services_*`, `ssh_*`, `cli_*` в `cascade.rs`.

#### Без терминала и `--define`

Без терминала `variable::prompt` отвечает «not a terminal», и `ask()` берёт умолчание:
OTA — `yes`, если схема помещается, иначе `no`; остальные — `no`/`none`/`yes`.
`--define` — режим для скриптов и **строгий**: опечатка и значение, невозможное для
чипа, — `throw` с объяснением, а не подстановка (иначе молча снятая защита, вроде
bootloader'а, всплыла бы на первом обновлении). Чип, заданный напрямую, не фильтруется
ответами; если же чип не задан, а через `--define` пришли ответы, список чипов в каскаде
сужается ими (`plan()` и `fits_answers()` — одно решение и для списка, и для выбранного
чипа). Тесты: `the_menus_come_in_order_and_offer_only_what_is_possible`, обход всех
путей по меню на характерных чипах (`every_path_through_the_menus_generates`; на каждом
пути заданы все переменные шаблона) и умолчания для каждого чипа
(`every_chip_generates_with_the_defaults`) в `tests/cascade.rs`.

### Значение в корневом workspace (`rust_lib`, `rust_lib_rev`, `newline`)

Адрес rust-lib — одна переменная `rust_lib` (хук; умолчания нет: шаблон не
называет сервер, адрес вводят при генерации или `--define rust_lib=…`, хранится
без `.git`). Так же `hw_drivers` (драйвер `w25q`) — только с внешней флешью: без
неё хук переменную не задаёт, и шаблон ссылается на неё только под `external_flash`.
`template-check` и тесты каскада подставляют свои адреса сами
(`REPO_DEFAULTS` в `template-check.rs`). В `crates-cross/Cargo.toml` и документации она подставляется
обычным `{{rust_lib}}`. Корневой `Cargo.toml` и `deny.toml` так не могут: в
репозитории шаблона они рабочие (`cargo xtask lint`, `cargo deny check`), а
Liquid в корневом workspace — только в комментариях и строковых литералах
(правило — `docs/architecture.md`), URL же из плейсхолдера не рабочий. Поэтому там пара:

```toml
# {%- comment %}
supervisor   = { git = "https://github.com/Sergycb/rust-lib.git", rev = "<ревизия>" }
# {%- endcomment %}
#{{newline}}supervisor   = { git = "{{rust_lib}}.git", rev = "{{rust_lib_rev}}" }
```

В шаблоне первая строка рабочая, вторая — комментарий; в проекте первой нет, а
`{{newline}}` (хук задаёт его как `"\n"`) отрывает строку от `#`, и она
становится рабочей. Адрес rust-lib в репозитории шаблона записан в трёх местах,
и меняются они вместе: `comment`-строки корневого `Cargo.toml`, `allow-git` в
`comment`-блоке `deny.toml` и `RUST_LIB` в `chip-data-gen/src/source.rs` (его же
берёт `REPO_DEFAULTS` в `template-check.rs`).

Ревизия — так же: переменная `rust_lib_rev` (умолчание в хуке, форк —
`--define rust_lib_rev=…`) и литерал в `comment`-строках корневого
`Cargo.toml`. Проекты не получают lock-файла, так что без `rev` каждая
генерация брала бы текущий main rust-lib, и смена его API роняла бы свежие
проекты без правки шаблона. Новая ревизия — правка шаблона под неё: хук,
литералы корневого `Cargo.toml`, `Cargo.lock`, затем проверка генерацией.

Удвоенная фигурная скобка в исходнике — тег Liquid, где бы она ни стояла: в
строке формата Rust (экранированная скобка в `write!`), в комментарии, в
литерале. Генерация падает на ней с «Substitution skipped, found invalid
syntax», а компилятор шаблона в репозитории ничего не замечает. Скобку пишут
отдельно (`write_char('{')`) или прячут участок в `{% raw %}`/`{% comment %}`.

### `${{ ... }}` в файлах GitHub Actions обязано быть в `{% raw %}`

Выражения GitHub Actions начинаются с тех же двух скобок, что и Liquid, и
cargo-generate честно пытается их подставить. Наткнувшись на неизвестную переменную, он
**пропускает подстановку во всём файле целиком** — не в строке, а в файле. Проверено
эмпирически: в файле с голым `${{ secrets.TOKEN }}` рядом стоявший `{{target}}` тоже
приезжал в проект сырым.

Поэтому в `.github/workflows/*.yml` каждое такое выражение оборачивается:

```yaml
GH_TOKEN: {% raw %}${{ secrets.GITHUB_TOKEN }}{% endraw %}
```

Внутри `raw` Liquid ничего не трогает, а остальной файл рендерится как обычно (тот же
`{{target}}` рядом подставляется). Симптом нарушения — не ошибка генерации, а тихо
сломанный workflow у пользователя, поэтому проверка стоит в `template-check`
(`check_no_raw_placeholders`); она же умеет отличать легитимное `${{ ... }}` в готовом
проекте от пережившего генерацию плейсхолдера — см. `without_actions_expressions` там
же. GitLab этой проблемы лишён: он подставляет переменные через `$VAR`.

Исключение — `template.yml`, CI самого шаблона: он в `[template].ignore` и не
рендерится, так что `{% raw %}` доезжает до GitHub как есть, а `{%` в начале
значения YAML не разбирает — workflow не запускается вовсе (так было с 29.09 по
02.11.2026). Там `${{ ... }}` пишется голым.

Обратная сторона того же: `ci.yml`, `pins.yml` и `release.yml` — workflow проектов,
и в самом репозитории шаблона они с Liquid и не разбираются. Чтобы каждый пуш не
приносил три красных прогона по 0 с (за этим шумом месяц не было видно, что сломан
`template.yml`), они в репозитории шаблона отключены: `gh workflow disable
.github/workflows/ci.yml` (и так же `pins.yml`, `release.yml`). Включать не надо;
на проекты это не влияет — у них свой репозиторий. `audit.yml` Liquid не содержит
и в шаблоне работает как есть.

### Ссылки на файлы в документах (`check_doc_paths`)

Так же тихо, как workflow выше, рвутся ссылки: файл, который называют доки или комментарий
(`` `docs/ota.md` ``, `[…](docs/flash.md)`), переехал или генерация убрала его вместе
с невыбранной частью. `check_doc_paths` в `template-check` сверяет каждый путь от
`crates-cross/`, `crates-host/`, `docs/` и `.github/` в `.md`, `.rs` и `.toml`
проекта с тем, что в нём есть; ссылку на файл, который есть не в каждой
конфигурации, держите под тем же условием, что и сам файл.

### Ответы `ota` и `config`: строка `yes`/`no`, «нет» — окончательное

`ota` и `config` — два плейсхолдера, которые хук не просто читает, а перезаписывает.
Спрашиваются они строкой `yes`/`no` (тип `bool` не годится: `variable::get` в rhai
читает только строки и падает с «Variable ota not a String» — проверено), а хук
приводит ответ к `"true"`/`"false"`, на которые смотрят Liquid-условия. «Нет» —
окончательное: для `ota` это один образ на весь flash, `crates-cross/boot` и
флеш под обновлением в `crates-cross/bsp/src/flash.rs` уходит (файл целиком — если нет и общего замка под настройки), даже если схема в чип помещается; для `config` —
носитель настроек (`ConfigFlash` в `bsp::flash` или `bsp::external`). На чипе, куда
выбранное не помещается, меню помечает пункт `DOES NOT FIT` и по умолчанию ставит «нет»,
а явное «да» (в меню или `--define`) переводит хук на ручную раскладку (как
`--define swap_buffer=...`) с причиной под «Выбранное не помещается» (см. «Чипы без OTA»
ниже). Для `ota` такое «да» окончательное — `ota` остаётся "true". Для `config` — только
на EEPROM и внешней флеши: раздел во внутреннем флеше живёт по границам из `memory.x`,
который в ручной раскладке пишет человек, поэтому там хук ставит `config` = "false" и
печатает «Раздел настроек не выделен» с подсказкой вписать регион `CONFIG` руками.

Порядок между ними не симметричен: в расчёте раскладки (`plan()` в `chip-select.rhai`;
в меню OTA спрашивается раньше) раздел настроек решается ПЕРВЫМ, потому что
меняет всю OTA-схему — в хвосте он отрезает flash, а в резерве перед `ACTIVE` теснит
bootloader и `STATE`. Отсюда и второй набор цифр в `MEMORY_LAYOUT` (см. ниже). У
большинства чипов раздел ложится в резерв перед `ACTIVE` или в хвост, и OTA с ним
сохраняется. Исключение — 20 чипов H742/H743/H745-cm7/H747-cm7 с 1 MiB: `DFU` у них в
банке 2, а bootloader, `STATE` и `ACTIVE` занимают весь банк 1 (4 × 128 KiB), и двум
страницам настроек места нет. Меню предупреждает об этом в самом пункте `config`
(`but then OTA will not fit: manual memory layout`), а под «Выбранное не помещается» хук
печатает `config_note` набора.

### Подпись образа — часть OTA, а не вопрос

Подпись OTA-образа — не вопрос и не переменная генерации, а часть OTA: есть OTA — есть
подпись, нет OTA (в том числе если схема не поместилась во flash) — нет и подписи. Всё,
что к ней относится, закрыто условием по `ota`: фича `boot` у `domain` (проверка подписи — `domain::ota::boot`, ею пользуется `boot`), ключ в `crates-cross/boot`
(`boot/build.rs`, `OTA_PUBLIC_KEY_IN_IMAGE`, вызов `screen_update`),
`running_version` во входе узла OTA (`app/src/graph.rs`, `app/src/tasks/ota.rs`) и файл `crates-cross/app/src/version.rs`
(`PACKAGE_VERSION` и свойства образа `Image` для него; без OTA его удаляет `post-script.rhai`). Режима без подписи нет и
в `domain`. Подпись проверяет bootloader
(`domain::ota::boot::screen_update`), приложение — только длину, занятость и версию
(`domain::ota::update::apply`), см. docs/ota.md.

### Modbus master (`modbus_master`)

`modbus_master` (Modbus master, клиентская половина; по умолчанию `no`) — той же формы:
строка `yes`/`no` (как у `ota`, `config`, `graph`, `ext_flash` — `yes_no_define`;
`true`/`false` на входе — ошибка), хук приводит ответ к `"true"`/`"false"`. Смысл он имеет только при
`protocol=modbus`: меню спрашивает его только тогда, а `--define modbus_master=yes` при другом
протоколе — ошибка (`no` принимается). Master не получают ни protobuf, ни CANopen. «true» оставляет `ports::ModbusClient`/`MasterError`,
`domain::modbus::master`, клиентские impl'ы транспортов `Rtu`/`Tcp`/`Udp` (в них же
слив `MAX_DRAIN` RTU и `master_error`) и их тесты; «false» вырезает всё это
Liquid-блоками `// {%- if modbus_master == "true" %}` … `// {%- endif %}` (в
комментариях — правило корневого workspace, `docs/architecture.md`), а `domain/src/modbus/master.rs`
хук удаляет `file::delete` — только при `protocol=modbus` и «false» (без modbus каталог
`modbus` уходит целиком). `MAX_LOST_IN_A_ROW` в UDP master'у не принадлежит — им пользуется
и приём slave'а, поэтому остаётся в обоих вариантах. Тесты —
`modbus_master_*` в `chip-data-gen/tests/cascade.rs`, конфигурации
`modbus-tcp-master`/`modbus-uart` в `template-check`.

### Граф задач (`graph`): порог размера, протоколы без графа, сеть

Четвёртый — `graph` (граф задач `supervisor`). Он выключается по размеру: раздел, в
который линкуется приложение (`ACTIVE` при OTA, иначе весь flash за вычетом настроек),
сравнивается с `GRAPH_MIN_PARTITION` — 32 KiB. Порог эмпирический, обе точки замерены
сборкой: на STM32L011F4 (16 KiB, Cortex-M0+) линкер не досчитывает двух сотен байт, на
STM32C011D6 (32 KiB, то же ядро) проект занимает 12.6 KiB из 32. Сам `supervisor`
стоит около полутора килобайт на Cortex-M4 и до пяти на Armv6-M, где крупнее и код, и
арифметика времени. Обе стороны решения закреплены тестом каскада
`graph_is_dropped_when_the_app_partition_is_too_small`; менять порог — вместе с ним.

Протоколу связи по UART, USB и CAN граф не нужен: при `graph=no` (и когда граф снят
размером) узел протокола и его `USB` спавнит `tasks::spawn_all` (модули задач в
`crates-cross/app/src/tasks/` над `domain::{server,canopen,protobuf,usb}::task`,
как `ota::task`). Канал протокола — конкретный тип из `adapters-logic`: граф
строит его в привязке узла (память — `static T`), модуль задачи — в теле задачи
(память — свои статики); общего модуля каналов в `app` нет. Тест каскада —
`protocol_does_not_need_the_graph`, конфигурации `*-no-graph` в `template-check`.

**Сеть — только с графом.** TCP/UDP без графа меню не предлагает, а `--define` с ними
при `graph=no` — ошибка хука. Сеть — это стек, его узел `NET` и узлы служб (REST, SSH,
MQTT) с порядком старта и номерами клиентов OTA; ручной путь к тому же без графа (модули
`tasks/{net,http,ssh,mqtt}.rs`) был вторым способом сделать одно, и его держали только
тесты шаблона. Тест каскада — `the_network_needs_the_graph`.

В ветке ручной раскладки (`--define swap_buffer=...`) размер раздела знает только
человек, поэтому ответ пользователя проходит как есть: не влезет — скажет линкер.

### Выбор чипа (`chip_feature`, `chip`/`cpu`/`target`)

`--define chip_feature=...` сверяется со списком валидных чипов (`CHIPS.contains(suffix)`)
— опечатка ловится сразу при генерации, а не на `cargo build` в сгенерированном проекте.
Массив `CHIPS` из-за этого объявлен на верхнем уровне скрипта (не внутри `if`/`else`) —
он нужен обеим веткам. `chip`/`cpu`/`target` сразу после выбора чипа выставляются, только
если ещё не заданы (`if !variable::is_set(...)`) — их тоже можно переопределить отдельным
`--define`, независимо от `chip_feature` (см. таблицу `PACKAGE_CHOICES` ниже — override
`chip` заодно и пропускает её).

### Таблицы `chip-data/` и генератор `chip-data-gen`

Все таблицы в `chip-data/` (список валидных чипов `CHIPS`, уточнение корпусировки
`PACKAGE_CHOICES`, банковая схема `BANK_MODE`, раскладка памяти `MEMORY_LAYOUT` и
остальные) пишет `chip-data-gen` — целиком, через соседний `chip-data.tmp` и подмену
каталога, чтобы файлы всегда были одного поколения и не оставалось файлов исчезнувших
семейств. Хук берёт их `import`'ом и копирует в одноимённые `const`, так что дальше по
скрипту они выглядят как раньше. Пишет их `chip-data-gen` — отдельный
standalone-крейт в корне репозитория, НЕ
член корневого `[workspace]` (свой `Cargo.toml` с пустым `[workspace]`) и НЕ часть
шаблона: он инструмент обслуживания САМОГО РЕПОЗИТОРИЯ, запускается мейнтейнером вручную
(`cargo run --manifest-path chip-data-gen/Cargo.toml`) при обновлении версии
`embassy-stm32` в `crates-cross/Cargo.toml` (обычный semver-пин на crates.io —
не путать с git-зависимостью rust-lib, закреплённой ревизией `rust_lib_rev`, см.
«Значение в корневом workspace» выше) или локальной
версии `probe-rs-tools`, и не
должен попадать в проекты пользователей шаблона — отсюда `ignore = ["chip-data-gen"]` в
`[template]` (не `exclude`: тот лишь отключил бы Liquid-подстановку, а каталог всё
равно уехал бы в проект; и без глоба `/**` — с ним cargo-generate директорию не распознаёт,
нужно имя каталога как есть, тоже проверено эмпирически). Он не может быть частью
`crates-host/xtask/`, хотя тот и выглядит подходящим местом по названию — `crates-host/xtask/` сам шаблонный
крейт и копируется в проекты пользователей, а этому инструменту там не место. Логика
`chip-data-gen`: чип-фичи `embassy-stm32` — из `cargo metadata` (полный список
объявленных features пакета, не только резолвящихся для этого воркспейса); валидные
идентификаторы probe-rs — из `probe-rs chip list`; итоговый список — пересечение (чип
исключается из каскада, если `embassy-stm32` его знает, а установленный `probe-rs` ещё
нет).

### Двухъядерные чипы (`dual_core`)

Двухъядерные чипы (STM32H745/747/755/757, STM32WL54/55) кодируют выбор ядра
суффиксом прямо в чип-фиче embassy (`stm32h745zi-cm7`/`-cm4`) — probe-rs про этот
суффикс не знает (одна цель `STM32H745ZI` на оба ядра), поэтому `chip` вычисляется от
части ДО дефиса, а `cpu`/`target` для такого суффикса берутся не из таблицы по
семейству, а из отдельного `core_override()` в `chip-select.rhai` (там же и полный
список причин).

Для этих ~60 двухъядерных чипов каскад дополнительно выставляет переменную `dual_core`
(`"true"`/`"false"`, безусловно — без `--define`-override, см. `is_dual_core()` в
`chip-select.rhai`). Она выбирает ветку **прямо при генерации**, Liquid-условием
`{% if dual_core == "true" %}` в `crates-cross/bsp/src/board.rs`: в
проект попадает ровно одна реализация `init_peripherals()` — под двухъядерный чип
`embassy_stm32::init_primary(config, &SHARED_DATA)` (`SHARED_DATA` — локальная
`static MaybeUninit<SharedData>`, требуемая сигнатурой, никуда не публикуется), под
одноядерный обычный `init()`. Комментарий про AMP и option byte BCM4 тоже лежит внутри
двухъядерной ветки и в одноядерный проект не попадает.

Cargo-фичи `dual-core` у `crates-cross/bsp`/`crates-cross/boot` с обеими реализациями
под `#[cfg(feature = ...)]` больше нет: убрана по решению пользователя (в проект не
должен попадать код для чужого класса чипа), не восстанавливать без запроса.
Рассинхрон по-прежнему шумит: `init_primary` не существует без настоящей `_dual-core`
у `embassy-stm32` (её он включает сам для любой `"...-cmN"` чип-фичи), поэтому ошибка
в `is_dual_core()` (двухъядерная ветка у одноядерного чипа) — ошибка компиляции, а не
тихая сборка с чужим API.

**Осознанное ограничение** (не забытая деталь, зафиксировано по решению пользователя —
не расширять без отдельного запроса): код пишется только под ОДНО ядро — то, что
выбрано в каскаде (например `stm32h745zi-cm7` — CM7). Шаблон не генерирует для второго
ядра ни кода, ни отдельного образа, взаимодействие с ним не оркеструется. Это НЕ значит,
что второе ядро гарантированно бездействует — зависит от семейства:

- **STM32WL54/55**: CPU2 (CM0+) по умолчанию не стартует при сбросе, пока CPU1 (CM4) явно
  не выставит `PWR_CR4.C2BOOT` — сгенерированный код этого не делает, второе ядро реально
  остаётся выключенным.
- **STM32H745/747/755/757**: заводские option bytes — `BCM7 = BCM4 = 1`,
  `BOOT_CM7_ADD0 = 0x0800`, `BOOT_CM4_ADD0 = 0x0810` (RM0399 §4.4.4 Table 20, §2.6
  Tables 8–9; AN5557 §3.2), без оговорок про ревизии: при сбросе стартуют ОБА ядра, CM7
  — с `0x08000000`, CM4 — с `0x08100000`, начала банка 2. Раскладка поэтому делит flash
  так же, как ST (`NUCLEO-H745ZI-Q/Templates`) и embassy (`examples/stm32h755cm4`,
  `stm32h755cm7`): `-cm7` — банк 1, а первый сектор банка 2 (`0x08100000–0x0811FFFF`)
  не занимает никогда — `DFU` с `0x08120000` через `Bank2Region` (смещения от начала
  банка, `dfu_bank_origin` = `0x08100000`), приложение без OTA — только банк 1; `-cm4` —
  вся раскладка (bootloader, `STATE`, `ACTIVE`, `DFU`, `CONFIG`) в банке 2 с
  `0x08100000` (`flash_origin`; символы разделов хук по-прежнему отсчитывает от базы
  цельного `Flash`, `0x08000000`). У 2×512 KiB (`…g-cm4`) банк 2 лежит за пределом
  цельного `Flash` embassy (`FLASH_SIZE` — сумма банков), и OTA, внешняя OTA и раздел
  настроек там отключены с объяснением, а не разложены туда, куда прошивка не напишет.
  Правила — `H7Core` в `chip-data-gen`, тесты — `h7_cm4_lives_in_bank_2`,
  `h7_cm7_keeps_the_cm4_boot_sector_free` там же и `cm4_of_a_dual_core_h7_*`/
  `cm7_of_a_dual_core_h7_*` в `cascade.rs`. Пустой сектор второе ядро не
  останавливает — оно стартует в стёртую память, — поэтому проекту остаётся снять бит
  второго ядра (для `-cm7` — `BCM4`, для `-cm4` — `BCM7`) через STM32CubeProgrammer
  (Option bytes → User Configuration): это единоразовая настройка платы, шаблон её не
  делает и не может (docs/flash.md, «Память второго ядра»).

Полноценная symmetric/asymmetric AMP-поддержка — отдельная архитектурная задача, в
шаблон не входит: второй прошиваемый образ (свои `cpu`/`target`/`chip_feature`) в
одной генерации, `SharedData` по одному адресу в обоих `memory.x` (а не локальная, как
сейчас), прошивка и `run` двух образов, OTA двух прошивок в `crates-cross/boot`.

Проверено ТОЛЬКО компиляцией (`cargo generate` → `cargo xtask build`/`lint cross` на
`stm32h745zi-cm4` — его гоняет `template-check`), не на железе: поведение второго ядра
на плате, в том числе старт обоих ядер с заводскими option bytes (он взят из RM0399),
не проверялось. Одноядерные чипы (в т.ч. остальные H7 — H743/H753 и т.п.) получают
одноядерную ветку: `Board::new()`/`main()` вызывают обычный `init()`.

### Суффиксы корпусировки (`PACKAGE_CHOICES`)

У чип-фич с суффиксом силиконовой градации, не обозначающим ядро (например `-a`/`-x` у
STM32L1xx — автомобильный температурный диапазон, не путать с `-cm7`/`-cm4` у
двухъядерных выше), просто взять часть ДО дефиса недостаточно: например для
`stm32l151c6-a` этот дефолт (`STM32L151C6`) существует и валиден, но не самый точный — у
probe-rs есть более специфичные `STM32L151C6TxA`/`STM32L151C6UxA` (16 KiB RAM против
10 KiB у общей цели — настоящая automotive-версия). Между собой такие цели различаются
только корпусировкой (`Tx`/`Ux`/`Hx`/`Yx`) — по `probe-rs chip info` они побайтово
идентичны (ядро, память), так что выбирать между ними незачем: `chip-data-gen` находит
все такие цели через `package_candidates()` и пишет их массивом в `PACKAGE_CHOICES`
(`chip-data/packages.rhai`), а
хук берёт первую (`PACKAGE_CHOICES[suffix][0]`) без вопроса — список из `BTreeSet`, поэтому
детерминирован. `CORE_MARKERS` в `chip-data-gen` (должен буквально совпадать со
списком в `core_override()`) исключает ядерные суффиксы из этого поиска — там
семантика другая (реально разные ядра, а не корпусировка одного и того же).

### Банковая схема (`bank_mode`, блок `BANK_MODE`)

У ~194 чипов (G4 cat3, L4+, F7, F4 dual-bank, L5, G0) `stm32-metapac` несёт НЕСКОЛЬКО
карт памяти — одно- и двухбанковую. Для них `build.rs` самого `embassy-stm32` ТРЕБУЕТ
фичу `single-bank`/`dual-bank` и без неё паникует («Chip supports single and dual bank
configuration. No Cargo feature to select one is enabled»), то есть сгенерированный
проект не собирается вовсе. `select_memory_config` повторяет его предикаты по именам
регионов (`BANK_1` без `BANK_2` → однобанковая) и предпочитает однобанковую: непрерывный
`ACTIVE`, а read-while-write, ради которого нужна двухбанковая, `crates-cross/boot` не
использует. Для одноконфигурационных чипов `bank_mode` — пустая строка, и `{% if %}` в
`crates-cross/Cargo.toml` фичу не выводит: лишняя фича так же фатальна («The 'single-bank'
feature is not supported on this dual bank chip»).

Предпочтение однобанковой стоит одного шага в прошивке: у G4 cat3, L4+, L5 и G0B/G0C с завода стоит
двухбанковый режим, и `bsp/src/banks.rs` (его же зовёт `boot` — `bsp::banks`) переключает
его при первом старте. Каким чипам, какой вариант регистров (`g0`/`g4`/`l4`/`l5`) и какой бит режима
(`g4:22`; у L4+/L5 бит зависит от объёма — `bank_switch_bits`) — блок
`BANK_SWITCH`: версия блока FLASH из метаданных через таблицу `FACTORY_DUAL_BANK` в
`chip-data-gen` — заводское значение option byte в метаданных нет, оно из документации. Каждый
вариант входит в набор `default_cases()` в `template-check` (`stm32g474re`,
`stm32g0b1rc`, `stm32l4r5zi`, `stm32l552ze`; список актуален на момент записи —
сверяйте с файлом), на плате — не проверен.

Второй банк за разрывом в адресах (`bank2_of` + проверка «вне цепочки» в
`compute_memory_layout`) — у 36 чипов с фиксированным dual: H742/743/745/747 и H7A3 с
1 MiB, U5F7/U5F9 с 2 MiB (у `…g-cm4` из них OTA отключена — см. абзац про
STM32H745/747/755/757 выше). С внутренней OTA там `DFU` в банке 2, раскладка несёт ключ
`dfu_bank_origin`, хук по нему выставляет `dfu_bank` и считает `__bootloader_dfu_*` от
начала банка, а `boot`/`bsp` пишут `DFU` через `Bank2Region` (почему не через цельный
`Flash` — docs/flash.md, «Банки flash»). Ветку проверяет `template-check`
(`stm32h743zg`, `dfu-bank`). Стыкующиеся банки — один непрерывный flash, `DFU` к банку
2 не привязан. Исключение — `-cm7` двухъядерных H7 любого объёма: первый сектор банка 2
у них — точка старта CM4, и `DFU` всегда в банке 2 за ним (`H7Core`), с тем же ключом
`dfu_bank_origin`.

### Сторожевой таймер (`watchdog_peripheral`, блок `WATCHDOG`)

Имя блока (`{{watchdog_peripheral}}`) `bsp` подставляет в группу `WatchdogResources { iwdg }`
(`resources.rs`) и в псевдонимы `wdg::UnarmedBoardWatchdog`/`wdg::BoardWatchdog`
(`Iwdg<peripherals::IWDG…, HW_TIMEOUT_US, Disarmed/Armed>`), `boot` — в свой
`IndependentWatchdog::new`, а имя типа в `embassy-stm32` — ровно то, что стоит в метаданных: у 800 наборов из 891 это `IWDG`, у 91 — `IWDG1`
(H7), и у 32 из них рядом ещё `IWDG2` (двухъядерные H7: первый принадлежит ядру CM7,
второй CM4). Блок `WATCHDOG` перечисляет только исключения — 131 чип каскада, — а
остальным хук подставляет `IWDG`; полная таблица на 1479 строк повторяла бы одно и то
же слово рядом с десятками тысяч сгенерированных.

Читается это не из `<chip>/metadata.rs`, в отличие от карты памяти: там лежат только
имя, семейство и `memory`, а перечень блоков — в общем файле, который тот включает
первой строкой (`include!("../metadata_0180.rs")`) и делит с десятками других чипов.
Отсюда две функции вместо одной: `parse_included_metadata` и `parse_watchdog_names`,
плюс кеш разобранных общих файлов.

Когда блоков `IWDG` два (`IWDG1`/`IWDG2` у двухъядерных H7), метаданные обоих ядер перечисляют оба — различить их там нечем, и
выбор делается по суффиксу ядра (`-cm4`), который каскад **уже** выбрал. Это не
эвристика по имени чипа: имя блока по-прежнему приходит из метаданных, по суффиксу
решается только который из двух. Настоящую эвристику по имени сюда заводить нельзя —
ровно на ней погорел признак `erase_zero` (см. ниже).

Остальное про сторож — по семейству, таблицей `watchdog_family_table()` в самом хуке
(переменные `lsi_max_hz`, `dbgmcu_freeze`, `dbgmcu_clock`): верхний предел LSI из
даташита (им `bsp::wdg::HW_TIMEOUT_MIN_US` поправляет цепочку таймаутов,
`docs/watchdog.md`), бит заморозки IWDG в `DBGMCU` и такт `DBGMCU` в `RCC` там, где без
него блок не пишется (C0/F0/F3/G0/L0/U0) — «регистр:поле» из
`stm32-metapac/src/peripherals/dbgmcu_<семейство>.rs` и `rcc_<версия>.rs`. Таблица ручная,
а не из генератора: версия блока `DBGMCU` в метаданных совпадает с префиксом семейства у
каждого чипа каскада (stm32-metapac 21; расходятся только WB0x и `wl5x-cm0p`, которых в
каскаде нет), предел LSI в метаданных не лежит вовсе. Поэтому при обновлении
`stm32-metapac` её сверяют руками: имена регистров и полей в новых `dbgmcu_*.rs`,
`rcc_*.rs` (поле `set_dbgen`/`set_dbgmcuen` у новых версий `RCC`), новое семейство — новая
строка; опечатку в строке поймает только сборка проекта под чип этого семейства.
`IWDG2` (двухъядерные H7, `-cm4`) заморозки не получает: в `dbgmcu_h7.rs` поля для него нет.

### Другие признаки чипа

#### `CPU_FREQ_BOOST`

Из того же общего файла метаданных, что и имена сторожей, берётся признак `CPU_FREQ_BOOST` (блок `CPU_FREQ_BOOST`,
переменная `cpu_freq_boost`): блок `PWR` версии `h7rm0468` — 25 чипов
H723/725/730/733/735. Им `bsp` получает `src/clocks.rs`, остальным хук его удаляет
(docs/clocks.md). Поэтому кеш хранит не список имён, а `SharedMetadata` — оба факта
файла разом.

#### Кэши (`CACHE`)

Кэши (блок `CACHE`, переменная `cache`) выводятся так же, из метаданных: `icache` — есть блок
`ICACHE` в общем файле; `icen`/`dcen` — есть ли `set_icen`/`set_dcen` в файле регистров
`FLASH` его версии (`stm32-metapac/src/peripherals/flash_<версия>.rs`, `chip_caches`) — таблицы
семейств нет. Кэши ядра M7 в блок не входят: хук добавляет тег `scb`, когда выбранное каскадом
`cpu` — `cortex-m7` (так двухъядерный H745 получает его только в `-cm7`). Чипу без тегов хук
удаляет `crates-cross/bsp/src/cache.rs`; `board.rs` и `lib.rs` смотрят на ту же переменную
(`unstable-pac` у `bsp` включён всегда — его требует `src/reset.rs`). Тест —
`caches_follow_the_metadata_and_the_core`.

#### Флаги сброса (`RESET`/`RESET_REGS`)

Флаги сброса (блоки `RESET`/`RESET_REGS`, переменные `reset_reg` и `reset_flags`) — тем же
приёмом: версия блока `RCC` из общего файла метаданных, в
`stm32-metapac/src/peripherals/rcc_<версия>.rs` — структура регистра с `set_rmvf` и её
аксессор в блоке `Rcc` (`csr`, `csr2` у C0, `rsr` у H5/H7; аксессоры ядер `c1_`/`c2_`
отбрасываются), а из её полей — пары по порядку причин `RESET_CAUSES` (`reset_register`).
Причин несколько на один вариант (`porrstf,borrstf:PowerOn`), потому что одинаковые ветки
подряд `clippy` не пропускает. Нет блока `RCC`, регистра с `set_rmvf` (или их два), ни одного
известного флага — генератор падает, хук без записи — тоже. `bsp/src/reset.rs` разворачивает
пары Liquid-циклом в цепочку `if`. Тесты — `reset_flags_of_*` (F4, H743, C0, G0) в
`chip-data-gen/src/metadata.rs`.

#### Регион `DMA_NC` и кэш данных M7

Кэш данных ядра M7 (тег `scb_d`) включается только вместе с регионом `DMA_NC`: `chip-data-gen`
(`dma_nc_region`) отрезает до 32 KiB от конца RAM (`PANIC` уходит под регион) и кладёт в
запись раскладки `dma_nc_origin`/`dma_nc_length`. RAM у H7 — самая большая непрерывная
область (AXI-SRAM), а не DTCM с `0x20000000`; у остальных семейств — цепочка с `0x20000000`
(у WB более крупная SRAM2 — память радиостека CPU2); у ядра CM4 двухъядерных H7 — SRAM домена
D2 с `0x30000000`, мимо AXI-SRAM ядра CM7. `DMA_NC` не берётся из SRAM домена D2:
до неё не дотягивается IDMA SDMMC1; у H7 `SRAM4` в `0x38000000` целиком — `bdma_nc_*` (память BDMA).
Ядро M7 генератор берёт по семейству (`f7`/`h7`, не `-cm4`) — как `family_table` в хуке.
Хук выставляет признаки `dma_nc`/`bdma_nc`, пишет в `memory.x` символы `__dma_nc_*`/`__bdma_nc_*`
с `ASSERT` годности для MPU (их читает `bsp::layout`),
удаляет `bsp/src/dma_nc.rs` там, где региона нет, дописывает `scb_d` в `cache` и вставляет в
`memory.x` приложения `SECTIONS { .dma_nc, .bdma_nc } INSERT AFTER .gnu.sgstubs;` (`INSERT AFTER
.uninit` не собирается под `flip-link`: проверено сборкой; инвариант «в `memory.x` нет SECTIONS»
в `memory_layout_invariants_hold_for_every_chip` сделан исключением для этих секций).
Тест — `every_m7_chip_gets_a_dma_region`. `DCACHE` (U5/H5) и предвыборка намеренно не включаются —
`docs/clocks.md`, «Кэши».

#### Ядра без `DWT.CYCCNT` (`core_baseline`)

`core_baseline` ("true" для Cortex-M0/M0+/M23 по `cpu`) — ядра без `DWT.CYCCNT`, `CFSR` и
`DIV_0_TRP`: им нет ловушки деления в `app/src/fault.rs`, а обработчик `HardFault` там
собирается короче (`pc`/`lr`). Тест — `baseline_cores_are_marked`. Обработчик остаётся у всех: `#[exception]` экспортирует имя, и
`app` держит его в образе без ссылок; на плате фолт не вызывался.

### Раскладка памяти (`swap_buffer`, `ota`, блок `MEMORY_LAYOUT`)

`embassy-stm32` уже зависит (фича `metadata`) от `stm32-metapac`, а тот для каждого чипа
несёт `chips/<chip>/metadata.rs` — обычный Rust-файл с литералом `Metadata { memory: &[&[
MemoryRegion { address, size, settings: Some(FlashSettings { erase_size, write_size, ..
}) } ]] }`, читается текстом без сборки (`parse_chip_memory`). **Формат при этом не
один**: у одноконфигурационных чипов `stm32-data` печатает `memory: &[&[` одной строкой,
у многоконфигурационных — `memory: &[` и `&[` на следующей. Поэтому разбор идёт счётом
скобок (`split_memory_configs`), а не поиском литерала `memory: &[&[`, как раньше — на
том поиске ~194 чипа молча выпадали из генерации.

Отсюда `chip-data-gen` считает адреса/размеры (`compute_memory_layout` +
`compute_ota_partitions`) и пишет их в `MEMORY_LAYOUT`, а хук в конце — если `swap_buffer`
не задан через `--define` (запись есть у каждого чипа, без неё хук делает `abort`) — выставляет `swap_buffer`/`ota` и
пишет `memory.x` через `file::write` (во временную копию шаблона ДО рендера — то самое
"the template folder", о котором предупреждает документация `file::write`, не в
`crates-cross/*/memory.x` этого репозитория).

**Границы, нужные прошивке в рантайме, — символы `memory.x`, а не `[env]`** (правило —
`docs/flash.md`, «Символы раскладки»). Хук пишет их рядом с регионами: размер
`ACTIVE` (из `__bootloader_active_*`), границы `CONFIG` (`__config_start`/`__config_end`:
от `ORIGIN(CONFIG)` во внутреннем флеше, литералами на внешней), конец внешней флеши
(`__ext_flash_end` = `MAX` по концам разделов), регионы DMA (`__dma_nc_*`, `__bdma_nc_*`)
и `ASSERT`'ы над ними (кратность `CONFIG` его странице — литералом из генерации). В
`[env]` из генерации едут `STATE_ERASE_SIZE`, `SWAP_PAGE_SIZE`, `EXT_PAGE_SIZE`,
`WATCHDOG_TIMEOUT_US`, `HTTP_CONNECTIONS`. Символы — в `memory.x` `app` и
`target-tests`; у `boot` — только символы внешней флеши. Ручные заготовки
`crates-cross/*/memory.x` показывают, какие символы вписать. Тесты —
`partition_bounds_are_linker_symbols` и соседние в `cascade.rs`.

**`erase_zero` в записи — из `erase_value` того же `FlashSettings`**, а не из имени
чипа. Раньше хук считал признак как «фича начинается на `l0`/`l1`» — и мимо проходили
STM32WB10CC/WB15CC (`erase_value: 0` при другом префиксе, оба в каскаде): проект под
них получал `embassy-boot` без `flash-erase-zero` и неработающий раздел настроек, обе
поломки молчаливые. Запасной эвристики по имени в хуке нет: запись раскладки есть у
каждого чипа из `CHIPS`, а без неё хук делает `abort` (см. конец раздела). Стережёт это тест каскада `erase_zero_follows_the_metadata_not_the_chip_name`, где
рядом с `wb10cc`/`wb15cc` стоит `wb55rg` с обычным флешем: без него зелёным остался бы
и вариант «всё семейство WB стирается в ноль».

**`page_size` в записи есть, а в `memory.x` его нет** — и это не забытая строка.
`page_size` записи — физическая страница чипа (максимальный сектор стирания), а
плейсхолдер `{{page_size}}` — **страница обмена** `embassy-boot` (`PAGE_SIZE`), поле
`swap_page_size` набора цифр (`config_swap_page_size` во втором): она больше физической,
когда `swap_paged` = "true" (см. ниже). Нужна она не линкеру, а `SWAP_PAGE_SIZE`
bootloader'а и `bsp::flash`: страницами обмена `swap()` переносит разделы (`ACTIVE[i]`
в `DFU[i + 1]`, прежний образ уезжает ровно на страницу). Поэтому хук раздаёт её
отдельной переменной. В ветках, где
раскладку пишет человек, и с внешними разделами переменная пустая — «неизвестен».

**Наборов цифр в записи чипа два.** Второй, с префиксом `config_`, — раскладка того же
чипа с разделом настроек (`compute_config_partition`). Без OTA раздел — две последние
страницы flash (`config_origin`/`config_length`/`config_erase_size`), и `FLASH`
приложения короче на них. С OTA раздел считается двумя способами — в хвосте (тогда
`ACTIVE`/`DFU`/`BOOTLOADER_STATE` съезжают целиком: `compute_ota_partitions` считает их
ОТ размера доступного flash) и в мелких секторах резерва перед `ACTIVE`
(`place_settings_and_state`: bootloader, настройки, `STATE`), — и берётся тот, где
`ACTIVE` больше, при равенстве хвост. Где он оказался — `config_ota_settings_*`.
Хук выбирает набор одной строкой (`let key = if in_flash { "config_" } else { "" }` в
`plan()`: только когда настройки лежат во внутреннем флеше) и дальше берёт из него всё. Считать это в rhai нельзя: там пришлось бы повторить все
четыре проверки `assert_partitions` из `embassy-boot`. В резерв раздел встаёт, только
если bootloader'у перед ним остаётся `BOOTLOADER_TARGET` (32 KiB), а не `BOOTLOADER_MIN`:
выгоду для `ACTIVE` нельзя оплачивать бинарником bootloader'а — без этой границы на
равносекторных чипах раздел ужимал bootloader до 16 KiB ради одной-двух страниц. Цифры:
раздел возможен на 1421 чипе из 1479, из них на 1183 вместе с ним помещается OTA. Из
остальных 40 чипов, у которых раскладка OTA без раздела сходится (всего их 1223), у 20
(H7R/H7S) OTA бесполезна и без него — `ACTIVE` меньше `OTA_MIN_ACTIVE`, а у 20
H742/H743/H745-cm7/H747-cm7 с 1 MiB раздел не умещается рядом с OTA в банке 1 (см.
выше про порядок `ota` и `config`); в резерв перед `ACTIVE` раздел лёг у 223 чипов F2/F4/F7, у остальных
он в хвосте.

**Файлы у `app` и `boot` разные.** У `app` `FLASH` = `ACTIVE` (приложение линкуется
именно туда), у `boot` `FLASH` = его собственная зона до `BOOTLOADER_STATE`. Раньше
писался один и тот же текст с `FLASH` от базы flash — и прошивка руками (`cargo flash -p boot --release`, затем
`cargo run -p app`) затирала бы bootloader образом приложения; OTA не работал ни на одном чипе.
Смещения `__bootloader_*` в обоих файлах считаются от литерала базы flash, а НЕ от
`ORIGIN(FLASH)`: их читает `embassy-boot`, работающий с флешем целиком, а `ORIGIN(FLASH)`
у `app` теперь означает начало `ACTIVE`.

**Выводятся ВСЕ регионы чипа**, а не только `FLASH`/`RAM`. `FLASH` и `RAM` — это
непрерывные цепочки от базовых адресов (их имена требует `link.x` у `cortex-m-rt`), а всё
остальное `extra_region_lines` отдаёт готовыми строками под своими именами из
`stm32-metapac`: ITCM, AXISRAM, CCMRAM, BKPSRAM, EEPROM, OTP и т.д. Раньше их не было
вовсе — на H723VE пользователь видел 128 KiB DTCM и не видел ни 320 KiB AXISRAM, ни
64 KiB ITCM, ни трёх SRAM. Три категории при этом выводятся ЗАКОММЕНТИРОВАННЫМИ, с
причиной прямо в строке:

- **окна внешних шин** (`EXTERNAL_BUS_PREFIXES` — `FMC_`, `SDRAM_`, `OCTOSPI_`, ...):
  памяти за ними нет, пока к плате не припаяна микросхема и не настроен контроллер.
  У всех них в метаданных стоит одинаковый размер 262144000 — это не память, а максимум
  адресного окна;
- **вторые окна того же блока** (`ALIAS_SUFFIX` — `CCMRAM_ICODE` при живом
  `CCMRAM_DCODE`, `SRAM2_ICODE` при живом `SRAM2`): физически это одна и та же память по
  двум адресам, и разместить данные в обоих окнах разом — молчаливое наложение, которого
  линкер не заметит.
- **память второго ядра** — SRAM2a/SRAM2b у STM32WB (`reserved_for_cpu2`, см.
  ниже) и банк другого ядра у двухъядерных H7 (`H7Core`, абзац про
  STM32H745/747/755/757 выше).

**Память второго ядра раскладка не раздаёт.** У STM32WB (серия `wb`, не `wba` и не
`wb0` — `has_wb_cpu2`) радиоядру CPU2 принадлежат верх SRAM2a/SRAM2b и flash от
`SFSA × 4K` до конца — всегда, даже без стека (AN5185 §1.4–1.5, Table 5); доступ CPU1
туда — bus error (RM0434 §3.6.4). SRAM2a/SRAM2b со SRAM1 стыкуются, и раньше RAM у
xE/xG/xY шла через них до `0x20040000`: стек под flip-link и `.bss` уезжали в память
CPU2, и прошивка падала на обнулении `.bss` до `main`. Теперь они исключаются ДО
построения цепочек (`ram_chains`, как `mem_filter` в `embassy-stm32/build.rs`), и `RAM`
— SRAM1, `PANIC` — в её конце. Flash для раскладки обрезает `flash_for_layout` по
таблице `WB_CPU2_FLASH` — адрес установки `stm32wb5x_BLE_Stack_full_fw.bin` из Release
Notes STM32WB Copro Wireless Binaries v1.24.0 по объёму: 1M — `0x080D0000`, 640K —
`0x0807C000`, 512K — `0x0805C000`, 256K — `0x0801C000` (WB30/WB35 — тот же кристалл,
WB50 — столбец xG). Все разделы (`ACTIVE`, `DFU`, `CONFIG`, внешняя OTA) кончаются ниже.
Для WB10/WB15 (320K) в этих Release Notes таблицы нет, граница взята с запасом —
`0x08020000` (192K от конца, как у xG); её стоит сверить с Release Notes копроцессора
`STM32WB1x`. Со стеком крупнее (`BLE_Stack_full_extended`, `BLE_Mac_802_15_4`, Thread,
Zigbee) границу проект опускает руками; `SFSA` установленного стека видно в
STM32CubeProgrammer (Option bytes → Secure) — docs/flash.md, «Память второго ядра».
Объём WB, которого нет в таблице, роняет генератор паникой: границу нового чипа берут
из Release Notes, а не угадывают. Тесты — `wb_layout_leaves_the_cpu2_memory_alone` в
`chip-data-gen/src/layout.rs` и `wb_leaves_sram2_and_the_cpu2_flash_alone` в `cascade.rs`.

Ограничения — четыре runtime-assert'а `assert_partitions` (`boot_loader.rs` из
`embassy-boot`; именно assert'ы, а не документация: нарушены — bootloader паникует на
старте, а не отказывается собираться):

1. `ACTIVE` кратен `PAGE_SIZE`;
2. `DFU` кратен `PAGE_SIZE`;
3. `DFU - ACTIVE >= PAGE_SIZE` — запас алгоритма swap;
4. `2 + 4 * (ACTIVE / PAGE_SIZE) <= BOOTLOADER_STATE / NorFlash::WRITE_SIZE`.

`PAGE_SIZE` здесь — **не** плейсхолдер `swap_buffer`, а `max(ACTIVE::ERASE_SIZE,
DFU::ERASE_SIZE)`, который `embassy-boot` вычисляет сам; обе партиции живут поверх
цельного `Flash` (`crates-cross/boot/src/main.rs`), у которого `NorFlash::ERASE_SIZE =
MAX_ERASE_SIZE` всего чипа, — либо поверх `ErasePage<_, SWAP_PAGE_SIZE>`, если страницу
обмена расширили (абзац про `swap_paged` ниже). Плейсхолдер `swap_buffer` — это const generic
`BootLoader::prepare::<_,_,_,N>`, размер буфера подкачки: обязан делить `PAGE_SIZE`, быть
кратным `NorFlash::WRITE_SIZE` и не меньше него — `NorFlash::WRITE_SIZE` чипа (4/8/32)
удовлетворяет всем трём, его и подставляем.

Четвёртый assert — причина, по которой `BOOTLOADER_STATE` нельзя делать «просто одним
сектором»: в нём лежит журнал прогресса swap, по слову на страницу `ACTIVE` в каждом из
четырёх проходов плюс два служебных. На L4 (1 MiB при секторе 2 KiB) при физической
странице обмена это `(2 + 4*247) * 8` байт — четыре сектора, а не один (сейчас L4
расширяет страницу обмена до 8 KiB, и `STATE` снова умещается в 2 KiB — см. `swap_paged`
ниже). Раньше здесь всегда стоял ровно один сектор, и **279 из
972 посчитанных раскладок роняли bootloader в панику при первом же старте** (среди них
l476rg — Nucleo-L476RG). Теперь размер `BOOTLOADER_STATE` подбирается под фактический
`ACTIVE`, а резерв при необходимости растёт на страницу (`BOOTLOADER_MIN` — сколько
обязано остаться под сам бинарник). Чтобы это не разъехалось снова, перед возвратом
раскладки вызывается `assert_embassy_boot_invariants` — те же четыре проверки, но на
этапе генерации.

`BOOTLOADER`/`BOOTLOADER_STATE` кратности `PAGE_SIZE` не подчиняются (в
`assert_partitions` их нет) и режутся по локальной границе сектора — на чипах с крупными
секторами (F4/F7/H7, до 128 KiB) целая страница под один отступ съела бы четверть чипа.
Но **пятая проверка** — уже не из `assert_partitions`, а из `Partition::new`
(`embassy-embedded-hal`): смещение и размер раздела кратны `ERASE_SIZE` флеша под ним,
иначе паника при построении раздела. Над цельным `Flash` (страница — `MAX_ERASE_SIZE`)
`STATE` в мелком секторе её не проходил, и у всех 223 чипов F2/F4/F7 с OTA и bootloader,
и приложение падали на первом старте. Теперь `STATE` живёт над `flash_page::ErasePage`
со страницей своего сектора — она лежит в записи полем `bootloader_state_erase_size`
(и `config_…` во втором наборе), хук раздаёт её плейсхолдером `state_erase_size`, а
`assert_embassy_boot_invariants` проверяет кратность всех трёх разделов своей странице.
`state_paged`/`config_paged` = "true", только если эта страница не равна физической
(`page_size`): тогда раздел оборачивается в `ErasePage`, иначе строится прямо над `Whole`, а
`const`-assert (`… == MAX_ERASE_SIZE`) держит равенство. `boot_partitioned` — строит ли
bootloader хоть один раздел над `BlockingPartition` (`STATE` со своей страницей или `ACTIVE`/`DFU`
со страницей обмена): только тогда ему нужны `FLASH_BYTES` и обёртки.
Сам сектор выбирает `place_state` — самый мелкий в резерве, как можно ближе к `ACTIVE`;
на чипах с равными секторами раскладка от этого не изменилась, на F4 `STATE` — 16 KiB в
секторе 3 вместо 64 KiB в секторе 4.
Краевой случай, ради которого `reserved_pages` растёт в цикле, — чипы, где уже первый
регион занимает целый `PAGE_SIZE` (H7 — 128 KiB с адреса 0, без мелких секторов в начале,
в отличие от F4): иначе `BOOTLOADER_STATE` съедал бы весь резерв.

**Страница обмена крупнее физической (`swap_paged`).** Подписанный `boot` весит ≈23 KiB,
а журнал из проверки 4 на чипе с мелкой страницей огромен: у L0 (страница 128 байт, ~640
страниц, слово 4) `STATE` — 10 KiB из блока в 32 KiB (`BOOTLOADER_TARGET`). Поэтому
`compute_ota_partitions` — обёртка над `compute_ota_at`, которая считает раскладку для
страницы обмена `S = p·2^k` (p — физическая, `S <= SWAP_PAGE_MAX` = 8 KiB) и берёт первую,
при которой журнал `(2 + 4*N) * WRITE_SIZE <= STATE_BUDGET` (2 KiB); `compute_ota_at`
считает всё — резерв, `ACTIVE`, `DFU`, сдвиг `ACTIVE` — в единицах `S`, а `STATE` по-прежнему
кладёт в физические сектора (`bootloader_state_erase_size`, отдельное число). Расширяется
только чип с равными секторами и без `DFU` в банке 2 за разрывом (`dfu_bank`): на
F2/F4/F7/H7 страница обмена и так крупнейший сектор, а банк 2 лежит в другом регионе
`Flash`. Не уложились на 8 KiB — остаётся физическая страница, а запас под код держит
`BOOTLOADER_MIN` (26 KiB; резерв растёт не менее чем на `MAX_EXTRA_RESERVED_BYTES` = 8 KiB
независимо от размера страницы). Запись несёт `swap_page_size` и `swap_paged` (и `config_…`
во втором наборе); хук выставляет `page_size` = `swap_page_size` и `swap_paged`; для `ota=no`,
`ext_flash=yes`, `dfu_bank` и ручной раскладки `swap_paged` = "false". Прошивка (`boot`,
`bsp::flash`) при "true" оборачивает `ACTIVE` и `DFU` в `flash_page::ErasePage<_, SWAP_PAGE_SIZE>`,
число — то же `{{page_size}}` (менять только вместе). `DFU` не короче `ACTIVE` + `S` и кратен
`S` (бывает на страницу длиннее, если остаток чётный). Инвариант «у каждого чипа с OTA зона
bootloader'а не меньше `BOOTLOADER_MIN`» стережёт `bootloader_zone_and_swap_page_hold_for_every_chip`.

**Раскладка есть у каждого чипа, и `PANIC` в ней — всегда.** `compute_memory_layout` возвращает `None` только когда считать не из чего: нет
непрерывной flash- или RAM-цепочки от базового адреса. Сейчас таких чипов нет ни одного,
и это не проза, а проверка: `chip-data-gen` падает с `ensure!`, если раскладок вышло
меньше, чем суффиксов, а хук — `abort`, если записи для чипа в `chip-data/layout/` нет
(разошлось правило семейства или каталог недоперегенерирован). Запасной ветки с
`memory.x`-плейсхолдером у хука больше нет; ручная раскладка — только через `--define
swap_buffer=...`. `PANIC` выводится всегда,
когда есть раскладка, и это обязательство, а не удобство: паникёр release-профиля `app`
(`panic-persist`) стоит безусловно, и без символов `_panic_dump_*` release-образ `app` не
линкуется. У `boot` паникёр свой — сброс без дампа, символов `_panic_dump_*` нет, — но
регион `PANIC` вырезан и из его RAM, чтобы стек bootloader'а не затёр дамп приложения
до чтения. Размер — доля RAM (`PANIC_FRACTION`, зажатая между `PANIC_MIN`
и `PANIC_MAX`): 512 байт на чипе с 8 KiB и больше, 128 на двух килобайтах у STM32L011.
Фиксированные полкилобайта были бы на таких чипах четвертью всей памяти, поэтому регион им
просто не доставался — а с безусловным `panic-persist` это означало бы «шестнадцать чипов
генерируются в заведомо несобираемый проект». Других резервов в RAM нет, кроме `DMA_NC` у
ядер M7 («Регион `DMA_NC` и кэш данных M7» выше): прежний `PERSIST`
(счётчик запусков) и символ `_hw_ram_start` (замер стека) ушли вместе со своими
потребителями. Ручной override — как и у `chip`/`cpu`/`target`: `--define swap_buffer=...`
отключает автогенерацию memory.x целиком (адреса привязаны именно к вычисленному
`swap_buffer`, доверять чужому нельзя) — тогда всё, как раньше, вручную.

Регрессионные тесты на всё перечисленное — `chip-data-gen/tests/cascade.rs`
(`memory_layout_invariants_hold_for_every_chip` проходит по всем чипам сразу) и юнит-тесты
в `chip-data-gen/src/layout.rs`.

### OTA на внешней флеши (`ext_flash=yes`, набор `ext_*`)

Третий набор цифр в `MEMORY_LAYOUT` — `compute_external_ota`: внутри
только bootloader и `ACTIVE`, снаружи `STATE`, `DFU` и место под настройки, всё по
`ext_align`. Набора «OTA снаружи, настройки во внутреннем флеше» нет: при
`ext_flash=yes` настройки тоже уезжают на внешнюю флеш. Почему так и какие числа — `docs/flash.md`. Проверки, которые
`assert_partitions` и `Partition::new` делают на плате, повторяет при генерации
`assert_external_invariants`.

Хук выбирает набор по ответам `ext_flash` (`yes`/`no` — внешняя флеш на плате;
есть — на неё уезжают и OTA, и настройки), `ota` и `config` (`yes`/`no`; незнакомый ответ и прежние
`internal`/`external` — ошибка генерации), пишет `memory.x` с символами-смещениями внешней флеши и
выставляет `ota_store` (на него смотрят `boot`, `bsp::flash`, `bsp::external`,
`target-tests`, `xtask`) и `ext_page_size`.

В ветке с ручной раскладкой (`swap_buffer` через `--define`) `ext_page_size` — 4 KiB
(сектор внешней NOR) с подсказкой вписать `max(сектор чипа, стирание драйвера)`;
`state_erase_size` там пуст, и хук просит вписать `STATE_ERASE_SIZE`.

`bsp/src/external.rs` (и `docs/modules/bsp-external.md`) хук удаляет, если на внешней
флеши ничего не лежит (`external_flash != "true"` — в том числе при `ext_flash=yes` с
`ota=no config=no`). Стерегут ветку тесты каскада `external_ota_*` и конфигурации
`template-check` с `ext_flash=yes` (`ota-external*`, `config-external`, `ext-flash-empty` и
др.).

### Чипы без OTA (`ota = "false"`)

`compute_ota_partitions` возвращает `Err` с человекочитаемой причиной, когда схема не
помещается: ей нужно минимум 5 стираемых страниц (`BOOTLOADER` + `BOOTLOADER_STATE` +
`ACTIVE` + `DFU` на страницу больше `ACTIVE`). На STM32H723VE, например, 512 KiB одним
регионом с сектором 128 KiB — четыре страницы, валидной раскладки не существует ни при
каком дележе. Для таких чипов (256 из 1479 — flash меньше резерва под bootloader,
сектора слишком крупные или, у `…g-cm4` двухъядерных H7, банк 2 вне досягаемости
`Flash`) `memory.x` всё равно заполняется — одним
образом на весь flash, — а `crates-cross/boot` из проекта убирается: `members` в
`crates-cross/Cargo.toml` под `{% if ota == "true" %}`, ветки прошивки и линта boot в `xtask`
вырезает Liquid при генерации, а сам каталог сносит `file::delete("crates-cross/boot")` в хуке.
В `.vscode/*.json` теги этого условия стоят только внутри `//`-комментариев и строковых
литералов: вне них Liquid сломал бы JSONC в самом репозитории шаблона, а после рендера от
тега в комментарии остаётся пустой комментарий.

**Вторая причина отказа — `OTA_MIN_ACTIVE` в `chip-select.rhai`.** Раскладка может
сойтись, а под приложение остаться меньше, чем занимает пустая прошивка шаблона: у
чипов с 64 KiB flash это 15–16 KiB против примерно 17 KiB минимального образа на
Cortex-M0+. Такой проект генерировался и не собирался — замерено сборкой: `f030c8`
переполнял раздел на 848 байт, `c051c8` на 1904, `l051c8` на 272. Порог 24 KiB выбран
не на глаз: у 160 чипов под приложение выходит 16256 байт и меньше, а следующий по
величине раздел — сразу 36 KiB (32 KiB с разделом настроек), так что любое значение внутри промежутка отсекает ровно
неработающие конфигурации. Стерегут это два теста каскада —
`ota_is_dropped_where_the_app_partition_is_too_small` и парный к нему
`ota_survives_where_the_app_partition_is_large_enough`: без второго порог мог бы снять
OTA у всех подряд незамеченным.

**Где пользователь видит причину.** Решение одно — `plan()`, а причину отказа печатает
только ручная раскладка: невместившиеся OTA или настройки до автоматической не доходят
(та строит лишь то, что поместилось). Под «Выбранное не помещается» хук пишет `note`
набора цифр, по которому считалась раскладка (`plan().ota_key`: `note`, `config_note`
или `ext_note`), а если цифры сошлись — что `ACTIVE` меньше `OTA_MIN_ACTIVE`; где
помогла бы внешняя флеш — подсказку `ext_flash=yes`; для настроек — что двух страниц
стирания под раздел не остаётся. Ответ «нет» (умолчание меню на таком чипе) причину не
печатает: пункт уже помечен `DOES NOT FIT`. Стережёт тест каскада
`refusal_names_the_reason_for_ota_and_settings`.

#### Почему `file::delete`, а не `[conditional]` в `cargo-generate.toml`

Условия `[conditional]` вычисляются только по значениям `[placeholders]` и переменных,
выставленных хуком через `variable::set`, НЕ видят — проверено эмпирически
(`[conditional.'ota != "true"']` каталог не убирал, то же условие по `ci` работало).
Порядок важен: после `file::delete` в этот каталог нельзя писать (`cargo generate` падает
с `os error 3`), поэтому в ветке без OTA пишутся только `memory.x` `app` и
`target-tests`, но не `boot`.

### Оценка RAM (`ram_estimate`, таблица `RAM_COST`)

Хук оценивает статическую RAM проекта (`.data` + `.bss` + `.uninit` release-образа
`app`) по таблице `RAM_COST` в `chip-select.rhai`: ядро, OTA, хранилище настроек, граф,
каждый транспорт `вид:протокол` вместе с его узлом, сетевой стек — один раз на
`tcp`/`udp` — и сетевые службы (`services`: SSH, REST, MQTT). Оценка плюс резерв стека (ниже) сравнивается с регионом `RAM` раскладки
(`ram_length`): пункт списка транспортов, с которым не помещается, помечен
` - DOES NOT FIT in RAM` (протокол там ещё не выбран — пункт стоит как худший
протокол своего вида), `--define links`/`interface` с ним — ошибка, а отсев чипов до
каскада по `links` или паре `interface` + `protocol` такие чипы не показывает (пара
без `protocol` оценивается как транспорт без протокола). Проект без транспортов не отвергается
никогда. С ручной раскладкой (`swap_buffer`, невлезающие OTA или настройки) регион RAM
пишет человек — оценки нет (`ram_estimate` пуст).

Числа в таблице — замеренные. `cargo xtask build` печатает факт строкой `ram:`, хук —
оценку строкой `ram_estimate:`; `template-check` в полном прогоне сверяет их у каждого
случая и падает, если оценка ниже факта. Тогда таблицу перемеряют:

1. Факт по случаям — таблица в конце полного прогона `template-check` (столбцы «факт»
   и «оценка»).
2. Стоимость части — разность пары сборок на одном чипе «с ней / без неё», например
   `--define links=uart:modbus` против проекта без транспортов. Пару, которой нет
   среди случаев, собирают точечно: `cargo generate` с нужными `--define`, затем
   `cargo xtask build` в проекте, строка `ram:`.
3. Из нескольких чипов берётся наибольшая разность, база — по наибольшему из чипов:
   оценка обязана быть не ниже факта на любом.

Под стек к оценке прибавляется резерв: `STACK_RESERVE` (1024 байта) и прибавки
`STACK_EXTRA` — `ota` 3072, `ssh` 40960. futures задач `embassy` и буферы транспортов
лежат в `.bss`, на стеке — цепочка `poll` одной задачи, кадры прерываний и
форматирование паники; под flip-link переполнение — HardFault, а не тихая порча
статиков. Базу больше 1 KiB не поднять: 2 KiB отвергли бы Modbus по UART на
STM32C011D6 (5760 байт RAM).

Замер — закраской стека на плате: первой строкой `main` залить стек ниже текущего SP
известным словом (`0xDEADBEEF`, 64 KiB вниз; под flip-link стек растёт вниз к
`ORIGIN(RAM)`), дать прошивке поработать под нагрузкой узлов, затем прочитать регион
(`probe-rs read --chip … b32 <_stack_start − 64K> 16384` или `read_memory` MCP
`embedded-debugger`): самое низкое перезаписанное слово — высшая отметка стека, от него
до `_stack_start` (`rust-nm` образа) — глубина. Закраска — временный код в
сгенерированном проекте, в шаблон она не входит. Замерено (NUCLEO-H743ZI2,
STM32H743ZI, граф, без транспортов, минута работы):

| Конфигурация | release | dev |
|---|---|---|
| без OTA | 576 | — |
| OTA internal | 2352 | 2336 |

Разницу даёт один кадр — `poll` задачи узла OTA, 2040 байт. Там, где на плате не
поднять (SSH без Ethernet), — статическая оценка по дизассемблеру release-образа
(`rust-objdump -d`): кадр функции — `push`/`vpush`/`sub sp`, глубина — кадр плюс
наибольшая глубина прямых вызовов (`bl`/`b.w`); косвенные вызовы (исполнитель → `poll`
задачи) она не видит, поэтому корень — `TaskStorage<…>::poll` задачи. На той же плате
она даёт для задачи OTA 2956 — не ниже замера, как и должна. Задача `SSH`
(stm32h743zg, задача SSH) — 39624 байта: обмен ключами ML-KEM-768, кадры
`domain::ssh::session::negotiate` 13712 и `EncapsulationKey::encapsulate_deterministic`
20552. Прибавки взяты от этих чисел с округлением вверх; на ядрах M0/M0+ кадры другие,
поэтому у чипов до `SMALL_RAM` хук просит проверить прошивку на плате.

Новая часть проекта со статиками (узел, буфер, сетевая служба из `services`) — новая
строка таблицы и пара сборок под неё.


## Проверка изменений в шаблоне

Команды проверки в репозитории шаблона — один список. Первые пять — перед каждым
коммитом; `template-check` — уровнем по таблице «Какой уровень когда» ниже (полный
прогон — перед вливанием в master). CI шаблона (`.github/workflows/template.yml`)
гоняет из списка подмножество, см. «Что из этого делает CI»:

```
cargo xtask lint          # корневой workspace: fmt --check + clippy -D warnings + cargo doc
cargo xtask test host     # domain: cargo nextest + doc-тесты

cargo fmt    --manifest-path chip-data-gen/Cargo.toml --check
cargo clippy --manifest-path chip-data-gen/Cargo.toml --all-targets -- -D warnings
cargo test   --manifest-path chip-data-gen/Cargo.toml --release

cargo run --manifest-path chip-data-gen/Cargo.toml --bin template-check
```

Последняя строка — полная генерация и сборка проектов (время уровней — в таблице
ниже), единственная проверка `crates-cross` и `chip-info`: ниже о ней.

### Какой уровень когда

Полный прогон на каждую правку не нужен. `template-check` в
таблице — сокращение для `cargo run --manifest-path chip-data-gen/Cargo.toml --bin
template-check --`:

| Когда | Команда | Время |
|---|---|---|
| каждая правка шаблона | `template-check -- --quick` | ~1 мин |
| правка конкретной ветки (протокол, OTA, граф…) | `template-check -- --only <подстроки меток>`, например `--only modbus,no-graph` | минуты |
| по ходу работы, перед коммитом | `template-check -- --smoke` (по конфигурации на ось генерации, `.smoke()` в `default_cases()`) | ~10–15 мин |
| перед вливанием в master | `template-check` без флагов | ~час |

`--only` выбирает конфигурации, в метке которых (`stm32g474re (modbus-uart)`) есть одна из
подстрок; вместе со `--smoke` — пересечение. Уровни друг друга не заменяют: `--smoke` и
`--only` собирают лишь часть конфигураций, а генерацию и проверки над файлами остальных
делает только `--quick` (или полный прогон).

### Что делает `template-check`

Репозиторий шаблона нельзя собрать как обычный проект: почти все файлы `crates-cross/`
(например, `Cargo.toml`, `.cargo/config.toml`, `bsp/src/board.rs`, `boot/src/main.rs`)
содержат Liquid (`{{...}}` и `{% if %}`), а до рендера это ни валидный TOML, ни валидный
Rust — rust-analyzer ругается на них прямо в репозитории, и так и должно быть.

Команда `template-check` — последняя строка списка выше. Он генерирует проект во
временный каталог (о нём — ниже, «Рабочий каталог и параллельность») под каждую
конфигурацию набора `default_cases()` в
`chip-data-gen/src/bin/template-check.rs` — они задевают разные ветки генерации.
Что входит в набор и зачем — doc-комментарий в начале того же файла; точный список —
сама функция (число конфигураций растёт вместе с ветками, здесь его не повторяем).
Часть конфигураций — `.render_only()`: генерация и проверки над файлами без сборки
даже в полном прогоне — ручная раскладка (`swap_buffer`, все три формы заготовок
`memory.x`: внутренняя OTA, внешняя, без OTA — собрать их нельзя, числа вписывает
человек), внешняя флеш, на которой хранить нечего, и чипы остальных серий (F0, F2,
F3, L1, U0, U3), у которых своих веток сборки нет. Дальше
проверяет, что не осталось ни одного
неподставленного плейсхолдера, что состав CI-файлов проекта совпадает с выбранным
`ci` (см. ниже про `--ci`), что в проекте нет файлов сопровождения шаблона и пустых
каталогов, а у каждого `.rs` под `src/` есть `mod` в родительском модуле
(`check_no_leftovers`: файл, чьё объявление вырезал Liquid, компилятор не видит
вовсе), и прогоняет в сгенерированном проекте `cargo xtask
lint`, `test host`, `lint cross`, `build` — то есть ровно то, что README обещает
пользователю, — плюс `cargo xtask pins` (четырежды: без аргумента, с `RCC`, с
`I2C1 --snippet` и `--check`) и fmt/clippy/test для `chip-info`; `cargo deny check` обоих
workspace; сверку оценки RAM хука с фактом сборки («Оценка RAM» выше) и, с OTA,
проверку, что `build` не собрал тестовый образ `app-unconfirmed` (сам бинарник есть
только при `test_image` — OTA и protobuf, `chip-select.rhai`).

Не всё из этого гоняется на каждой конфигурации — повторять проверку на тех же
входных данных незачем:

- **`chip-info` и заготовки** зависят только от чипа: раз на чип (чипов в наборе
  намного меньше, чем конфигураций). Ещё раз — только на первом проекте чипа без интерфейса: половина
  `assign_resources!` проверяется лишь на заглушке `resources.rs` (ниже). `pins --check`
  от проекта зависит и идёт в каждом. Его обратная сторона — отказ на занятом
  отладочном порте (`PA13` вписывается в `assign_resources!` на один запуск,
  `check_pins_reject_debug_port`) — раз на прогон: от конфигурации она не
  зависит.
- **Хостовый workspace** (`xtask lint`, `test host`, `cargo deny` корня) — раз на
  отпечаток: хеш всех файлов проекта, кроме `NOT_HOST` (`crates-cross/`,
  `crates-host/chip-info/`, `docs/`, `.git/`, `.github/`, `.vscode/`, `.claude/`,
  `target/`) и `.md`, с именем проекта и чип-фичей, заменёнными на одно и то же
  (`host_key`). Исключения перечислены, а не включения: забытое исключение стоит
  лишнего прогона, забытое включение — пропущенной проверки. От чипа хостовый workspace
  зависит мало — целевым triple (`TARGET` в `xtask`, `rust-toolchain.toml`) и признаками
  раскладки вроде `erase_page`, — поэтому совпадения бывают и между разными чипами одной
  архитектуры с одинаковыми ответами.

Отдельным шагом идёт **компиляция заготовок**: для каждого блока с выводами (у
STM32F407 их 38) берётся вывод `pins <БЛОК> --snippet`, всё складывается во
временный модуль `bsp` и прогоняется через clippy с `-D warnings`. Заготовку
человек вставляет в свой проект как есть, значит она обязана собираться, — а
раньше проверялось только то, что команда не упала. Цена этого пробела:
пять дефектов разом, каждый ронял вставленный код (дублирующиеся ключи там, где
два сигнала делят вектор; `Usb_otg_fsResources`, не проходящий
`non_camel_case_types`; несуществующий `adc::InterruptHandler` на большинстве
версий ADC; пустая `bind_interrupts!` у классического USB; недостающий импорт
`Peri`). Половина `assign_resources!` берётся ровно у одного блока — макрос
кладёт `split_resources` в корень крейта через `#[macro_export]`, и двух
вызовов в одном крейте не бывает; поэтому она на время проверки встаёт на место
`bsp/src/resources.rs`, а не рядом с первым макросом.

Команды `chip-info` (`pins` и fmt/clippy/test) — единственная его проверка
вообще: манифест до генерации не резолвится (чип выбирается Cargo-фичей, а в
ней Liquid), поэтому ни `cargo xtask lint`, ни CI самого шаблона его не видят,
и в репозитории шаблона `cargo xtask pins` намеренно падает с объяснением вместо
невнятной ошибки Liquid.
`cargo xtask lint` в сгенерированном проекте его тоже не трогает — иначе каждый
пользовательский CI тянул бы `stm32-metapac` ради инструмента, который на сборку
прошивки не влияет.

Исключение одно, и оно устроено так, чтобы правило выше осталось в силе: есть
отдельный джоб (`pins.yml` на GitHub, `pins:check` на GitLab), зовущий
`chip-info --check` по фильтру путей — при правке `crates-cross/bsp/src/**`,
самого `crates-host/chip-info/**` или `crates-cross/Cargo.toml`. Последние два не для
полноты: у `chip-info` своя запись в dependabot (renovate находит его манифест сам), и обновление
`stm32-metapac` меняет ровно те метаданные, по которым идёт проверка, а смена чипа
правит обе чип-фичи сразу. Метапак таким образом собирается не на каждый пуш, а
тогда, когда трогали проверяемое.

Зовётся `chip-info` напрямую, а не через `cargo xtask pins --check`: обёртка живёт в
корневом workspace, и её сборка потянула бы резолв `domain` с приватными
git-зависимостями, которых этому джобу не нужно.

**Файл `pins.yml` лежит и в репозитории шаблона** — в отличие от `template.yml`, он
не в `ignore`, потому что должен доехать до проектов. Поэтому первым шагом он
проверяет, подставлена ли чип-фича в манифесте `chip-info`, и в репозитории шаблона
завершается успехом, ничего не собирая: там этот манифест не резолвится вовсе. Уберёте
проверку — джоб покраснеет у мейнтейнера при первой же правке `bsp/src`.

Обязательной проверкой в branch protection этот джоб делать не стоит: он запускается
по фильтру путей, и PR, не трогающий распиновку, оставит обязательный статус висеть в
ожидании навсегда.

Флаги: `--quick` — только генерация и проверки над файлами проекта без сборки
(плейсхолдеры, состав CI-файлов и упоминания CI, пути в доках, лишние файлы, пустые
каталоги и модули без `mod`), `--ci gitlab|none` — другой CI-провайдер, `--define ключ=значение` (можно
несколько раз) — дополнительный ответ ко всем проверяемым конфигурациям, например
`--ci gitlab --define config=yes stm32f407ve`, `--keep` — не удалять проекты после
успеха, `--smoke`/`--only` — уровни выше, `--jobs N` — сколько конфигураций
одновременно (по умолчанию 3), позиционные аргументы — свой список чип-фич. `--help`
печатает и метки всех конфигураций набора (для `--only`); `--smoke`/`--only` выбирают
только из набора по умолчанию и с позиционными чипами не сочетаются.

### Рабочий каталог и параллельность

Каталог — `%TEMP%/rtc-<хеш пути рабочей копии>` (свой у каждого worktree) или
`TEMPLATE_CHECK_DIR`, если задан. Он постоянный: кеш сборки остаётся тёплым между
прогонами, холодный прогон дольше тёплого примерно в полтора раза. Второй прогон на той
же рабочей копии не перезапишет первый — каталог держит блокировка ОС (`lock`, её
снимает и падение процесса), и второй сразу падает с подсказкой задать
`TEMPLATE_CHECK_DIR` (путь короткий — из длинного генерация падает на `git init` с
`path too long`, а debug-образ толстеет: пути исходников в местах паник лежат в образе,
и конфигурация на впритык заполненном чипе может не влезть во flash).

Конфигурации идут полосами (`--jobs`): у каждой полосы свой каталог сборки
`target-<N>` (cargo держит каталог под блокировкой всю сборку — общий выстроил бы
полосы в очередь), конфигурации одного чипа — в одной полосе, чтобы `embassy-stm32`
под чип собирался один раз. Ядер сборка цепочки проектных крейтов почти не
загружает, поэтому полосы окупаются; цена — диск, по кешу на полосу. Вывод каждой
конфигурации — в `logs/<проект>.log`, в консоли — строка на итог, у упавшей —
причина и хвост лога. После первого падения новые конфигурации не начинаются.

Кеш одного рабочего каталога — гигабайты (порядка 5–7 ГБ), и сам он не чистится.
Больше двух сборочных прогонов (`--smoke`, `--only`, полный) разом не запускайте — диск
и память машины они делят, — а лишний `TEMPLATE_CHECK_DIR` удаляйте, как только ветка
проверена.

`--ci` проверяет не только подстановку, но и состав: при `ci=github` в проекте есть
`.github/workflows/ci.yml` и нет `.gitlab-ci.yml` и `renovate.json`, при `gitlab` — наоборот,
при `none` нет ни того, ни другого (это делают `[conditional]` в `cargo-generate.toml`).
Ветки `gitlab` и `none` CI шаблона генерирует на одном чипе (`template.yml`, `--quick --ci …
stm32f407ve`); весь набор конфигураций идёт только с `ci=github` — остальные ветки
мейнтейнер проверяет вручную с `--ci`.

Отдельная ценность прогона в том, что каждая конфигурация резолвит зависимости
заново: lock-файлов шаблон не раздаёт (см. ниже). git-зависимости закреплены `rev`
(`rust_lib_rev`, ревизия `w25q` в `crates-cross/Cargo.toml`), а версии с crates.io —
только semver-диапазоном. Новая совместимая по semver версия, которая всё же ломает
сборку, видна только так: у самого шаблона `Cargo.lock` держит прежние, поэтому
локальные `cargo xtask lint`/`test host` остаются зелёными, даже когда свежий проект
уже не собирается.

### Генерация из локального пути

`cargo generate --path <каталог>` копирует каталог шаблона во временную папку
целиком, вместе с неотслеживаемыми файлами, и только потом читает
`cargo-generate.toml`: `ignore` решает лишь, что попадёт в готовый проект.
С 0.24 cargo-generate не копирует каталоги с `CACHEDIR.TAG` — его кладёт cargo,
но только в `target/`, который создал сам. Каталог, который первым создал
rust-analyzer (`target/flycheck0`) или `cargo llvm-cov`, остаётся без метки —
так было у корневого `target/` и у `crates-host/chip-info/target/` этого
репозитория, — и копируется целиком: генерация из каталога с 3 ГБ в `target/` —
169 секунд против одной.

Отсюда три решения:

- рабочие каталоги и кеш сборки `template-check` живут во временной папке
  (`%TEMP%/rtc-…`), а не в репозитории — чтобы прогоны проверки
  не утяжеляли его и не попадали в следующую генерацию;
- сам `template-check` генерирует не из репозитория, а из его копии: файлы под git
  (`git ls-files`) в рабочем состоянии, без `chip-data-gen/` — как увидел бы `--git`,
  но с незакоммиченными правками. Неотслеживаемое в неё не попадает, его список
  печатается в начале прогона — забыли `git add` нового файла шаблона;
- руками шаблон удобнее брать через `--git` даже локально: `cargo generate --git
  <путь к рабочей копии>` клонирует только отслеживаемое в git.
  Единственное «но»: клонируется закоммиченное, поэтому незакоммиченные правки
  шаблона так не проверить — для них и есть `template-check`.

`template-check` генерирует с `--no-fmt`: rustfmt генерации (умолчание с 0.26)
выправил бы огрехи формы в Liquid, и `cargo xtask lint` их бы уже не увидел, а у
пользователя без `rustfmt` на тулчейне по умолчанию они остались бы в проекте.

### Lock-файлы шаблона

**Шаблон не раздаёт ни одного lock-файла** (`ignore` в `cargo-generate.toml`) —
каждый проект считает свои сам первой сборкой: корневой — `cargo xtask lint`/`test
host`, `crates-cross/Cargo.lock` — `cargo xtask lint cross`/`build`,
`crates-host/chip-info/Cargo.lock` — первым `cargo xtask pins`. Состав пакетов зависит от ответов при генерации: при
`ota=no` уходят `embassy-boot*`, при `config=yes` добавляются
`sequential-storage` и `embedded-storage-async`, при OTA — `salty`, а
протокол уносит или приносит целые крейты корневого workspace (`crates-host/proto`,
`crates-host/canopen`). Шаблонный lock подходил бы одному сочетанию, а остальным ронял
бы `cargo fetch --locked` (проверено вживую: проект без `crates-host/proto` на
шаблонном корневом lock падает с `cannot update the lock file`). Post-хук говорит о
lock-файлах прямо при генерации, а `--locked` в обоих CI проекта условный — строгий,
как только файл закоммичен.

Корневой `Cargo.lock` в самом репозитории шаблона остаётся — для его собственной
сборки (`cargo xtask lint`/`test host`, `cargo deny check`); в проекты он не едет.
Свой lock есть и у `chip-data-gen` (`chip-data-gen/Cargo.lock`) — он остаётся здесь
вместе с каталогом (`ignore`). Lock-файла `chip-info` в шаблоне нет: его манифест здесь не резолвится (Liquid в
чип-фиче), и такой lock никто бы не читал — ни сборка, ни `template-check` (генерация
его не берёт), ни бот (см. ниже).

Цена решения, которую надо знать: свежесгенерированный проект берёт с crates.io
текущие совместимые по semver версии, а не проверенные мейнтейнером. git-зависимости
от этого защищены: `rust-lib` (`supervisor`, `watchdog`, `sync-request`) закреплена
`rust_lib_rev`, `w25q` — литералом `rev`. Если новая версия с crates.io ломает
сборку — проект не соберётся с первого раза. Риск принят сознательно: ни одна
конфигурация не получает lock, который ей не подходит, а такая поломка всплывает
и в `template-check` — каждая конфигурация резолвит заново.

### Версии зависимостей: бот сюда не дотягивается

`.github/dependabot.yml` копируется в проекты и там работает, а в самом репозитории
шаблона из четырёх его записей живёт ровно одна — `github-actions`. Знать это надо,
чтобы не ждать обновлений, которые не придут:

- **`/crates-cross`** — строки-теги Liquid вокруг `members` (`{%- if ota == "true" %}` …
  `{%- else %}` … `{%- endif %}`) — не TOML: там падает даже `cargo metadata --no-deps`.
- **`/crates-host/chip-info`** — TOML валиден (Liquid стоит строкой в списке фич), но
  резолв падает: `stm32-metapac` не имеет фичи `{{chip_feature}}`. Именно резолв и
  делает бот, так что PR отсюда не появится. Живое доказательство, что не появлялся
  никогда: манифест объявлял `anyhow 1.0.100`, а лежавший тогда в шаблоне lock давно
  держал 1.0.104.
- **Корневой** — граф тянет git-зависимости из приватного `rust-lib`, а доступа к нему
  у бота нет: резолв падает, и PR отсюда тоже не приходят.
- **`chip-data-gen`** в списке отсутствует вовсе, и добавить его нельзя: файл уезжает
  в проекты пользователей, а этого каталога там нет (`ignore` в
  `cargo-generate.toml`) — запись указывала бы в пустоту и ломала бы бота уже у них.

Отсюда практика: версии во всех манифестах мейнтейнер поднимает руками. Что отстало — видно так (имена берутся из самого манифеста, поэтому список не
надо поддерживать):

```bash
for manifest in Cargo.toml crates-cross/Cargo.toml crates-host/xtask/Cargo.toml \
                crates-host/host-target-tests/Cargo.toml \
                crates-host/chip-info/Cargo.toml chip-data-gen/Cargo.toml; do
  grep -oE '^[a-z0-9_-]+ *= *(\{ *version *= *)?"[0-9][^"]*"' "$manifest" \
  | grep -vE '^(version|edition|rust-version|resolver|name) ' \
  | while read -r line; do
      name=${line%% *}
      cur=$(printf '%s' "$line" | grep -oE '"[^"]+"$' | tr -d '"')
      # User-Agent обязателен: без него crates.io отвечает отказом, и пустой
      # ответ выглядел бы как «версия неизвестна» для каждого крейта.
      new=$(curl -s --max-time 12 -H "User-Agent: template-maintainer" \
            "https://crates.io/api/v1/crates/$name" \
            | grep -o '"max_stable_version":"[^"]*"' | head -1 | cut -d'"' -f4)
      if [ -z "$new" ]; then
        echo "$manifest: $name — не удалось спросить crates.io"
      elif [ "$cur" != "$new" ]; then
        echo "$manifest: $name $cur -> $new"
      fi
    done
done
true   # чтобы статус не зависел от последнего сравнения
```

Одно ложное срабатывание в нём заложено и лечению не подлежит: сравнение
текстовое, поэтому `stm32-metapac = "21"` показывается как «21 -> 21.0.0». Это одна и
та же версия, записанная по-разному, и привязка к мажорной там намеренная — см.
следующий абзац.

Две оговорки, без которых механическое «поднять до последнего» ломает проект:

- **embassy — это набор.** Все `embassy-*` (`-stm32`, `-executor`, `-sync`, `-time`,
  `-boot`, `-boot-stm32`, `-embedded-hal`, `-net`, `-usb`, `-futures`) двигаются вместе,
  и в корневом `Cargo.toml`, и в `crates-cross/Cargo.toml`; одиночный бамп даёт две
  несовместимые копии в графе.
- **Мажорная версия `stm32-metapac` в `chip-info` обязана совпадать с той, что тянет
  `embassy-stm32`** (об этом же говорит комментарий в `dependabot.yml`). Разъедутся —
  `cargo xtask pins` начнёт показывать данные другого поколения `stm32-data`, чем то,
  по которому собрана прошивка. Молча и правдоподобно.

Поднимать версии в манифесте стоит даже тогда, когда lock уже содержит свежие (так
бывает: semver-диапазон допускает патчи, и cargo подтягивает их сам). Бот сравнивает
манифест, а не lock, и отставший манифест молча прячет от него обновления.

Остальное проверяется командами из списка в начале раздела.

`chip-data-gen` не член ни одного `[workspace]`, поэтому в `cargo xtask lint` он не
попадает — его команды идут отдельными строками в том списке. `chip-info` тоже не член, но с
ним так не выйдет: до генерации его манифест не резолвится вовсе, и локально проверить
его нечем — только `template-check` (см. выше).

### Что из этого делает CI

`.github/workflows/template.yml` — CI самого репозитория (в проекты не копируется,
см. `[template].ignore`). На пуш в `master`/`main` и на каждый PR он гоняет всё, что
обходится без доступа к приватному `rust-lib`: `cargo fmt --check` обоих манифестов,
clippy и тесты `chip-data-gen` (включая тесты каскада по всем чипам) и
`template-check --quick` — генерацию под каждый чип набора с проверками
сгенерированного проекта, которым не нужна сборка (остаточные плейсхолдеры, состав
файлов, пути в документах). Проверку
штампа версий (`generated_blocks_match_the_declared_embassy_version`) CI пропускает
(`--skip`): она резолвит граф `crates-cross`, а в нём git-зависимость `rust-lib`. Её
гоняет локальный `cargo test --manifest-path chip-data-gen/Cargo.toml --release`.

Что CI сделать не может — собрать сгенерированный проект: `domain` тянет приватный
репозиторий, которого у Actions нет. Поэтому сборочные уровни `template-check`
(`--smoke`, `--only`, полный прогон) остаются локальными, а полный прогон перед
вливанием в master обязателен («Какой уровень когда»): именно он ловит ломающие
изменения `rust-lib` и ошибки, которые видны только компилятору.

Кстати о том, почему `--quick` в CI вообще работает без доступа к `rust-lib`:
генерация зависимости не резолвит вовсе. `cargo update` в post-хуке был и убран
(причина — комментарий в начале `post-script.rhai`), а в `template-check` их
резолвит первая команда `cargo xtask` в сгенерированном проекте — она есть только
в прогонах без `--quick`, то есть локально, где доступ есть.

### Тесты каскада

`chip-data-gen/tests/cascade.rs` — интеграционный тест на сам `chip-select.rhai`, не на
Rust-код генератора: гоняет реальный скрипт через движок `rhai` (dev-dependency) с
подменённым модулем `variable` (`is_set`/`get`/`set`/`prompt`) и `file`
(`write`/`delete`), без `cargo generate` и
без TTY. Таблицы из `chip-data/` разбираются один раз и подаются движку через
`StaticModuleResolver` под теми же путями, что пишет `import`, — так что выбор файла
семейства проверяется кодом самого хука. `variable::prompt` в моке сам ведёт каскад к заранее известной цели (выбирает
самый длинный вариант из choices, который сам является префиксом цели, — не первый попавшийся,
иначе он ошибочно "останавливается" там, где чип совпадает с началом другого, того же
класса бага, что тест и должен ловить). `cascade_reaches_every_chip_without_hanging` и
`memory_layout_invariants_hold_for_every_chip` прогоняют так все чипы из `CHIPS`
(~1479 каждый) — ловят именно тот класс бага, который `--define chip_feature=...` в
принципе не может поймать (та ветка не задаёт ни одного вопроса «Выберите STM32…»,
значит не исполняет сам цикл каскада). Второй из них проверяет разом четыре уже случавшиеся
регрессии: `BOOTLOADER_STATE` с самого начала flash, одинаковый `memory.x` у app и boot
(app затирал bootloader), регионы OTA в проекте, который собирается без bootloader'а, и
незаполненный `crates-cross/target-tests/memory.x` (каскад его когда-то не писал вовсе, и
`cargo xtask test target` не линковался ни на одном чипе). В
`--release` — секунды на оба полных прогона (в dev-профиле
— единицы минут, интерпретация Rhai). Не в `cargo xtask lint` (`chip-data-gen` не
член workspace, см. выше); CI шаблона их гоняет (`template.yml`), а локально — при правке
`chip-select.rhai`/`chip-data-gen`:
`cargo test --manifest-path chip-data-gen/Cargo.toml --release` (та же команда
запускает и юнит-тесты генератора из модулей `chip-data-gen/src/`).

### Когда перегенерировать данные

Списки в `chip-data/` собраны из чип-фич конкретной версии `embassy-stm32`,
метаданных `stm32-metapac`, которую он разрешил, и из `probe-rs chip list`
конкретной установленной версии probe-rs. Все три версии записаны штампом в начале
`chip-data/chips.rhai`:

```
// Источник: embassy-stm32 0.6.0 (crates-cross/Cargo.toml), stm32-metapac <версия>, probe-rs <версия>
```

Тест `generated_blocks_match_the_declared_embassy_version` сверяет штамп с версией
`embassy-stm32`, объявленной в `crates-cross/Cargo.toml`, и с версией `stm32-metapac`,
которую сейчас разрешает `cargo metadata`, и падает, если хоть одна разошлась. Это не
формальность: `embassy-stm32` в `crates-cross/Cargo.toml` мейнтейнер поднимает руками
(бот сюда не дотягивается — «Версии зависимостей…» выше), и перегенерировать списки при
этом легко забыть, а metapac `embassy-stm32` тянет диапазоном (`"21"`) — у
`crates-cross` в шаблоне lock-файла нет, генератор резолвит его граф заново, и минорный
релиз metapac меняет данные при той же версии `embassy-stm32`. Списки при этом
остались бы от старой — расхождение вылезло бы уже у пользователя шаблона, при
генерации. Тест резолвит граф, как генератор, без lock-файла — ему нужен доступ к
реестру crates.io и к `rust-lib` (git-зависимость `crates-cross`), поэтому в CI его
нет (см. «Что из этого делает CI»). Увидели красный тест — перегенерируйте:

```
cargo run --manifest-path chip-data-gen/Cargo.toml
```

Версию probe-rs тест не проверяет: она у каждого мейнтейнера своя и в репозитории не
объявлена. Штамп её фиксирует справочно — чтобы было видно, из какого набора целей
собран список.

**Осторожно с Liquid в манифестах.** Генератор резолвит зависимости через `cargo
metadata`, а для этого снимает из временной копии все `{% if %}`-блоки
(`strip_liquid`). Форму с управлением пробелами (`{%- if`) он раньше не понимал — и
после того, как условие такого вида появилось в `crates-cross/bsp/Cargo.toml`, генератор
перестал работать целиком, с невнятным «invalid key-value pair, expected key».
Заметно это только при запуске самого генератора, то есть раз в обновление
embassy-stm32, поэтому обе формы теперь под тестами
(`liquid_whitespace_control_is_stripped_too`, `every_template_manifest_strips_clean`).
Из `{% if %}…{% else %}…{% endif %}` остаётся ветка `else` (`the_else_branch_is_kept`):
`members` в `crates-cross/Cargo.toml` записан так, и без неё `cargo metadata` видел пустой
workspace — валидный TOML, поэтому тест манифестов этого не ловил.
Добавляете в манифест шаблона новую Liquid-конструкцию — прогоните
`cargo test --manifest-path chip-data-gen/Cargo.toml --release`.
