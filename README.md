# rust-embedded-template

`cargo-generate` шаблон для embedded-проектов на STM32 (Rust, `no_std`, [Embassy](https://embassy.dev)),
с трёхэтапной моделью тестирования и единой точкой входа для сборки/тестов через `xtask`.

```sh
cargo generate --git https://github.com/Sergycb/rust-embedded-template
```

Сначала вопросы про CI-провайдера и адрес git-репозитория `rust-lib` (шаблон сервер
не называет — вписывается свой), затем каскадный выбор конкретного STM32. Потом вопросы о составе проекта по порядку, и каждый предлагает
только то, что для выбранного чипа возможно: чего у чипа нет, в меню не показывается.
Вариант, который на чип не помещается по памяти, остаётся в меню с пометкой
«DOES NOT FIT»: выбрав его, вы получаете ручную раскладку памяти (`memory.x` и числа в
`[env]` заполняете сами). Скриптам и CI подходит `--define` с ответами на те же
вопросы: он строгий — опечатка и невозможное для чипа значение дают ошибку с
объяснением, а не подстановку. По выбранному чипу шаблон сам подставит идентификаторы
`probe-rs`/`embassy-stm32`, целевой triple, фичу банковой схемы и — главное — посчитает
раскладку памяти: адреса и размеры {% if ota == "true" %}`FLASH`/`BOOTLOADER_STATE`/`ACTIVE`/`DFU`/`RAM`{% else %}`FLASH`/`RAM`{% endif %}
по реальным границам секторов вашего чипа. Подробности — в разделе
[«Как выбирается чип»](#как-выбирается-чип) в конце.

## Быстрый старт

```sh
cargo xtask setup        # тулчейн, probe-rs, flip-link и cargo-плагины (CI и ручные)
cargo xtask lint         # проверить, что окружение на месте
cargo xtask test host    # тесты domain — железо не нужно

# дальше нужна плата, подключённая через отладочный пробник:
cd crates-cross
{%- if ota == "true" %}
cargo flash -p boot --release --chip {{chip}}   # bootloader (всегда release), первым
{%- endif %}
cargo run -p app                    # прошить приложение и смотреть defmt-лог
```

Первые сборки создадут lock-файлы — корневой `Cargo.lock`, `crates-cross/Cargo.lock`
и (после `cargo xtask pins`) `crates-host/chip-info/Cargo.lock` — **закоммитьте их**,
а не принимайте за мусор сборки.
Из шаблона они не приезжают намеренно: состав зависимостей зависит от ответов при
генерации, и один файл на все варианты был бы
неверен для остальных — а `cargo fetch --locked` в CI на таком падает. Пока lock не
закоммичен, CI резолвит версии заново на каждом прогоне и говорит об этом
предупреждением.

С чем проект сгенерирован — чип, OTA, граф, транспорты, протокол, службы, — записано в
`.template-answers.toml` в корне: его тоже стоит закоммитить. По нему видно, почему в
проекте нет той или иной части, и с ним сравнивают проект с новой версией шаблона.

Свежесгенерированный проект собирается и запускается как есть: `main.rs` поднимает
`Board`, печатает версию и коммит, из которого собран образ, и
{%- if graph == "true" %} спавнит граф задач — узел `HEARTBEAT`,
который сообщает о старте и ждёт, и узел `CPU_LOAD`, который меряет загрузку
процессора. Это каркас: оба уже стоят в графе под сторожем, и дописывать
свою работу вы будете внутрь `HEARTBEAT`, а не с нуля. Загрузку же читать уже вам:
`CPU_LOAD` только публикует процент (`docs/modules/app-cpu-load.md`).
{%- else %} спавнит задачи: замер загрузки процессора `CPU_LOAD`, который
пишет процент в лог (`docs/modules/app-cpu-load.md`), и узлы проекта —
`tasks::spawn_all` (`crates-cross/app/src/tasks.rs`, подмодуль на задачу над
`domain::*::task`). Сторожа и перезапусков нет: узлы не падают, а зависший
остаётся зависшим.
{%- endif %}

Цикл исполнителя в `main.rs` поднят руками, а не макросом
`#[embassy_executor::main]`, — ради того самого измерения
(`docs/modules/app-cpu-load.md`).

## Структура проекта

Два основных Cargo workspace, потому что `cross` собирается под другой target и не может
делить `Cargo.lock`/профили с host-ориентированной частью. Третий, `chip-info`, стоит
особняком по другой причине — чип в нём выбирается Cargo-фичей, подставляемой при
генерации (см. ниже, «`pins`: справочник по чипу»).

Дальше по тексту `domain` и `cross` — это имена крейта и воркспейса, а `crates-host/` и
`crates-cross/` — каталоги, в которых они лежат:

```
├── crates-host/          # Всё, что собирается под хост
│   ├── domain/            # Бизнес-логика, no_std
│   ├── ports/             # Трейты-границы домена
│   ├── adapters/          # Реализации трейтов без чипа
{%- if flash_page == "true" %}
│   ├── flash-page/        # Страница стирания раздела (общая у bsp и boot)
{%- endif %}
{%- if has_canopen == "true" %}
│   ├── canopen/           # Словарь объектов CANopen
{%- endif %}
{%- if has_protobuf == "true" %}
│   ├── proto/             # Сообщения protobuf
{%- endif %}
│   ├── host-target-tests/ # Тесты, гоняющие хост против прошитого устройства
│   ├── xtask/             # Единая точка входа для сборки/тестов/флешинга
│   └── chip-info/         # Справочник по чипу (`cargo xtask pins`), свой workspace
├── Cargo.toml            # Корневой workspace: все крейты crates-host/, кроме chip-info
│
└── crates-cross/         # Отдельный workspace, аппаратная часть (thumbv7em-none-eabihf и т.п.)
    ├── app/               # Основная прошивка (bin)
{%- if ota == "true" %}
    ├── boot/              # Bootloader (bin, embassy-boot)
{%- endif %}
    ├── bsp/               # Board support package (lib)
    ├── target-tests/      # Тесты, исполняемые прямо на устройстве
    └── Cargo.toml
```

`domain` не входит в workspace `cross` (у него другой target), а подключается туда как обычная
path-зависимость. Версии зависимостей у `root` и `cross` объявлены раздельно и намеренно не
реэкспортируются друг через друга — `domain` не должен быть фасадом для инфраструктурных крейтов
вроде `static_cell`/`heapless`, которые `cross` использует для оркестрации задач. Синхронизацию
версий между двумя `[workspace.dependencies]` {% if ci == "github" %}со временем берёт на себя Dependabot (см. ниже){% elsif ci == "gitlab" %}со временем берёт на себя Renovate (см. ниже){% else %}держат руками: бота обновлений без CI нет{% endif %}. Lock-файлов свежесгенерированный
проект из шаблона не получает: их состав зависит от ответов при генерации, и первая
сборка считает их сама (см. «Быстрый старт»).

## Архитектура и когда что применять

**Главный принцип**: `cross` остаётся минимальным — рычаги платы (`bsp`), статики,
которые домен получает ссылками (буферы, DMA), и оркестрация задач (`Spawner`{% if graph == "true" %},
supervisor-графы, watchdog{% endif %}). Вся остальная логика — в `domain`, даже асинхронная и
«системная» на вид (стейтчарты, RPC, конкурентные примитивы). Подробное правило
«куда класть что» и разбор пограничных случаев — в docs/architecture.md.

Границу `bsp` → `app` пересекают **объекты под трейтами, а не периферия**.
Путь драйвера микросхемы платы такой:

```
вывод чипа → группа assign_resources! (bsp/src/resources.rs)
           → тип драйвера, generic по трейтам embedded-hal, живёт в crates-host/adapters
             (или во внешнем крейте) и проверяется на хосте моком — до тех пор,
             пока ему не понадобится периферия конкретного чипа
           → объект драйвера над шиной собирает bsp в Board::new
           → готовый объект становится полем Board
           → узел domain получает его во входе и зовёт через порт из ports
```

Где лежит тип — в `adapters` или в `bsp`, — решает один признак, нужен ли чип
(docs/architecture.md, «Адаптеры делятся по одному признаку — нужен ли чип»).
В `ports` — трейты, которыми домен говорит с миром.
{%- if ota == "true" %} `FirmwareUpdate` реализован в `adapters`, а строит его `app` над
разделами флеша, которые отдаёт `Board`; порт перезагрузки `Reboot` для узла OTA
реализует `bsp::reset`.{% endif %}
{%- if config == "true" %} `SettingsStorage` реализован в `adapters`, а строит его
`app` над носителем, который отдаёт `Board`.{% endif %}
{%- if link_port == "true" %} `FrameLink` — канал целых кадров, который держит свой буфер (один на
приём и ответ).{% if has_modbus == "true" %} `Handler` — протокол над ним: что ответить на кадр; обоих
обслуживает узел протокола `domain::SERVER_FRAG`.{% endif %}
{%- if has_modbus == "true" or has_protobuf == "true" %} {% if graph == "true" %}Граф называет{% else %}Модули задач называют{% endif %} узел по
протоколу и транспорту ({% if has_modbus == "true" %}`MODBUS_<транспорт>`{% if has_protobuf == "true" %}, {% endif %}{% endif %}{% if has_protobuf == "true" %}`PROTOBUF_<транспорт>`{% endif %}).{% endif %}

### `cross` — железо и оркестрация

как git-зависимость; они заменили сторонние аналоги (`embassy-supervisor`,
`embassy-task-watchdog`, `ector`) — чем именно лучше, написано в столбце ниже.{% else %}`supervisor` берётся из [rust-lib]({{rust_lib}}) как git-зависимость: узлы `domain`
объявлены его фрагментами (`supervisor_fragment!`).{% endif %}

| Крейт | Для чего | Где документирован |
|---|---|---|
{%- if graph == "true" %}
| `supervisor` | Весь граф embassy-задач одним макросом `supervisor_graph!` из фрагментов `domain`: передача рычагов платы в задачу через `resources:`, почтовые ящики `inbox:`, broadcast `publish:`/`subscribe:`{% if ota == "true" %}, упорядоченный старт по `deps:`, RPC `request:`/`calls:`{% endif %} и общий watchdog. {%- endif %}
| свой `#[global_logger]` (например, над `bbqueue` — рецепт в `docs/buffers.md`, зависимости в шаблоне нет) | любой транспорт для `release` без пробника — turnkey-крейта нет: `defmt-bbq` и `defmt-serial` держат `defmt@0.3.x` при `defmt@1.x` у нас (`symbol multiply defined` при реальной проверке){% if has_usb == "true" %}, а `defmt-embassy-usbserial` требует `embassy-usb ^0.5` вместо версии, парной к текущей `embassy-stm32`{% endif %}. | `docs/modules/app.md` |

Шаблон собирается на обычном исполнителе, который между задачами уходит в `WFE`:
ядро стоит, тактирование и регуляторы работают. Устройству от батареи нужен режим
STOP — это разница между единицами миллиампер и единицами микроампер, — и включается
он не одной фичей: меняется сон исполнителя (свой pender и `low_power::sleep` вместо
`WFE`, замер загрузки при этом остаётся), а занятая периферия перестаёт пускать чип в
сон. Рецепт целиком, вместе с местами, где на этом спотыкаются{% if graph == "true" %} (тикер сторожа в 100 мс
не пускает в STOP вовсе){% endif %}, — в `docs/modules/app.md`, раздел «Питание от батареи».
Шаблон этого за вас не делает намеренно: USB, Ethernet и CAN в STOP не работают, и
выигрыш получит не каждая плата.

### Bootloader

`crates-cross/boot` — минимальный `embassy-boot-stm32` bootloader: определяет активный банк
flash и безусловно прыгает в него (`unsafe { bl.load(entry) }`), как и официальный
пример `embassy-boot-stm32`. Проверки целостности образа (вектора сброса/SP) не
делает — это осознанный компромисс минимального шаблона, не забытая деталь. `write_size`
(параметр буфера подкачки `BootLoader::prepare::<_,_,_,N>` — не путать ни с минимальной
порцией записи flash, у STM32 она всегда маленькая, 4-8 байт, ни с `PAGE_SIZE`, который
`embassy-boot` вычисляет сам из `NorFlash::ERASE_SIZE`) и оба `memory.x` вычисляются
автоматически по выбранному чипу — см. [«Как выбирается чип»](#как-выбирается-чип) ниже. На
чипах, куда схема не помещается, `crates-cross/boot` в проект не входит вовсе — см.
[«Чипы, куда OTA не помещается»](#чипы-куда-ota-не-помещается).

{% if graph == "true" %}В release-сборке bootloader запускает сторож последним, прямо
перед прыжком в образ. Образ, который после прыжка зависнет раньше графа задач, сторож
сбросит, не дав ему подтвердить себя, — и bootloader откатит его на прежний
(`docs/watchdog.md`). Обмен разделов идёт без сторожа и может длиться сколько нужно.{% else %}Сторожа нет ни в bootloader'е, ни в приложении: образ, повисший до
`mark_booted`, сам не откатится, пока не сбросят питание — откат зависшего образа
в таком проекте ручной.{% endif %}

### Обновление прошивки

От OTA можно отказаться прямо при генерации — ответом `no` на вопрос про неё (или
`--define ota=no`). Тогда приложению достаётся весь flash вместо раздела `ACTIVE`, а
из проекта уходят `crates-cross/boot`, разделы OTA в `bsp::flash` и всё, что ниже.

{%- if ota_store == "external" %}

`DFU` и `BOOTLOADER_STATE` в этом проекте — на внешней SPI NOR: внутри
остаются bootloader и `ACTIVE` почти на весь чип (на F407VE 384 KiB вместо 128).
Драйвер микросхемы подставляете вы — в `bsp/src/external.rs` (асинхронный) и в
`crates-cross/boot/src/external.rs` (блокирующий); в шаблоне там заглушки. Требование к
драйверу одно — стирание делит страницу обмена `EXT_PAGE_SIZE` (сектор 4 KiB годится
везде), его проверяет компилятор. Раскладка и ограничения — `docs/flash.md`,
поведение bootloader'а — `docs/ota.md`.
{%- endif %}

Всё, что не зависит от протокола, готово и уже крутится{% if graph == "true" %} в графе задач{% endif %}: узел
`OTA` (`domain::ota`) принимает образ командами в раздел `DFU`, применяет его
(`domain::ota::update::apply_signed`) и отвечает
исходом на каждую команду. Адаптер `adapters::ota` (поверх `embassy-boot`) пишет
образ и хранит состояние bootloader'а. Плата отдаёт ему только флеш —
поле `firmware` (`bsp::FirmwareFlash`, `crates-cross/bsp/src/{% if ota_store == "external" %}external{% else %}flash{% endif %}.rs`: носители
со своими страницами из чисел раскладки в `[env]`), разделы `DFU` и
`BOOTLOADER_STATE` в нём плата нарезает по символам `memory.x`, адаптер над ними
(`adapters::ota::Updater`) строит `app`. {% if graph == "true" %}Граф забирает поле одной строкой (`fragments:` в
`crates-cross/app/src/graph.rs`){% else %}Задача забирает поле в `crates-cross/app/src/tasks/ota.rs`{% endif %}. Версию образа задаёт приложение
(`crates-cross/app/src/version.rs`), а не плата; ключ подписи зашит в bootloader
(`crates-cross/boot`).

Своего канала у образа нет — он идёт через протокол, по которому хост и так
говорит с устройством. Узел протокола переводит свои сообщения в команды
`ports::OtaCommand` и отдаёт их узлу `OTA` (вход `CMD` — запрос с ответом).
Клиента входа — {% if graph == "true" %}`ota_cmd_requester()` графа{% else %}`crate::tasks::ota::CMD.requester()`, `static` в
`crates-cross/app/src/tasks/ota.rs`{% endif %} — узел протокола держит обёрнутым в
`domain::ota::OtaClient::new(.., domain::ota::ClientId(n))`, где `n` —
порядковый номер транспорта с протоколом в `links`, с 0. Ответ узла
`ports::OtaReply` уходит хосту как есть:

| Команда | Ответ |
|---|---|
| `Start { len, signature }` — стереть раздел под образ | `Started` |
| `Chunk` — кусок до 128 байт | `Received(принято всего)` |
| `Finish` — сверить длину и применить | `Ready` |
| `Reboot` — сбросить МК, чтобы bootloader обменял разделы | `Rebooting` (до сброса) |

{% if protocol == "protobuf" %}В этом проекте команды — сообщения схемы `crates-host/proto/proto/host.proto`
(`ota_start`, `ota_chunk`, `ota_finish`, `reboot`, ответ `Ok` или `Error`), перевод — в
`domain::protobuf::Service`.{% elsif protocol == "modbus" %}В этом проекте команды — записи FC16 в окно holding-регистров с `0xF000`
(`domain::modbus::OtaRegisters` вокруг карты проекта): одна запись — одна команда,
ответ на запись — её исход, точный код и принятая длина — во входных регистрах
(FC04) с той же базы. Карта окна — `crates-host/domain/src/modbus/ota.rs`, тайм-аут
master'а на `Start` должен быть длиннее стирания раздела.{% elsif protocol == "canopen" %}В этом проекте команды — записи SDO в объект `0x4F00` (`domain::canopen::OtaObject`,
описан в `crates-host/canopen/device.toml`): sub 1 — `Start`, 2 — `Chunk`, 3 — `Finish`,
4 — `Reboot`. `zencan` отвечает на SDO синхронно, поэтому запись только ставит
команду, а исход хост читает из sub 5, перечитывая, пока там 0 (ещё выполняется), и
принятую длину — из sub 6. Узел CANopen всё это время обслуживает шину; команду до
исхода прежней он отвергает отказом SDO `0x0800_0022`.{% elsif protocol == "none" %}Протокола в этом проекте нет, и узел только подтверждает образ: команды
шлёт ваш протокол: клиент входа{% if graph == "true" %} `ota_cmd_requester()` графа{% else %} — `crate::tasks::ota::CMD.requester()`
(`static` в `crates-cross/app/src/tasks/ota.rs`){% endif %}, обёрнутый в
`domain::ota::OtaClient::new(.., domain::ota::ClientId(n))`; номер `n` — следующий
свободный после транспортов в `links`.{% endif %}

Отказы приходят хосту кодом `Rejection` — `Length`, `Transfer`, `Busy`,
`Rollback`, `Signature`, `Device`, `NoSession`, `Layout` (образ собран под другую
раскладку памяти), — а полная причина уходит в лог
устройства. Отказ команде владельца приёма обрывает приём, хост начинает с
`Start`; `Busy` другому транспорту, пока приём идёт, чужой приём не трогает —
тому хосту ждать и повторить позже. Занятый раздел и негодная длина отвергаются
**до** стирания. Писать приём руками не стоит: узел и `download::Transfer`
закрывают его грабли и проверены host-тестами (`crates-host/domain/src/ota.rs`
и `download.rs`).

Под приёмом лежит `prepare` — стирание места под образ, самый долгий вызов
обновления: всё это время исполнитель embassy стоит{% if graph == "true" %}, и одна страница
стирания обязана укладываться в таймаут сторожа{% endif %}. Подробно —
docs/ota.md, «Приём образа: стирание отдельно от записи».

Одну вещь стоит знать заранее: `embassy-boot` ждёт, что новый образ отметится
работоспособным (`mark_booted()`), иначе следующий сброс откатит обновление обратно.
Вызов уже стоит в узле OTA при старте — это самое раннее из возможных мест, и его
стоит перенести туда, где ваше устройство действительно доказало, что работает
(docs/ota.md, «Подтверждение образа — в узле OTA, один раз за запуск»).

Проверено на STM32F3Discovery целиком: запись в `DFU`, обмен разделами по сбросу,
подтверждение и отсутствие отката на следующем сбросе. Под присмотром это держат оба
этапа с платой: `cargo xtask test target` пишет в раздел `DFU` и читает записанное
обратно прямо на чипе — в том числе двумя кусками в один сектор, то есть так, как это
делает настоящий приём образа, — а `cargo xtask test host-target` прогоняет цикл
целиком: смену разделов и откат образа, который себя не подтвердил (см. «Трёхэтапное
тестирование»).

#### Подпись образа

Подпись идёт вместе с OTA: отдельного вопроса нет, при `ota` она всегда включена. {% if graph == "true" %}Граф
кормит{% else %}Задача кормит{% endif %} узел OTA версией этого образа (`running_version` во входе `OTA_FRAG`):
принятый образ применяет `domain::ota::update::apply_signed` с
подписью из команды `Start`: она проверяет образ (защита от отката — ниже) и оставляет
подпись bootloader'у. **Подпись проверяет bootloader** — перед обменом, открытым ключом,
зашитым в него; не сошлось — устройство загружается с прежним образом, и отправитель
узнаёт об этом по версии после перезагрузки. Подробности, порядок проверок и
цена (время проверки, размер bootloader'а) — docs/ota.md, «Подпись OTA-образа».

Отдельных команд для этого нет — всё делает обычная сборка:

```sh
cargo xtask build     # создаст ключ при первой сборке, соберёт app.bin и подпишет его
```

Рядом с ELF появляются `app.bin` (то, что уезжает в раздел `DFU`) и `app.bin.sig`;
длину образа, которая нужна устройству вместе с подписью, команда печатает.

Ключей два, и обращаются с ними по-разному:

| Файл | Где живёт | Зачем |
|---|---|---|
| `ota-signing-key.bin` | только у вас, в `.gitignore` | им подписываются образы; закоммитить его — отменить смысл подписи |
| `ota-public-key.bin` | **коммитится** | попадает в bootloader через `build.rs` крейта `boot`; им устройство проверяет подпись |

Правка исходника после создания ключа не нужна: `OTA_PUBLIC_KEY_IN_IMAGE` в
`crates-cross/boot/src/signature.rs` читает файл, а не хранит массив. Файла нет — там нули, и
bootloader отклоняет с ними любое обновление отдельной проверкой.

Одно поведение стоит знать заранее: **если открытый ключ в репозитории есть, а
закрытого рядом нет, образ собирается, но не подписывается** — и `build` об этом
говорит. Так выглядит свежий клон и любой CI, и это нормальный режим: для компиляции
закрытый ключ не нужен, в прошивку уезжает открытый. Новый ключ при этом не создаётся
намеренно — прошивка с ним не принималась бы уже прошитыми устройствами. Нужен именно
новый корень доверия — удалите оба файла, и пара создастся заново.

Из этого следует практика выпуска: подписанные образы выпускает тот, у кого есть
закрытый ключ, а CI собирает и проверяет всё остальное.{% if ci != "none" %} Либо — тот же CI, если отдать
ему ключ секретом: как раз это и делает релиз по тегу, описанный ниже.

### Выпуск релиза по тегу

Проектам с OTA в комплекте идёт релизный прогон: пуш тега `v1.2.3` собирает release,
подписывает образ и кладёт `app.bin` (и `app.bin.sig`), `app.elf` для расшифровки лога
и стека и `SHA256SUMS` в {% if ci == "github" %}GitHub Release{% else %}релиз GitLab (джобы `release:build` и
`release:publish`){% endif %}. Смысл простой: то, что
уезжает на устройства, начинает браться из версионированного места, а не из папки на
машине того, кто собирал.

```sh
git tag v1.2.3 && git push origin v1.2.3
```

Три вещи, которые стоит знать до первого тега:

1. **Тег обязан совпадать с версией проекта.** Прогон сверяет `v1.2.3` с
   `version` в `crates-cross/Cargo.toml` и падает при расхождении. Причина не в
   аккуратности: прошивка печатает свою версию при старте (её берёт `shadow-rs`), и
   разойдись они — по логу с устройства уже не понять, какой релиз на нём стоит.
2. **Закрытый ключ приходит секретом, открытый — из репозитория.** Заведите
   {% if ci == "github" %}секрет `OTA_SIGNING_KEY` в окружении `release` (Settings → Environments), а
   не в секретах репозитория, и задайте окружению обязательных ревьюеров и правило
   «только теги `v*`»{% else %}CI/CD variable `OTA_SIGNING_KEY` (masked и **protected**) и защитите теги `v*`
   (Settings → Repository → Protected tags){% endif %}: иначе подписанный релиз выпускает
   любой, кто может запушить тег. Значение — 32 байта seed в base64
   (`base64 -w0 < ota-signing-key.bin`). `ota-public-key.bin` обязан быть закоммичен.
   Нет того или другого — прогон падает до сборки: без секрета образ вышел бы
   неподписанным, без открытого ключа bootloader релиза доверял бы одноразовой паре.
3. **Сборка идёт той же командой, что у вас локально** — `cargo xtask build`. Отдельного
   «релизного» пути нет намеренно: иначе на устройства уезжало бы не то, что
   проверялось. Подписывает релиз отдельный шаг, `cargo xtask sign`: закрытый ключ
   появляется только после сборки, и код зависимостей его не видит.{% if ci == "github" %} Выкладывает
   релиз отдельный джоб — право записи в репозиторий есть только у него.{% endif %}
{% endif %}

Считает и проверяет одно и то же — `salty`, тот же крейт на обеих сторонах. Взят он, а
не `ed25519-dalek`: меньше и написан под микроконтроллеры. Фича `slow-motion` выбирает
портируемую реализацию вместо ассемблерной под Cortex-M4/M33 — компактнее и работает на
любом ядре, ценой скорости: проверка — порядка сотни миллионов тактов, на частоте после
сброса это секунды, и случается она однократно, перед обменом разделов.

Логику проверки подписи в bootloader'е (запись о подписи, отличие нового запроса на
обмен от отката) стерегут host-тесты `domain::ota::boot` — с настоящими ключами и
настоящим обменом `embassy-boot`; подробности — docs/ota.md.

#### Защита от отката

Подпись доказывает, **кто** прислал образ, но не то, что он **новее**. Без второй
проверки злоумышленнику достаточно взять вашу же прошлую прошивку — честно подписанную,
с уже закрытой уязвимостью — и скормить её устройству. Поэтому вместе с подписью
включается сравнение версий: образ не новее текущего отвергается с
`UpdateError::Rollback { current, incoming }`.

Работает это так:

1. `cargo xtask build` находит в ELF символ `FW_VERSION_IN_IMAGE` (его определяет
   `crates-cross/app/src/version.rs` из `version` в `crates-cross/Cargo.toml`) и **дописывает эти четыре байта
   в хвост `app.bin`** — до подписи, поэтому версия оказывается внутри подписанных
   байтов и соврать ею нельзя. Хвост целиком — `[образ][раскладка u32 LE][версия u32 LE]`:
   перед версией лежит отпечаток раскладки памяти (см. ниже).
2. Устройство читает их из принятого образа по `length - 4` и сравнивает со своей
   версией через `domain::ota::version::is_upgrade`.

Отпечаток раскладки `cargo xtask build` печатает строкой `раскладка: 0x…`; образ под
другую раскладку устройство отвергает (`Layout`) до пометки обмена. Сменили раскладку —
bootloader прошивается по проводу: образом по OTA её не сменить (docs/ota.md,
«Подпись OTA-образа»).

Под присмотром это держит target-тест `ota_rejects_an_older_image`: он кладёт в `DFU`
хвост с версией `0.0.0` — и с отпечатком раскладки самой платы перед ней, иначе отказ
пришёл бы раньше, `Layout`, — и требует отказа `Rollback`, а следом — с заведомо большей и
требует, чтобы отказ пришёл уже не по версии. Вторая половина не для симметрии: без неё
тест остался бы зелёным, даже если бы проверка отвергала вообще всё.

Следствия, которые лучше знать заранее:

- **Версия должна расти.** Та же самая версия — тоже отказ: повторная заливка одного
  номера с другим содержимым это и есть типичный откат. Выпускайте по тегам, и вопрос
  не возникнет.
- **Пререлизные суффиксы отбрасываются.** `1.2.3-rc1` и `1.2.3` дают одно число: в
  четыре байта уместить semver-пререлизы нечем, а сравнение строгое — устройство с
  `1.2.3-rc1` не примет релиз `1.2.3`. Поднимите патч.
- **Образы, собранные до появления этой проверки, четырёх байт версии в хвосте не
  имеют.** Что там окажется — не определено, и если больше текущей версии, такой образ
  устройство примет. Проектам, созданным этим шаблоном, это не грозит (проверка есть с
  первого дня); а вот при переносе фичи в живой проект первое обновление стоит выпустить
  с версией заведомо выше всего, что уже разослано.
- **Образы без отпечатка раскладки устройство отвергает.** Прошивка с проверкой
  раскладки ждёт отпечаток на `length - 8`, и образ, собранный `xtask` до неё (старый
  конвейер CI, сохранённый `app.bin` прошлого релиза), получает `Layout`, хотя `memory.x`
  не менялся. Пересоберите образ текущим `cargo xtask build`.

## Трёхэтапное тестирование

| Этап | Где выполняется | Команда | Нужна плата |
|---|---|---|---|
| host | обычный `cargo nextest`, логика `domain` | `cargo xtask test host` | нет |
| target | внутри МК, `embedded-test` + `probe-rs run` | `cargo xtask test target` | да |
| host-target | хост смотрит на прошитое устройство снаружи | `cargo xtask test host-target` | да |

`cargo xtask test all` прогоняет все три подряд, `cargo xtask test` без аргумента —
печатает список этапов и завершается с ошибкой, ничего не запуская.

Второй и третий этапы приезжают с рабочим минимумом, а не пустым файлом:
`crates-cross/target-tests/tests/test.rs` проверяет на реальном чипе, что `Board::new()`
доходит до конца и что драйвер времени тикает (частая молчаливая поломка
тактирования — прошивка стартует, но любой `Timer::after` висит вечно), а
`crates-host/host-target-tests/tests/test.rs` прошивает release-образ и {% if ota == "true" %}прогоняет
полный цикл обновления (смена разделов и откат){% else %}больше
ничего не делает, пока у платы нет своего канала связи{% endif %}. Через defmt такие проверки не делаются: у
`probe-rs attach` нет режима «прочитать и выйти», а убитый на Windows он оставляет
ST-Link захваченным до переподключения кабеля (поймано вживую). Дальше их дополняют под
свою плату: `target` — для
кода, которому нужны регистры, `host-target` — для сценариев поверх канала связи
устройства.

Подсказка: пока `EXPECTED_SYS_HZ` в `crates-cross/target-tests/tests/test.rs` равна
`None`, проверка тактирования (`clocks_match_intent`) отключена — тест зелёный без
проверки; задайте частоту ядра, и он начнёт её стеречь (раздел «Тактирование: дамп при старте и контракт платы»).
{%- if ota == "true" %}

Отдельно стоит знать про один host-target тест: `ota_swaps_partitions_and_reverts_unconfirmed_image`
прогоняет полный цикл обновления — заливает в `DFU` заведомо инертный образ (таблица
векторов и бесконечный цикл), просит bootloader поменять разделы, проверяет, что тот их
поменял, и что на следующем сбросе неподтверждённый образ откатился. Инертный, а не
настоящий, именно поэтому: настоящий подтверждает сам себя, и откат стало бы нечем

## Тактирование: дамп при старте и контракт платы

`Board::new()` печатает в defmt фактические частоты, посчитанные HAL
(`bsp: board initialized, clocks ...`). Это не отладочный
вывод, а единственный способ увидеть, что получилось: компилятор про частоты не знает
ничего, а embassy проверяет только верхние границы шин (`assert!(hclk <= hclk_max)`).
Конфигурация, из-за которой HSE не завёлся и HAL молча уехал на HSI, или та, что даёт
шине частоту на пару процентов ниже задуманной, стартует без единой жалобы — и
всплывает потом «иногда сбоящим» обменом с периферией.

Когда тактирование настроено под плату, впишите задуманную частоту ядра в
`EXPECTED_SYS_HZ` (`crates-cross/target-tests/tests/test.rs`) — тест `clocks_match_intent`
начнёт её стеречь на реальном железе. По умолчанию там `None`: чип шаблон знает, а
вашу плату — нет, — и тест в этом состоянии честно предупреждает в логе, что проверка
выключена, вместо того чтобы выдавать зелёную галочку за проверенное тактирование.

## Команды `xtask`

```
cargo xtask setup                  # тулчейн, probe-rs-tools, flip-link, cargo-плагины (CI и ручные)
cargo xtask build                  # cross: debug + release{% if ota == "true" %}, app.bin, размер (в т.ч. зона bootloader), подпись{% else %}, размер{% endif %}
cargo xtask lint [cross]           # fmt --check + clippy -D warnings (host или cross; у host ещё cargo doc)
cargo xtask test [host|target|host-target|all]
cargo xtask pins [БЛОК|ПИН]        # справочник по чипу
cargo xtask panic-info             # причина последнего падения, снятая с платы
```

`cargo xtask test` без этапа печатает список этапов, ничего не запускает и завершается
с ошибкой — чтобы в скрипте это не выглядело как пройденные тесты.

Отдельной команды прошивки нет: это `cargo flash`/`cargo run` в `crates-cross` (см.
«Быстрый старт»). Этапы `test target` и `test host-target` заливают нужные образы
сами{% if ota == "true" %}, сначала bootloader{% endif %}, и оба оставляют на плате рабочую прошивку — release{% if ota == "true" %}-пару
bootloader со сторожем и `app`: `test target` гоняет тесты над bootloader'ом без
сторожа (`no-watchdog`) и после них, даже упавших, заливает пару{% else %} `app`:
`test target` после тестов, даже упавших, заливает её{% endif %}. `test all` эту заливку
пропускает — её тут же делает `test host-target`, — так что каждый образ шьётся по разу. Начало образа приложения с началом раздела из `memory.x`
перед записью сверяет только `test host-target`; `test target` заливает тестовый образ
через `probe-rs run` без этой сверки, а то, что `memory.x` тестов совпадает с
`memory.x` приложения, проверяет `lint cross`.

Здесь только то, что одной командой `cargo` не делается: две сборки подряд, два
воркспейса с разными наборами флагов, прошивка{% if ota == "true" %} в правильном порядке (сначала
bootloader){% endif %}, тесты, которым нужна залитая плата. Всё остальное про устройство —
напрямую через `probe-rs`, он и так стоит:

```sh
probe-rs attach --chip {{chip}} crates-cross/target/{{target}}/debug/app   # defmt-лог живой платы
probe-rs reset --chip {{chip}}
probe-rs erase --chip {{chip}} --connect-under-reset              # см. ниже про цикл паник
```

`build` не только собирает: он печатает, сколько release-образ занимает от раздела, в
который линкуется (`app: 12.8 KiB из 128.0 KiB {% if ota == "true" %}ACTIVE{% else %}FLASH{% endif %} (9%)`){% if ota == "true" %}, кладёт рядом с ELF сырой
`app.bin` для доставки по OTA и создаёт при первой сборке
ключевую пару и подписывает образ. Отдельных команд под это нет намеренно: выпуск
обновления не должен зависеть от того, вспомнил ли человек про третий шаг ритуала{% endif %}.

### Бюджет размера прошивки

По умолчанию `build` ругается только на то, что образ **не влез** в раздел, и
предупреждает, когда до границы осталось меньше десятой части. Этого мало проекту,
который ещё растёт: узнать о нехватке места на сборке гораздо дешевле, чем {% if ota == "true" %}при первом
OTA — там образ в `DFU` ещё поместится, а вот запаса на следующее обновление уже не
будет, и устройство в поле останется без пути назад{% else %}когда очередная
правка перестанет влезать{% endif %}.

Поэтому в [`crates-host/xtask/src/size.rs`](crates-host/xtask/src/size.rs) есть
константа:

```rust
const IMAGE_BUDGET_PERCENT: Option<u64> = None;
```

Поставьте `Some(85)` — и сборка начнёт падать, стоит образу перерасти 85% раздела:

```
Error: образ занял 86% раздела {% if ota == "true" %}ACTIVE{% else %}FLASH{% endif %} при бюджете 85% (IMAGE_BUDGET_PERCENT в ...)
```

`None` в шаблоне по той же причине, по которой `None` стоит в `EXPECTED_SYS_HZ`
(см. «Тактирование»): чип шаблон знает, а сколько места ваш проект хочет оставить про
запас — нет. Константа, а не переменная окружения CI-джоба, потому что порог — свойство
проекта: он одинаково действует локально и в CI, и в CI для него ничего не настраивают.

{% if ci != "none" %}
#### На сколько вырос образ

Бюджет отвечает на вопрос «место кончилось?», и отвечает поздно: flash растёт по
паре сотен байт за коммит, порог срабатывает через полсотни коммитов после того, как
место реально съели, — и искать виноватого в этот момент дорого. Поэтому cross-джоб
дополнительно показывает **разницу с веткой по умолчанию**:

```
app: 12.8 KiB из 128.0 KiB {% if ota == "true" %}ACTIVE{% else %}FLASH{% endif %} (10%)
     +312 байт к ветке по умолчанию (было 12.5 KiB, 9.8% → 10.0%)
```

Порога тут нет и не будет — ровно как у покрытия: цифра нужна, чтобы увидеть рост
тогда, когда автор ещё помнит, зачем он его добавил. Это не второй бюджет, а другой
инструмент.

Настраивать ничего не нужно, но знать про два свойства стоит:

- {% if ci == "github" %}**База лежит в кеше** и пишется только на ветке по умолчанию (иначе размер из
  чужого PR стал бы базой для всех остальных), а строку с дельтой печатает
  `cargo xtask build` в лог джоба.{% else %}**Разницу считает сам GitLab**: размер уезжает metrics-отчётом, и сравнение с
  целевой веткой видно прямо в виджете merge request'а.{% endif %}
- **Первый прогон дельты не покажет** — базы ещё нет.{% if ci == "github" %} Джоб скажет об этом
  отдельной заметкой.{% endif %} Это нормальный режим, а не поломка.

Локально `build` про дельту молчит: сравнивать не с чем, а «столько же, сколько в
прошлой вашей сборке» — сигнал, который шумит от каждого переключения ветки.
{% endif %}

### `pins`: справочник по чипу

`pins` отвечает на три вопроса, на которые компилятор ответить не может: какие выводы
вообще умеют нужный сигнал, не занимаете ли вы отладочный порт или выводы кварца, и от
чего тактируется блок. Всё остальное про распиновку проверяют типы — `SpiSck<SPI1>`
для чужого пина не реализован, а `Peri` не `Copy`, поэтому один вывод нельзя отдать
двум задачам, — поэтому генерации распиновки здесь нет и не планируется.

```sh
cargo xtask pins                  # какие блоки на этом чипе вообще имеют выводы
cargo xtask pins SPI1             # выводы с AF, DMA-каналы, источник тактирования, прерывания
cargo xtask pins PA9              # что умеет конкретный вывод
cargo xtask pins I2C1 --snippet   # заготовка bind_interrupts! и assign_resources!
cargo xtask pins --check          # не занят ли распиновкой отладочный порт
```

`--snippet` печатает (именно печатает, а не пишет файл) готовый к вставке фрагмент с
правильными типами обработчиков прерываний — там, где ошибиться легче всего: у `I2C`
обработчика два и они разные (`EventInterruptHandler` и `ErrorInterruptHandler`), у
FDCAN свои `IT0`/`IT1`, а у `SPI` и таймеров их нет вовсе. Выводы подставляются
реальные, свободные — служебные уезжают в конец списка альтернатив.

`--check` — единственная проверка распиновки, которую не делает компилятор: заняли
`PA13`/`PA14` — команда завершается ошибкой (после прошивки плата перестанет отвечать
пробнику), заняли выводы кварца, MCO или JTAG — предупреждает, но не падает: на вашей
плате кварца может и не быть.

Данные — из `stm32-metapac`, то есть из того же `stm32-data`, по которому
`embassy-stm32` генерирует свои типы: разойтись справочник и компилятор не могут.
Живёт это в отдельном крейте `crates-host/chip-info/` со своим `[workspace]`, потому что чип там
выбирается Cargo-фичей, подставляемой при генерации. Сменили чип в `crates-cross/Cargo.toml` —
поправьте фичу и в `crates-host/chip-info/Cargo.toml`; команда предупредит о расхождении, но
данные покажет старые.

## Что происходит при падении

Паникёр приложения выбирает профиль (`#[cfg(debug_assertions)]` в
`crates-cross/app/src/panic.rs`{% if ota == "true" %}; у bootloader'а свой — сброс МК без
сообщения{% endif %}):

| Профиль | Паникёр | После падения | Почему |
|---|---|---|---|
| debug | `panic-probe` | причина в defmt-логе, остановка на месте | пробник ловит её прямо там, где упало, со стеком |
| release | свой, поверх `panic-persist` | причина в регионе `PANIC` и в defmt-логе, сброс МК (`bsp::reset::Reboot`) | устройство возвращается в работу; причина уже сохранена |

Регион `PANIC` отрезан от конца RAM при генерации. При следующем старте release-`app`
читает сохранённое сообщение и печатает его первым делом — одной строкой
`предыдущий запуск упал: ...`. Читается оно ровно один раз: `panic-persist` стирает
свою магию, чтобы одно и то же падение не всплывало после каждого сброса.

Рядом — причина сброса: `main` ещё до `Board::new` читает флаги `RCC` (сторож,
программный сброс, питание, вывод `NRST`…) и снимает их (`bsp::reset::take_cause`), а
строка старта `app: причина сброса …` её показывает.
{%- if has_protobuf == "true" or net_services != "" %}
Без пробника обе вещи видны хосту в сведениях об устройстве — поля `reset` и
`last_panic`{% if has_protobuf == "true" %} (protobuf `Info`){% endif %}{% if net_services contains "rest" %}, REST `/api/info`{% endif %}{% if net_services contains "mqtt" %}, MQTT `info`{% endif %}{% if net_services contains "ssh" %}, `info` в SSH{% endif %}; паника там коротко: файл, строка
и первая строка сообщения.
{%- endif %} Подробности — `docs/diagnostics.md`.

Аппаратный отказ приложения (`HardFault`: мусорный указатель, прыжок по битому
адресу) обработчик `crates-cross/app/src/fault.rs` превращает в панику с регистрами
причины — дальше тот же путь, с записью в `PANIC`.{% if ota == "true" %} У bootloader'а обработчика нет:
`cortex-m-rt` подставляет в вектор бесконечный цикл, под пробником `probe-rs run`
останавливает ядро vector catch'ем и показывает место.{% endif %}

### Достать причину с зависшей платы

Чтобы увидеть строку при старте, пробник должен быть подключён **в момент** старта.
Дамп пишет только release-паникёр `app` (`panic-probe` в debug его не пишет{% if ota == "true" %}, паникёр
bootloader'а — тоже{% endif %}), а живёт он ровно до следующего старта release-`app`: тот
первым делом его вычитывает и стирает магию. Поэтому команда достаёт причину, только
если после паники приложение до этого чтения не дошло — например, ядро остановлено
пробником сразу после сброса{% if ota == "true" %} или плата повисла в bootloader'е{% endif %}, — а питание не
снимали:

```sh
cargo xtask panic-info   # причина последнего падения, снятая с платы как есть
```

Команда читает регион `PANIC` через `probe-rs` — ни перепрошивки, ни открытой RTT-сессии
не нужно:

```
причина последнего падения (54 байта):
panicked at crates-cross/app/src/main.rs:194:5:
...
```

Если приложение уже успело стартовать и вычитать дамп, команда так и скажет: магии на
месте нет, причина ушла в лог того запуска.

Развилка по профилю во всём шаблоне ровно одна — выбор паникёра (и под тем же `cfg`
чтение дампа при старте `app`); Cargo-фич `debug`/`release` нет нигде
(`docs/diagnostics.md`).

У перезапуска есть оборотная сторона: если release-прошивка паникует прямо на старте,
плата уходит в цикл «старт → паника → сброс», и подключиться к ней обычным способом уже
не выходит — `cargo flash` не успевает захватить ядро и падает с таймаутом. На
этот случай есть подключение с удержанным reset'ом — `probe-rs erase --chip {{chip}}
--connect-under-reset` захватывает ядро до того, как оно снова дойдёт до паники.
Сотрите флеш этой командой, и плата снова станет доступной для прошивки.

`defmt-rtt` — дефолтный транспорт в обоих профилях; паттерн для `release` без пробника
задокументирован в `docs/modules/app.md`. При его подключении держите инвариант «ровно один
активный `#[global_logger]` на бинарник» — там же объяснено, почему линкер на этом
падает жёстко. Подробности — в docs/conventions.md.

Каждая строка лога помечена временем с момента старта (`0.000`, `0.042`, ...) — это
фича `defmt-timestamp-uptime-ms` у `embassy-time`, она сама определяет
`defmt::timestamp!`. Разница заметна там, где важнее всего: «упал» и «упал через 40 мс
после старта» — разные диагнозы. Своя отметка времени (RTC, счётчик тактов `DWT`)
подключается вместо неё, а не вместе: макрос допускает ровно одно определение на
бинарник.

## Что проверяет CI

Основной прогон — то же, что вы запускаете локально: `cargo xtask lint` и
`test host` на хосте, `lint cross` и `build` для прошивки. Этапы с платой в CI не
идут: пробника у раннера нет. Сгенерированный проект тянет приватный `rust-lib`, поэтому
без доступа к нему CI будет красным (`docs/conventions.md`, «Известные, осознанные
ограничения»). Состав самих джобов — {% if ci == "github" %}`.github/workflows/*.yml`{% else %}`.gitlab-ci.yml`{% endif %};
в `AGENTS.md` перечень дан одной строкой. Отдельным дешёвым джобом идёт `typos`
(опечатки в коде и документации); что он считает не опечаткой — в `.typos.toml`.

Сверх этих четырёх команд host-прогон гоняет `cargo hack check --feature-powerset` —
`check` каждого сочетания фич каждого крейта (`log` и `defmt` взаимоисключающие, но одна
из них обязательна) — и `cargo deny check` по `deny.toml`: лицензии, источники
зависимостей, уязвимости. Прошивка проходит тот же `cargo deny check` по своему
`crates-cross/Cargo.lock`. Локально — те же команды, их ставит `cargo xtask setup`.
{%- if ci == "gitlab" %} По расписанию, кроме `audit` (ниже), идёт джоб `renovate` — см.
[«Обновление зависимостей»](#обновление-зависимостей).{% endif %}
{%- if ota == "true" %} Пуш тега `v*` запускает релизный прогон —
{% if ci == "github" %}`.github/workflows/release.yml`{% else %}джобы `release:build` и `release:publish`{% endif %}, см.
[«Выпуск релиза по тегу»](#выпуск-релиза-по-тегу).{% endif %}

Уязвимости проверяются ещё и по ночам: база RustSec пополняется и тогда, когда в
проекте ничего не меняли, а основной прогон идёт только на push и PR. Это
{% if ci == "github" %}`.github/workflows/audit.yml`{% else %}джоб `audit` (ему нужен Pipeline schedule, тот же, что у
`renovate`){% endif %}: `cargo deny check advisories` по обоим lock-файлам.

К host-прогону добавлено покрытие — `cargo llvm-cov`. {% if ci == "github" %}Таблица попадает в
сводку прогона{% else %}Процент показывается рядом с пайплайном, а cobertura-отчёт
подсвечивает непокрытые строки прямо в диффе merge request'а{% endif %}. Локально — ровно та же
команда, что в CI, чтобы цифры можно было сравнивать:

```sh
cargo install cargo-llvm-cov --locked
cargo llvm-cov nextest --workspace --exclude host-target-tests \
  --features domain/log{% if ota == "true" %},domain/signed{% endif %} --release \
  --ignore-filename-regex 'xtask' --summary-only
```

{% if ota == "true" %}`domain/signed`, {% endif %}`--release` и `--ignore-filename-regex` — не украшение: без них
локальный прогон считает не то же, что CI, и сравнивать проценты бессмысленно.
`--release` обязателен ещё и потому, что `llvm-cov` ищет объектные файлы в каталоге
своего профиля: `cargo-llvm-cov report` без него смотрел бы в `debug/`.

Непокрытые строки прямо в редакторе показывает расширение Coverage Gutters
(`ryanluker.vscode-coverage-gutters`, оно в рекомендациях `.vscode/extensions.json`):
задача VSCode `coverage: lcov` гоняет ту же команду с `--lcov --output-path lcov.info`
вместо `--summary-only`, а «Coverage Gutters: Watch» подхватывает файл и перерисовывает
подсветку после каждого прогона. `lcov.info` — в `.gitignore`.

Считается покрытие **только логики**: прошивка (`crates-cross`) живёт в другом
воркспейсе и в отчёт не попадает вовсе, а `xtask` исключён явно
(`--ignore-filename-regex`). Без этого исключения цифра меряла бы в основном сборочную
утилиту — в ней три четверти всех регионов проекта, и покрыты они на четверть, потому
что почти каждая строка там зовёт `cargo` или `probe-rs`. Сейчас в отчёте остаётся
`domain` с адаптерами, где тесты и должны быть: 95%.

**Порога намеренно нет.** Числу здесь место в роли подсказки «куда тесты не
заглядывают», а не ворот: требование «не ниже N%» на практике приводит к тестам,
написанным ради процента. Если решите добавить — считайте порог по этому же отчёту, а
не по всему проекту.

По той же логике cross-джоб показывает, **на сколько байт вырос образ** относительно
ветки по умолчанию — тоже без порога и тоже как подсказка. Подробности — в разделе
[«На сколько вырос образ»](#на-сколько-вырос-образ).

Отдельно стоит джоб **{% if ci == "github" %}`Pins`{% else %}`pins:check`{% endif %}**. Он запускается **только**
когда правили `crates-cross/bsp/src/`, сам `crates-host/chip-info/` или
`crates-cross/Cargo.toml`, и проверяет то, чего не видит компилятор: не заняли ли вы
выводы отладочного порта. Заняли `PA13`/`PA14` — джоб падает, и это правильно: с
такой прошивкой плата перестанет отвечать пробнику, доставать её придётся через
`probe-rs erase --connect-under-reset`. Выводы кварца и MCO дают предупреждение, а не
отказ: на вашей плате кварца может и не быть.

Такой фильтр путей — не экономия ради экономии: джоб тянет `stm32-metapac`, и без
фильтра каждый пуш платил бы его сборкой ради инструмента, который на саму прошивку
не влияет.{% if ci == "github" %} По той же причине не делайте `Pins` обязательной проверкой в branch
protection: PR, не трогающий распиновку, его не запустит, и обязательный статус
останется висеть в ожидании.{% endif %}

### Тесты на плате в CI

Два из трёх этапов тестирования требуют железа, поэтому на обычных раннерах не
идут. Но плата, подключённая к машине с раннером, снимает это ограничение — и джоб
{% if ci == "github" %}`Board`{% else %}`board:test`{% endif %} прогоняет `test target` и `test host-target` на каждом
пуше.

По умолчанию он **выключен** и не ждёт раннера, которого ни у кого нет. Включается
одной переменной `HIL` = `true` в {% if ci == "github" %}*Settings → Secrets and variables → Actions → Variables*{% else %}*Settings → CI/CD → Variables*{% endif %}.

Что нужно самой машине с платой:

1. **Раннер с меткой `stm32`** — {% if ci == "github" %}self-hosted runner.{% else %}обычный GitLab Runner с тегом `stm32`. Executor —
   `shell`: пробник пробрасывать в docker можно, но это отдельная возня с `--device`, а
   выигрыша никакого.{% endif %}
2. **Окружение** ставится одной командой в клоне проекта: `cargo xtask setup` (target
   тулчейна, `probe-rs-tools`, `flip-link`, `cargo-nextest` и остальные cargo-плагины).
3. **Плата с отладочным пробником**, видимая `probe-rs list` от имени пользователя
   раннера. На Linux это обычно про udev-правила: без них пробник виден только root.

Одна вещь настроена не для красоты: {% if ci == "github" %}`concurrency`{% else %}`resource_group`{% endif %}. Пробник у платы
один, и два пайплайна за него подерутся — поэтому такие джобы идут строго по одному.{% if ci == "github" %}
Отмена на лету при этом запрещена (`cancel-in-progress: false`): оборвать прогон
посреди прошивки — значит оставить плату с половиной образа.{% endif %}

{% if ci == "github" %}PR из форка джоб пропускает: иначе чужой код исполнился бы на машине с
пробником.{% else %}Пайплайн MR из форка идёт в проекте форка, где нет ни раннера `stm32`, ни
переменной `HIL`, — чужой код до машины с пробником не доберётся.{% endif %}

## Обновление зависимостей

{% if ci == "github" %}Обновления версий приносит Dependabot (`.github/dependabot.yml`) — по обеим
`[workspace.dependencies]` (корневой и `crates-cross/`). **Работает он сразу после
пуша**: его исполняет сама платформа, ничего настраивать не нужно. SHA-пины
экшенов он обновляет тоже.{% else %}Обновления версий приносит Renovate (`renovate.json` плюс джоб `renovate` в
`.gitlab-ci.yml`) — по обеим `[workspace.dependencies]` (корневой и `crates-cross/`).
**Сам он не запускается**:
`renovate.json` — это конфигурация репозитория, а не запускалка, и без того, кто его
выполняет, никаких MR не появится. Поэтому в `.gitlab-ci.yml` есть отдельный джоб
`renovate` (образ `renovate/renovate`, запускается ТОЛЬКО по расписанию — остальные джобы
из расписания, наоборот, исключены). Чтобы он заработал, нужны две вещи со стороны
проекта:

1. **CI/CD variable `RENOVATE_TOKEN`** — Project или Group Access Token с ролью
   `Developer` и скоупом `api`. Пометьте masked; protected ставить не надо, если
   расписание будет ходить по незащищённой ветке.
2. **Pipeline schedule** (*CI/CD → Schedules*), например ежедневно ночью. Без расписания
   джоб не запустится никогда — на обычных push/MR он намеренно не срабатывает.

Образы в `.gitlab-ci.yml` (`rust`, `release-cli`, сам `renovate`) запинены на версии, а
не на `latest` — два из трёх получают секреты. Поднимает их Renovate: в `renovate.json`
включён менеджер `docker` с правилом на `.gitlab-ci.yml`.

Альтернатива джобу — подключить к проекту [Mend Renovate App](https://docs.renovatebot.com/getting-started/running/)
(он поддерживает GitLab); тогда джоб можно удалить.{% endif %}
{% endif %}

## Инструменты

`cargo xtask setup` ставит всё нужное: целевой target тулчейна, компоненты `rustfmt`,
`clippy` и `llvm-tools-preview`, `probe-rs-tools` (прошивка, отладка, запуск тестов на
устройстве), `flip-link` (линкер, уводящий стек от переполнения в статические данные),
`cargo-nextest`, а также то, что гоняет CI: `cargo-deny`, `cargo-hack`, `cargo-llvm-cov`,
`typos-cli` и `cargo-insta` (разбор изменившихся снапшотов). Уже установленное не
переставляется.

Четыре инструмента ставятся для ручного запуска, в CI их нет:

- `cargo mutants` — мутационное тестирование: правит код `domain` и смотрит, замечают ли
  это тесты. Дополняет покрытие (покрытая строка ещё не проверенная), но идёт часами —
  запускайте на одном модуле: `cargo mutants -f crates-host/domain/src/cpu_load.rs`.
- `cargo bloat -p app --release` (в `crates-cross`, с `--target`) — из каких функций и
  крейтов состоит образ. `cargo xtask build` печатает только итоговый размер.
- `cargo machete` — неиспользуемые зависимости. Ищет по тексту исходников, поэтому
  ошибается на том, что используется без `use` (`cortex-m` ради линковки, символы из
  макросов), — выдачу нужно читать, а не доверять. Исключения для заведомо ложных
  срабатываний пишутся в `[package.metadata.cargo-machete]` манифеста крейта.
- `taplo` — формат и проверка манифестов. `taplo check` проверяет синтаксис; `taplo fmt`
  использовать не стоит: он заменит табы на пробелы и уберёт выравнивание `=`, принятое
  в манифестах проекта.

`flip-link` даёт HardFault при переполнении стека вместо тихой порчи статики; замера
«сколько запаса осталось» в шаблоне нет. Версия компилятора закреплена в
`rust-toolchain.toml` — rustup поставит её сам при первой команде; это условие
воспроизводимого релиза (`docs/conventions.md`). Нижняя граница — `[workspace.package]
rust-version`, 1.96.

В `.vscode/` — задачи под все команды `xtask` (`tasks.json`), запуск и подключение
отладчика через `probe-rs` (`launch.json`, `F5`) и список рекомендуемых расширений
(`extensions.json`).

## Как выбирается чип

Всё ниже происходит один раз, при `cargo generate`, — в готовом проекте от этого
остаются только подставленные значения.

Сначала — каскадный выбор конкретного STM32: семейство (`F`, `G`, `H`, `L`...), затем
линейка (`F0`, `F1`, `F3`, `G4`...), и дальше посимвольно, пока список не сузится до одного
чипа. Список вариантов на каждом шаге — реальные чипы, поддерживаемые одновременно и
`embassy-stm32`, и `probe-rs` (список зашит в шаблон заранее, см. ниже). По результату
автоматически подставляются:

- `chip` — идентификатор чипа для `probe-rs` (например `STM32F407VE`);
- `chip_feature` — фича `embassy-stm32` для этого чипа (например `stm32f407ve`);
- `target` — целевой target triple (`thumbv7em-none-eabihf` и т.п.);
- `cpu` — `target-cpu` для rustflags (`cortex-m4` и т.п.);
{%- if ota == "true" %}
- `write_size` — параметр буфера подкачки для bootloader (`BootLoader::prepare::<_,_,_,N>`);
{%- endif %}
- фича банковой схемы `embassy-stm32` (`single-bank`) — только для чипов, у которых
  их несколько; без неё build-скрипт `embassy-stm32` просто паникует;
- `MEMORY {}` в `crates-cross/*/memory.x` — адреса и размеры {% if ota == "true" %}`FLASH`/`BOOTLOADER_STATE`/
  `ACTIVE`/`DFU`/`RAM`/`PANIC`{% else %}`FLASH`/`RAM`/`PANIC`{% endif %}, посчитанные по реальным границам секторов вашего чипа
  (источник — `stm32-metapac`, та же зависимость, что уже тянет `embassy-stm32`), плюс
  **все остальные регионы памяти чипа** под своими именами: `ITCM`, `DTCM`, `CCMRAM`,
  `BKPSRAM`, `EEPROM`, `OTP` и т.д. Окна внешних шин (`FMC_*`, `SDRAM_*`, `OCTOSPI_*`) и
  вторые окна того же блока (`CCMRAM_ICODE` при `CCMRAM_DCODE`) выводятся
  закомментированными с причиной: за первыми нет памяти, пока микросхема не распаяна и
  не настроен контроллер, а вторые — та же физическая память по другому адресу, и
  разместить данные в обоих окнах разом линкер не помешает;
- реализация инициализации HAL под ваш класс чипа: одноядерный получает
  `embassy_stm32::init()`, двухъядерный — `init_primary()` с `SharedData`. В проект
  попадает только одна ветка, без `#[cfg]` и без кода для чужого класса чипа.
{%- if ota == "true" %}
  Файлы у `crates-cross/app` и `crates-cross/boot` **разные**: приложение линкуется в `ACTIVE`
  (с базы flash стартует bootloader), bootloader — в свою зону до `BOOTLOADER_STATE`,
  чтобы разросшийся образ ловил линкер, а не молчаливое наложение на `ACTIVE`.
{%- endif %}

Чтобы задать чип без интерактивного каскада (например в CI/скриптах), передайте
`--define chip_feature=stm32f407ve` — остальные поля выведутся из него автоматически
(опечатка в значении будет замечена сразу, до генерации файлов). Любое из `chip`/`cpu`/
`target`/`write_size` можно и переопределить по отдельности своим `--define` — например
если дефолтный `chip` указывает не на самый специфичный вариант probe-rs для вашего чипа.
`--define write_size=...` заодно отключает автогенерацию `memory.x` (адреса привязаны
именно к вычисленному `write_size`) — в этом случае `MEMORY {}` в обоих `crates-cross/*/memory.x`
придётся заполнить вручную, как раньше.
{%- if ota == "true" %}

### Чипы, куда OTA не помещается

`memory.x` заполняется автоматически для всех чипов каскада, но схема с bootloader'ом
влезает не в каждый. Ей нужно минимум пять стираемых страниц: `BOOTLOADER` + отдельная
страница `BOOTLOADER_STATE` (её стирают независимо от кода) + `ACTIVE` + `DFU`, который
по требованию алгоритма swap на страницу больше `ACTIVE`. На чипе с крупными секторами
это много: у STM32H723VE, например, 512 KiB flash одним регионом с сектором 128 KiB —
всего четыре страницы, и валидной раскладки не существует ни при каком дележе.

Вторая причина отказа — раздел под приложение, куда не помещается даже пустая прошивка
шаблона. У чипа с 64 KiB flash схема формально сходится, но приложению остаётся около
15 KiB, а минимальный образ занимает больше: такой проект генерировался бы, но не
собирался. Порог — 24 KiB под `ACTIVE`; он стоит между двумя реальными группами чипов
(у 160 из них под приложение выходит 16 KiB и меньше, а следующий по величине раздел
сразу 40 KiB), поэтому отсекает ровно неработающие конфигурации. Под него попадают в том
числе ходовые Nucleo-F030R8 и F051R8.

{% if ota_store == "external" %}С внешней SPI NOR, как в этом проекте, OTA помещается чаще: внутри
остаются только bootloader и `ACTIVE` (1290 чипов против 1043 со схемой во внутреннем
flash после порога в 24 KiB выше, H723VE среди них).

{% endif %}У таких чипов в вопросе об OTA пункт «yes» помечен `DOES NOT FIT on this chip:
manual memory layout`. Ответ «no» даёт проект **без OTA**: один образ на весь flash,
каталог `crates-cross/boot` в проект не попадает, прошивается только приложение. Ответ
«yes» (или `--define ota=yes`) даёт проект с OTA, но раскладку памяти (`memory.x` и числа
в `[env]` `crates-cross/.cargo/config.toml`) вы заполняете сами; причину генерация
печатает:

```
Выбранное не помещается на STM32H723VE: раскладку памяти (memory.x и числа в [env]
  crates-cross/.cargo/config.toml) вы заполняете сами — так же, как при --define write_size=...
  OTA: flash 512 KiB при секторе 128 KiB: под BOOTLOADER+STATE уходит 256 KiB, на ACTIVE+DFU остаётся стираемых страниц: 2 (нужно 3)
```

Если OTA нужен именно на таком чипе — возьмите модель с большим flash (тот же
корпус, например STM32H723VG на 1 MiB — у него раскладка считается){% if ota_store == "external" %} или
вынесите `DFU` и `STATE` на внешнюю SPI NOR, как в этом проекте{% endif %}.
{%- endif %}

**Двухъядерные чипы** (STM32H745/747/755/757, STM32WL54/55 — выбираются в каскаде явно,
отдельным вариантом на каждое ядро) собираются (проверено компиляцией, не на железе), но
код пишется только под ОДНО, выбранное в каскаде ядро (например `stm32h745zi-cm7` — CM7):
шаблон не генерирует для второго ядра ни кода, ни отдельной прошивки. **На STM32H7 (не
WL) это НЕ значит, что второе ядро бездействует** — с заводскими option bytes
(`BCM7 = BCM4 = 1`, RM0399 Table 20) оба ядра стартуют при сбросе: CM7 — с `0x08000000`,
CM4 — с `0x08100000`, начала банка 2. Раскладка поэтому делит flash, как ST и embassy в
своих примерах: проект `-cm7` живёт в банке 1 и не занимает первый сектор банка 2
(`0x08100000–0x0811FFFF`), проект `-cm4` — целиком в банке 2. Пустой сектор не
останавливает второе ядро, а лишь даёт ему стартовать в стёртую память, поэтому **снимите
у второго ядра его бит** через STM32CubeProgrammer (Option bytes → User Configuration):
для `-cm7` — `BCM4`; для `-cm4` — `BCM7` (ведущим станет CM4) или держите первый сектор
банка 1 стёртым. Это единоразовая настройка конкретной платы, прошивкой её не
сделать{% if dual_core == "true" and chip_feature contains "stm32h7" %} (подробности — `docs/flash.md`, «Память второго ядра»){% endif %}. У STM32WL54/55 такой проблемы нет —
CPU2 не стартует, пока CPU1 не выставит `PWR_CR4.C2BOOT`, а сгенерированный код этого не
делает.

**STM32WB** (кроме WBA) — тоже два ядра, и радиоядро CPU2 занимает свою память всегда:
верх flash (FUS и радиостек) и SRAM2a/SRAM2b. Раскладка отдаёт приложению только SRAM1 и
flash ниже стека `BLE_Stack_full`; со стеком крупнее границу нужно опустить{% if chip_feature contains "stm32wb" %}{% unless chip_feature contains "stm32wba" %} —
`docs/flash.md`, «Память второго ядра»{% endunless %}{% endif %}.

Полноценная symmetric/asymmetric AMP-поддержка (два независимых образа, синхронизация
между ними) — осознанно не входит в шаблон, это отдельная архитектурная задача.

Список чипов для каскада вшит в шаблон заранее (мейнтейнером, не опрашивается при вашей
генерации): это пересечение чип-фич `embassy-stm32` и целей установленного `probe-rs`,
1479 чипов. Инструменты, которые его собирают и проверяют шаблон целиком, живут в
репозитории шаблона и в сгенерированные проекты не попадают — про них написано в
`MAINTAINING.md` там же.
