# rust-embedded-template

`cargo-generate` шаблон для embedded-проектов на STM32 (Rust, `no_std`, [Embassy](https://embassy.dev)),
с трёхэтапной моделью тестирования и единой точкой входа для сборки/тестов через `xtask`.

```sh
cargo generate --git https://github.com/Sergycb/rust-embedded-template
```

Сначала пять вопросов: CI-провайдер (`github` / `gitlab` / `none`), нужен ли OTA
(bootloader с разделами `ACTIVE`/`DFU` — или один образ на весь flash), нужен ли раздел
под настройки во flash, надо ли проверять подпись OTA-образа и нужен ли граф задач
`supervisor`. Потом — каскадный выбор конкретного STM32. Порядок именно такой, поэтому вопросы и не ссылаются на ваш чип:
на момент ответа он ещё не выбран, а вот раскладка памяти считается уже с оглядкой на
ответы. По выбранному чипу шаблон сам подставит идентификаторы
`probe-rs`/`embassy-stm32`, целевой triple, фичу банковой схемы и — главное — посчитает
раскладку памяти: адреса и размеры `FLASH`/`BOOTLOADER_STATE`/`ACTIVE`/`DFU`/`RAM`
по реальным границам секторов вашего чипа. Подробности — в разделе
[«Как выбирается чип»](#как-выбирается-чип) в конце.

## Быстрый старт

```sh
cargo xtask setup        # target тулчейна + probe-rs, flip-link, cargo-nextest
cargo xtask lint         # проверить, что окружение на месте
cargo xtask test host    # тесты domain — железо не нужно

# дальше нужна плата, подключённая через отладочный пробник:
cargo xtask flash        # прошить плату
```

Первая сборка прошивки (`flash`, `build` или `lint cross`) создаст
`crates-cross/Cargo.lock` — **закоммитьте его**. Из шаблона он не приезжает намеренно:
состав зависимостей зависит от ответов при генерации (OTA, раздел настроек, подпись),
и один файл на все варианты был бы неверен для пяти сочетаний из шести — а
`cargo fetch --locked` в CI на таком падает. Пока lock не закоммичен, cross-джоб
резолвит версии заново на каждом прогоне и говорит об этом предупреждением.

Свежесгенерированный проект собирается и запускается как есть: `main.rs` поднимает
`Board`, печатает версию с номером запуска и спавнит граф задач — один узел `APP`,
который сообщает о старте и ждёт. Это каркас: у него уже есть политика перезапуска, и
дописывать свою работу вы будете внутрь него, а не с нуля.

На чипах, где под приложение отведено меньше 32 KiB, графа в проекте не будет:
`supervisor` стоит порядка полутора килобайт на Cortex-M4 и до пяти на Cortex-M0+, и в
16-килобайтный flash он просто не помещается. Генерация скажет об этом отдельной
строкой, а `main` тогда заканчивается сразу после инициализации.

Наполнять проект — в таком порядке:

| Что | Где | Зачем |
|---|---|---|
| Распиновка платы | `crates-cross/bsp/src/resources.rs` | `assign_resources!` разложит `Peripherals` по именованным группам — из них `bsp` соберёт драйверы; наружу уходит не периферия, а готовый объект |
| Граф задач | `crates-cross/app/src/task_orchestration.rs` | `supervisor_graph!`: порядок старта, рестарты с backoff, watchdog, обмен между задачами |
| Логика | `crates-host/domain/` | всё, что не про регистры: автоматы, протоколы, конфигурация — тестируется на хосте |

Каждый из этих файлов уже содержит рабочие примеры в doc-комментариях — с объяснением,
почему выбрана именно эта библиотека, а не соседняя.

`Board::init()` — единственное место, где начинается владение железом, и единственное
место, где оно заканчивается: наружу `Board` отдаёт не периферию, а объекты,
реализующие трейты из `crates-host/domain/ports`. Приложение зовёт `board.boot.bump()`
или `board.ota.mark_booted()` через порт и про регион `PERSIST`, разделы флеша и шины
не знает. Единственное исключение — периферия ядра Cortex-M: `board.core` — это целиком
`cortex_m::Peripherals` (`DWT`, `MPU`, `NVIC`, `SCB`, `SYST`, ...). Забрать её можно
ровно один раз за запуск, поэтому она и лежит в `Board`: иначе второй
`cortex_m::Peripherals::take()` где-нибудь в задаче молча вернул бы `None` уже в
рантайме. Обычно из неё берут `DWT` с `DCB` (счётчик тактов для профилирования), `MPU`
(защита стека) и `SYST` — SysTick свободен, драйвер времени embassy сидит на `TIM`.

## Структура проекта

Два основных Cargo workspace, потому что `cross` собирается под другой target и не может
делить `Cargo.lock`/профили с host-ориентированной частью. Третий, `chip-info`, стоит
особняком по другой причине — чип в нём выбирается Cargo-фичей, подставляемой при
генерации (см. ниже, «Команды `xtask`»).

Дальше по тексту `domain` и `cross` — это имена крейта и воркспейса, а `crates-host/` и
`crates-cross/` — каталоги, в которых они лежат:

```
├── crates-host/          # Всё, что собирается под хост
│   ├── domain/            # Бизнес-логика, no_std. Корневой workspace.
│   │   ├── adapters/       # Реализации портов
│   │   └── ports/          # Трейты-границы домена
│   ├── host-target-tests/ # Тесты, гоняющие хост против прошитого устройства
│   ├── xtask/             # Единая точка входа для сборки/тестов/флешинга
│   └── chip-info/         # Справочник по чипу (`cargo xtask pins`), свой workspace
├── Cargo.toml            # Корневой workspace: domain, adapters, ports, xtask, host-target-tests
│
└── crates-cross/         # Отдельный workspace, аппаратная часть (thumbv7em-none-eabihf и т.п.)
    ├── app/               # Основная прошивка (bin)
    ├── boot/              # Bootloader (bin, embassy-boot)
    ├── bsp/               # Board support package (lib)
    ├── target-tests/      # Тесты, исполняемые прямо на устройстве
    └── Cargo.toml
```

`domain` не входит в workspace `cross` (у него другой target), а подключается туда как обычная
path-зависимость. Версии зависимостей у `root` и `cross` объявлены раздельно и намеренно не
реэкспортируются друг через друга — `domain` не должен быть фасадом для инфраструктурных крейтов
вроде `static_cell`/`heapless`, которые `cross` использует для оркестрации задач. Синхронизацию
версий между двумя `[workspace.dependencies]` со временем берёт на себя бот, выбранный через
`ci` (Dependabot на GitHub, Renovate на GitLab — см. ниже). Свежесгенерированный проект
получает lock-файлы такими, какими их проверял мейнтейнер: генерация ничего не
обновляет, чтобы не уводить проект с проверенных версий (и не тратить на это минуту).

## Архитектура и когда что применять

**Главный принцип**: `cross` остаётся минимальным — только создание статических
hardware-объектов (буферы, DMA, периферия) и оркестрация задач (`Spawner`,
supervisor-графы, watchdog). Вся остальная логика — в `domain`, даже асинхронная и
«системная» на вид (стейтчарты, RPC, конкурентные примитивы). Подробное правило
«куда класть что» и разбор пограничных случаев — в CLAUDE.md.

Отсюда следует, что именно пересекает границу `bsp` → `app`: **объекты, а не
периферия**. `Board` не отдаёт наружу ни `Peripherals`, ни отдельные пины — он
собирает из них драйверы и отдаёт готовые объекты, реализующие трейты из
`crates-host/domain/ports`. Полный путь такой:

```
вывод чипа → группа assign_resources! (bsp/src/resources.rs)
           → шина и драйвер собираются в Board::init
           → драйвер живёт в domain/adapters, generic по embedded-hal-async,
             и потому проверяется на хосте моком (образец — adapters/src/lm75.rs)
           → готовый объект становится полем Board
           → app зовёт его методы через порт из ports
```

Драйвер переезжает из `adapters` в `bsp` только тогда, когда ему перестаёт хватать
трейтов `embedded-hal`: понадобились `embassy_stm32::peripherals` или статический
DMA-буфер. До этого момента его место — в `domain`, где он тестируется без железа.
Портов в шаблоне четыре: `BootCounter`, `FirmwareUpdate` и `SettingsStorage` стоят за
тем, что `bsp` отдаёт уже сейчас, а `TemperatureSensor` показывает форму для датчиков
вашего устройства.

Ниже — курированный набор зависимостей, уже подключённых в шаблоне, с кратким
обоснованием выбора и ссылкой на рабочий пример. Полное обоснование (сравнение с
альтернативами, тонкости API) — в doc-комментарии над каждым примером.

Часть из них — `fsm`, `fsm-async`, `sync-request`, `typestate`, `supervisor`,
`watchdog` — берётся из [rust-lib](https://github.com/Sergycb/rust-lib) как
git-зависимость; они заменили сторонние аналоги (`statig`, `hsmc`,
`embedded-rpc`, `typestate` 0.9.0-rc2, `embassy-supervisor`,
`embassy-task-watchdog`, `ector`). Чем именно каждый из них лучше того, что
стоял раньше, написано в примере/doc-комментарии, на который ссылается таблица.

### `domain` — бизнес-логика

| Крейт | Для чего | Пример |
|---|---|---|
| `fsm` | Иерархический автомат как **компонент** внутри произвольной задачи: владелец сам подаёт события через `dispatch()`. Синхронный, без исполнителя и таймеров. | `crates-host/domain/examples/fsm_light_machine.rs` |
| `fsm-async` | Тот же `fsm::Machine`, но владеющий **своей задачей целиком**: `run()` сам ждёт события из `embassy_sync`-канала и взводит таймауты состояний по `embassy_time`. Не другая модель состояний, а другой владелец цикла. | `crates-host/domain/examples/fsm_async_connection_chart.rs` |
| `typestate` | Compile-time автомат: недопустимый переход состояния — ошибка компиляции, а не runtime-проверка (в отличие от `fsm`/`fsm-async`). Настоящий `no_std`, поэтому обычная зависимость, а не только host/dev. | `crates-host/domain/examples/typestate_connection.rs` |
| `type-state-builder` | Typestate-builder: `build()` доступен только когда выставлены все обязательные поля — компилятор ловит недостающее поле, а не рантайм. Не пересекается с `typestate` (тот про переходы поведения, этот — про конструирование). | `crates-host/domain/examples/type_state_builder_config.rs` |
| `mitsein` | `NonEmpty`-обёртка над `heapless::Vec` — непустота как инвариант типа, а не проверка `Option`/`is_empty()` в каждом месте. Дополняет `heapless`, не конкурирует. | `crates-host/domain/examples/mitsein_nonempty_buffer.rs` |
| `futures-concurrency` | `race!`/`merge` для потоков поверх `Future` — то, чего нет в `embassy_futures::select`/`select3`/`select4` (только 2-4 ветки, без `race`/`merge` для потоков). Alloc-free. | `crates-host/domain/examples/futures_concurrency_race.rs` |
| `aselect` | Альтернатива `select!`, где непроигравшие ветки гарантированно НЕ отменяются на середине (cancellation-safety) — в отличие от tokio/embassy `select!`. `no_std`, zero-alloc, реализует `Stream`. | `crates-host/domain/examples/aselect_stream.rs` |
| `sync_wrapper` | Заставляет компилятор считать `!Sync`-тип `Sync`, когда эксклюзивный доступ гарантирован вручную — нужен, если `Future` должен быть `Sync`, а внутри держит не-`Sync` тип (`RefCell`) в многопоточном/multi-core сценарии. | `crates-host/domain/examples/sync_wrapper_example.rs` |
| `sync-request` | Межзадачный (не host↔target!) request/response поверх `embassy_sync`, без зависимости от `embassy-executor`. Отменённый (по таймауту, проигравшей веткой `select!`) запрос помечен номером поколения и не «протечёт» ответом в следующий. | `crates-host/domain/examples/sync_request_service.rs` |
| `miniconf` | Runtime-конфигурация устройства: адресуемое дерево настроек, доступ к листьям по JSON-пути, без аллокатора. | `crates-host/domain/examples/miniconf_settings.rs` |
| `test-log` | Автоинициализация `log` в host-тестах (тихо на успехе, видно на провале/`--nocapture`), цветной вывод из коробки — без ручного `env_logger::init()` в каждом тесте. | `crates-host/domain/tests/logging.rs` |

### `cross` — железо и оркестрация

| Крейт | Для чего | Где документирован |
|---|---|---|
| `supervisor` | Весь граф embassy-задач одним макросом `supervisor_graph!`: упорядоченный старт по `deps:`, рестарты с backoff, graceful shutdown, передача периферии через `resources:` (переживает перезапуск задачи), почтовые ящики `inbox:`, broadcast `publish:`/`subscribe:`, RPC `request:`/`calls:` и общий watchdog. Заменил связку `embassy-supervisor` + `embassy-task-watchdog` + `ector`, где один и тот же граф описывался тремя независимыми DSL. | `crates-cross/app/src/task_orchestration.rs` |
| `watchdog` | `no_std`-ядро мультиплексора: несколько программных watchdog'ов задач, каждый со своим таймаутом, поверх одного аппаратного. Привязку к железу задаёт единственный трейт `HardwareWatchdog`, и она в шаблоне уже написана — `bsp::wdg::Iwdg` поверх IWDG; `supervisor` использует всё это из блока `watchdog:`. | `crates-cross/bsp/src/wdg.rs` |
| `bbqueue` | Zero-copy DMA-буфер: grant/commit API, DMA пишет напрямую в backing storage. Не дублирует `embassy_sync::Pipe` (тот copy-based, для обычного межзадачного обмена без DMA). | `crates-cross/bsp/src/buffers.rs` |
| свой `#[global_logger]` над `bbqueue` | UART/любой другой транспорт для `release` без пробника — turnkey-крейта нет: `defmt-bbq` и `defmt-serial` держат `defmt@0.3.x` при `defmt@1.x` у нас (`symbol multiply defined` при реальной проверке), а `defmt-embassy-usbserial` требует `embassy-usb ^0.5` вместо версии, парной к текущей `embassy-stm32`. | `crates-cross/app/src/task_orchestration.rs` |

Шаблон собирается на обычном исполнителе, который между задачами уходит в `WFE`:
ядро стоит, тактирование и регуляторы работают. Устройству от батареи нужен режим
STOP — это разница между единицами миллиампер и единицами микроампер, — и включается
он не одной фичей: переключается сам исполнитель, драйвер времени переезжает с `TIM` на
`LPTIM`, а занятая периферия перестаёт пускать чип в сон. Рецепт целиком, вместе с тремя
местами, где на этом спотыкаются (включая сторож, который в STOP продолжает считать), —
в `crates-cross/app/src/task_orchestration.rs`, раздел «Питание от батареи». Шаблон
этого за вас не делает намеренно: STOP держится на часовом кварце, а он есть не на
каждой плате.

### Bootloader

`crates-cross/boot` — минимальный `embassy-boot-stm32` bootloader: определяет активный банк
flash и безусловно прыгает в него (`unsafe { bl.load(entry) }`), как и официальный
пример `embassy-boot-stm32`. Проверки целостности образа (вектора сброса/SP) не
делает — это осознанный компромисс минимального шаблона, не забытая деталь. `write_size`
(параметр буфера подкачки `BootLoader::prepare::<_,_,_,N>` — не путать ни с минимальной
порцией записи flash, у STM32 она всегда маленькая, 4-8 байт, ни с `PAGE_SIZE`, который
`embassy-boot` вычисляет сам из `NorFlash::ERASE_SIZE`) и оба `memory.x` вычисляются
автоматически по выбранному чипу — см. «Генерация проекта» выше. На чипах, куда схема не
помещается, `crates-cross/boot` в проект не входит вовсе — см. там же.

### Обновление прошивки

От OTA можно отказаться прямо при генерации — ответом `no` на вопрос про неё (или
`--define ota=no`). Тогда приложению достаётся весь flash вместо раздела `ACTIVE`, а
из проекта уходят `crates-cross/boot`, `bsp::ota` и всё, что ниже.

Всё, что не зависит от канала доставки, готово и живёт в `crates-cross/bsp/src/ota.rs`;
`Board` отдаёт это полем `ota`:

```rust
use domain::download::Download;

// Download берёт на себя всё, что не зависит от канала: сверяет длину с
// вместимостью до стирания, готовит раздел, копит куски до слова флеша.
let mut download = Download::begin(&mut board.ota, link.announced_len())?;
while let Some(chunk) = link.next_chunk().await {
    download.push(&mut board.ota, chunk)?;
}
download.finish(&mut board.ota)?;

board.ota.mark_updated()?;         // поменять разделы на следующем сбросе
cortex_m::peripheral::SCB::sys_reset();
```

Писать этот цикл руками не стоит: половина здешних граблей не видна, пока в них не
попадёшь. Флеш принимает запись только словами (от четырёх до тридцати двух байт
в зависимости от чипа), а канал отдаёт пакеты какой угодно длины — значит куски надо
копить; последний почти никогда не кратен слову; смещение надо вести самому и не дать
образу вылезти за обещанную длину; а длину — сверить с вместимостью **до** стирания,
потому что стирание уничтожает образ, в который устройство откатывается. `Download`
делает всё это и проверен host-тестами на кусках по одному байту, обрыве связи и лишних
данных — `crates-host/domain/src/download.rs`.

Под ним лежит `prepare`, и он не формальность: без него запись ляжет в нестёртую память
— на F2/F4/F7 молча, побитовым И со старым содержимым, на остальных семействах ошибкой.
Он же самый долгий вызов: стирание занимает от сотен миллисекунд на чипах с мелкими
страницами до нескольких секунд там, где сектор — четверть мегабайта. Всё это время
исполнитель embassy не работает (драйвер флеша стирает внутри критической секции),
поэтому не ставьте приём внутрь узла графа с коротким `watchdog:` — сторож успеет
сбросить устройство. Длина нужна именно для того, чтобы стирать не весь раздел, а столько
страниц, сколько накроет образ: на типичном «образ вдвое меньше раздела» это вдвое
короче пауза. Износ флеша тоже меньше, но не вдвое — страницы `DFU` всё равно
стирает обмен разделов при следующей загрузке. Не знаете длину заранее — передайте
`capacity()`.

Канал остаётся за вами — USB CDC, UART, сеть, SD-карта: формат пакета и проверка
целостности у каждого свои, и шаблон их не выбирает.

Одну вещь стоит знать заранее: `embassy-boot` ждёт, что новый образ отметится
работоспособным (`mark_booted()`), иначе следующий сброс откатит обновление обратно.
Вызов уже стоит в `main.rs` сразу после инициализации — это самое раннее из возможных
мест, и его стоит перенести туда, где ваше устройство действительно доказало, что
работает (подняло связь, ответило на первый запрос, отработало цикл). Тогда откат
начнёт страховать и от образа, который стартует, но не работает.

Проверено на STM32F3Discovery целиком: запись в `DFU`, обмен разделами по сбросу,
подтверждение и отсутствие отката на следующем сбросе. Под присмотром это держат оба
этапа с платой: `cargo xtask test target` пишет в раздел `DFU` и читает записанное
обратно прямо на чипе — в том числе двумя кусками в один сектор, то есть так, как это
делает настоящий приём образа, — а `cargo xtask test host-target` прогоняет цикл
целиком: смену разделов и откат образа, который себя не подтвердил (см. «Трёхэтапное
тестирование»).

#### Подпись образа

Четвёртый и последний вопрос при генерации (`--define signed=yes`, требует OTA). С ним вместо
`mark_updated()` появляется `verify_and_mark_updated(&signature, length)`: устройство
считает SHA-512 принятого образа и проверяет его подпись открытым ключом, зашитым в
прошивку. Не сошлось — разделы не меняются, устройство продолжает работать на текущем
образе.

Отдельных команд для этого нет — всё делает обычная сборка:

```sh
cargo xtask build     # создаст ключ при первой сборке, соберёт app.bin и подпишет его
```

Рядом с ELF появляются `app.bin` (то, что уезжает в раздел `DFU`) и `app.bin.sig`;
длину образа, которая нужна устройству вместе с подписью, команда печатает.

Ключей два, и обращаются с ними по-разному:

| Файл | Где живёт | Зачем |
|---|---|---|
| `ota-signing-key.bin` | только у вас, в `.gitignore` | им подписываются образы; закоммитить его — отменить смысл подписи |
| `ota-public-key.bin` | **коммитится** | попадает в прошивку через `build.rs` крейта `bsp`; им устройство проверяет подпись |

Правка исходника после создания ключа не нужна: `PUBLIC_KEY` в
`crates-cross/bsp/src/ota.rs` читает файл, а не хранит массив. Файла нет — там нули, и
обновление с ними отклоняется отдельной проверкой.

Одно поведение стоит знать заранее: **если открытый ключ в репозитории есть, а
закрытого рядом нет, образ собирается, но не подписывается** — и `build` об этом
говорит. Так выглядит свежий клон и любой CI, и это нормальный режим: для компиляции
закрытый ключ не нужен, в прошивку уезжает открытый. Новый ключ при этом не создаётся
намеренно — прошивка с ним не принималась бы уже прошитыми устройствами. Нужен именно
новый корень доверия — удалите оба файла, и пара создастся заново.

Из этого следует практика выпуска: подписанные образы выпускает тот, у кого есть
закрытый ключ, а CI собирает и проверяет всё остальное. Либо — тот же CI, если отдать
ему ключ секретом: как раз это и делает релиз по тегу, описанный ниже.

### Выпуск релиза по тегу

Проектам с OTA в комплекте идёт релизный прогон: пуш тега `v1.2.3` собирает release,
подписывает образ и кладёт `app.bin` (и `app.bin.sig`) в GitHub Release — на GitLab то
же самое делают джобы `release:build` и `release:publish`. Смысл простой: то, что
уезжает на устройства, начинает браться из версионированного места, а не из папки на
машине того, кто собирал.

```sh
git tag v1.2.3 && git push origin v1.2.3
```

Три вещи, которые стоит знать до первого тега:

1. **Тег обязан совпадать с версией проекта.** Прогон сверяет `v1.2.3` с
   `version` в `crates-cross/Cargo.toml` и падает при расхождении. Причина не в
   аккуратности: прошивка печатает свою версию при старте (её берёт `shadow-rs`), и
   разойдись они — по логу с устройства уже не понять, какой релиз на нём стоит.
2. **Закрытый ключ приходит секретом.** Заведите `OTA_SIGNING_KEY` — 32 байта seed в
   base64 (`base64 -w0 < ota-signing-key.bin`); на GitLab это CI/CD variable, masked.
   Секрета нет — образ соберётся, но **без подписи**, и прогон об этом предупредит:
   такой релиз не примет ни одно уже прошитое устройство.
3. **Сборка идёт той же командой, что у вас локально** — `cargo xtask build`. Отдельного
   «релизного» пути нет намеренно: иначе на устройства уезжало бы не то, что
   проверялось.

Проектам без OTA релизный прогон не достаётся вовсе — доставлять образ некуда, и файл
удаляется при генерации.

Считает и проверяет одно и то же — `salty`, тот же крейт на обеих сторонах. Взят он, а
не `ed25519-dalek`: меньше и написан под микроконтроллеры. Фича `slow-motion` выбирает
портируемую реализацию вместо ассемблерной под Cortex-M4/M33 — компактнее и работает на
любом ядре, ценой скорости (проверка занимает доли секунды, происходит однократно перед
перезагрузкой).

Проверяется подпись **в приложении, а не в bootloader'е**: тот прыгает в `ACTIVE`
безусловно (см. «Bootloader» выше), поэтому отвергать чужой образ нужно до того, как он
стал активным.

`cargo xtask test target` держит это под присмотром: тест `ota_rejects_a_bad_signature`
подсовывает заведомо неверную подпись и требует отказа. Пока ключа нет, он проверяет
защиту от незаполненного ключа, а после первой сборки — что ed25519 действительно
считается на вашем ядре и отвергает мусор. Заодно тот же тест стережёт проверку длины
образа: она приходит из недоверенного канала, а внутри `embassy-boot` на ней стоит
`assert!`, то есть паника.

#### Защита от отката

Подпись доказывает, **кто** прислал образ, но не то, что он **новее**. Без второй
проверки злоумышленнику достаточно взять вашу же прошлую прошивку — честно подписанную,
с уже закрытой уязвимостью — и скормить её устройству. Поэтому вместе с подписью
включается сравнение версий: образ не новее текущего отвергается с
`UpdateError::Rollback { current, incoming }`.

Работает это так:

1. `cargo xtask build` находит в ELF символ `FW_VERSION_IN_IMAGE` (его определяет
   `bsp::ota` из `version` в `crates-cross/Cargo.toml`) и **дописывает эти четыре байта
   в хвост `app.bin`** — до подписи, поэтому версия оказывается внутри подписанных
   байтов и соврать ею нельзя.
2. Устройство читает их из принятого образа по `length - 4` и сравнивает со своей
   версией через `domain::firmware::is_upgrade`.

Отсюда два следствия, которые лучше знать заранее:

- **Версия должна расти.** Та же самая версия — тоже отказ: повторная заливка одного
  номера с другим содержимым это и есть типичный откат. Выпускайте по тегам, и вопрос
  не возникнет.
- **Пререлизные суффиксы отбрасываются.** `1.2.3-rc1` и `1.2.3` дают одно число: в
  четыре байта уместить semver-пререлизы нечем.

Хвост образа, а не фиксированное место внутри — потому что своя секция сразу за
таблицей векторов накладывается на `.text` (линкер отказывается собирать, проверено), а
любое другое место внутри образа разъезжается от первой же правки кода. Конец же
образа подписывается наравне с началом и находится одним вычитанием.

Под присмотром это держит target-тест `ota_rejects_an_older_image`: он кладёт в `DFU`
хвост с версией `0.0.0` и требует отказа `Rollback`, а следом — с заведомо большей и
требует, чтобы отказ пришёл уже не по версии. Вторая половина не для симметрии: без неё
тест остался бы зелёным, даже если бы проверка отвергала вообще всё.

Два следствия, которые лучше знать заранее:

- **Версия должна расти.** Устройство с прошивкой `1.2.3-rc1` не примет релиз `1.2.3`:
  суффикс отбрасывается, номера равны, а сравнение строгое. Поднимите патч.
- **Образы, собранные до появления этой проверки, четырёх байт версии в хвосте не
  имеют.** Что там окажется — не определено, и если больше текущей версии, такой образ
  устройство примет. Проектам, созданным этим шаблоном, это не грозит (проверка есть с
  первого дня); а вот при переносе фичи в живой проект первое обновление стоит выпустить
  с версией заведомо выше всего, что уже разослано.

### Настройки во flash

Третий вопрос при генерации (после CI-провайдера и OTA) — нужен ли раздел `CONFIG`
(или `--define config=yes`).
Ответили «да» — в проект попадает `crates-cross/bsp/src/config.rs`, а `Board` отдаёт поле
`settings`: пары «ключ — значение» поверх `sequential-storage`, переживающие и
перезапуск, и обновление прошивки.

```rust
use ports::SettingsStorage;        // чтение и запись живут в порту

board.settings.write(KEY_CALIBRATION, &encoded).await?;
if let Some(raw) = board.settings.read(KEY_CALIBRATION, &mut scratch).await? {
    // раскодировать тем же, чем кодировали: postcard, miniconf, свой формат
}
```

Формат значения шаблон не выбирает — хранилище отдаёт байты. Дерево настроек, если
нужно именно оно, уже есть в `domain`: `miniconf` (см. `crates-host/domain/examples/`), и до
появления этого раздела его негде было хранить.

По умолчанию раздел выключен, и это не случайность: он стоит **две страницы стирания**,
а страница здесь — максимальный сектор чипа. На STM32G0 с секторами по 2 KiB это 4 KiB,
а на F4/F7/H7 со 128-килобайтными — 256 KiB, которые вдобавок могут вытеснить
OTA-схему. Хук при генерации печатает и размер, и такое вытеснение, если оно случилось:

```
Раздел настроек: 4K с адреса 0x0801F000
```

Удаления ключа в API нет: `sequential-storage` требует для него флеш, в одно слово
которого можно писать дважды, а у STM32 это не так. «Удаление» — запись значения,
которое ваш формат читает как «данных нет».

## Трёхэтапное тестирование

| Этап | Где выполняется | Команда | Нужна плата |
|---|---|---|---|
| host | обычный `cargo nextest`, логика `domain` | `cargo xtask test host` | нет |
| target | внутри МК, `embedded-test` + `probe-rs run` | `cargo xtask test target` | да |
| host-target | хост смотрит на прошитое устройство снаружи | `cargo xtask test host-target` | да |

`cargo xtask test all` прогоняет все три подряд, `cargo xtask test` без аргумента —
только host.

Второй и третий этапы приезжают с рабочим минимумом, а не пустым файлом:
`crates-cross/target-tests/tests/test.rs` проверяет на реальном чипе, что `Board::init()`
доходит до конца и что драйвер времени тикает (частая молчаливая поломка
тактирования — прошивка стартует, но любой `Timer::after` висит вечно), а
`crates-host/host-target-tests/tests/test.rs` прошивает release-образ, сбрасывает плату и
читает пробником счётчик запусков из региона `PERSIST` — так видно, что прошивка
действительно исполняется, а не просто залита. Через defmt это не сделать: у
`probe-rs attach` нет режима «прочитать и выйти», а убитый на Windows он оставляет
ST-Link захваченным до переподключения кабеля (поймано вживую). Дальше их дополняют под
свою плату: `target` — для
кода, которому нужны регистры, `host-target` — для сценариев поверх канала связи
устройства (USB CDC, UART-протокол, сеть).

Отдельно стоит знать про один host-target тест: `ota_swaps_partitions_and_reverts_unconfirmed_image`
прогоняет полный цикл обновления — заливает в `DFU` заведомо инертный образ (таблица
векторов и бесконечный цикл), просит bootloader поменять разделы, проверяет, что тот их
поменял, и что на следующем сбросе неподтверждённый образ откатился. Инертный, а не
настоящий, именно поэтому: настоящий подтверждает сам себя, и откат стало бы нечем
проверять. Плата после теста остаётся на исходном образе.

### Тактирование: дамп при старте и контракт платы

`Board::init()` печатает в defmt фактические частоты, посчитанные HAL
(`bsp: board initialized, clocks ...`), и хранит их в `Board::clocks`. Это не отладочный
вывод, а единственный способ увидеть, что получилось: компилятор про частоты не знает
ничего, а embassy проверяет только верхние границы шин (`assert!(hclk <= hclk_max)`).
Конфигурация, из-за которой HSE не завёлся и HAL молча уехал на HSI, или та, что даёт
USB 47.5 МГц вместо 48, стартует без единой жалобы — и всплывает потом «иногда
сыпящимся» UART.

Когда тактирование настроено под плату, впишите задуманную частоту ядра в
`EXPECTED_SYS_HZ` (`crates-cross/target-tests/tests/test.rs`) — тест `clocks_match_intent`
начнёт её стеречь на реальном железе. По умолчанию там `None`: чип шаблон знает, а
вашу плату — нет, — и тест в этом состоянии честно предупреждает в логе, что проверка
выключена, вместо того чтобы выдавать зелёную галочку за проверенное тактирование.

### Формальная верификация (Kani)

`crates-host/domain/src/kani_proofs.rs` — харнессы `#[kani::proof]` над чистой `no_std`-логикой.
Модуль под `cfg(kani)`, на обычные `cargo build`/`test`/`clippy` не влияет вовсе.
Запуск вручную:

```
cd crates-host/domain && cargo kani --features log
```

**В CI этого джоба нет намеренно.** Kani компилирует крейт вместе со всеми
зависимостями своим тулчейном (в 0.67.0 это `rustc 1.93.0-nightly`), а крейты из
`rust-lib` объявляют `rust-version = 1.96` — cargo отказывается резолвить ещё до
верификации. Вернуть джоб имеет смысл, когда тулчейн Kani дорастёт до 1.96.
Под Windows Kani не собирается вовсе (`kani-verifier` использует `std::os::unix`) —
нужен Linux, macOS или WSL.

## Команды `xtask`

```
cargo xtask setup                  # rustup target + probe-rs-tools, flip-link, nextest
cargo xtask build                  # cross: debug + release, app.bin, размер, подпись
cargo xtask flash [debug|release]  # прошить boot+app
cargo xtask lint [cross]           # fmt --check + clippy -D warnings (host или cross)
cargo xtask test [host|target|host-target|all]
cargo xtask pins [БЛОК|ПИН]        # справочник по чипу
cargo xtask panic                  # причина последней паники с платы
```

Профиль по умолчанию — `debug`, этап тестирования по умолчанию — `host`.

`build` не только собирает: он печатает, сколько release-образ занимает от раздела, в
который линкуется (`app: 12.8 KiB из 128.0 KiB ACTIVE (9%)`), кладёт рядом с ELF сырой
`app.bin` для доставки по OTA и — если подпись включена — создаёт при первой сборке
ключевую пару и подписывает образ. Отдельных команд под это нет намеренно: выпуск
обновления не должен зависеть от того, вспомнил ли человек про третий шаг ритуала.

### Бюджет размера прошивки

По умолчанию `build` ругается только на то, что образ **не влез** в раздел, и
предупреждает, когда до границы осталось меньше десятой части. Этого мало проекту,
который ещё растёт: узнать о нехватке места на сборке гораздо дешевле, чем при первом
OTA — там образ в `DFU` ещё поместится, а вот запаса на следующее обновление уже не
будет, и устройство в поле останется без пути назад.

Поэтому в [`crates-host/xtask/src/main.rs`](crates-host/xtask/src/main.rs) есть
константа:

```rust
const IMAGE_BUDGET_PERCENT: Option<u64> = None;
```

Поставьте `Some(85)` — и сборка начнёт падать, стоит образу перерасти 85% раздела:

```
Error: образ занял 86% раздела ACTIVE при бюджете 85% (IMAGE_BUDGET_PERCENT в ...)
```

`None` в шаблоне по той же причине, по которой `None` стоит в `EXPECTED_SYS_HZ`
(см. «Тактирование»): чип шаблон знает, а сколько места ваш проект хочет оставить про
запас — нет. Константа, а не переменная окружения CI-джоба, потому что порог — свойство
проекта: он одинаково действует локально и в CI, и в CI для него ничего не настраивают.

`pins` отвечает на три вопроса, на которые компилятор ответить не может: какие выводы
вообще умеют нужный сигнал, не занимаете ли вы отладочный порт или выводы кварца, и от
чего тактируется блок. Всё остальное про распиновку проверяют типы — `SpiSck<SPI1>`
для чужого пина не реализован, а `Peri` не `Copy`, поэтому один вывод нельзя отдать
двум задачам, — поэтому генерации `resources.rs` здесь нет и не планируется.

```sh
cargo xtask pins                  # какие блоки на этом чипе вообще имеют выводы
cargo xtask pins SPI1             # выводы с AF, DMA-каналы, источник тактирования, прерывания
cargo xtask pins PA9              # что умеет конкретный вывод
cargo xtask pins USART1 --snippet # заготовка bind_interrupts! и assign_resources!
cargo xtask pins --check          # не занят ли в resources.rs отладочный порт
```

`--snippet` печатает (именно печатает, а не пишет файл) готовый к вставке фрагмент с
правильными типами обработчиков прерываний — там, где ошибиться легче всего: у `I2C`
обработчика два и они разные (`EventInterruptHandler` и `ErrorInterruptHandler`), у
FDCAN свои `IT0`/`IT1`, а у `SPI` и таймеров их нет вовсе. Выводы подставляются
реальные, свободные — служебные уезжают в конец списка альтернатив.

`--check` — единственная проверка распиновки, которую не делает компилятор: заняли
`PA13`/`PA14` — команда завершается ошибкой (после прошивки плата перестанет отвечать
пробнику), заняли выводы кварца, MCO или JTAG — предупреждает, но не падает: на вашей
плате кварца может и не быть.

Данные — из `stm32-metapac`, то есть из того же `stm32-data`, по которому
`embassy-stm32` генерирует свои типы: разойтись справочник и компилятор не могут.
Живёт это в отдельном крейте `crates-host/chip-info/` со своим `[workspace]`, потому что чип там
выбирается Cargo-фичей, подставляемой при генерации. Сменили чип в `crates-cross/Cargo.toml` —
поправьте фичу и в `crates-host/chip-info/Cargo.toml`; команда предупредит о расхождении, но
данные покажет старые.

Здесь только то, что одной командой `cargo` не делается: две сборки подряд, два
воркспейса с разными наборами флагов, прошивка в правильном порядке (сначала
bootloader), тесты, которым нужна залитая плата. Всё остальное про устройство —
напрямую через `probe-rs`, он и так стоит:

```sh
probe-rs attach --chip <CHIP> crates-cross/target/<TARGET>/debug/app   # defmt-лог живой платы
probe-rs reset --chip <CHIP>
probe-rs erase --chip <CHIP> --connect-under-reset              # см. ниже про цикл паник
```

## Что происходит при панике

Причина падения сохраняется в RAM и переживает сброс, поэтому её видно, даже если
пробника рядом не было. Регион `PANIC` под это отрезан от конца RAM при генерации
(соседний `PERSIST` держит счётчик запусков в первых двух словах, остальное свободно
под собственные переживающие сброс данные — см. `crates-cross/app/src/task_orchestration.rs`), а
`#[panic_handler]` в `crates-cross/app/src/main.rs` делает три вещи: пишет туда сообщение
через `panic-persist`, печатает его же через defmt — и дальше расходится по профилю:

| Профиль | После паники | Почему |
|---|---|---|
| debug | `udf()` → HardFault | пробник ловит остановку прямо на месте падения, со стеком |
| release | `SCB::sys_reset()` | устройство возвращается в работу; причина уже сохранена |

При следующем старте `app` читает сохранённое сообщение и печатает его первым делом —
одной строкой `предыдущий запуск упал: ...`. Читается оно ровно один раз: `panic-persist`
стирает свою магию, чтобы одна и та же паника не всплывала после каждого сброса.

Но чтобы эту строку увидеть, пробник должен быть подключён **в момент** старта, а под
отладкой плата после паники не стартует вовсе — стоит в HardFault. Для этого случая:

```sh
cargo xtask panic     # причина последней паники, снятая с платы как есть
```

Команда читает регион `PANIC` через `probe-rs` — ни перепрошивки, ни открытой RTT-сессии
не нужно. Если приложение уже успело стартовать и вычитать дамп (release-профиль), она
так и скажет: магии на месте нет, причина ушла в лог того запуска.

Это единственная развилка по профилю во всём шаблоне. Cargo-фич `debug`/`release` нет
нигде: `defmt` включён безусловно в обоих профилях (`log` в прошивке не используется
вовсе, только в host-тестах `domain`), `bootloader` панику не сохраняет и остаётся на
`panic-probe`, а тесты на устройстве — на паникёре `embedded-test`, для которого паника
это способ сообщить раннеру про упавший тест.

У перезапуска есть оборотная сторона: если release-прошивка паникует прямо на старте,
плата уходит в цикл «старт → паника → сброс», и подключиться к ней обычным способом уже
не выходит — `cargo xtask flash` не успевает захватить ядро и падает с таймаутом. На
этот случай есть подключение с удержанным reset'ом — `probe-rs erase --chip <CHIP>
--connect-under-reset` захватывает ядро до того, как оно снова дойдёт до паники.
Сотрите флеш этой командой, и плата снова станет доступной для прошивки.

`defmt-rtt` — дефолтный транспорт в обоих профилях; паттерн для `release` без пробника
(UART, когда на плате появится нужная периферия) задокументирован в
`crates-cross/app/src/task_orchestration.rs`. При его подключении держите инвариант «ровно один
активный `#[global_logger]` на бинарник» — там же объяснено, почему линкер на этом
падает жёстко. Подробности — в CLAUDE.md.

Каждая строка лога помечена временем с момента старта (`0.000`, `0.042`, ...) — это
фича `defmt-timestamp-uptime-ms` у `embassy-time`, она сама определяет
`defmt::timestamp!`. Разница заметна там, где важнее всего: «упал» и «упал через 40 мс
после старта» — разные диагнозы. Своя отметка времени (RTC, счётчик тактов `DWT`)
подключается вместо неё, а не вместе: макрос допускает ровно одно определение на
бинарник.

## Что проверяет CI

Основной прогон — то же, что вы запускаете локально: `cargo xtask lint` и
`test host` на хосте, `lint cross` и `build` для прошивки. Этапы с платой в CI не
идут: пробника у раннера нет.

К host-прогону добавлено покрытие — `cargo llvm-cov`. На GitHub таблица попадает в
сводку прогона, на GitLab процент показывается рядом с пайплайном, а cobertura-отчёт
подсвечивает непокрытые строки прямо в диффе merge request'а. Локально то же самое:

```sh
cargo install cargo-llvm-cov --locked
cargo llvm-cov nextest --workspace --exclude host-target-tests \
  --features domain/log,domain/std --summary-only
```

Считается покрытие **только логики**: прошивка (`crates-cross`) живёт в другом
воркспейсе и в отчёт не попадает вовсе, а `xtask` исключён явно
(`--ignore-filename-regex`). Без этого исключения цифра меряла бы в основном сборочную
утилиту — в ней три четверти всех регионов проекта, и покрыты они на четверть, потому
что почти каждая строка там зовёт `cargo` или `probe-rs`. Сейчас в отчёте остаётся
`domain` с адаптерами, где тесты и должны быть: 95%.

**Порога намеренно нет.** Числу здесь место в роли подсказки «куда тесты не
заглядывают», а не ворот: требование «не ниже N%» на практике приводит к тестам,
написанным ради процента. Если решите добавить — считайте порог по этому же отчёту, а
не по всему проекту.

Отдельно стоит джоб **`Pins`** (`pins:check` на GitLab). Он запускается **только**
когда правили `crates-cross/bsp/src/resources.rs`, сам `crates-host/chip-info/` или
`crates-cross/Cargo.toml`, и проверяет то, чего не видит компилятор: не заняли ли вы
выводы отладочного порта. Заняли `PA13`/`PA14` — джоб падает, и это правильно: с
такой прошивкой плата перестанет отвечать пробнику, доставать её придётся через
`probe-rs erase --connect-under-reset`. Выводы кварца и MCO дают предупреждение, а не
отказ: на вашей плате кварца может и не быть.

Такой фильтр путей — не экономия ради экономии: джоб тянет `stm32-metapac`, и без
фильтра каждый пуш платил бы его сборкой ради инструмента, который на саму прошивку
не влияет. По той же причине не делайте `Pins` обязательной проверкой в branch
protection: PR, не трогающий распиновку, его не запустит, и обязательный статус
останется висеть в ожидании.

### Тесты на плате в CI

Два из четырёх этапов тестирования требуют железа, поэтому на обычных раннерах не
идут. Но плата, подключённая к машине с раннером, снимает это ограничение — и джоб
`Board` (`board:test` на GitLab) прогоняет `test target` и `test host-target` на каждом
пуше.

По умолчанию он **выключен** и не ждёт раннера, которого ни у кого нет. Включается
одной переменной:

| | Где завести | Что поставить |
|---|---|---|
| GitHub | Settings → Secrets and variables → Actions → Variables | `HIL` = `true` |
| GitLab | Settings → CI/CD → Variables | `HIL` = `true` |

Что нужно самой машине с платой:

1. **Раннер с меткой `stm32`** — self-hosted runner на GitHub, обычный GitLab Runner с
   тегом `stm32`. Executor — `shell`: пробник пробрасывать в docker можно, но это
   отдельная возня с `--device`, а выигрыша никакого.
2. **Окружение** ставится одной командой в клоне проекта: `cargo xtask setup` (target
   тулчейна, `probe-rs-tools`, `flip-link`, `cargo-nextest`).
3. **Плата с отладочным пробником**, видимая `probe-rs list` от имени пользователя
   раннера. На Linux это обычно про udev-правила: без них пробник виден только root.

Одна вещь настроена не для красоты: `concurrency`/`resource_group`. Пробник у платы
один, и два пайплайна за него подерутся — GitLab и GitHub выполняют такие джобы строго
по одному. Отмена на лету при этом запрещена (`cancel-in-progress: false`): оборвать
прогон посреди прошивки — значит оставить плату с половиной образа.

## Обновление зависимостей

`ci` определяет не только CI-workflow, но и бота для PR с обновлениями версий:
`github` → `.github/dependabot.yml`, `gitlab` → `renovate.json` плюс джоб `renovate`
в `.gitlab-ci.yml`, `none` → ни того, ни другого. Оба покрывают обе
`[workspace.dependencies]` (корневую и `crates-cross/`).

Разница между ними важна на практике: **dependabot работает сразу после пуша** — его
исполняет сама платформа, ничего настраивать не нужно. **Renovate так не умеет**:
`renovate.json` — это конфигурация репозитория, а не запускалка, и без того, кто его
выполняет, никаких MR не появится. Поэтому в `.gitlab-ci.yml` есть отдельный джоб
`renovate` (образ `renovate/renovate`, запускается ТОЛЬКО по расписанию — остальные джобы
из расписания, наоборот, исключены). Чтобы он заработал, нужны две вещи со стороны
проекта:

1. **CI/CD variable `RENOVATE_TOKEN`** — Project или Group Access Token с ролью
   `Developer` и скоупом `api`. Пометьте masked; protected ставить не надо, если
   расписание будет ходить по незащищённой ветке.
2. **Pipeline schedule** (*CI/CD → Schedules*), например ежедневно ночью. Без расписания
   джоб не запустится никогда — на обычных push/MR он намеренно не срабатывает.

Альтернатива джобу — подключить к проекту [Mend Renovate App](https://docs.renovatebot.com/getting-started/running/)
(он поддерживает и GitLab); тогда джоб можно удалить.

## Инструменты

`cargo xtask setup` ставит всё нужное: целевой target тулчейна, `probe-rs-tools`
(прошивка, отладка, запуск тестов на устройстве), `flip-link` (линкер, уводящий стек
от переполнения в статические данные) и `cargo-nextest`.

`flip-link` отвечает на вопрос «сломались или нет»: с ним переполнение стека даёт
HardFault вместо тихой порчи статики. На вопрос «сколько запаса осталось» отвечает
`bsp::stack::never_used()` — `Board::init` заливает свободный стек узором, а эта
функция говорит, сколько байт так и не понадобилось:

```rust
defmt::info!("стека не тронуто: {} байт", bsp::stack::never_used());
```

Число — нижняя оценка расхода, а не гарантия запаса: видно только то, что уже
случилось в этом запуске. Ограничения перечислены в doc-комментарии
`crates-cross/bsp/src/stack.rs`; на плате это единственный способ узнать, влезет ли
ещё одна задача или буфер побольше. Тулчейн при этом не запинен
(`rust-toolchain.toml` в шаблоне нет) — берётся установленный; минимальная версия
объявлена в `[workspace.package] rust-version` и равна 1.96.

В `.vscode/` — задачи под все команды `xtask` (`tasks.json`), запуск и подключение
отладчика через `probe-rs` (`launch.json`, `F5`) и список рекомендуемых расширений
(`extensions.json`).

## Как выбирается чип

Всё ниже происходит один раз, при `cargo generate`, — в готовом проекте от этого
остаются только подставленные значения.

Сначала — каскадный выбор конкретного STM32: семейство (`F`, `G`, `H`, `L`...), затем
линейка (`F0`, `F1`, `F3`, `G4`...), и дальше посимвольно, пока список не сузится до одного
чипа. Список вариантов на каждом шаге — реальные чипы, поддерживаемые одновременно и
`embassy-stm32`, и `probe-rs` (список зашит в шаблон заранее, см. ниже). По результату
автоматически подставляются:

- `chip` — идентификатор чипа для `probe-rs` (например `STM32F407VE`);
- `chip_feature` — фича `embassy-stm32` для этого чипа (например `stm32f407ve`);
- `target` — целевой target triple (`thumbv7em-none-eabihf` и т.п.);
- `cpu` — `target-cpu` для rustflags (`cortex-m4` и т.п.);
- `write_size` — параметр буфера подкачки для bootloader (`BootLoader::prepare::<_,_,_,N>`);
- фича банковой схемы `embassy-stm32` (`single-bank`) — только для чипов, у которых
  их несколько; без неё build-скрипт `embassy-stm32` просто паникует;
- `MEMORY {}` в `crates-cross/*/memory.x` — адреса и размеры `FLASH`/`BOOTLOADER_STATE`/
  `ACTIVE`/`DFU`/`RAM`/`PERSIST`/`PANIC`, посчитанные по реальным границам секторов вашего чипа
  (источник — `stm32-metapac`, та же зависимость, что уже тянет `embassy-stm32`), плюс
  **все остальные регионы памяти чипа** под своими именами: `ITCM`, `AXISRAM`, `CCMRAM`,
  `BKPSRAM`, `EEPROM`, `OTP` и т.д. Окна внешних шин (`FMC_*`, `SDRAM_*`, `OCTOSPI_*`) и
  вторые окна того же блока (`CCMRAM_ICODE` при `CCMRAM_DCODE`) выводятся
  закомментированными с причиной: за первыми нет памяти, пока микросхема не распаяна и
  не настроен контроллер, а вторые — та же физическая память по другому адресу, и
  разместить данные в обоих окнах разом линкер не помешает;
- реализация инициализации HAL под ваш класс чипа: одноядерный получает
  `embassy_stm32::init()`, двухъядерный — `init_primary()` с `SharedData`. В проект
  попадает только одна ветка, без `#[cfg]` и без кода для чужого класса чипа;
  Файлы у `crates-cross/app` и `crates-cross/boot` **разные**: приложение линкуется в `ACTIVE`
  (с базы flash стартует bootloader), bootloader — в свою зону до `BOOTLOADER_STATE`,
  чтобы разросшийся образ ловил линкер, а не молчаливое наложение на `ACTIVE`.

Чтобы задать чип без интерактивного каскада (например в CI/скриптах), передайте
`--define chip_feature=stm32f407ve` — остальные поля выведутся из него автоматически
(опечатка в значении будет замечена сразу, до генерации файлов). Любое из `chip`/`cpu`/
`target`/`write_size` можно и переопределить по отдельности своим `--define` — например
если дефолтный `chip` указывает не на самый специфичный вариант probe-rs для вашего чипа.
`--define write_size=...` заодно отключает автогенерацию `memory.x` (адреса привязаны
именно к вычисленному `write_size`) — в этом случае `MEMORY {}` в обоих `crates-cross/*/memory.x`
придётся заполнить вручную, как раньше.

### Чипы, куда OTA не помещается

`memory.x` заполняется автоматически для всех чипов каскада, но схема с bootloader'ом
влезает не в каждый. Ей нужно минимум пять стираемых страниц: `BOOTLOADER` + отдельная
страница `BOOTLOADER_STATE` (её стирают независимо от кода) + `ACTIVE` + `DFU`, который
по требованию алгоритма swap на страницу больше `ACTIVE`. На чипе с крупными секторами
это много: у STM32H723VE, например, 512 KiB flash одним регионом с сектором 128 KiB —
всего четыре страницы, и валидной раскладки не существует ни при каком дележе.

Вторая причина отказа — раздел под приложение, куда не помещается даже пустая прошивка
шаблона. У чипа с 64 KiB flash схема формально сходится, но приложению остаётся около
15 KiB, а минимальный образ занимает больше: такой проект генерировался бы, но не
собирался. Порог — 24 KiB под `ACTIVE`; он стоит между двумя реальными группами чипов
(у 160 из них под приложение выходит 16 KiB и меньше, а следующий по величине раздел
сразу 40 KiB), поэтому отсекает ровно неработающие конфигурации. Под него попадают в том
числе ходовые Nucleo-F030R8 и F051R8.

Для таких чипов генерируется проект **без OTA**: один образ на весь flash, каталог
`crates-cross/boot` в проект не попадает, `cargo xtask flash` прошивает только приложение.
Причина печатается при генерации и остаётся комментарием в самом `memory.x`:

```
OTA отключён для h723ve: flash 512 KiB при секторе 128 KiB: под BOOTLOADER+STATE
уходит 256 KiB, на ACTIVE+DFU остаётся стираемых страниц: 2 (нужно 3)
```

Если OTA нужен именно на этом чипе — вариантов два: взять модель с большим flash (тот же
корпус, например STM32H723VG на 1 MiB — у него раскладка считается) или вынести `DFU` на
внешнюю flash (`embassy-boot` умеет работать с любым `NorFlash`; шаблон этого не делает —
периферия и разводка зависят от платы).

**Двухъядерные чипы** (STM32H745/747/755/757, STM32WL54/55 — выбираются в каскаде явно,
отдельным вариантом на каждое ядро) собираются (проверено компиляцией, не на железе), но
код пишется только под ОДНО, выбранное в каскаде ядро (например `stm32h745zi-cm7` — CM7):
шаблон не генерирует для второго ядра ни кода, ни отдельной прошивки. **На STM32H7 (не
WL) это НЕ значит, что второе ядро бездействует** — по умолчанию (option bytes
BCM7=BCM4=1 у большинства ревизий) оба ядра стартуют при сбросе, причём CM4 — с адреса
`BOOT_CM4_ADD0`, заводское значение которого (`0x08100000`, база Flash Bank2) совпадает
с `DFU` из посчитанной раскладки. После первого же OTA-обновления там окажется валидный
образ прошивки CM7, и CM4 начнёт исполнять его параллельно, поверх общей периферии и
DMA. **Перед использованием снимите BCM4** (или уведите `BOOT_CM4_ADDx` на пустую
область) через `probe-rs` или STM32CubeProgrammer: это единоразовая настройка конкретной
платы, прошивкой её не сделать. У STM32WL54/55 такой проблемы нет — CPU2 не стартует,
пока CPU1 не выставит `PWR_CR4.C2BOOT`, а сгенерированный код этого не делает.

Полноценная symmetric/asymmetric AMP-поддержка (два независимых образа, синхронизация
между ними) — осознанно не входит в шаблон, это отдельная архитектурная задача.

Список чипов для каскада вшит в шаблон заранее (мейнтейнером, не опрашивается при вашей
генерации): это пересечение чип-фич `embassy-stm32` и целей установленного `probe-rs`,
1479 чипов. Инструменты, которые его собирают и проверяют шаблон целиком, живут в
репозитории шаблона и в сгенерированные проекты не попадают — про них написано в
`MAINTAINING.md` там же.
