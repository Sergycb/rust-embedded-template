- `no_std`, но тестируется на хосте (`cargo xtask test host`). `embassy-stm32` и любое
  знание о железе здесь запрещены — всё, что их требует, живёт в `crates-cross`.
- `supervisor` (и приезжающий с ним `embassy-executor`) — можно и нужно: здесь лежат
  и объявления узлов (`supervisor_fragment!`), и их задачи{% if graph == "true" %} (`domain::cpu_load::task`){% endif %},
  сигнатуры которых называют контекст узла{% if graph == "true" %}, и их таймаут сторожа
  (`domain::cpu_load::WATCHDOG` — `const`){% endif %}. Фрагмент самодостаточен: один узел
  без имени, всё, что он называет, — полным путём ({% if graph == "true" %}`$crate::cpu_load::WATCHDOG`{% else %}`$crate::<узел>::task`{% endif %},
  `::supervisor::…`), потому что токены `macro_rules!` резолвятся
  на compose-site, а голое имя искалось бы там; тип, которого фрагмент не видит
  (адаптер в слоте), — его параметр{% if ota == "true" %} (`name: OTA_FRAG<F, R>`){% endif %}. Compose-site —
  {% if graph == "true" %}граф в `crates-cross/app` — перечисляет фрагменты в `fragments:`, даёт узлам имена
  (`as HEARTBEAT`), подставляет типы и раздаёт поля платы{% else %}модули задач
  (подмодули `crates-cross/app/src/tasks.rs`) — подставляют типы и раздают поля платы{% endif %}.
- Адаптер над рычагом платы, чей тип или память выбирает приложение, узел
  получает готовым во входе (`LINK: local L = inputs.link`), а строит его
  compose-site; трейта сборки у таких адаптеров нет — `docs/architecture.md`,
  «Адаптеры делятся по одному признаку — нужен ли чип».
- Liquid в корневом workspace — только внутри комментариев и строковых литералов:
  код шаблона компилируется целиком — правила и приёмы в `docs/architecture.md`. Стек протокола — порт, адаптер, узел, крейт примера и их
  зависимости — есть только в проекте, где протокол выбран; без протокола их нет вовсе.
- Асинхронный код и стейтчарты — это логика, и место им здесь, а не в
  `cross`, даже если результат используется только оттуда.
- **Каждая задача узла — автомат `#[fsm::typestate]`** на контексте, который
  эмитит фрагмент ({% if graph == "true" %}`ctx: $crate::heartbeat::HeartbeatCtx, task: $crate::heartbeat::task;`{% else %}`ctx: $crate::<узел>::<Узел>Ctx, task: $crate::<узел>::task;`{% endif %}): таблица
  на `impl <Узел>Ctx`, действия — его методы, задача — `match ctx.run().await {}`
  (с выходным состоянием — `ctx.run().await;`; состоянию, которое
  заимствует данные кадра задачи, — аргументы стартового действия
  `start(..) => begin`{% if has_canopen == "true" %}, как у `canopen::task`{% endif %}, а не `static`). Проекцию аргументов
  (`task: f(ctx.поле)`) и голый `loop` в функции `task` узла (вне действий автомата)
  не писать; второй структуры вокруг контекста не заводить.{% if graph != "true" %} Исключение —
  `cpu_load::log_load`: не узел, контекста нет.{% endif %} Бесконечное обслуживание
  внутри действия, которое ведёт в `exit Down`, — можно.
- Узлы не падают: `restart:` нет ни у одного, задача возвращает `()`.
  Слово DSL без своей фичи `supervisor` не компилируется: новое слово во
  фрагменте — фича в `crates-host/domain/Cargo.toml`.
  Отказ связи — запись в лог и возврат в начальное состояние автомата или переход
  в себя, без отдельного состояния восстановления и пауз в `domain`: переждать отказ (не
  вернуть ошибку снова без ожидания) — контракт порта, его держит реализация.
- Своих типов в `domain` — только контексты узлов (их эмитит фрагмент), состояния
  автоматов, входы фрагментов ({% if ota == "true" %}`OtaWiring`, {% endif %}`IdleMeter`{% if ota == "true" %}, `Mode`{% endif %}), буферы кадра
  задачи, которые автомат получает аргументами стартового действия{% if has_canopen == "true" %} (`canopen::Persisted`){% endif %}{% if has_modbus == "true" or has_protobuf == "true" or has_canopen == "true" %} и обработчик протокола,
  который фрагмент получает на входе ({% if has_protobuf == "true" %}`protobuf::Service`{% elsif has_modbus == "true" %}карта регистров (порт `Registers`; по умолчанию `modbus::EmptyRegisters`, тип выбирает `crate::modbus::Map` в `app`, карта общая у всех узлов Modbus){% else %}`canopen::dictionary` (словарь объектов){% endif %}): это логика
  приложения, и проект правит его здесь{% endif %}.{% if ota == "true" %} Исключение — решение
  bootloader'а в `domain::ota::boot`: {% if ota_store == "external" %}`BootPlan`, {% endif %}`Screening`, `ScreenFailure` — типы
  результата {% if ota_store == "external" %}двух свободных функций{% else %}свободной функции{% endif %} над блокирующими разделами, которые
  зовёт `crates-cross/boot` (`docs/architecture.md`).{% endif %} Всё, чем логика разговаривает
  с портами (ошибки), лежит в `ports`; логика вне автоматов — функции над портами,
  её состояние — локальные переменные вызова. Состояние, которое живёт дольше
  прогона автомата, — `resources:` узла, сброс — в стартовом действии.
- Порт (`ports`) — только граница логики с адаптером или платой, и заводится
  по одной из трёх причин — `docs/architecture.md`, «Порт и адаптер — или
  библиотека прямо в `domain`».
- `adapters` — реализации без чипа; нужен чип — место в `crates-cross/bsp`
  (`docs/architecture.md`, «Адаптеры делятся по одному признаку — нужен ли чип»).
