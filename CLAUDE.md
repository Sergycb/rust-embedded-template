# Конвенции проекта

Cargo-generate шаблон embedded-проекта на STM32 (Rust, `no_std`, [Embassy](https://embassy.dev)).
Этот файл — для ИИ-сессий, работающих с репозиторием: что здесь нельзя нарушать и почему.
Человеко-читаемое описание архитектуры и таблицы зависимостей — в README.md, разделе
«Архитектура и когда что применять». Обоснование выбора каждой конкретной библиотеки — в
doc-комментариях (`//!`) над её примером использования, см. ссылки в README — не дублируется здесь.

Общие идиомы Rust (структура workspace, naming, типы, ошибки, async cancel-safety,
embedded/`no_std` паттерны — Embassy, HAL, BSP, DMA, MPU, watchdog) покрыты установленным
skill'ом `rust-engineering` и не дублируются здесь. Этот файл фиксирует только решения,
специфичные для данного шаблона, и осознанные отступления от общих рекомендаций skill'а.

## Главный принцип: domain — логика, cross — железо

Два независимых Cargo workspace:

- **`domain`** (корень репозитория) — вся бизнес-логика. `no_std`, не зависит от
  `embassy-executor`/`embassy-stm32`, тестируется на host (`cargo xtask test host`).
- **`cross/`** — аппаратная прошивка STM32 (`bsp`, `app`, `boot`). Собирается под
  `thumbv7em-none-eabihf` (или другой ARM target), подключает `domain` как обычную
  path-зависимость.

**Правило**: `cross` должен оставаться минимальным — только создание статических
hardware-объектов (буферы, DMA, периферия) и оркестрация задач (`Spawner`,
supervisor-графы, watchdog). Вся остальная логика — в `domain`, даже если она
асинхронная и типа выглядит «системной» (стейтчарты, RPC, синхронизация задач).

Как решить, куда класть новую зависимость/код:
- Требует `Spawner`/`embassy-executor`, создаёт `static` hardware-объект (DMA-буфер,
  периферия) → `cross`.
- Всё остальное (FSM, конкурентные примитивы, конфигурация, коллекции, RPC-протокол
  между задачами) → `domain`, даже если результат используется только из `cross`.

Если сомневаетесь — смотрите прецеденты (обоснование целиком в doc-комментарии, не
повторяется здесь): `hsmc` — последний абзац `cross/app/src/task_orchestration.rs`;
`intrusive-collections` — последний абзац `cross/bsp/src/buffers.rs`.

## Правила добавления новых зависимостей

1. **Не верить кешу.** Компиляция на `thumbv7em-none-eabihf` после `cargo build`
   с уже тёплым `target/` может «пройти», даже если чистая сборка не проходит.
   Перед тем как считать зависимость рабочей на ARM — обязательно
   `rm -rf target && cargo build --target thumbv7em-none-eabihf ...`. Прецедент
   (детали — в README, таблица `cross`): `firmware-controller` дважды казался
   рабочим на тёплом кеше, реально не собирается на no_std ARM.
2. **`domain` не отключать `default-features` не глядя** (общее правило
   `default-features = false` — из skill'а `rust-engineering`, здесь только
   проектное исключение). У `domain` `default = ["embassy"]` — это не просто
   удобство, а обязательное условие корректной кодогенерации `hsmc::statechart!`
   (см. предупреждение в `domain/Cargo.toml` у фичи `"embassy"`). Любая новая
   зависимость на `domain` с `default-features = false` должна явно включать
   `features = ["embassy"]` обратно, иначе `hsmc` молча сгенерирует урезанный
   sync-вариант без `run()`.
3. **Каждая новая библиотека в `domain` — с примером** в `domain/examples/*.rs`,
   реально компилируемым (`cargo run -p domain --example <name> --features log`;
   без явной фичи `log`/`defmt` голый `cargo build -p domain` не соберётся —
   `defmt-or-log` требует одну из них). Начинайте пример с doc-комментария `//!`:
   что это, чем отличается от уже имеющихся в проекте альтернатив (не «что такое X
   вообще», а «почему X, а не Y, который уже в проекте»).
4. **Каждая новая библиотека в `cross`, для которой ещё нет компилируемого
   примера** (обычно потому что нужен реальный `{{chip_feature}}`, недоступный в
   сыром шаблоне) — документируется как doc-комментарий с ```` ```ignore ```` блоком
   в `cross/app/src/task_orchestration.rs` (оркестрация) или
   `cross/bsp/src/buffers.rs` (буферы/периферия), с тем же обоснованием «почему
   именно эта библиотека».
5. **Если библиотека не подошла** (не собирается на ARM/требует alloc без
   альтернатив/дублирует уже используемую) — не удалять молча: короткий комментарий
   рядом с местом, где она могла бы быть объявлена (см. `wg`, `firmware-controller`
   в истории коммитов и комментариях `Cargo.toml`), чтобы никто не предлагал её
   повторно без контекста.
6. **Перед тем как исключить зависимость из-за `no_std`/`no-alloc` ограничения** —
   поискать альтернативы в экосистеме, а не просто убрать (см. `wg`: проверены
   `waitgroup`, `awaitgroup`, `async-wg`, `mea`, `compact-waitgroup` — все
   Arc-based, альтернативы без alloc не нашлось, только после этого исключён).

## Feature-flag конвенции

- `cross/app` и `cross/boot`: `debug` (defmt+RTT+`panic-probe`) и `release`
  (`log`+`panic-halt`) — взаимоисключающие, проверяется `compile_error!` в начале
  `main.rs`. `domain` и `bsp` сами профиль не выбирают, только прокидывают
  одноимённые `defmt`/`log` фичи дальше. Это осознанное отступление от общего
  правила skill'а `rust-engineering` «фичи аддитивны, никогда не взаимоисключающие»
  (unification фич по графу зависимостей — риск для библиотек с несколькими
  потребителями; `cross/app`/`cross/boot` — терминальные бинарные крейты, которые
  никто не подключает как зависимость, поэтому этого риска нет, а выбор ровно
  одного профиля через `compile_error!` — стандартный паттерн для embedded-прошивки).
- `-Tdefmt.x` линкуется условно из `build.rs` (`CARGO_FEATURE_DEFMT`), не
  безусловно из `.cargo/config.toml` — иначе `release`-профиль (только `log`,
  без `defmt`) не слинкуется. При добавлении нового бинарного крейта в `cross`
  с фичей `defmt` — скопировать этот же блок build.rs (per-crate, Cargo
  build-скрипты не переиспользуются между крейтами).
- `panic-abort` не использовать — не собирается на stable (требует nightly
  `#![feature(core_intrinsics)]`, не обновлялся с 2019). Везде `panic-halt`.

## Плейсхолдеры шаблона (`cargo-generate.toml`)

`{{chip}}`, `{{chip_feature}}`, `{{cpu}}`, `{{target}}`, `{{write_size}}` — плейсхолдеры
из `[placeholders]` в `cargo-generate.toml`. Список файлов, где они встречаются,
меняется по мере развития шаблона — **перед проверкой найти все вхождения заново**:
`grep -rln '{{' --include='*.rs' --include='*.toml' --include='*.json' cross xtask
.vscode .gitlab-ci.yml`. На момент написания реально блокируют компиляцию `cross`
(нужны для `cargo build`/`clippy`): `cross/Cargo.toml`, `cross/.cargo/config.toml`,
`cross/boot/src/main.rs`, `cross/rust-toolchain.toml`. Остальные вхождения
(`xtask/src/main.rs`, `.vscode/launch.json`, `.gitlab-ci.yml`, doc-комментарии в
`cross/app/src/task_orchestration.rs`/`cross/bsp/src/buffers.rs`/`cross/bsp/src/resources.rs`)
не мешают сборке — там `{{...}}` либо в некомпилируемом `` ```ignore `` -блоке, либо
используется только `cargo xtask run`/`flash`/CI/IDE, подставлять их для проверки
одной лишь сборки не обязательно. `memory.x` в `cross/app/` и `cross/boot/` содержит
свои placeholder-комментарии (не `{{...}}`) — заполняются пользователем руками после
генерации, адреса зависят от того, сколько места отвести под bootloader/DFU.

**Перед тем как проверять сборку `cross`** (компиляция, clippy, release) — временно
подставить реальные значения во все найденные вхождения (например
`stm32f303vc`/`cortex-m4`/`thumbv7em-none-eabihf`/`2048` + реальные адреса в оба
`memory.x`, см. STM32F3Discovery как референс в истории коммитов). **После проверки —
обязательно вернуть все файлы к плейсхолдерам** (`git checkout -- <файлы>` там, где
правка была только временной подстановкой, либо руками — там, где в тех же файлах
есть и настоящие изменения, которые `git checkout` иначе тоже отменит). Проверить
`git diff` перед коммитом — в нём не должно остаться реальных значений вместо
`{{...}}`.

## Порядок проверки перед коммитом

```
cargo xtask lint          # domain: fmt --check + clippy -D warnings
cargo xtask test host     # domain: cargo nextest
cargo xtask deny          # licenses/advisories/bans

cargo xtask lint cross    # cross: fmt --check + clippy -D warnings
cargo xtask build         # cross: debug + release
```

`cargo xtask lint cross` и `cargo xtask build` требуют подставленных плейсхолдеров
(см. выше) — самостоятельно вызывают `cargo` с `--target`/`--features`, но не
подставляют `{{...}}` за вас.

## Известные, осознанные ограничения (не баги)

Bootloader (безусловный прыжок без проверки образа) и дефолт `write_size = 2048` —
осознанные компромиссы, описаны в README, раздел «Bootloader»; не пытайтесь «исправить»
их без запроса пользователя. Дополнительно: `cargo-deny` `multiple-versions` — `warn`,
не `deny` (например `heapless` 0.8 у `hsmc` и 0.9 в workspace) — оставлено на
усмотрение разработчика, использующего шаблон.
