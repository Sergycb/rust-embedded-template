# Несколько транспортов в одном проекте

Дата: 2026-10-20 · ветка `feat/multi-transport`

## Зачем

Задача от пользователя, своими словами: в реальных проектах на одной плате
почти всегда несколько интерфейсов — два UART и TCP, два USB, TCP + UDP.
Устройство одно и умеет одно и то же, а пользователь «захотел общаться
по-другому — воткнулся в другой разъём». Сейчас генерация даёт ровно один
транспорт (`interface`) и один протокол (`protocol`), всё остальное
проект дописывает руками.

Нужно: при генерации, после выбора транспорта и протокола, вопрос «Добавить
ещё один транспорт?» — и так сколько угодно раз, пока у МК есть свободные
блоки.

## Цели

1. В проекте может быть **несколько транспортов**, в том числе одного вида
   (`uart`, `uart`, `tcp`).
2. **Протокол в проекте один** (сейчас). Каждый транспорт либо несёт этот
   протокол, либо идёт **без протокола** (заглушка драйвера, протокол пишет
   проект) — так же, как сегодня одиночный транспорт без протокола.
3. Все транспорты с протоколом **работают параллельно** и обслуживают **одни
   и те же данные**: одна карта регистров Modbus / один обработчик protobuf
   на всех. Отказ одного транспорта не трогает остальные (уже так: узлы не
   падают, `AGENTS.md`).
4. **OTA доступна с любого транспорта** с протоколом; пока идёт загрузка с
   одного, попытка начать её с другого получает `Busy`.
5. Транспорт одного вида выбирается **столько раз, сколько у МК физических
   блоков этого вида, выведенных в корпус**. Один CAN — `can` второй раз не
   предлагается. То же для USB (два USB = два физических разъёма на двух
   блоках, например `OTG_FS` и `OTG_HS`, а не композитное устройство).
6. Конкретный блок (`USART2`, `OTG_HS`) **выбирает генерация**, не
   пользователь.
7. **Меню не предлагает то, что не помещается в RAM чипа**: хук оценивает
   RAM каждого транспорта и узла (раздел 8).
8. **CANopen — на нескольких шинах CAN**, если у чипа их несколько (F4/F7 —
   bxCAN `CAN1`..`CAN3`, G4/H7 — `FDCAN1`..`FDCAN3`). *Снято 2026-10-21:*
   в меню CAN выбирается один раз, хук отвергает второй CANopen и в
   `--define`.

## Потом (не в этой работе, но не закрывать дорогу)

- **Разные протоколы на разных транспортах** (Modbus по UART + protobuf по
  TCP). Модель данных, порядок вопросов и формат `--define` с самого начала
  — пары «транспорт + протокол»; правило «протокол в проекте один» —
  единственная проверка в хуке, которую тогда снимут.

## Не цели

- Композитное USB-устройство (несколько CDC на одном разъёме).
- Выбор конкретного блока или выводов пользователем в меню.
- Несколько Ethernet-блоков; несколько TCP-серверов (портов) на одном
  Ethernet.
- Арбитраж записи регистров из двух транспортов сверх «последний записавший
  прав» (решение пользователя: так и задумано).

## Анти-цели

- Сломать существующие однотранспортные конфигурации: все 33 случая
  `template-check` должны по-прежнему генерироваться и собираться (`lint`,
  `test host`, `lint cross`, `build`).
- Предложить в меню то, чего у чипа физически нет (второй CAN на чипе с
  одним FDCAN).
- Вторая загрузка OTA, молча оборвавшая первую.

## Решения пользователя

| Вопрос | Ответ |
|---|---|
| Параллельно или по одному | Все транспорты с протоколом работают одновременно |
| Транспорт без протокола в смеси | Допустим (`uart:modbus`, `tcp:modbus`, `can` без протокола) |
| Два USB | Два физических разъёма на разных блоках чипа |
| Кто выбирает блок | Генерация |
| Сколько раз один вид | По числу физических блоков у МК |
| Разные протоколы | Позже; сейчас один протокол на несколько транспортов |
| Работа | В ветке `feat/multi-transport` |
| Ограничение по RAM | Да, оценка в хуке |
| CANopen на нескольких CAN | Да, если у чипа их несколько; снято 2026-10-21 — CAN один |

## Как устроено

### 1. Данные о чипах (`chip-data-gen`)

Сейчас `instances.rhai` хранит **одно** имя блока на метку
(`"usart": "USART1"`), выбранное `parse_instances`
(`chip-data-gen/src/main.rs:847-867`) по рангу «предпочтительный, короче,
по имени»; остальные отбрасываются. Нужен **список всех** выведенных в
корпус блоков, в том же порядке ранга: `"usart": ["USART1", "USART2",
"UART4"]`, `"otg": ["USB_OTG_FS", "USB_OTG_HS"]`. Первый элемент списка —
нынешний единственный блок, поэтому однотранспортные проекты получают тот
же блок, что и сейчас.

Метки `fdcan` и `bxcan` — разные виды одного транспорта `can`, `usb` и
`otg` — одного `usb`: число доступных `can` = сумма по обеим меткам. Если у
чипа оба вида (не проверено, есть ли такие) — порядок: как сейчас выбирает
`found[0]` в хуке (`chip-select.rhai:1601-1617`).

«Выведен в корпус» сейчас = у блока есть хоть один вывод
(`interface_block`, `main.rs:818-835`). Для второго и далее экземпляра
этого мало: USART с одним только TX транспортом не будет. *Моё решение:*
блок считается доступным, только если у него есть выводы нужных сигналов
(USART/UART — TX и RX; CAN — TX и RX; USB — DP и DM; Ethernet — как
сейчас). Критерий применяется ко всем экземплярам; если он поменяет
**первый** блок у каких-то чипов или уберёт интерфейс целиком — это
показывается списком при перегенерации таблиц и решается отдельно, до
коммита таблиц.

### 2. Модель ответов и вопросы (`chip-select.rhai`)

Вместо скаляров `iface`/`protocol` — **список транспортов**; у каждого:

- вид (`uart`, `can`, `tcp`, `udp`, `usb`);
- блок чипа (`USART2`, `FDCAN1`, `USB_OTG_HS`; для `tcp`/`udp` — блок ETH);
- имя в проекте (см. ниже);
- протокол или `none`.

Порядок вопросов, после чипа, OTA, настроек и графа:

> **Изменено 2026-10-21 (решение пользователя):** цикл «`interface` →
> `protocol` → „добавить ещё один транспорт?“ (`more_links`)» заменён одним
> списком с отметками; план — `docs/superpowers/plans/2026-10-21-transport-checklist.md`.

1. `transports` — список с отметками. У хуков `cargo-generate` только
   одиночный выбор, поэтому отметка `[x] `/`[ ] ` нарисована в тексте пункта, и
   меню после каждого выбора показывается заново. Первый пункт `готово` — он
   же умолчание и ответ без терминала (тогда проект без транспорта). Дальше —
   по одному пункту на вид: `uart`, `can`, `ethernet`, `usb`, и только если у
   чипа есть блок этого вида. Имён блоков в пунктах нет. `ethernet` пока даёт
   транспорт `tcp` — до отдельного вопроса о возможностях сети, который выберет
   TCP/UDP.
2. `protocol` — на каждый отмеченный транспорт, в порядке пунктов. Пока
   протокол проекта не выбран (это первый транспорт с протоколом) — всё, что
   работает поверх вида, и `none`. Когда выбран — только он и `none`; если он
   поверх этого вида не работает (`can` в проекте с Modbus) — вопрос не
   задаётся, транспорт без протокола.
3. `modbus_master` — как сейчас, один раз, когда впервые выбран Modbus.

Отмеченный транспорт получает первый свободный блок своего вида из списка
чипа; сменить блок — дело `resources.rs`, о назначенных блоках говорит
`post-script.rhai`. Второй транспорт того же вида и `udp` из меню не
выбираются — только `--define links` (ниже): там блоки назначаются по порядку
(первый `uart` — первый свободный USART, второй — следующий), а `tcp` и `udp`
— по одному разу каждый, оба на одном ETH и одном сетевом стеке (`net.rs`:
`SOCKETS` растёт на число сокетов).

**Имена в проекте** — *моё решение:* от имени блока, в нижнем регистре:
`usart2`, `fdcan1`, `usb_otg_hs`; для сети — `tcp`, `udp`. Имя физическое
(его же печатает `cargo xtask pins`), уникально и не меняется от порядка
ответов. Из него — группа в `resources.rs`, поле `Board`, модуль/тип в
`bsp`, имя узла в графе (`MODBUS_USART2`, `HOST_TCP`).

Цена: однотранспортный проект тоже получает новые имена (`board.usart1`
вместо `board.serial`/`board.link`), то есть его текст меняется. Отдельной
ветки «один транспорт — старые имена» не делать: два пути в шаблоне дороже
одной переименовки.

**`--define`** (строгий, как сейчас):

- новый ключ `links` — список через запятую, элемент `вид[:протокол]`:
  `links=uart:modbus,uart:modbus,tcp:modbus,can`. Без `:протокол` — без
  протокола.
- `interface` + `protocol` по-старому = одна пара; вместе с `links` —
  ошибка.
- Ошибки с объяснением: вида больше, чем блоков у чипа; два разных
  протокола (пока); протокол, не работающий поверх вида.
- Без терминала и без `--define` — умолчание как сейчас: без транспорта.

**Отсев чипов до каскада** (`chip-select.rhai:572-608`): по `links` — чип
подходит, если блоков каждого вида у него не меньше, чем запрошено.

**Производные переменные** (`link_port`, `crc_used`, `framing_tests`,
`ports_async`, `protocol_socket`, `protocol_link`, `stream_io`,
`has_resources`, `iface_periph`, `can_kind`, `usb_kind`, таблица в
`chip-select.rhai:1625-1671`) и `file::delete` (`:1675-1808`) считаются по
**множеству** транспортов: «есть хоть один `uart`», «Modbus поверх хоть
одного потока», а не `iface == …`. Пример, который сейчас сломался бы:
`cobs.rs` удаляется при protobuf + udp (`:1728-1730`), а при protobuf по
udp **и** uart он нужен.

### 3. Liquid в файлах шаблона

Около 260 условий `{% if interface == … %}` / `{% if protocol == … %}` в 29
файлах. Два вида правки:

- **Наличие** («в проекте есть uart», «протокол Modbus») — булевы
  переменные, которые выставляет хук (`has_uart`, `has_can`, `has_net`,
  `has_usb`, …; `protocol` остаётся строкой — он один). Манифесты, `lib.rs`,
  `adapters`, `ports`, `domain`, `deny.toml`, README — в основном это.
- **Перечисление** («для каждого транспорта — поле, группа, узел») — в
  `resources.rs`, `board.rs`, `link.rs`, `graph.rs`, `main.rs`, а также
  модули драйверов `bsp` (`serial.rs`, `can.rs`, `usb.rs`). Цикл Liquid по
  списку из хука, либо файлы на транспорт, которые пишет хук (`file::`).
  Выбор механизма — за исполнителем; сначала проверить спайком, что
  `liquid` в `cargo-generate` даёт `split` + `for` по строковой переменной
  (все переменные хука — строки).

Liquid в корневом workspace — только в комментариях (`AGENTS.md`); это
правило сохраняется.

### 4. `bsp`

- **`resources.rs`**: группа на транспорт с именем от блока
  (`usart2: Usart2Resources { usart: USART2, … }`); все группы — в одном
  `assign_resources!` (иначе E0428).
- **`board.rs`**: поле на транспорт. С протоколом — его готовый транспорт
  (сегодняшний `link`), без протокола — заглушка (сегодняшние
  `serial`/`can`/`usb`). `net` — одно на все сетевые транспорты;
  `host_buffers` — на каждый узел protobuf.
- **`link.rs`**: сейчас один `pub type Link` и статики `HOST_*`,
  `SOCKET_*`, константы `PORT` — всё на транспорт (модуль на транспорт или
  префиксы имён). У `tcp` и `udp` — свои порты.
- **`serial.rs`/`can.rs`/`usb.rs`**: тип и конструктор на экземпляр; у USB
  статики `BUFFERS`, `CDC_STATE` — на экземпляр. Общие векторы прерываний
  (USART3_4 на F0/G0 и т. п.) должны связываться одним `bind_interrupts!` —
  в заглушках прерываний нет, но рецепт в `docs/modules/bsp-serial.md`
  должен об этом сказать.
- Задачи Embassy не generic (`AGENTS.md`): каждому транспорту — свой
  псевдоним типа в `bsp`.

### 5. `domain` и общие данные

- Узел протокола — **на каждый транспорт**, фрагмент тот же под разными
  именами (`MODBUS_SLAVE_FRAG<…> as MODBUS_USART2`). `supervisor` это
  поддерживает (`check_fragment_list` запрещает только повтор имени,
  golden-тест `PORTS_FRAG as P, PORTS_FRAG as Q`); исполнитель проверяет
  кодогенерацию задач на два экземпляра.
- **Общая карта регистров Modbus**: `ports::Registers` берёт `&mut self`,
  карта уезжает в слот узла. Нужен тип-ручка в `domain` — ссылка на
  `static` под `Mutex<NoopRawMutex, _>`, реализующая `Registers` с
  блокировкой на один запрос; каждому узлу — своя ручка. *Моё решение:* под
  мьютексом — только карта проекта; окно OTA (`OtaRegisters`) оборачивает
  ручку снаружи, у каждого узла своё. Иначе запрос OTA, ждущий стирания
  сектора на `CMD`, держал бы мьютекс и останавливал все остальные
  транспорты Modbus на время стирания. `NoopRawMutex` —
  то же допущение «один исполнитель», что уже записано в `AGENTS.md`; туда
  же дописать эту ручку.
- **protobuf**: `host::Service` — `DeviceInfo` + `Requester`, оба `Copy`;
  узлам — по своему `Service::new(…)`. Общее изменяемое состояние, если
  проект его добавит, — по тому же образцу ручки.
- **Без графа** (`main.rs`): задача на транспорт (сейчас модули
  `modbus`/`host`/`net`/`usb` по одному); `pool_size` не годится — типы
  `Link` разные.

### 5a. CANopen на нескольких шинах

*Снято 2026-10-21:* в меню CAN выбирается один раз, хук отвергает второй
CANopen и в `--define`. Ниже — исходный замысел, оставлен для истории.

Узел CANopen — на каждую выбранную шину CAN, как узел Modbus на каждый
транспорт. Сейчас это упирается в фиксированные `static`, которые
генерирует `zencan` из одного `device.toml`: `NODE_MBOX`, `NODE_STATE`,
`OD_TABLE`, `OBJECT4F00` (`domain/src/canopen.rs:122-131`), и `pub static
OTA: OtaObject` (`domain/src/canopen/ota.rs:41`).

*Моё решение по смыслу* (тот же принцип «одно устройство через разные
разъёмы»):

- **Своё на шину:** состояние NMT и почтовый ящик узла, адрес в сети
  (`node_id`; сохранённый по LSS — свой ключ хранилища на шину вместо одного
  `NODE_ID_KEY`), объект OTA `0x4F00` (своя сессия OTA на шину, владелец —
  как в разделе 6).
- **Общее:** значения объектов приложения в словаре — один набор данных,
  как общая карта регистров Modbus; сохранённые объекты (`OBJECTS_KEY`) —
  один набор.

Первый шаг этого раздела — **исследование `zencan`**: умеет ли его
кодогенерация несколько экземпляров состояния узла над одним словарём (или
несколько словарей из одного `device.toml`). Если не умеет — вернуться к
пользователю с вариантами (несколько словарей без общих значений; правка
или форк `zencan`, что упирается в правило «зависимости — только с
разрешения»), а не выбирать молча.

### 6. OTA с нескольких транспортов

Вход `CMD` уже многоклиентский (`Requester: Copy`, вызовы сериализуются).
Но автомат OTA клиентов не различает: `* + Start` начинает сессию заново
из любого состояния, то есть `Start` со второго транспорта оборвёт загрузку
с первого (`domain/src/ota.rs:233-241`) — это анти-цель.

Нужен **владелец сессии**: команды несут идентификатор клиента (номер
транспорта, раздаётся при сборке графа), сессию в `Receiving` держит тот,
кто её начал.

- `Start` от владельца — как сейчас (перезапуск сессии хостом).
- `Start`/`Chunk`/`Finish` от другого клиента в `Receiving` — `Busy`.
- Владелец освобождается на `Finish`, ошибке и по существующему сроку
  молчания (`Receiving + expired => abandon -> Idle`) — так оборванный
  посреди загрузки разъём не запирает OTA навсегда.
- `Reboot` — от любого клиента, как сейчас.

*Моё решение:* клиент — **транспорт**, а не удалённый хост. Два хоста на
одном транспорте (два UDP-отправителя, следующий клиент TCP-сервера)
по-прежнему делят одну сессию — так и сегодня с одним транспортом, и это
не новая проблема этой работы. Различать хосты — отдельная задача: признак
хоста пришлось бы протащить через `adapters::net` в `ports::OtaCommand`.

Окно OTA в `OtaRegisters` (статус, счётчик принятого) — своё у каждого
узла Modbus; это верно: каждый хост видит свою сессию. Объект `0x4F00`
CANopen — `static` и нужен на каждую шину (раздел 5a).

`PARKED_CALLERS = 4` в `sync-request` — потолок одновременно ждущих
клиентов; при числе транспортов с протоколом больше 4 — проверить, что
лишний клиент ждёт корректно, или ограничить число в хуке.

### 8. Оценка RAM в хуке

Сейчас хук считает только flash (`plan`, `GRAPH_MIN_PARTITION`, раскладка
`memory.x`); RAM не проверяется вовсе. С несколькими транспортами каждый
добавляет буферы (`HOST_RX`/`HOST_TX`/`HOST_FRAME`, `SOCKET_*`, USB
`BUFFERS`/`CDC_STATE`, кадр Modbus), узел графа (слоты, будущее задачи) и
стек сетевого сокета.

- **Модель:** RAM проекта ≈ база (ответы без транспортов: OTA, настройки,
  граф) + сумма стоимостей транспортов (вид × протокол; сетевой стек — один
  раз на `tcp`/`udp` вместе) + запас под стек. Сравнивается с RAM, куда
  линкуются `.data`/`.bss` (регион `RAM` в `memory.x`, а не сумма всех SRAM
  чипа).
- **Числа** — таблица констант в хуке, **измеренные**, а не выведенные:
  размер `.data` + `.bss` release-сборки показательных случаев
  `template-check` (разница «с транспортом» − «без»). Как измерять и как
  обновлять таблицу при изменении буферов — записать в `MAINTAINING.md`;
  при желании — проверка в `template-check`, что оценка не ниже факта.
- **Меню:** транспорт, который с уже выбранным не помещается, остаётся в
  меню с пометкой «НЕ ПОМЕЩАЕТСЯ в RAM», как OTA сейчас; `--define` —
  ошибка с объяснением. Вопрос «Добавить ещё?» не задаётся, если не
  помещается ничего.
- **Отсев до каскада** (`links` в `--define`): чип подходит, только если
  оценка помещается.
- Запас под стек и погрешность — *за исполнителем*, с обоснованием из
  измерений.
