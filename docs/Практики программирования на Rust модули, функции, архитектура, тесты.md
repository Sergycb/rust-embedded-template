# Практики программирования на Rust: модули, функции, архитектура, тесты

Oct 11, 2026 · @Sergey

## Введение

Документ сводит в один свод правила, по которым сообщество Rust организует код: от порядка элементов в файле до архитектуры смешанного embedded + host репозитория. Каждое правило помечено кодом первоисточника, чтобы его можно было проверить.

**Основные источники:**

| Код в тексте | Источник | Что даёт |
| --- | --- | --- |
| `C-*` | [Rust API Guidelines](https://rust-lang.github.io/api-guidelines/checklist.html) | Официальный чеклист проектирования API |
| `M-*` | [Microsoft Pragmatic Rust Guidelines](https://microsoft.github.io/rust-guidelines/) | Практические правила для библиотек и приложений |
| Style Guide | [Rust Style Guide](https://doc.rust-lang.org/style-guide/items.html) | Официальный стиль, его применяет rustfmt |
| Book / Reference | [The Rust Book](https://doc.rust-lang.org/book/), [Reference](https://doc.rust-lang.org/reference/items/modules.html) | Модули, тесты, видимость |
| clippy | [Clippy lints](https://rust-lang.github.io/rust-clippy/master/index.html) | Правила, которые можно проверять автоматически |
| Ferrous | [Ferrous Systems: Testing an embedded application](https://ferrous-systems.com/blog/test-embedded-app/) | Раскладка firmware + host, три вида тестов |
| Embedded Book | [Embedded Rust Book, HAL patterns](https://docs.rust-embedded.org/book/design-patterns/hal/) | Правила для HAL и драйверов |

**Уровни обязательности.** «Обязательно» означает, что нарушение ломает тестируемость, безопасность или совместимость. «Рекомендуется» означает устоявшуюся конвенцию; отступать можно, но осознанно и единообразно по проекту. Где источники расходятся, это сказано прямо.

**Главная идея всего документа:** отделяйте чистую логику от ввода-вывода. Код, который считает, решает и ведёт конечный автомат, не трогает железо, часы и сеть. Почти все остальные правила следуют из этого.

## 1. Устройство модуля: наполнение и порядок элементов

Модуль называется по предметной области и содержит одну связную тему. Внутри файла элементы идут сверху вниз: документация, атрибуты, объявления подмодулей и импорты, константы, типы, impl-блоки, функции, тесты.

### 1.1. Что класть в модуль

- Модуль называется по домену: `frame`, `calibration`, `can_bus`, `status`. Имена `utils`, `helpers`, `common`, `types`, `traits`, `errors`, `misc` не несут информации и запрещены `[M-BALANCED-MODULES]`. Microsoft прямо пишет, что модули `traits` и `errors` никому не помогают.
- Модуль — это «меню»: несколько главных элементов лежат в корне крейта, остальное сгруппировано по смыслу. Две ошибки: плоский корень с тридцатью типами и лес подмодулей при пустом корне.
- Каждый публичный модуль начинается с `//!`-документации: что в нём, когда использовать, когда нет `[M-MODULE-DOCS]`.
- Тип, его inherent `impl` и реализации трейтов для него живут в одном модуле, рядом с определением.
- Ошибки операции лежат рядом с операцией, а не в общем `error.rs` на весь крейт (см. раздел 3.4).

### 1.2. Рекомендуемый порядок элементов в файле

```rust
//! Разбор и сборка CAN-кадров протокола узла.        // 1. Документация модуля

#![cfg_attr(not(test), no_std)]                    // 2. Внутренние атрибуты (только в lib.rs/main.rs)

mod crc;                                           // 3. Объявления подмодулей
mod header;

use core::fmt;                                     // 4. Импорты: std/core → внешние → crate

use heapless::Vec;

use crate::node::NodeId;

pub use header::Header;                            // 5. Ре-экспорты своих элементов

/// Максимальная длина полезной нагрузки CAN FD, байт.
pub const MAX_PAYLOAD: usize = 64;                 // 6. Константы и статики

/// Разобранный кадр.
pub struct Frame { /* ... */ }                     // 7. Типы: публичные, затем приватные

impl Frame { /* ... */ }                           // 8. impl сразу после своего типа
impl fmt::Display for Frame { /* ... */ }

pub fn decode(raw: &[u8]) -> Result<Frame, DecodeError> { /* ... */ }  // 9. Публичные функции

fn checksum(data: &[u8]) -> u16 { /* ... */ }      // 10. Приватные помощники

#[cfg(test)]
mod tests { /* ... */ }                            // 11. Тесты — всегда последними
```

Обоснование по пунктам:

1. **Тесты в конце** обязательны: clippy-линт [`items_after_test_module`](https://rust-lang.github.io/rust-clippy/master/index.html#items_after_test_module) входит в группу `style` и предупреждает по умолчанию, если после `#[cfg(test)] mod tests` есть элементы. Пример в [Book, гл. 11.3](https://doc.rust-lang.org/book/ch11-03-test-organization.html) тоже ставит тесты в конец.
2. **Импорты сортируются** rustfmt автоматически (`reorder_imports = true` по умолчанию). Группы `std/core → внешние → crate` даёт `group_imports = "StdExternalCrate"`, но эта опция пока нестабильна и требует `cargo +nightly fmt` ([rustfmt Configurations](https://github.com/rust-lang/rustfmt/blob/master/Configurations.md)). Без nightly держите группы вручную, разделяя пустой строкой: rustfmt не переставляет группы между собой.
3. **Публичное выше приватного, типы выше функций.** Так требует [style guide rust-analyzer](https://github.com/rust-lang/rust-analyzer/blob/master/docs/book/src/contributing/style.md): читатель видит API раньше деталей.
4. **Константы выше типов, типы выше функций.** Это порядок по умолчанию clippy-линта `arbitrary_source_item_ordering` (см. 1.3).

### 1.3. Где источники расходятся: `mod` или `use` первым

| Источник | Порядок |
| --- | --- |
| [Rust Style Guide](https://doc.rust-lang.org/style-guide/items.html) | `extern crate` → `use` → `mod` → остальное |
| [rust-analyzer style](https://github.com/rust-lang/rust-analyzer/blob/master/docs/book/src/contributing/style.md) | `mod` → `use` → ре-экспорты → остальное |
| clippy `arbitrary_source_item_ordering` | `mod` → `use` → макросы → `static`/`const` → типы и `impl` → `fn` |

rustfmt не переставляет `use` относительно `mod`, поэтому выбор за проектом. Практичный выбор: `mod` перед `use`, как у rust-analyzer и clippy, ведь эту версию можно проверять автоматически. Главное — одинаково во всём репозитории.

**Автоматическая проверка порядка.** Линт `arbitrary_source_item_ordering` появился в clippy 1.84, входит в группу `restriction` и выключен по умолчанию. Его порядок по умолчанию:

1. модули: `extern crate`, `mod`, `extern {}`;
2. `use`;
3. макросы;
4. `global_asm!`;
5. `static`, `const`;
6. `type`, `enum`, `struct`, `union`, `trait`, `impl`;
7. `fn`.

Внутри трейта он требует порядок `const → type → fn`, а в `impl Trait for T` — алфавитный (настраивается на «как в трейте»). Порядок настраивается в `clippy.toml` ключами `module-item-order-groupings` и `trait-assoc-item-kinds-order`. Включать стоит, только если команда согласна на порядок, иначе линт станет шумом.

### 1.4. Видимость и ре-экспорт

- По умолчанию всё приватно. Повышайте по шагам: приватно → `pub(super)` → `pub(crate)` → `pub`. `pub` — это контракт на годы.
- Один публичный элемент имеет один путь `[M-SINGLE-ITEM-PATH]`. Не экспортируйте `db::Connection` ещё и как `crate::Connection`.
- Без glob-ре-экспорта `pub use foo::*` `[M-NO-GLOB-REEXPORTS]`. Исключение: модули платформ, выбранные через `cfg`, в HAL.
- Без модуля `prelude` в библиотеке `[M-NO-PRELUDE]`: если он кажется нужным, плохо разложены модули.
- Не ре-экспортируйте чужие типы `[M-FOREIGN-REEXPORTS]`. Исключения: зонтичные крейты и крейты, разрезанные по техническим причинам.
- Внутри крейта предпочитайте `use crate::foo::bar` вместо `use super::bar`: путь от корня не ломается при переносе модуля (rust-analyzer style).

## 2. Подмодули: где располагать и как вкладывать

Подмодуль `foo` живёт в файле `foo.rs`, его дети — в каталоге `foo/` рядом с ним. Стиль с `mod.rs` устарел, а когда модулю становится тесно, его выносят в отдельный крейт.

### 2.1. `foo.rs` + `foo/` вместо `foo/mod.rs`

```text
src/
├── lib.rs          // mod frame; mod node;
├── frame.rs        // mod header; mod crc;  + общий код frame
├── frame/
│   ├── header.rs
│   └── crc.rs
└── node.rs
```

- [Reference](https://doc.rust-lang.org/reference/items/modules.html): `mod.rs` был единственным способом до rustc 1.30. Новый стиль рекомендуется как более последовательный, без множества одинаковых файлов `mod.rs`.
- [Book, гл. 7.5](https://doc.rust-lang.org/book/ch07-05-separating-modules-into-different-files.html) называет `mod.rs` «старым, но поддерживаемым» стилем. Иметь одновременно `frame.rs` и `frame/mod.rs` — ошибка компиляции.
- Чтобы стиль не расползался, включите в `[workspace.lints.clippy]` линт `mod_module_files = "warn"`: он запрещает `mod.rs`. Обратный линт `self_named_module_files` требует только `mod.rs`. Оба в группе `restriction`, выберите один.
- Исключение: в `tests/` общий код кладут в `tests/common/mod.rs`. Файл `tests/common.rs` cargo считал бы отдельным тестовым крейтом ([Book, гл. 11.3](https://doc.rust-lang.org/book/ch11-03-test-organization.html)).

### 2.2. Сколько уровней вложенности

- Два-три уровня внутри крейта — норма. Если путь длиннее `crate::a::b::c::Item`, модуль, скорее всего, пора выделять в крейт.
- Не создавайте подмодуль ради одного маленького типа. Подмодуль оправдан, когда у него есть своя приватная реализация и свой небольшой публичный интерфейс.
- Приватные помощники подмодуля остаются приватными. Родителю отдаётся только то, что нужно, через `pub(super)` или `pub(crate)`.

### 2.3. Когда подмодуль становится крейтом

«Если сомневаетесь — разделяйте крейт» `[M-SMALLER-CRATES]`. Крейт — единица компиляции и параллелизма, cargo запрещает циклы между крейтами, а потеря доступа через `pub(crate)` заставляет спроектировать честный интерфейс.

Признаки, что пора выносить: модуль нужен и прошивке, и хост-утилите; он не зависит от железа и его хочется тестировать на хосте; ему нужны другие зависимости или фичи, чем остальному крейту.

### 2.4. Раскладка workspace

- Крейты лежат плоско в `crates/`, имя каталога совпадает с именем крейта, корневой `Cargo.toml` — виртуальный манифест ([matklad, Large Rust Workspaces](https://matklad.github.io/2021/08/22/large-rust-workspaces.html)). Иерархия каталогов «не бывает идеальной», поэтому родство выражают префиксами имён: `node`, `node_proto`, `node_sim`.
- Крейт внутри каталога другого крейта, тем более внутри его `src/`, недопустим `[M-CRATES-FLAT-FOLDER]`.
- Все зависимости объявляются один раз в `[workspace.dependencies]`, члены пишут `serde.workspace = true`. Внутренние крейты тоже подключаются через workspace, а не через голый `path = "../sibling"` `[M-CRATES-IN-WORKSPACE]`.
- Линты задаются один раз в `[workspace.lints]`, а в каждом крейте стоит `[lints] workspace = true` (таблица `[lints]` стабильна с Rust 1.74).
- Фичи только аддитивны: фича `std` включена по умолчанию, фичи `no-std` не бывает `[M-FEATURES-ADDITIVE]`. Cargo объединяет фичи по всему графу, поэтому «невозможная» комбинация обязательно встретится.

Для проекта с прошивкой одного workspace недостаточно: см. раздел 5.3.

## 3. Функции: как писать и описывать

Функция делает одно дело, принимает самый слабый подходящий тип, возвращает значение, а ожидаемые ошибки отдаёт через `Result`. Каждая публичная функция документирована по канону: строка-резюме и разделы `# Errors`, `# Panics`, `# Safety`.

### 3.1. Метод или свободная функция

- Есть очевидный получатель (`self`) — метод. Иначе свободная функция `[M-REGULAR-FN]`. Не вешайте посторонние помощники на `impl` ради пространства имён:

```rust
impl Database {
    fn query(&self, q: &Query) -> Rows { /* ... */ }   // да: работает с self
    fn check_params(p: &str) -> bool { /* ... */ }      // нет: к Database не относится
}
fn check_params(p: &str) -> bool { /* ... */ }          // так правильно
```

- Если внутри функции понадобился комментарий-заголовок раздела, это две функции.

### 3.2. Имена

| Ситуация | Правило | Пример |
| --- | --- | --- |
| Регистр | `snake_case` для функций и переменных `[C-CASE]` | `read_frame` |
| Геттер | без `get_` `[C-GETTER]` | `fn id(&self) -> NodeId`, `fn id_mut(&mut self)` |
| Дешёвое заимствование | `as_*` `[C-CONV]` | `as_bytes()` |
| Дорогое или с владением | `to_*` | `to_vec()` |
| Поглощает `self` | `into_*` | `into_inner()` |
| Итераторы | `iter` / `iter_mut` / `into_iter` `[C-ITER]` |  |
| Fallible-конструктор | `try_*` или `TryFrom` | `NodeId::try_from(7)` |

Имена короткие: вызывающий уточнит модулем (`frame::decode`, а не `decode_frame_from_bytes`) `[M-SHORT-NAMES]`.

### 3.3. Аргументы

- Берите самый слабый тип: `&str` вместо `&String`, `&[T]` вместо `&Vec<T>`, `&T` вместо `&Box<T>`.
- Если владение не нужно, принимайте `impl AsRef<[u8]>`, `impl AsRef<str>`, `impl RangeBounds<T>` вместо пары `(lo, hi)` `[M-IMPL-ASREF]`, `[M-IMPL-RANGEBOUNDS]`. Такие границы ставятся на функции, но не на типы.
- Никаких `bool`-флагов со скрытым смыслом: `write(p, Overwrite::No)` читается, `write(p, false)` нет `[C-CUSTOM-TYPE]`.
- Четыре и больше параметров — группируйте их в типы (`Deposit::new(account, amount)`) `[M-INIT-CASCADED]`.
- Порядок параметров единый по крейту; вездесущие параметры (контекст, логгер) идут последними, замыкание одно и тоже последнее `[M-PARAMETER-CONSISTENCY]`.
- Время передаётся параметром (`now: Instant`), а не читается внутри: так функцию можно тестировать (раздел 5.2).

### 3.4. Возвращаемое значение и ошибки

- Возвращайте значения, а не out-параметры `[C-NO-OUT]`. Исключение: вариант `_into`, пишущий в буфер вызывающего, — нормальная форма в `no_std`, где нет кучи.
- Ожидаемый сбой (разбор, ввод-вывод, таймаут, плохой ввод) возвращается через `Result`. Обнаруженный баг (нарушен инвариант) вызывает `panic!`: с ним на рантайме ничего не сделать `[M-PANIC-ON-BUG]`.
- Тип ошибки — свой для операции, а не один «божественный» enum на весь крейт: `fn download() -> Result<(), DownloadError>` честно говорит, что может сломаться.
- Выбор между `thiserror` и `anyhow` решает вопрос «будет ли вызывающий ветвиться по виду ошибки?», а не «библиотека или приложение» ([Luca Palmieri](https://www.lpalmieri.com/posts/error-handling-rust/)). Будет — структурированный enum (`thiserror`), не будет — непрозрачная ошибка (`anyhow`). Библиотека никогда не возвращает `anyhow::Error` из публичного API.
- `thiserror` 2.x работает в `no_std` с `default-features = false` ([релиз 2.0.0](https://github.com/dtolnay/thiserror/releases/tag/2.0.0)).
- Причину не теряйте: `#[from]` / `#[source]`, а не `map_err(|_| Error::Failed)`. Конверсию задают один раз через `impl From`, дальше работает `?`.
- Публичные enum ошибок в библиотеках помечаются `#[non_exhaustive]`.
- `.unwrap()` допустим только как документированное доказательство: `.expect("проверено в new()")`. Сообщение `panic!`/`assert!` содержит реальные значения.

### 3.5. Атрибуты и модификаторы

- `#[must_use]` на функциях, результат которых бессмысленно игнорировать (чистые вычисления, builder-методы). clippy `pedantic` подсказывает, где он нужен (`must_use_candidate`).
- `const fn` везде, где тело это позволяет: конструкторы newtype, табличные вычисления. Тогда `const { Month::new(14) }` упадёт при компиляции, а не в поле.
- `#[inline]` только по данным профилировщика или на маленьких функциях, которые пересекают границу крейта.
- `unsafe fn` означает «неопределённое поведение при неправильном вызове», а не «опасно» `[M-UNSAFE-IMPLIES-UB]`. Каждый блок `unsafe` сопровождает комментарий `// SAFETY:` с доказательством.

### 3.6. Документация функции

````rust
/// Декодирует CAN-кадр из сырого буфера.
///
/// Подробности: формат заголовка, порядок байтов, что считается
/// валидной длиной. Параметры объясняются прозой, без таблиц.
///
/// # Examples
/// ```
/// let frame = proto::decode(&[0x01, 0x02])?;
/// # Ok::<(), proto::DecodeError>(())
/// ```
///
/// # Errors
/// Возвращает [`DecodeError::Length`], если буфер короче заголовка.
///
/// # Panics
/// Не паникует.
pub fn decode(raw: &[u8]) -> Result<Frame, DecodeError> { /* ... */ }
````

Первая строка — не длиннее примерно 15 слов: она попадает в индекс модуля `[M-FIRST-DOC-SENTENCE]`. Doc-тесты — настоящие тесты, в них используется `?`, а не `unwrap()` `[C-QUESTION-MARK]`. Каждое «магическое» число становится именованной `const` с комментарием, почему именно это значение и что сломается при его изменении `[M-DOCUMENTED-MAGIC]`.

## 4. Объекты: как строить типы и где их держать

Тип строится так, чтобы недопустимое состояние нельзя было выразить: поля приватные, инвариант проверяется один раз в конструкторе, а состояние кодируется enum или типом-параметром, а не набором `Option` и `bool`.

### 4.1. «Parse, don't validate» и newtype

Сырые данные превращаются в тип, доказывающий инвариант, один раз на границе. Дальше код полагается на тип и не перепроверяет ([Rustfinity](https://rustfinity.com/blog/parse-dont-validate)).

```rust
/// Идентификатор узла CANopen, 1..=127.
#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
pub struct NodeId(u8);                       // поле приватное

impl NodeId {
    pub const fn new(v: u8) -> Self {        // паникует; годится в const {}
        assert!(v >= 1 && v <= 127, "node id out of range");
        Self(v)
    }
    pub const fn get(self) -> u8 { self.0 }
}

impl TryFrom<u8> for NodeId {               // fallible — без infallible From
    type Error = NodeIdError;
    fn try_from(v: u8) -> Result<Self, Self::Error> { /* ... */ }
}
```

Правила newtype с инвариантом `[C-NEWTYPE]`, `[M-STRONG-TYPES-GUARD]`: приватное поле, хотя бы один fallible-конструктор, конверсия из «слабого» типа только через `TryFrom`/`FromStr`. Newtype с публичным полем бесполезен: каждый вызывающий снова проверяет диапазон. Убирайте «одержимость примитивами»: `Celsius(f32)`, `NodeId(u8)`, `Millis(u32)`.

### 4.2. Struct, enum, typestate

| Ситуация | Форма |
| --- | --- |
| Структура с пятью `Option`, из которых валидны три комбинации | `enum` с вариантами-комбинациями |
| Состояние меняется на рантайме | `enum` + `match` |
| Операция допустима только в определённой конфигурации | typestate: `Uart<Disabled>` → `Uart<Enabled>`, переход поглощает `self` |
| Набор флагов | `bitflags` или `enumflags2`, не пачка `bool` `[C-BITFLAG]` |
| Ресурс надо освободить | RAII-guard + `Drop` |

Typestate кодирует состояние объекта в его типе, а значит, ошибка использования становится ошибкой компиляции ([Cliffle](https://cliffle.com/blog/rust-typestate/)). Маркеры состояний — типы нулевого размера, поэтому накладных расходов нет. Трейт-ограничение на состояние делается «запечатанным» (sealed), чтобы снаружи нельзя было добавить своё состояние.

### 4.3. Конструирование

- Конструктор — inherent-метод `Foo::new()`, даже если есть `Default` `[C-CTOR]`.
- Один-два необязательных параметра: методы `with_a()`, `with_b()`.
- Четыре и больше вариантов конструирования: builder `[M-INIT-BUILDER]`. Он называется `FooBuilder`, создаётся через `Foo::builder(обязательные)`, сеттеры `x(..)` без `set_`, валидация в `.build() -> Result<Foo, E>`, а не в сеттерах.
- Набирает популярность крейт [`bon`](https://github.com/elastio/bon) (v3.x): генерирует builder с typestate, где `.build()` не существует, пока не заданы все обязательные поля. Работает в `no_std` при `default-features = false`.

### 4.4. Трейты

- Трейты узкие: `LoadObject` и `StoreObject` вместо одного `IDatabase` с двадцатью методами. Объединение — через супертрейт.
- Основная функциональность делается inherent-методом, а реализация трейта перенаправляет к нему `[M-ESSENTIAL-FN-INHERENT]`. Иначе пользователь гадает, какой трейт импортировать.
- Трейт, который пользователи не должны реализовывать, запечатывается приватным супертрейтом `[C-SEALED]`.
- «Лестница абстракции» `[M-DI-HIERARCHY]`: конкретный тип → дженерик / `impl Trait` → `enum` известных реализаций → `dyn Trait` за собственным newtype. Подниматься только под давлением. Если вторая реализация нужна лишь для тестов, это скорее `enum { Native, Mocked }`, чем трейт.
- `async fn` в трейтах работает с Rust 1.75, но такие трейты по-прежнему не dyn-совместимы; дженерики предпочтительнее, `dyn` нужен лишь для смены реализации на рантайме или смешанных коллекций ([corrode.dev](https://corrode.dev/blog/dyn-compatibility/)).

### 4.5. Derive и стандартные трейты

- `Debug` на всём публичном, обязательно `[C-COMMON-TRAITS]`. Затем `Clone`, `Copy`, `PartialEq`, `Eq`, `Hash`, `Ord`, `Default` там, где это семантически верно. `Display` на всём, что читает человек.
- В embedded добавляйте `defmt::Format`, но за фичей, чтобы крейт оставался пригодным для любого логгера.
- Ограничения дженериков не пишутся в определении структуры (`struct Foo<T: Clone>`), а только на `impl` `[C-STRUCT-BOUNDS]`.
- `Deref` реализуют только умные указатели, это не наследование `[C-DEREF]`.

### 4.6. Где располагать объекты

- Тип живёт в модуле своей предметной области, рядом со всеми своими `impl`. Отдельный файл `types.rs` для «всех типов» — анти-паттерн.
- Доменные типы (newtype, сущности, ошибки операций) лежат в доменном крейте и не зависят от сериализации, железа и рантайма. Никаких `serde`-derive на доменных типах: десериализация обойдёт проверяющий конструктор ([howtocodeit](https://www.howtocodeit.com/articles/master-hexagonal-architecture-rust)).
- Типы для провода (DTO, кадры протокола) лежат в отдельном крейте `proto` и переводятся в доменные через `TryFrom` на границе.
- В публичных сигнатурах нет `Arc<Mutex<T>>`, `Rc<RefCell<T>>`, `Box<T>` `[M-AVOID-WRAPPERS]`: это деталь реализации, которая заражает пользователей.
- Без имён-«пустышек»: `Manager`, `Service`, `Factory`, `Helper`, `Handler`, `Data`, `Info` `[M-WEASEL-WORDS]`. Тип, хранящий бронирования, — `Bookings`; отправляющий их — `BookingDispatcher`.

## 5. Архитектура приложения

Домен не знает о железе, часах и сети; порты — это трейты, которые домен объявляет; адаптеры реализуют порты для конкретной платформы. В репозитории с прошивкой это превращается в два вложенных workspace: хостовый корень с `no_std`-логикой и кросс-компилируемый `device/`.

&#91;embedded content: зависимости крейтов · прошивка, общие no\_std крейты, хост\]

Стрелки идут только вниз и вверх к `crates/`: прошивка и хостовые утилиты зависят от общей логики, а логика не зависит ни от кого из них. Поэтому её можно тестировать на ПК.

### 5.1. Гексагональная архитектура (ports & adapters) в Rust

По статье [howtocodeit: Master hexagonal architecture in Rust](https://www.howtocodeit.com/articles/master-hexagonal-architecture-rust) и [Alexis Lozano](https://alexis-lozano.com/hexagonal-architecture-in-rust-1/):

| Слой | Что содержит | Чего нет |
| --- | --- | --- |
| `domain` | Модели (newtype с проверкой), бизнес-правила, ошибки операций (`CreateAuthorError`) | I/O, serde, HAL, рантайм |
| порты (`domain::ports`) | Трейты, которые объявляет домен: исходящие (`Repository`, `Sensor`, `Transport`) и входящий API сервиса | Реализаций |
| `inbound` адаптеры | Принимают внешние события (HTTP, CAN, UART-команды) и вызывают сервис | Бизнес-логики |
| `outbound` адаптеры | Реализуют порты через сторонние библиотеки или железо, переводят их ошибки в доменные | Решений |
| `main` / `app` | Выбирает адаптеры, собирает сервис, запускает | Логики |

Ключевые решения из источников:

- Порты — дженерики, а не `dyn`: `Service<R: Repository>`. Это бесплатно и работает в `no_std` без кучи.
- Адаптер выставляет только то, что нужно приложению, и прячет сторонний API. Коды ошибок SQL или HAL не выходят за адаптер.
- Модели запроса и сохранённые сущности — разные типы.
- Имена слоёв не догма, но выбранную конвенцию надо задокументировать.

### 5.2. Sans-IO: сердцевина домена

Протокольный и управляющий код пишется как чистый конечный автомат, который не делает ввод-вывод и не читает часы ([firezone: sans-IO](https://www.firezone.dev/blog/sans-io), 2024). Внешний цикл событий делает I/O и «крутит ручку»:

```rust
impl Node {
    pub fn handle_input(&mut self, frame: Frame, now: Instant);
    pub fn handle_timeout(&mut self, now: Instant);
    pub fn poll_transmit(&mut self) -> Option<Frame>;
    pub fn poll_timeout(&self) -> Option<Instant>;
}
```

Так устроены `quinn-proto` (QUIC без сетевого кода и без системного времени, [docs.rs](https://docs.rs/quinn-proto/latest/quinn_proto/)) и `rustls` (не делает сетевой I/O, [docs.rs](https://docs.rs/rustls/latest/rustls/)). Выигрыш: тесты идут с мгновенным временем и пакетами в памяти; один автомат работает в sync, async и `no_std`; вместо `Arc<Mutex>` и каналов — `&mut self`. Цена: автомат пишется вручную, а в цикле событий легко ошибиться (например, зациклиться, если `poll_timeout` не двигается).

В терминах гексагона sans-IO-автомат и есть домен, а цикл Embassy-задачи — входящий и исходящий адаптер одновременно.

### 5.3. Совмещение embedded и host крейтов

Один вызов cargo собирает под одну целевую платформу, поэтому прошивка и хостовый код не живут в одном workspace. Решение Ferrous Systems — два вложенных workspace, внутренний настроен на кросс-компиляцию ([Testing an embedded application](https://ferrous-systems.com/blog/test-embedded-app/)):

```text
Cargo.toml                 # корневой workspace — хост; build.target НЕ задан
.cargo/config.toml         # alias xtask; без build.target
crates/
  logic/                   # #![cfg_attr(not(test), no_std)] — домен, автоматы, порты-трейты
  proto/                   # форматы на проводе, общие для хоста и прошивки
  drivers/<dev>/           # драйверы, generic над embedded-hal(-async)
host-tools/                # симулятор, декодер логов, конфигуратор (std)
host-target-tests/         # std-тесты, общающиеся с прошитым устройством
xtask/                     # оркестрация сборок и тестов
device/                    # ВНУТРЕННИЙ workspace — только кросс-компиляция
  Cargo.toml
  .cargo/config.toml       # build.target = thumbv7em-none-eabihf, runner = probe-rs
  bsp/                     # часы, пины, периферия, Board::init() -> Result<Board, _>
  app/                     # Embassy main: задачи, каналы, связывание — без логики
  self-tests/              # тесты на железе (embedded-test)
```

Правила, без которых раскладка не работает:

1. Корневой `.cargo/config.toml` не задаёт `build.target`, иначе хостовые тесты начнут кросс-компилироваться.
2. `logic`, `proto`, `drivers` лежат в корне и пишутся с `#![cfg_attr(not(test), no_std)]`: в тестах на хосте доступен `std`, `dbg!`, `proptest`. Std-only тестовые крейты подключаются только в `[dev-dependencies]`.
3. Для крейтов, которым нужен `std` вне тестов, используйте фичу `std` и `#![cfg_attr(not(feature = "std"), no_std)]`. Добавьте в CI сборку под `no_std`-цель, например `thumbv6m-none-eabi`, иначе `std` незаметно просочится ([Effective Rust](https://effective-rust.com/no-std.html)).
4. `device/` подключает общие крейты по пути `../crates/logic`. У двух workspace свои `Cargo.lock` и `target/` — это нормально. Блок `[workspace.lints]` придётся продублировать в `device/Cargo.toml`.
5. rust-analyzer получает оба корня, корневой первым: `"rust-analyzer.linkedProjects": ["Cargo.toml", "device/Cargo.toml"]`.
6. Единая точка входа — [`cargo xtask`](https://github.com/matklad/cargo-xtask): алиас `xtask = "run --package xtask --"` и команды `cargo xtask test host`, `test target`, `test host-target`. Сам репозиторий xtask оговаривает, что это не официально рекомендуемый процесс, а соглашение сообщества.

### 5.4. Распределение ответственности в прошивке

| Крейт | Отвечает за | Запрещено |
| --- | --- | --- |
| `logic` | Решения, автоматы, вычисления, порты-трейты | Зависеть от `embassy-stm32`, читать время, трогать железо |
| `drivers` | Внешние микросхемы через `embedded-hal` / `embedded-hal-async` | Зависеть от конкретного HAL |
| `bsp` | Тактирование, мультиплексирование пинов, создание периферии и драйверов, `Board::init() -> Result` | Создавать каналы и задачи, паниковать при инициализации |
| `app` | `StaticCell`, каналы, порождение задач, связь `Board` с задачами, политика деградации | Бизнес-логику в теле задачи |

- Драйверы generic над трейтами [embedded-hal 1.0](https://blog.rust-embedded.org/embedded-hal-v1/) (январь 2024). Трейты стабильны, версия 2.0 не планируется; `embedded-hal-async` работает без кучи с Rust 1.75. Это и есть порты на уровне драйверов.
- Структура `Board` нужна, чтобы `self-tests` поднимали то же железо без приложения. Если инициализация живёт в `app`, тесты её копируют, и копии расходятся.
- `app` не называет типы `embassy_stm32`: он видит только поля `board.can`, `board.imu`.
- `#[embassy_executor::task]` не может быть дженериком и не принимает не-`'static` ссылки. Поэтому в задачу передаются конкретные типы или группа ресурсов из `bsp`, а каналы — как `&'static` из `StaticCell`.
- Один владелец на периферию: перемещение значения и есть взаимоисключение. Двум задачам нужна одна периферия — одна владеет, другая шлёт сообщения, или `embassy_sync::mutex::Mutex`.
- Без `static mut`; без аллокатора «чтобы был `Vec`»: коллекции `heapless` с документированной ёмкостью.

Для вашей пары STM32H723ZE + STM32G483 это даёт два крейта приложений (`device/app-h7`, `device/app-g4`) и два BSP поверх общих `logic`, `proto` (CAN/CANopen-кадры, RS-485-протокол) и `drivers`. Общая логика тестируется один раз на хосте.

## 6. Вычисления и декомпозиция кода

Вычисление — чистая функция над типами с единицами измерения, без I/O и без скрытого состояния. Код декомпозируется по данным и предметной области, а не по техническим слоям вроде `utils`.

### 6.1. Как писать вычисления

- **Чистые функции.** Вход — значения, выход — значение. Всё недетерминированное (время, случайность, АЦП) передаётся параметром. Такая функция тестируется таблицей входов и свойствами (раздел 7).
- **Единицы в типах.** `Celsius(f32)`, `Millivolts(i32)`, `Hertz(u32)` вместо голых чисел. Сложение вольт с герцами перестаёт компилироваться.
- **Переполнение — явное решение.** Выберите `checked_*`, `saturating_*`, `wrapping_*` или `overflowing_*` по смыслу. Арифметика по умолчанию паникует в debug и тихо переполняется в release, поэтому на ней не полагайтесь. Для счётчиков с намеренным переполнением есть `core::num::Wrapping`.
- **Приведения без `as`.** `as` молча обрезает и меняет знак. Используйте `From`/`TryFrom` (`u16::try_from(x)?`, `i32::from(x)`). Линты `clippy::cast_possible_truncation`, `cast_sign_loss`, `cast_lossless` (группа `pedantic`) находят опасные места.
- **Фиксированная точка** на МК без FPU или для детерминизма: крейт [`fixed`](https://docs.rs/fixed) (`I16F16` и т. п.) вместо самописных сдвигов. На H7 и G4 есть FPU, поэтому `f32` там дёшев, но точность и порядок операций всё равно фиксируйте тестами.
- **Константы и таблицы — во время компиляции.** `const fn` и `const`-блоки для коэффициентов фильтров, таблиц CRC, синусов. Ошибка в таблице становится ошибкой сборки.
- **Итераторы вместо ручных циклов с индексами.** `iter().zip().map().sum()` убирает проверки границ и читается как формула. Для окон фильтра есть `windows()` и `chunks_exact()`.
- **Без аллокаций на горячем пути.** Пишите в буфер вызывающего (`fn filter_into(&mut self, input: &[f32], out: &mut [f32])`), а не возвращайте `Vec`.
- **Магические числа** — именованные `const` с комментарием о происхождении (раздел 3.6).

### 6.2. Как декомпозировать код

| Сигнал | Действие |
| --- | --- |
| Функции нужен комментарий-заголовок раздела | Разбить на две функции |
| Нужен `&mut` на два поля одной структуры одновременно | Разбить структуру, заимствовать поля, а не `self` |
| `.clone()` только чтобы успокоить borrow checker | Сузить область заимствования, `mem::take` / `mem::replace` / `Option::take` |
| Вычисление смешано с чтением регистров | Вынести вычисление в `logic`, передавать отсчёты параметром |
| Бизнес-логика в теле Embassy-задачи | Перенести в автомат `handle(event, now) -> actions`; задача только крутит цикл |
| Модуль разросся, нужен и прошивке, и хосту | Вынести в отдельный крейт (раздел 2.3) |
| Дженерик раздувает код (мономорфизация) | Тонкая дженерик-обёртка над нединамической внутренней функцией |
| Нужно расширить чужой тип | Extension-трейт |
| Вставить-или-создать в словаре | `entry()` API |

### 6.3. Конечные автоматы

Управляющая логика (режимы узла, протокол обмена, обработка отказов) — это `enum` состояний и `match` по паре (состояние, событие). Для иерархических автоматов есть крейты вроде [`statig`](https://github.com/mdeloof/statig). Автомат не владеет периферией и не ждёт `.await`: он возвращает действия, а задача их выполняет. Так автомат проверяется на хосте последовательностями событий.

### 6.4. Чего избегать

1. `.clone()` ради borrow checker.
2. `Deref` как наследование.
3. Перенос структуры из C#/Java один к одному: `IFooService` → трейт → `Arc<dyn>` `[M-RUST-SHAPED]`.
4. Макросы там, где справился бы язык: макрос — последнее средство `[M-MACRO-LAST-RESORT]`.
5. Изменяемые `static` и `thread_local` в библиотеках: две версии крейта в графе дадут две копии статика `[M-AVOID-STATICS]`.
6. Блокирующая задержка или busy-wait внутри async-задачи: она останавливает весь исполнитель.

## 7. Тестирование: виды и этапы

Для проекта с прошивкой тестирование идёт в пять этапов: статические проверки, хостовые тесты логики, хостовые тесты драйверов на моках, тесты на железе и сквозные тесты host-target. Основная масса тестов — хостовые: если логику нельзя проверить без платы, это ошибка архитектуры, а не тестов.

### 7.1. Этапы

| # | Этап | Где и чем | Что ловит |
| --- | --- | --- | --- |
| 0 | Статика | `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo doc`, сборка под `no_std`-цель | Стиль, типовые ошибки, утечку `std` |
| 1 | Unit-тесты логики | `#[cfg(test)] mod tests` в `crates/logic`, на хосте | Ошибки вычислений и автоматов |
| 2 | Интеграционные и property-тесты | `tests/` крейта, `proptest`, `rstest`, `insta` | Ошибки публичного API, граничные случаи, round-trip кодеков |
| 3 | Драйверы на моках | [`embedded-hal-mock`](https://docs.rs/embedded-hal-mock/) (v0.11, модуль `eh1`; async за фичей `embedded-hal-async`) | Неверные транзакции по I²C/SPI |
| 4 | Тесты на железе | `device/self-tests` + [`embedded-test`](https://github.com/probe-rs/embedded-test) через `probe-rs run` | Отсутствующий подтягивающий резистор, эррата кремния, другой WHO\_AM\_I |
| 5 | Host-target (сквозные) | `host-target-tests`: std-тесты на ПК говорят с прошитым устройством по UART/USB/CAN | Поведение системы целиком |

Этапы 0–3 идут на каждый коммит в обычном CI. Этапы 4–5 — на раннере с подключённой платой (`cargo xtask test target`, `cargo xtask test host-target`).

### 7.2. Unit, интеграционные и doc-тесты

По [Book, гл. 11.3](https://doc.rust-lang.org/book/ch11-03-test-organization.html):

- **Unit-тесты** лежат в том же файле в `#[cfg(test)] mod tests { use super::*; }`, в конце файла. Только они видят приватные функции.
- **Интеграционные тесты** лежат в `tests/`; каждый файл — отдельный крейт, видящий только публичный API. Общий код — в `tests/common/mod.rs`.
- Тесты, использующие только публичный API, Microsoft рекомендует переносить в `tests/`, а `mod tests` оставлять для приватных деталей `[M-INTEGRATION-TESTS]`: иначе файлы `src/` распухают от тестов.
- **Doc-тесты** — третья часть `cargo test`; пример в документации обязан компилироваться и проходить.
- Бинарный крейт без `lib.rs` нельзя протестировать интеграционно, поэтому `main.rs` оставляют тонким над `lib.rs`.
- Официальной конвенции имён тестов нет. Практичный вариант: имя описывает поведение, `decode_rejects_short_buffer`, а не `test_decode_2`.

### 7.3. Какими должны быть тесты

- **Проверяют свойство, а не повторяют код.** Тест, сравнивающий константу с той же константой, проходит по построению и только шумит `[M-TAUTOLOGICAL-TESTS]`.
- **Детерминированы.** Время, случайность и железо приходят параметром или через мок-адаптер порта.
- **Табличные случаи** — через [`rstest`](https://github.com/la10736/rstest) (`#[case]`, фикстуры `#[fixture]`).
- **Свойства** — через [`proptest`](https://github.com/proptest-rs/proptest): `decode(encode(x)) == x`, «никогда не паникует», монотонность. Для форматов на проводе здесь находятся настоящие баги; минимальный контрпример получается автоматически (shrinking).
- **Снимки** сложного вывода — через [`insta`](https://insta.rs/) и `cargo insta review`.
- **Порты в тестах** заменяются фейковыми адаптерами: фейковый `Transport` пишет кадры в `Vec`, фейковые часы двигаются вручную.

### 7.4. Тесты на железе

- [`embedded-test`](https://github.com/probe-rs/embedded-test) — v0.7.1 (март 2026). Даёт libtest-совместимый раннер через `probe-rs run`, сброс устройства перед каждым тестом, `#[init]` с передачей состояния, async-тесты (фичи `embassy-09` / `embassy-010` под вашу версию Embassy), `#[should_panic]`, `#[ignore]`, `#[timeout(secs)]` (по умолчанию 60 с) и запуск отдельного теста из IDE.
- `defmt-test` формально не объявлен устаревшим, но [книга defmt](https://defmt.ferrous-systems.com/) связывает его с устаревшим раннером `probe-run` и советует `embedded-test`. Для нового кода выбирайте `embedded-test`.
- `#[init]` вызывает тот же `Board::init()`, что и приложение. Один файл — один аппаратный компонент в изоляции.
- Host-target тесты используют тот же крейт `proto`, что и прошивка, — сообщения не разойдутся. Устройство одно, а `cargo test` параллелит: сериализуйте доступ мьютексом внутри конструктора соединения.

## 8. Практики, которые набирают популярность

За 2023–2026 годы сообщество перешло к централизованным линтам в `Cargo.toml`, `#[expect]` вместо `#[allow]`, редакции 2024, генерации builder-ов с typestate и проверке кода инструментами формальной верификации. Ниже — что стоит внедрить и зачем.

### 8.1. Язык и Cargo

| Практика | С какой версии | Что даёт |
| --- | --- | --- |
| Таблица `[lints]` и `[workspace.lints]` в `Cargo.toml` | Rust 1.74 (ноябрь 2023, [releases.rs](https://releases.rs/docs/1.74.0/)) | Линты задаются один раз на workspace, а не атрибутами в каждом `lib.rs` |
| `#[expect(lint, reason = "...")]` вместо `#[allow]` | Rust 1.81 (сентябрь 2024, [releases.rs](https://releases.rs/docs/1.81.0/)) | Предупреждает, когда подавление больше не нужно, — мёртвые `allow` не копятся |
| Редакция 2024 | Rust 1.85 (февраль 2025, [Edition Guide](https://doc.rust-lang.org/edition-guide/rust-2024/index.html)) | Резолвер 3 с учётом MSRV, `#[unsafe(no_mangle)]`, запрет ссылок на `static mut` |
| `async fn` в трейтах | Rust 1.75 | Async-порты без `async-trait`; для `dyn` по-прежнему нужны обходные пути |

### 8.2. Линты: рекомендуемая конфигурация

```toml
[workspace.lints.rust]
missing_debug_implementations = "warn"
unsafe_op_in_unsafe_fn        = "warn"

[workspace.lints.clippy]
pedantic = { level = "warn", priority = -1 }
# точечно из restriction — всю группу целиком не включают
undocumented_unsafe_blocks      = "warn"
allow_attributes_without_reason = "warn"
mod_module_files                = "warn"
map_err_ignore                  = "warn"
```

- По умолчанию в clippy `correctness` — deny; `suspicious`, `style`, `complexity`, `perf` — warn; `pedantic`, `nursery`, `cargo`, `restriction` выключены ([Clippy docs](https://doc.rust-lang.org/clippy/)). Группу `restriction` целиком не включают: её линты противоречат друг другу.
- `#![deny(warnings)]` в исходниках — анти-паттерн: новая версия компилятора добавит линт, и крейт перестанет собираться. Отказ по предупреждениям делается в CI через `RUSTFLAGS="-D warnings"`.

### 8.3. Инструменты цепочки поставок и CI

- [`cargo-deny`](https://github.com/EmbarkStudios/cargo-deny): лицензии, дубликаты версий, уязвимости (RustSec), разрешённые источники.
- [`cargo-hack`](https://github.com/taiki-e/cargo-hack): `--feature-powerset` проверяет, что собирается каждая комбинация фич; `--rust-version` проверяет MSRV.
- `cargo xtask` как единая точка входа вместо Makefile и shell-скриптов: работает везде, где есть cargo.

Минимальный набор шагов CI: `fmt --check` → `clippy -D warnings` → `nextest run` + `test --doc` → `doc --no-deps` → `hack --feature-powerset check` → `deny check` → сборка `device/` и контроль размера прошивки (`cargo size`).

### 8.4. Библиотеки и паттерны

- [`bon`](https://github.com/elastio/bon) (v3.x) — builder-ы с проверкой полноты при компиляции, в том числе для функций и методов; работает в `no_std`.
- [`thiserror`](https://github.com/dtolnay/thiserror/releases) 2.x — теперь и для `no_std`. Альтернатива с контекстными селекторами — [`snafu`](https://docs.rs/snafu/latest/snafu/) (0.9, тоже `no_std`).
- Typestate и «parse, don't validate» стали стандартным способом проектирования API, а не экзотикой (разделы 4.1–4.2).
- Sans-IO для протоколов (раздел 5.2): после статьи firezone 2024 года стал распространённым подходом.
- Формальная проверка входит в повседневную практику: Kani для доказательства отсутствия паник в парсерах, Miri в CI для любого `unsafe`, `cargo-mutants` для оценки качества тестов.

### 8.5. Embedded-специфика

- `embedded-hal` 1.0 стабилизировал трейты драйверов; `embedded-hal-bus` разделяет шину между устройствами. Старый `shared-bus` вытеснен.
- `embedded-test` вместо `defmt-test` для тестов на железе.
- `defmt` для логирования с почти нулевой ценой во флеше: строки формата лежат в незагружаемой секции. Уровень фильтруется при компиляции переменной `DEFMT_LOG`. `defmt-rtt` блокируется без подключённого отладчика, поэтому в изделии без пробника он не может быть единственным приёмником логов.
- `flip-link` в линкере: стек растёт прочь от статических данных, и переполнение даёт HardFault вместо тихой порчи `.bss`.
- `static_cell` вместо `static mut` для `'static`-ресурсов задач Embassy.
- На Cortex-M7 (ваш STM32H723) DMA и D-cache не согласованы аппаратно. Буферы DMA и дескрипторы Ethernet кладутся в некэшируемую область MPU — это самая частая причина отказа Ethernet через некоторое время работы.

## 9. Паттерны: что применять, когда и когда нет

Паттерн в Rust выбирают по проблеме, а не по привычке из другого языка: многие классические паттерны здесь сводятся к трейту, enum или типу. Начинайте с таблицы выбора 9.1, затем смотрите карточку паттерна. Названия даны так, как они озаглавлены в книге [Rust Design Patterns](https://rust-unofficial.github.io/patterns/) (далее RDP).

### 9.1. Таблица выбора: ситуация → паттерн

| Ситуация | Паттерн | Раздел |
| --- | --- | --- |
| Примитив с единицами или инвариантом | Newtype | 9.4 |
| Много необязательных параметров конструктора (4+ комбинаций) | Builder | 9.3 |
| Операции допустимы только в определённом порядке или конфигурации | Typestate | 9.5 |
| Состояние меняется на рантайме | `enum` + `match`, конечный автомат | 6.3 |
| Ресурс надо освободить на любом пути выхода | RAII Guard / Finalisation in Destructors | 9.4 |
| Нужен `&mut` к двум полям одновременно | Compose Structs | 9.3 |
| Забрать значение из-под `&mut` без `clone` | `mem::take` / `mem::replace` | 9.2 |
| Поведение подменяется (формат, транспорт, бэкенд) | Strategy = трейт + дженерик | 9.4 |
| Действие нужно отложить, поставить в очередь, отменить | Command | 9.4 |
| Несколько алгоритмов над одним деревом данных | Visitor; преобразование дерева — Fold | 9.4 |
| Добавить методы чужому типу | Extension trait | 9.3 |

| Граф или сущности без ясного владельца | Арена с индексами-newtype | 9.6 |

| Периферия нужна нескольким задачам | Актор (владелец + канал) или `Mutex` | 9.7 |

| Данные между прерыванием и задачей | `critical_section::Mutex`, атомики | 9.7 |

### 9.2. Идиомы

| Идиома (RDP) | Что | Когда | Когда нет / подвох |
| --- | --- | --- | --- |
| [Use borrowed types for arguments](https://rust-unofficial.github.io/patterns/idioms/coercion-arguments.html) | Принимать `&str`, `&[T]`, `&T` | Функция только читает | Нужно владение — принимайте по значению |
| [The Default Trait](https://rust-unofficial.github.io/patterns/idioms/default.html) | `#[derive(Default)]`, `..Default::default()` | Конфигурации, `unwrap_or_default` | У поля нет разумного значения по умолчанию — конструктор или builder |
| [mem::take / mem::replace](https://rust-unofficial.github.io/patterns/idioms/mem-replace.html) | Забрать значение, оставив заглушку | Смена варианта enum без `clone` | Для `Option` проще `Option::take()` |
| [Finalisation in Destructors](https://rust-unofficial.github.io/patterns/idioms/dtor-finally.html) | Guard с `Drop` вместо `finally` | Много путей выхода: `?`, ранний `return` | `Drop` не гарантирован (abort, вечный цикл); `let _ = guard` уничтожает guard сразу, нужно `let _guard` |
| [Temporary mutability](https://rust-unofficial.github.io/patterns/idioms/temporary-mutability.html) | Подготовить мутабельно, затем `let data = data;` | «Отсортировать и дальше только читать» | — |
| [Return consumed arg on error](https://rust-unofficial.github.io/patterns/idioms/return-consumed-arg-on-error.html) | Вернуть переданный аргумент внутри `Err` | Вызывающий повторит попытку без копии (буфер, кадр) | Тип ошибки усложняется |
| [Privacy For Extensibility](https://rust-unofficial.github.io/patterns/idioms/priv-extend.html) | `#[non_exhaustive]` | Публичные типы, которые будут расти | Клиенты обязаны писать `_ =>`; RDP советует применять экономно |
| [On-Stack Dynamic Dispatch](https://rust-unofficial.github.io/patterns/idioms/on-stack-dyn-dispatch.html) | `let r: &mut dyn Read = if .. { &mut a } else { &mut b };` | `dyn` без кучи и без мономорфизации — удобно в `no_std` | — |
| [Iterating over an Option](https://rust-unofficial.github.io/patterns/idioms/option-iter.html) | `Option` — итератор: `v.extend(opt)` | Склейка итераторов | Для одного значения — `if let` или `iter::once` |
| [Pass Variables to Closure](https://rust-unofficial.github.io/patterns/idioms/pass-var-to-closure.html) | Блок с перепривязкой перед `move` | Выборочно клонировать или заимствовать захваты | Лишний уровень отступа |
| Комбинаторы `Option`/`Result` ([Effective Rust](https://effective-rust.com/transform.html)) | `map`, `and_then`, `ok_or`, `?` вместо `match` | Почти всегда, стоят столько же, сколько `match` | Сложная логика читается лучше явным `match` |
| [Entry API](https://doc.rust-lang.org/std/collections/hash_map/enum.Entry.html) | `map.entry(k).or_insert(v)` | «Вставить или обновить» за один поиск | — |

### 9.3. Создающие и структурные паттерны

**Builder.** Отдельный тип `FooBuilder` + `build() -> Result<Foo, E>` ([RDP](https://rust-unofficial.github.io/patterns/patterns/creational/builder.html), [Effective Rust](https://effective-rust.com/builders.html)).

- Когда: от 4 вариантов инициализации `[M-INIT-BUILDER]`, много необязательных полей, валидация между полями.
- Когда нет: 1–2 необязательных параметра — хватит `with_x()`; простая структура — хватит `new()`.
- Форма: API Guidelines предпочитают сеттеры `&mut self`, а `self` по значению — только когда результату нужно владение конфигурацией ([C-BUILDER](https://rust-lang.github.io/api-guidelines/type-safety.html)). По значению неудобно при условных шагах (приходится переприсваивать).
- [`bon`](https://bon-rs.com/guide/overview) проверяет при компиляции, что заданы все обязательные поля и ни одно не задано дважды. Генерирует builder и для функций: `#[builder] fn ..` и затем `.call()`.

**Compose Structs** ([RDP](https://rust-unofficial.github.io/patterns/patterns/structural/compose-structs.html)). Большая структура делится на подструктуры, чтобы заимствовать поля независимо.

- Когда: компилятор пишет, что весь `self` уже заимствован.
- Подвох: если подструктура получается бессмысленной абстракцией, ошибка в самом дизайне.

**Contain unsafety in small modules** ([RDP](https://rust-unofficial.github.io/patterns/patterns/structural/unsafe-mods.html)). Весь `unsafe` — в минимальном модуле, наружу торчит безопасный фасад. Граница модуля и есть граница корректности. В прошивке это крейт `hal_ext` или модуль MPU/DMA, а не блоки `unsafe` по всем задачам.

**Sealed trait** ([C-SEALED](https://rust-lang.github.io/api-guidelines/future-proofing.html)). `pub trait State: private::Sealed {}`.

- Когда: трейт реализуется только в вашем крейте — состояния typestate, режимы пинов; методы можно добавлять без поломки совместимости.
- Подвох: пользователь не может добавить свою реализацию даже законно; явно напишите в документации, что трейт запечатан.

**Extension trait** ([RFC 445](https://rust-lang.github.io/rfcs/0445-extension-trait-conventions.html)). `trait FrameExt { .. } impl FrameExt for [u8] { .. }`.

- Когда: методы для чужого типа; отделить dyn-совместимое ядро трейта от дженерик-методов.
- Когда нет: свой тип — пишите inherent-методы; свой трейт — default-методы. Каждое расширение требует лишнего `use`.

**Avoid complex type bounds with custom traits** ([RDP](https://rust-unofficial.github.io/patterns/patterns/structural/trait-for-bounds.html)). Громоздкое `F: FnMut() -> Result<T, E>` заменяется своим трейтом с blanket-реализацией. Подвох: читателю не очевидно, что обычное замыкание подходит.

**Prefer Small Crates** ([RDP](https://rust-unofficial.github.io/patterns/patterns/structural/small-crates.html)) — см. раздел 2.3.

### 9.4. Поведенческие паттерны

| Паттерн | Что | Когда | Когда нет / подвох |
| --- | --- | --- | --- |
| [Newtype](https://rust-unofficial.github.io/patterns/patterns/behavioural/newtype.html) | `struct Millivolts(i32)` | Единицы, валидация, скрытие реализации, обход orphan rule, замена `bool` | Трейты внутреннего типа не наследуются — нужны derive или [`derive_more`](https://docs.rs/derive_more) |
| [RAII Guards](https://rust-unofficial.github.io/patterns/patterns/behavioural/RAII.html) | Guard владеет доступом, `Drop` освобождает | Блокировки, CS-пин, режим питания, FFI-ресурсы | `Drop` не возвращает ошибку — нужен отдельный `release() -> Result` |
| [Strategy](https://rust-unofficial.github.io/patterns/patterns/behavioural/strategy.html) | Алгоритм за трейтом | Набор реализаций заранее неизвестен (транспорт CAN/RS-485/UART) | Начинайте с дженерика; `dyn` — для разнородных коллекций, выбора на рантайме, экономии кода ([Effective Rust, Item 12](https://effective-rust.com/generics.html)) |
| [Command](https://rust-unofficial.github.io/patterns/patterns/behavioural/command.html) | Действие как значение | Очередь команд, журнал, откат | В `no_std` лучше `enum Command { .. }`: без кучи и без `dyn` |
| [Visitor](https://rust-unofficial.github.io/patterns/patterns/behavioural/visitor.html) | `visit_*` по разнородному дереву, обход в `walk_*` | Несколько алгоритмов над AST, конфигурацией, деревом объектов | Однородные данные — обычный итератор |
| [Fold](https://rust-unofficial.github.io/patterns/patterns/creational/fold.html) | Обход, строящий новое дерево | Преобразование AST → AST | Простые случаи — `Iterator::map` |
| [Interpreter](https://rust-unofficial.github.io/patterns/patterns/behavioural/interpreter.html) | Маленький DSL или `macro_rules!` | Скрипты команд, формулы калибровки | Макрос может вычислить аргумент дважды |

В Rust отдельного «паттерна Strategy» почти нет: трейт и есть стратегия. Порядок выбора — лестница из раздела 4.4: конкретный тип → дженерик → `enum` известных вариантов → `dyn` за своим newtype. Для прошивки `enum` часто лучше трейта: набор транспортов известен при сборке, `match` дешёв, куча не нужна.

### 9.5. Паттерны на уровне типов

**Typestate** ([Cliffle](https://cliffle.com/blog/rust-typestate/), [Embedded Book](https://docs.rust-embedded.org/book/static-guarantees/design-contracts.html)).

```rust
pub struct Adc<S> { regs: AdcRegs, _s: PhantomData<S> }
pub struct Off; pub struct Calibrated;

impl Adc<Off> {
    pub fn calibrate(self) -> Adc<Calibrated> { /* ... */ }
}
impl Adc<Calibrated> {
    pub fn read(&mut self, ch: Channel) -> u16 { /* ... */ }   // у Adc<Off> метода нет
}
```

- Когда: обязательный порядок «инициализировать → настроить → работать»; конфигурация известна при сборке.
- Когда нет: состояние выбирается на рантайме, объекты в разных состояниях лежат в одном массиве, переходы в цикле — тогда `enum`. Параметры типа расползаются по дженерикам. Трейт состояний запечатайте.

**Generics as Type Classes** ([RDP](https://rust-unofficial.github.io/patterns/functional/generics-type-classes.html)). `Req<P: ProtoKind>` и `impl Req<Nfs> { .. }` — методы, доступные только для одного варианта. Когда: варианты отличаются API. Если отличается только поведение — это Strategy. Подвох: рост бинарника из-за мономорфизации.

**PhantomData-маркеры** ([std](https://doc.rust-lang.org/std/marker/struct.PhantomData.html)). Тип нулевого размера для неиспользуемого параметра: маркеры состояний, типизированные хэндлы (`Handle<Uart>` против `Handle<Spi>`). Учтите, что `Send`/`Sync` наследуются от `T` в `PhantomData<T>`.

**Const generics** ([Reference](https://doc.rust-lang.org/reference/items/generics.html)). `struct Ring<T, const N: usize>([T; N])` — ёмкость в типе, без кучи; так устроен `heapless`. Ограничение: выражение вроде `{N + 1}` в позиции типа на стабильном Rust нельзя.

### 9.6. Данные и владение

**Арена с индексами вместо ссылок.** Узлы хранятся в коллекции, связи — индексами-newtype. [`slotmap`](https://docs.rs/slotmap/latest/slotmap/) даёт ключи с поколением (защита от ABA), а `new_key_type!` — отдельный тип ключа на каждую карту.

- Когда: граф, дерево с обратными ссылками, сущности без ясного владельца — вместо `Rc<RefCell<..>>`.
- Подвох: ключ чужой карты на рантайме не ловится, если не завести отдельный тип ключа. `slotmap` требует `alloc`; в `no_std` без кучи то же делается на `heapless::Vec` + свой `struct NodeIdx(u8)`.

**Внутренняя изменяемость** ([std::cell](https://doc.rust-lang.org/std/cell/index.html)). Сначала `&mut`; ячейки — последнее средство.

| Нужно | Брать |
| --- | --- |
| Маленькое `Copy`-значение, один поток | `Cell<T>` — без паник |
| Не-`Copy`, один поток | `RefCell<T>` — паникует при конфликте, есть `try_borrow` |
| Ленивая однократная инициализация | `OnceCell` / `LazyCell`; между потоками `OnceLock` / `LazyLock` |
| Между потоками | `Mutex`, `RwLock`, атомики |
| Между прерыванием и задачей в `no_std` | раздел 9.7 |

### 9.7. Embedded-паттерны

**Singleton периферии** ([Embedded Book](https://docs.rust-embedded.org/book/peripherals/singletons.html)). Периферия забирается один раз через `take()`, повторный вызов паникует; в Embassy это `embassy_stm32::init()`. Владение заменяет `static mut`: компилятор не даст использовать пин дважды. Анти-паттерн: `Peripherals::steal()` в задаче — он отменяет эту гарантию.

**Чек-лист HAL** ([Embedded Book](https://docs.rust-embedded.org/book/design-patterns/hal/checklist.html)):

- `free()` возвращает сырую периферию `[C-FREE]`;
- конструкторы, а не extension-трейты `[C-CTOR]`;
- пины — типы нулевого размера `[C-ZST-PIN]`; стёртый пин хранит номер на рантайме, его можно класть в массивы ценой проверок при компиляции `[C-ERASED-PIN]`;
- состояние пина — параметр типа с запечатанным трейтом `[C-PIN-STATE]`.

**Драйвер микросхемы.** Дженерик над трейтами [embedded-hal 1.0](https://docs.rs/embedded-hal/latest/embedded_hal/), метод `release()` возвращает шину, ошибка параметризована ошибкой шины: `enum Error<E> { Bus(E), Crc }`. Если у микросхемы есть CS, драйвер берёт `SpiDevice` и сам CS не трогает; `SpiBus` — только без CS (WS2812, 1-wire), такую шину безопасно не разделить ([embedded-hal spi](https://docs.rs/embedded-hal/latest/embedded_hal/spi/index.html)). Карты регистров генерируются ([`device-driver`](https://docs.rs/device-driver/latest/device_driver/)), а не пишутся вручную.

**Общая шина.** `embassy_embedded_hal::shared_bus::asynch::i2c::I2cDevice::new(&BUS_MUTEX)` даёт каждому драйверу свою «шину», транзакция `write_read` не прерывается чужой ([docs.rs](https://docs.rs/embassy-embedded-hal/latest/embassy_embedded_hal/shared_bus/index.html)). Для блокирующего кода — `embedded-hal-bus`.

**Периферия нужна нескольким задачам** ([Embassy Book](https://embassy.dev/book/)):

| Подход | Когда | Подвох |
| --- | --- | --- |
| Актор: одна задача владеет периферией, остальные шлют сообщения в `Channel` | Операции длинные, нужна очередь, разделение ответственности | Ответ требует обратного канала или `Signal`; цикл ограниченных каналов может зависнуть ([Alice Ryhl, Actors with Tokio](https://ryhl.io/blog/actors-with-tokio/)) |
| `static Mutex<_, Option<T>>` | Короткая операция, задача ждёт её завершения | Блокировка через `.await` сериализует задачи |

**Выбор примитива `embassy-sync`** ([docs.rs, 0.8](https://docs.rs/embassy-sync/latest/embassy_sync/)):

| Нужно | Примитив |
| --- | --- |
| Команды актору, каждое сообщение одному получателю | `Channel` |
| Последнее значение, промежуточные можно терять, один получатель | `Signal` |
| Последнее значение для N получателей (конфигурация, режим) | `Watch` |
| Каждое событие всем подписчикам | `PubSubChannel` (`publish_immediate` вытесняет старое, отстающий получает `Lagged`) |
| Поток байтов | `Pipe` |
| Удержание ресурса через `.await` | `mutex::Mutex` |

RawMutex: `NoopRawMutex` — один исполнитель; `ThreadModeRawMutex` — только thread mode; `CriticalSectionRawMutex` — общий с прерываниями или другим исполнителем. Берите самый слабый корректный. `'static`-ресурсы задач — через [`StaticCell`](https://docs.rs/static_cell/latest/static_cell/): повторный `init()` паникует. Разбить периферию по задачам помогает [`assign-resources`](https://docs.rs/assign-resources/latest/assign_resources/).

**Прерывание ↔ задача.** `critical_section::Mutex<RefCell<T>>` и доступ внутри `critical_section::with(|cs| ..)`; для `Copy`-данных — `Mutex<Cell<T>>`; для флагов и счётчиков — атомики без критической секции ([docs.rs](https://docs.rs/critical-section/latest/critical_section/struct.Mutex.html)). Критическая секция короткая и не содержит `.await`. Для сравнения, в RTIC v2 ресурс `#[local]` принадлежит одной задаче без блокировки, а `#[shared]` блокируется по протоколу потолка приоритетов ([RTIC Book](https://rtic.rs/2/book/en/by-example/resources.html)).

**DMA-передача как guard** ([Embedonomicon](https://docs.rust-embedded.org/embedonomicon/dma.html)). Буфер переходит во владение передачи и возвращается из `wait()`; `Drop` останавливает DMA. Буфер должен быть `'static`: `mem::forget` безопасен, поэтому полагаться на запуск деструктора для безопасности памяти нельзя. Трейты [`embedded-dma`](https://docs.rs/embedded-dma/latest/embedded_dma/) `ReadBuffer`/`WriteBuffer` формализуют это требование.

### 9.8. Async: отмена и блокировки

- **Отменобезопасность.** `select` в embassy-futures уничтожает проигравшую future ([исходник](https://docs.rs/embassy-futures/latest/src/embassy_futures/select.rs.html)). Future отменобезопасна, если её уничтожение и пересоздание ничего не теряет ([tokio](https://docs.rs/tokio/latest/tokio/macro.select.html)): `Channel::receive`, `Signal::wait` — да; «прочитать ровно N байт» или «записать всё» — нет. Частично выполненную операцию держите вне цикла или вынесите в отдельную задачу.
- **Блокировки через `.await`.** Tokio прямо предупреждает, что удержание блокировки через `.await` почти никогда не даёт корректного кода ([tokio Mutex](https://docs.rs/tokio/latest/tokio/sync/struct.Mutex.html)). Ресурс ввода-вывода отдайте отдельной задаче-актору.
- **Цикл Embassy-задачи как адаптер sans-IO-автомата** (раздел 5.2): задача ждёт событие или таймаут, передаёт его автомату, исполняет действия. Логика остаётся тестируемой на хосте.

### 9.9. Анти-паттерны

| Анти-паттерн | Почему плохо | Вместо |
| --- | --- | --- |
| [Clone to satisfy the borrow checker](https://rust-unofficial.github.io/patterns/anti_patterns/borrow_clone.html) | Копии расходятся, рождаются тонкие баги | Compose Structs, `mem::take`, сужение заимствования |
| [#\!\[deny(warnings)\]](https://rust-unofficial.github.io/patterns/anti_patterns/deny-warnings.html) | Новый компилятор ломает сборку | `RUSTFLAGS="-D warnings"` в CI |
| [Deref Polymorphism](https://rust-unofficial.github.io/patterns/anti_patterns/deref.html) | Эмуляция наследования, неожиданная для читателя | Трейты, явное делегирование |
| `Rc`/`Arc`/`RefCell` в публичном API | Навязывает пользователю детали реализации `[M-AVOID-WRAPPERS]` | `&T`, `&mut T`, `T` |
| `static mut`, `Peripherals::steal()` | Отключают проверку владения | `StaticCell`, передача владения, singleton |
| `IFooService` → трейт → `Arc<dyn>` по привычке из Java/C# | Лишняя косвенность и куча | Лестница абстракции (4.4) |

## Чеклист перед ревью

- [ ] Модуль назван по домену, начинается с `//!`, тесты в конце файла
- [ ] Подмодули в стиле `foo.rs` + `foo/`, без `mod.rs`
- [ ] Видимость минимальная, нет glob-ре-экспортов и `prelude`
- [ ] Публичные структуры с приватными полями, инварианты в fallible-конструкторах
- [ ] Нет `bool`-параметров со скрытым смыслом и наборов `Option` вместо enum
- [ ] Ошибки своего типа на операцию, причина сохранена через `#[from]`/`#[source]`
- [ ] Публичные функции документированы: резюме, `# Errors`, `# Panics`, `# Safety`
- [ ] Каждое магическое число — именованная `const` с объяснением
- [ ] Логика не читает время, не трогает железо и сеть; тестируется на хосте
- [ ] `logic` не зависит от `embassy-stm32`; драйверы generic над `embedded-hal`
- [ ] Нет `static mut`, нет `#[allow]` без причины, у каждого `unsafe` есть `// SAFETY:`
- [ ] Тесты проверяют свойства; round-trip кодеков покрыт `proptest`
- [ ] CI: fmt, clippy `-D warnings`, nextest + doc-тесты, cargo-deny, сборка под `no_std`
