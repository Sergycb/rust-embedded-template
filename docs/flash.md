## Стёртый флеш: 0xFF, но не везде

`embassy-boot` отличает стёртую память от записанной сравнением с зашитой
константой и переключает её фичей `flash-erase-zero`. У подавляющего
большинства семейств стёртая страница читается `0xFF`, а у 188 чипов каскада
— `0x00` (их NVM стирается в ноль). Признак `erase_zero` приходит из
метаданных полем `MEMORY_LAYOUT`, и по нему включается фича.

Что здесь нельзя нарушать:

- **Признак берётся из `erase_value`, а НЕ выводится из имени чипа.** Раньше
  хук считал его как `starts_with("l0") || starts_with("l1")` — и мимо
  проходили **STM32WB10CC и STM32WB15CC**: `erase_value: 0` при совсем другом
  префиксе, оба в каскаде. Такому проекту доставался `embassy-boot` без
  `flash-erase-zero`{% if config == "true" %} и раздел настроек, который не работает вовсе, — молча в
  обоих случаях{% else %} — молча{% endif %}. `chip-data-gen` читает `erase_value` из того же блока
  `FlashSettings`, откуда берёт `erase_size`/`write_size`, и кладёт результат
  полем `erase_zero` в `MEMORY_LAYOUT`. Эвристика по имени осталась ровно
  одним последним рубежом — для чипа, которого нет в таблице (сейчас таких
  нет), и она печатает предупреждение. Не возвращайте её в основной путь: это
  второй источник правды рядом с метаданными, и он уже ошибся.
- **Фича объявляется в `bsp` И в `boot` по отдельности.** `embassy-boot-stm32`
  её не пробрасывает, а объединение фич внутри воркспейса не спасает:
  bootloader собирается своей командой (`cargo build -p boot`), где соседних
  крейтов в дереве зависимостей нет. Разойдись эти две стороны — приложение писало бы
  состояние в одном формате, а bootloader читал его в другом.
- **L4 и L5 сюда не относятся** — у них обычный флеш со стиранием в `0xFF`.
  Семейство вообще ничего не решает: решает `erase_value` конкретного чипа.
- **Стережёт это target-тест `prepare_erases_only_what_the_image_needs`** (его первая
  часть):
  он стирает раздел и сверяет прочитанное с тем, что подставлено при
  генерации. Тавтологией выглядит только до первого чипа, где ожидание
  разошлось с железом; на новых семействах это первое, что упадёт.
- В `template-check` для этой ветки заведена отдельная конфигурация
  (`stm32l073rz`) — без неё ветка не проверялась бы вообще.

## Страница раздела — не всегда страница чипа

Цельный `embassy_stm32::flash::Flash` объявляет `NorFlash::ERASE_SIZE` самым
крупным сектором чипа (`MAX_ERASE_SIZE`), а стирает по настоящим: `erase(from,
to)` проходит сектор за сектором и отказывает, только если границы диапазона не
совпали с границами секторов. Разница видна там, где сектора неравные, — на
F2/F4/F7 (у F4 16, 64 и 128 KiB): в мелких секторах можно держать мелкий
раздел, но только объявив ему страницу этого сектора. Это делает
`flash_page::ErasePage<F, ERASE_SIZE>`; само число считает `chip-data-gen`.

Что здесь нельзя нарушать:

- **Раздел, не кратный странице флеша под ним, роняет прошивку на старте.**
  `Partition::new` из `embassy-embedded-hal` паникует, если смещение или размер
  не кратны `ERASE_SIZE`.{% if ota == "true" %} Ровно так был сломан `BOOTLOADER_STATE` у всех 223
  чипов F2/F4/F7 с OTA: он лежал в мелком секторе над цельным `Flash` со
  страницей 128 KiB — и bootloader, и приложение (нарезка разделов) падали при
  первом запуске.{% endif %} `template-check` этого не видит (он собирает, а не
  запускает), поэтому та же проверка стоит в `chip-data-gen`
  (`assert_embassy_boot_invariants`) — при генерации, а не на плате.
{%- if ota == "true" %}
- **`BOOTLOADER_STATE` — в самом мелком секторе перед `ACTIVE`.** Журналу обмена
  нужны десятки байт, а стирается раздел при каждом обновлении: мелкий сектор и
  места не отнимает, и стирается быстрее. На F4 это сектор 3 (16 KiB), перед ним
  bootloader (48 KiB), а сектор 4 (64 KiB) пустует — под `ACTIVE` он не годится,
  там страница 128 KiB. На чипах с равными секторами раскладка от этого не
  меняется. Расчёт — `place_state` в `chip-data-gen`.{% if config == "true" %} С разделом настроек мелкие
  сектора отдаются ему (ему нужны две равные страницы), и `STATE` на F4 уходит
  в сектор 4 — см. раздел про `CONFIG` ниже.{% endif %}
- **`STATE_ERASE_SIZE` — одно число на `boot` и `bsp::flash`** из плейсхолдера
  `state_erase_size`: оно едет переменной среды в `[env]`
  `crates-cross/.cargo/config.toml`, и оба крейта читают её через `env!` —
  разделу в bootloader'е и в приложении расходиться нельзя.{% if swap_paged == "true" or ota_store == "external" %} Так же едет{% if swap_paged == "true" %} `SWAP_PAGE_SIZE`{% endif %}{% if ota_store == "external" %} `EXT_PAGE_SIZE`{% endif %}.{% endif %}
  В `[env]` — только числа, которые нужны компилятору (параметр `ErasePage`,
  `const`-assert). Границы разделов — размер `ACTIVE`{% if config == "true" %}, границы раздела настроек{% endif %} —
  туда не ездят: это символы `memory.x` (`__bootloader_active_*`{% if config == "true" %},
  `__config_start`/`__config_end`{% endif %}), их вычисляет линкер, а читает `bsp::layout`
  (подробнее — «Символы раскладки» ниже). **`ErasePage` над `STATE` нужен не всегда**:
  плейсхолдер `state_paged` = "true" только там, где сектор `STATE` мельче страницы
  цельного `Flash` (F2/F4/F7). На чипах с равными секторами раздел строится прямо
  над `Whole`, а `const`-assert (`STATE_ERASE_SIZE == MAX_ERASE_SIZE`) в `boot` и
  `bsp::flash` ловит расхождение генерации с реальным чипом.{% if config == "true" %} Так же и `CONFIG`
  (`config_paged`).{% endif %} При ручной раскладке (`--define write_size=...`) хук
  подставляет страницу цельного `Flash` — на F2/F4/F7 туда надо вписать размер
  сектора `STATE` руками.
- **Страница обмена `ACTIVE`/`DFU` бывает крупнее физической — ради `STATE`.**
  `PAGE_SIZE` обмена в `embassy-boot` — `max` из страниц обоих разделов, а журнал
  `STATE` — `(2 + 4*N) * WRITE_SIZE` байт при N страницах обмена в `ACTIVE`. На
  чипе с мелкой страницей и крупным flash N огромно: у L0 (страница 128 байт,
  ~640 страниц) журнал занимал 10 KiB из 32 KiB зоны bootloader'а, и на код
  оставалось 22 KiB — подписанный `boot` (≈23 KiB) не влезал. Поэтому
  `chip-data-gen`, когда журнал при физической странице больше 2 KiB
  (`STATE_BUDGET`), удваивает страницу обмена (`p·2^k`, не больше 8 KiB,
  `SWAP_PAGE_MAX`) до первой, при которой он укладывается; `STATE` сжимается до
  сотен байт, а bootloader получает почти весь блок в 32 KiB. Прошивка при этом
  оборачивает `ACTIVE` и `DFU` в `flash_page::ErasePage<_, SWAP_PAGE_SIZE>`
  (плейсхолдер `swap_paged` = "true", число — `page_size`): `ErasePage` лишь
  объявляет большую `ERASE_SIZE`, а стирание остаётся физическим. `STATE`
  по-прежнему строится над страницей своего сектора (`STATE_ERASE_SIZE`) — это
  другое число. Страница **не** расширяется там, где она и так крупнейший сектор
  (F2/F4/F7/H7) и при `DFU` во втором банке за разрывом (`dfu_bank`). Не уложился журнал и на 8 KiB
  (U5/H5 со словом записи 16, WB55/L4+ с мегабайтом) — страница остаётся
  физической, и запас под код держит `BOOTLOADER_MIN` (26 KiB): резерв просто
  растёт. Без расширения `ACTIVE` над цельным `Flash` не имеет смысла делить
  мельче сектора: стирание «половины сектора» снесло бы и вторую половину.
{%- else %}
- **`CONFIG_ERASE_SIZE` — число из генерации**: страница сектора раздела
  настроек — литерал в `bsp::flash` (`bsp::flash` строит раздел над
  `ErasePage` с этой страницей) и тот же литерал в `ASSERT` `memory.x`, который
  держит границы раздела (символы `__config_start`/`__config_end`) кратными ей. При ручной раскладке
  (`--define write_size=...`) хук подставляет страницу цельного `Flash` — на
  F2/F4/F7 туда надо вписать размер сектора раздела руками.
{%- endif %}

## {% if config == "true" %}Хранилище настроек{% if shared_flash == "true" %} и общий `Flash`{% endif %}{% else %}Общий `Flash`{% endif %}
{%- if config == "true" %}

Опциональное, спрашивается при генерации (`config`, в меню после выбора чипа). Хранилище — `adapters::settings` поверх `sequential-storage`
— принимает любой асинхронный `NorFlash`, и плата подставляет в этот слот
носитель (`config_store` в хуке; `ConfigFlash` в `crates-cross/bsp/src/{% if config_store == "external" %}external{% else %}flash{% endif %}.rs`):
{% if config_store == "eeprom" %}внутренняя EEPROM чипа целиком — `adapters::eeprom::Eeprom` над `Flash::eeprom_*`{% elsif config_store == "external" %}раздел на внешней флеши W25Q над драйвером `w25q` (`bsp::external`); шина — заглушка, пока плата её не подставит{% else %}раздел `CONFIG` во внутреннем флеше — `BlockingAsync<{% if config_paged == "true" %}ErasePage<Whole>{% else %}Whole{% endif %}>`{% endif %}.

`Board` отдаёт поле `config` (`bsp::ConfigFlash`).
{%- endif %}
{%- if config_store == "external" %}

**Внешняя флеш — W25Q, шина за платой.** Микросхема — Winbond W25Q
(W25Q10..W25Q128): драйвер `w25q` из hw-drivers стоит в `bsp::external`
настоящий, объём он узнаёт по JEDEC ID. Шину генерация выбирает по чипу:
QSPI, где он выведен (`QUADSPI`, иначе `OCTOSPI`), иначе SPI; блок кладётся в
группу `ext_flash` в `resources.rs`. Выводы шаблон не выбирает, поэтому шина
под драйвером — заглушка `bsp::stub::FlashBus`: `init` не проходит, каждая
операция отвечает ошибкой, и проект работает без сохранения настроек, сказав
об этом строкой в лог при старте. Раздел — {% if ota_store == "external" %}за `DFU`, см. ниже{% else %}с начала микросхемы, 128 KiB{% endif %}. Подключить — заменить шину в
`bsp/src/external.rs`: рецепт под SPI и QSPI — docs/modules/bsp-external.md.
Внутренний флеш под настройки при этом не тратится вовсе{% if shared_flash != "true" %}, а общий объект
`Flash` не создаётся (`shared_flash` в хуке){% endif %}.
{%- endif %}

Что здесь нельзя нарушать:

- **`Flash` на чипе один и создаётся ровно один раз** — `FLASH: StaticCell` в
  `bsp/src/flash.rs`. {% if ota_in == "1" and cfg_in == "1" %}И носители обновления, и настройки получают{% elsif ota_in == "1" %}Носители обновления получают{% else %}Носитель настроек получает{% endif %} `&'static FlashMutex`, а не
  свой объект: контроллер физически один. Ссылка `'static`, потому что {% if ota_in == "1" and cfg_in == "1" %}обе
  половины отдаются{% else %}носитель отдаётся в задачу{% endif %}{% if ota_in == "1" and cfg_in == "1" %} в задачи{% endif %}, а аргументы задач embassy обязаны быть `'static`.
- **К общему флешу ходят через раздел на весь флеш.** `bsp::flash::FlashMutex` —
  псевдоним на `Mutex<NoopRawMutex, RefCell<…>>` (`RefCell` нужен блокирующему
  `Mutex` embassy), а над ним потребитель строит на месте
  `embassy_embedded_hal::flash::partition::BlockingPartition::new(flash, 0, flash::SIZE)`
  (`Whole` в `bsp::flash`) — раздел с нулевым смещением: операции идут под замком, по одной. `BlockingPartition::new`
  паникует, если объём флеша не кратен `ERASE_SIZE`; у STM32 он всегда кратен
  самому крупному сектору, и `const`-assert в `bsp::flash`{% if ota == "true" %} и `boot`{% endif %} проверяет это
  при сборке{% if dfu_bank == "true" %} (банк 2 на чипе с `dfu_bank` — отдельный раздел){% endif %}.{% if ota_in == "1" %} Потребители —
  разделы OTA{% if cfg_flash == "1" %} и настройки{% endif %} — асинхронные и стоят на `BlockingAsync` поверх `Whole`; `boot` строит разделы над тем же
  `Mutex<_, RefCell<_>>` блокирующе.{% elsif cfg_flash == "1" %} Потребитель —
  раздел настроек — асинхронный и стоит на `BlockingAsync` поверх `Whole`.{% endif %}{% if config_store == "eeprom" %} Свой тип поверх мьютекса есть только в

{%- if config == "true" and erase_zero == "true" %}
- **На флеше, стирающемся в ноль, раздела во флеше не будет вовсе** (L0/L1 и
  STM32WB10CC/WB15CC — список решает не семейство, а `erase_zero`{% if ota == "true" %}, см.
  предыдущий раздел{% endif %}). `sequential-storage` считает стёртым
  состоянием `0xFF` — и заголовок записи ищет как «все байты `0xFF`»
  (`item.rs`), и состояние страницы определяет по нулевым маркерам. На флеше,
  стирающемся в ноль, свежая страница выглядит «уже закрытой», то есть
  хранилище молча не работает; настраиваемого значения у крейта нет.{% if config_store == "eeprom" %} У этого
  чипа на этот случай есть EEPROM — настройки ушли в неё.{% endif %}
{%- endif %}
{%- if config_store == "eeprom" %}
- **EEPROM под хранилищем инвертирована.** Чистая EEPROM L0/L1 читается
  нулями, а хранилищу нужны `0xFF`: обёртка `adapters::eeprom::Eeprom` отдаёт
  каждый байт инвертированным, и заводской ноль сразу выглядит стёртым — без
  первичной подготовки. Запись — побитовое И со старым значением, как у NOR
  (сама EEPROM перезаписывает байт целиком), «стирание» страницы (128 байт) —
  запись, и пишутся только изменившиеся слова: слово EEPROM L0 пишется ~3 мс,
  и всё это время исполнитель стоит под замком общего флеша (как и при
  стирании флеша). EEPROM меньше двух страниц (256 байт; у STM32L010F4/K4 её
  128) хук под настройки не берёт.
  Не уберите инверсию «для простоты»: без неё свежая EEPROM выглядела бы
  закрытыми страницами — тот же дефект, что с флешем выше.
{%- endif %}
{%- if config == "true" %}
- **Удаления ключа нет и не будет** без смены хранилища: `remove_item`
  требует `MultiwriteNorFlash`, а STM32 в одно слово дважды не пишет.
  «Удаление» — запись значения, которое формат проекта читает как «данных
  нет». Часть носителей повторную запись умеет, но `Settings` удаление не
  предлагает ни для одного — одинаковое поведение важнее.
{%- endif %}
{%- endif %}
{%- if ota == "true" or config_store == "flash" or config_store == "external" or dma_nc == "true" %}

## Символы раскладки: границы — в `memory.x`, а не в `[env]`

Границы, которые нужны рычагам платы в рантайме, — символы `memory.x`, и линкер
вычисляет их из тех же регионов, по которым раскладывает образ:

| Символ | Что | Чем задан |
|---|---|---|
{%- if ota == "true" %}
| `__bootloader_active_start`/`_end` | `ACTIVE`; разность — самый длинный образ | от регионов, их же читает `embassy-boot` |
{%- endif %}
{%- if config_store == "flash" %}
| `__config_start`/`__config_end` | раздел настроек, смещения от базы flash | `ORIGIN(CONFIG)`/`LENGTH(CONFIG)` |
{%- elsif config_store == "external" %}
| `__config_start`/`__config_end` | раздел настроек, смещения от начала внешней флеши | литералы генерации |
{%- endif %}
{%- if external_flash == "true" %}
| `__ext_flash_end` | конец последнего раздела на внешней флеши | `MAX` по концам разделов |
{%- endif %}
{%- if dma_nc == "true" %}
| `__dma_nc_start`/`_end` | регион `DMA_NC` под буферы DMA | `ORIGIN`/`LENGTH(DMA_NC)` |
{%- endif %}
{%- if bdma_nc == "true" %}
| `__bdma_nc_start`/`_end` | `SRAM4` целиком — память BDMA | `ORIGIN`/`LENGTH(SRAM4)` |
{%- endif %}

- **Одно место чтения — `bsp::layout`.** Символы объявлены в одном блоке
  `unsafe extern "C"` как `safe static … : u8`; значение символа — его адрес
  (`&raw const`), содержимое не читается. Блок — единственный unsafe ради них
  (`#[expect(unsafe_code)]`: `unsafe extern` линт считает unsafe и с
  `safe static`). Символ со значением 0 (раздел с начала внешней флеши)
  допустим так же, как у `embassy-boot`: адрес только переводится в число и ни
  с чем не сравнивается.
- **Проверки — `ASSERT` в `memory.x`, а не `const`-assert.** Значения символа
  компилятор не знает, поэтому то, что раньше было `const`-assert'ом над числом
  из `[env]`, — теперь `ASSERT(условие, "сообщение")` там же, где символ:
  {% if config_store == "flash" %}границы `CONFIG` кратны его странице (иначе `Partition::new` паникует на старте),
  {% endif %}{% if dma_nc == "true" %}регионы DMA годятся для MPU Armv7-M (размер — степень двойки от 32 байт, адрес
  кратен размеру), {% endif %}— нарушение роняет линковку, до прошивки. Величину,
  которой линкер не знает ({% if config_store == "flash" %}страница `CONFIG` — `CONFIG_ERASE_SIZE`{% else %}страницу раздела{% endif %}),
  генерация знает сама и вписывает в `ASSERT` литералом — тем же, что в коде.
  Символ из константы Rust линкеру не передать без `build.rs`, который читал бы
  `memory.x`, а это второй разбор раскладки ради одного числа.
- **`[env]` — только то, что нужно компилятору**: параметр `ErasePage`,
  `const`-assert, размер пула (`STATE_ERASE_SIZE`, `SWAP_PAGE_SIZE`,
  `EXT_PAGE_SIZE`, `HTTP_CONNECTIONS`, …). Граница раздела в `[env]` была бы вторым
  экземпляром числа, который ручная правка `memory.x` молча обгоняет.
- **Символы — в `memory.x` каждого бинарника, который их читает**: `app` и
  `target-tests` (у них одна раскладка){% if ota == "true" and ota_store == "external" %}, `boot` — символы внешней флеши
  (`boot` сверяет объём микросхемы){% endif %}. Чего бинарник не собирает{% if ota == "true" %} (bootloader —
  `CONFIG`, `DMA_NC`){% endif %}, того в его `memory.x` нет: с `--gc-sections` ссылка из
  выброшенного кода линкеру не нужна. Пишет их генерация (`chip-select.rhai`);
  ручная заготовка `memory.x` (раскладку не посчитали) показывает, что вписать.
{%- endif %}

## Банки flash

Два банка — это один массив флеша, а не две памяти: контроллер либо склеивает
их в одну непрерывную область (single-bank), либо показывает раздельно
(dual-bank, со своей страницей и read-while-write). Отдельной областью второй
банк выглядит только там, где между банками разрыв в адресах.

- **Флеш сплошной — один банк.** У чипов с выбором режима (G4 cat3, L4+, L5,
  G0B/G0C, F4 с 1 MiB, F76x/F77x) генерация берёт одобанковую карту
  (`bank_mode = single-bank`), у чипов с фиксированным dual и стыкующимися
  банками (H743ZI, L476, F42xxI…) банки — просто продолжение flash.{% if ota == "true" and ota_store != "external" %} `ACTIVE` и
  `DFU` делят остаток после bootloader'а пополам: прошивка выходит наибольшей.{% endif %}
{%- if bank_switch != "" %}
- **Новый кристалл G4 cat3, L4+, L5, G0B/G0C прошивается дважды.** Режим
  банков — option byte, и у этих семейств он с завода двухбанковый, а
  раскладка одобанковая: `embassy-stm32` на G0/G4 паникует в `Flash::new`
  («configured as single-bank, but the hardware is running in dual-bank
  mode»), а на L4+ молча стирает страницы не того размера.
  `bsp::banks::ensure_single_bank()` переключает режим сама — первым делом в
  {% if ota == "true" %}`boot` и в {% endif %}`Board::new`, до любой работы с флешем: сбрасывает бит режима и
  запускает загрузку option bytes, а та сбрасывает МК. Бит — `DBANK` у G4,
  `DUAL_BANK` у G0, а у L4+ и L5 зависит от объёма: `DBANK` у чипа с
  наибольшим flash в серии, `DB1M`/`DB256` у остальных (чужой бит может быть
  не определён и не трогается); выбирает его генерация. В
  одобанковом режиме контроллер читает оба массива 128-битным словом
  вперемешку, поэтому залитый до переключения образ по тем же адресам
  становится мусором. Порядок для новой платы и для производства: прошить,
  дать стартовать (в логе «переключаю в одобанковый»), прошить ещё раз. Дальше
  бит уже сброшен, функция выходит сразу и флеш не трогает. То же касается
  `cargo xtask test target`{% if ota == "true" %}/`host-target`{% endif %}: на новой плате первый прогон
  падает ({% if ota == "true" %}bootloader{% else %}прошивка{% endif %} переключает режим, и залитые образы читаются мусором), а
  повторный проходит. Запертый контроллер, флаг ошибки в `SR` или бит, не
  сброшенный в `OPTR`, — паника до сброса, а не бесконечные перезапуски с
  новой записью. Какие чипы — таблица `BANK_SWITCH` в `chip-data/`
  (версия блока FLASH из метаданных плюс заводское значение из документации);
  F4 с 1 MiB и F76x/F77x с завода одобанковые и в нём не значатся.
{%- endif %}
- **Банки разделены разрывом — dual-bank{% if dfu_bank == "true" %}, `DFU` во втором{% endif %}.** У H742/743/745/747
  и H7A3 с 1 MiB банк 2 начинается с 0x0810_0000, у U5F7/U5F9 с 2 MiB — с
  0x0820_0000. Кода там быть не может (раздел приложения обязан быть
  непрерывным), поэтому {% if ota == "true" and ota_store != "external" %}банк 2 целиком под `DFU`, а `ACTIVE` —
  весь банк 1 за вычетом резерва под bootloader{% else %}приложению достаётся
  банк 1, а банк 2 перечислен в `memory.x` регионом `BANK_2`{% endif %}.
{%- if dfu_bank == "true" %}
- **`DFU` за разрывом пишется через регион банка, а не через цельный
  `Flash`.** У того `FLASH_SIZE` — сумма банков, она меньше смещения банка 2, и
  запись туда кончилась бы `Error::Size`. Поэтому `boot` и `bsp` при
  `dfu_bank = true` разбирают флеш на `Bank1Region` (bootloader, `STATE`,
  `ACTIVE`{% if config_store == "flash" %}, настройки{% endif %} — смещения от базы flash, как у цельного `Flash`) и
  `Bank2Region` (`DFU`), а символы `__bootloader_dfu_*` в `memory.x` отсчитаны
  от начала банка 2. Признак — ключ `dfu_bank_origin` в `MEMORY_LAYOUT`.
{%- endif %}
- **Банк 2, начинающийся внутри банка 1, — ошибка метаданных, а не банк.** Так
  `stm32-data` описывает U375/U385 (`BANK_2` с 0x0801_0000 при `BANK_1` на
  512 KiB с базы). Такой регион генератор не считает банком: раздел там лёг бы
  поверх кода.
{%- if ota_store == "external" %}

## OTA с разделами на внешней флеши (`ext_flash=yes`)

Ответ `external` на вопрос про OTA уносит `BOOTLOADER_STATE` и `DFU` на внешнюю
NOR. Во внутреннем флеше остаются bootloader и `ACTIVE` — он и обязан быть
внутри, из него исполняется код, — и `ACTIVE` забирает почти весь чип: на F407VE
384 KiB вместо 128, на G071RB 96 вместо 46, а H723VE, куда внутренняя схема не
помещается вовсе, получает OTA. Смысл варианта — именно в этом: `STATE` — это
десятки байт, а `DFU` — копия `ACTIVE` плюс страница, и на чипе с крупными
секторами оба съедают больше половины flash.

Раскладку считает `chip-data-gen` — наборы `ext_*` и `ext_cfg_*` в
`MEMORY_LAYOUT` (`compute_external_ota`):

- **Внутри:** bootloader с базы до первой границы страницы чипа за
  `BOOTLOADER_TARGET` (32 KiB), дальше `ACTIVE` — столько, сколько ложится
  целыми страницами обмена. На F2/F4/F7 зона bootloader'а всё равно 128 KiB:
  `ACTIVE` не начинается посреди 128-килобайтного сектора.
- **Снаружи:** `STATE`, `DFU`{% if config == "true" %} и место под настройки{% endif %} — подряд с нуля, каждый
  кратен `ext_align` = max(страница обмена, 64 KiB). Символы
  `__bootloader_state_*`/`__bootloader_dfu_*` в `memory.x` — смещения от начала внешней флеши, без
  регионов в `MEMORY`: в адресном пространстве МК её нет.
- **Страница обмена** (`ext_page_size`, переменная среды `EXT_PAGE_SIZE` в
  `[env]` `crates-cross/.cargo/config.toml`, общая у `boot` и `bsp::external`) — max(крупнейший сектор чипа, 4 KiB). `embassy-boot`
  меняет разделы страницами `max(ACTIVE::ERASE_SIZE, DFU::ERASE_SIZE)`, и
  `ACTIVE` обязан быть им кратен, иначе `assert_partitions` паникует на
  старте. Поэтому **стирание драйвера обязано делить `EXT_PAGE_SIZE`** — это
  единственное требование к микросхеме, и оба места проверяют его
  `const`-assert'ом. У W25Q сектор 4 KiB — `ERASE_SIZE` драйвера.
- **Журнал `STATE`** посчитан на самую мелкую возможную страницу обмена
  (страницу чипа) и слово записи до 32 байт — с любым годным драйвером его
  хватит.

Объём микросхемы генератор не знает — его узнаёт драйвер по JEDEC ID при
`init`; поэтому выравнивание с запасом (64 KiB — самый крупный блок стирания
NOR), а конец разделов — символ `memory.x` `__ext_flash_end` (`MAX` по концам
разделов, считает линкер): микросхему меньше
`Board::new` называет в логе при старте, а операции за её концом отказывают.
{%- if config == "true" %}

**Настройки — там же, где OTA.** Внешняя флеш на плате либо есть, либо нет
(`ext_flash`), и на неё уезжает всё сразу: раздел настроек ложится на ту
же микросхему за `DFU`. Смешанного варианта — OTA снаружи, настройки внутри —
генерация не предлагает (наборы `ext_cfg_*` в `MEMORY_LAYOUT` остались от
него, хук их больше не выбирает).
{%- endif %}

**Драйвер — два вида, микросхема одна.** Приложение работает с ней асинхронно
(`bsp::external`: `W25qAsync` под одним `embassy_sync::mutex::Mutex` на
`DFU`, `STATE`{% if config == "true" %} и настройки{% endif %} — команды разных разделов не должны
перемежаться), bootloader — блокирующим `W25qSync` (`ExternalFlash` в
`crates-cross/boot/src/external.rs`: исполнителя там нет, задержки — на
`SysTick`, `cortex_m::delay::Delay`). Оба опознают микросхему (`init`) при старте:
`Board::new` поэтому асинхронный, и `main` зовёт его через `block_on`. Шина
под обоими в шаблоне — заглушка `bsp::stub::FlashBus`: проект собирается и
работает, OTA не принимает образы, bootloader грузит текущий
(docs/modules/bsp-external.md).

**Стёртое состояние:** внешняя NOR стирается в `0xFF`, даже если внутренний
флеш — в ноль (L0/L1). `flash-erase-zero` у `embassy-boot` — про `STATE`, и
с `ext_flash=yes` хук его не включает.

**Внутренний `Flash` приложению не нужен:** `ACTIVE` пишет только bootloader,
и `bsp` объект `Flash` не создаёт.
{%- endif %}
