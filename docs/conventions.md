# Конвенции: фичи, зависимости, осознанные ограничения

## Правила добавления новых зависимостей

1. **Не верить кешу.** Компиляция на `{{target}}` после `cargo build`
   с уже тёплым `target/` может «пройти», даже если чистая сборка не проходит.
   Перед тем как считать зависимость рабочей на ARM — обязательно
   `rm -rf target && cargo build --target {{target}} ...`. Прецедент
   (детали — в README, таблица `cross`): `firmware-controller` дважды казался
   рабочим на тёплом кеше, реально не собирается на no_std ARM.
2. **Крейты из личной библиотеки** ([rust-lib]({{rust_lib}}))
   объявляются в том workspace'е, где реально используются, а не «про запас».
   В `crates-cross/Cargo.toml` это `supervisor` и `watchdog` (первый спавнит
   `#[embassy_executor::task]`, второй драйвит аппаратный IWDG), в корневом —
   тот же `supervisor` у `domain`: там лежат узлы{% if graph == "true" %} графа{% endif %} и их задачи, а сигнатуры
   называют контекст узла и `Heartbeat` (обоснование — `docs/architecture.md`).
   Обе строки — самостоятельные объявления одного крейта, и версия у них одна
   по построению: cargo резолвит git-зависимость на одну ревизию для всей
   сборки прошивки.
   Git-зависимости не запинены на `rev`/`tag` — сгенерированный проект едет по
   `main`; если это станет проблемой, пинить надо оба манифеста разом.
3. **Каждая новая библиотека в `cross`, для которой ещё нет компилируемого
   примера** (обычно потому, что примеру нужна реальная периферия платы, а
   `Board` её пока не отдаёт) — документируется как doc-комментарий с ```` ```ignore ```` блоком
   в `docs/modules/app.md` (крейт `app`) или
   `docs/buffers.md` (буферы/периферия), с обоснованием «почему
   именно эта библиотека».
4. **Если библиотека не подошла** (не собирается на ARM/требует alloc без
   альтернатив/дублирует уже используемую) — не удалять молча: короткий комментарий
   рядом с местом, где она могла бы быть объявлена (см. `wg`, `firmware-controller`
   в истории коммитов и комментариях `Cargo.toml`), чтобы никто не предлагал её
   повторно без контекста.
5. **Перед тем как исключить зависимость из-за `no_std`/`no-alloc` ограничения** —
   поискать альтернативы в экосистеме, а не просто убрать (см. `wg`: проверены
   `waitgroup`, `awaitgroup`, `async-wg`, `mea`, `compact-waitgroup` — все
   Arc-based, альтернативы без alloc не нашлось, только после этого исключён).

`domain` больше не держит курируемый набор бизнес-логических библиотек «на
вырост» с компилируемым примером на каждую (`fsm`, `typestate`, `miniconf` и
т.п.) — по решению пользователя это задача самих крейтов (их собственная
документация), не шаблона{% if settings_port == "true" %}; единственное исключение — набросок подключения
`miniconf` поверх порта настроек в шапке `adapters::settings`, потому что
порт (`u32`-ключ → байты) проектировался под эту связку{% endif %}. Из `[dev-dependencies]` у `domain` (сверх того, что
нужно для линковки `supervisor`, — см. комментарий в манифесте) главная —
`tokio` (`rt` + `macros`, без
`default-features`) — исполнитель для `#[tokio::test]` над фейками портов; у
`adapters` он же для фейка флеша. Своего `block_on` в тестах нет намеренно:
он был бы двумя копиями одних и тех же восьми строк в двух крейтах. Что он
давал сверх tokio — панику на `Pending` (фейки не ждут), — теперь делает
`.config/nextest.toml`: тест этих двух крейтов, не кончившийся за 20 с,
nextest убивает, а не ждёт до таймаута CI.

## Feature-flag конвенции

- `crates-cross/app`{% if ota == "true" %}, `crates-cross/boot`{% endif %} и `crates-cross/bsp` **не имеют фич `debug`/`release`,
  `log` и `defmt`**: `log` в прошивке не используется вовсе, `defmt` включён
  безусловно в обоих профилях, транспорт — `defmt-rtt` в обоих. Фич у
  `crates-cross/bsp`{% if ota == "true" %}/`crates-cross/boot`{% endif %} нет вообще никаких: выбор одно-/двухъядерной
  реализации делается Liquid-условием при генерации, а не Cargo-фичей (см.
  раздел про двухъядерные чипы ниже).
- **У самой `embassy-stm32` фича `defmt` включена безусловно**, и это не
  «за компанию» с остальным defmt: без неё сгенерированная под чип структура
  `rcc::Clocks` не реализует `defmt::Format`, а перечислить её поля вручную
  шаблон не может — их состав различается по семействам. То есть дамп частот
  в `Board::new` без этой фичи нереализуем. Побочно включаются собственные
  логи embassy; flash это не занимает (строки defmt лежат в отдельной секции
  ELF).
- **У `supervisor` включена только `metadata-name`**: она кладёт имя узла из
  DSL в `embassy_executor::Metadata` и занимает flash, по `&'static str` на
  узел. Фичи `defmt` у `supervisor`/`watchdog` нет — библиотека сама ничего не
  печатает, и всё, что раньше писала её трассировка, прошивка логирует сама:
  {% if graph == "true" %}ошибку `spawn_all` — `main.rs` (через `Display`: `Debug` у ошибки графа нет),
  имя узла, переставшего кормить сторож, перед аппаратным сбросом —
  `before_reset` в `bsp::wdg`, застой узла — наблюдатель `observe:` в
  `graph.rs`{% else %}ошибку спавна задачи — `expect` в `tasks::spawn_all`{% endif %}. Перезапусков узлов в шаблоне нет: отказ связи узел пишет в лог
  и продолжает, а пережидает его реализация порта.
- **Паникёр — у каждого бинарника свой.** У `app` —
  `crates-cross/app/src/panic.rs`, выбирает профиль:
  `#[cfg(debug_assertions)]` на `use panic_probe as _;`, `#[cfg(not(debug_assertions))]`
  на собственном `#[panic_handler]`, который пишет причину через `panic-persist`
  (фича `custom-panic-handler`, штатного обработчика у крейта нет).{% if ota == "true" %} У `boot` —
  сброс МК без сообщения (`boot/src/main.rs`).{% endif %} У
  `crates-cross/target-tests` — паникёр самого `embedded-test`, там паника это
  способ сообщить раннеру про упавший тест. Инвариант «ровно один
  `#[panic_handler]` на бинарник» — именно на бинарник, а не на workspace
  (`docs/diagnostics.md`).
- **`HardFault` перехватывает `app`** (`crates-cross/app/src/fault.rs`): фолт
  становится паникой с регистрами причины и дальше идёт штатным путём паники. У
  {% if ota == "true" %}`boot` и {% endif %}`target-tests` — дефолт `cortex-m-rt`; см. `docs/diagnostics.md`.
- **Развилка по профилю в шаблоне ровно одна** — выбор паникёра (`app/src/panic.rs` под
  `cfg(debug_assertions)`) и чтение дампа при старте `app` под тем
  же `cfg`. Появится вторая — держите её в той же форме, см. следующий пункт.
- **Если развилка по профилю всё-таки понадобится** (реалистичный случай —
  release-транспорт defmt без пробника, см. следующий пункт), делать её через
  `#[cfg(debug_assertions)]` на `use ... as _;`, а не через Cargo-фичу. И
  `#[panic_handler]`, и `#[global_logger]` требуют ровно одной активной
  реализации **на бинарник** — это ограничение rustc/линкера, а не Cargo, а
  `debug_assertions` уже даёт ровно одно значение на сборку (`dev`/`test` →
  `true`, `release` → `false`). **Cargo при этом не умеет** гейтить сами
  зависимости по `debug_assertions`
  (`[target.'cfg(debug_assertions)'.dependencies]` не работает — резолвится
  через `rustc --print=cfg` независимо от профиля, см. rust-lang/cargo#7634),
  поэтому обе стороны развилки остаются обычными зависимостями `app`, а
  выбор — только через `cfg` на `use`.
  **Проверено эмпирически** (два разных механизма, не путать): крейт, на
  который в исходнике нет ни одной ссылки (`use` отсутствует вовсе, а не
  `cfg`-исключён), не регистрирует `#[panic_handler]` как lang item — поэтому
  `panic-probe` обычной зависимостью + `cfg` на `use` не конфликтует с
  release-обработчиком — так и устроен выбор паникёра сейчас.
  `#[global_logger]` устроен иначе: резолвится линковкой по имени символа
  (`_defmt_acquire` и т.п.), и если два `use` окажутся активны одновременно —
  жёсткий `error: Linking globals named '_defmt_acquire': symbol multiply
  defined!`. При правке `main.rs` держите инвариант «ровно один
  `use <логгер> as _;` активен на сборку».
  **Осторожно с `[profile.dev]`/`[profile.release]` в `crates-cross/Cargo.toml`**:
  `debug-assertions` там задан явно (ради `overflow-checks`) — если развилка
  по профилю появится, правка этого поля по несвязанной причине молча
  переключит и её, без предупреждения компилятора.
- defmt-транспорт для `release` без пробника (UART) — не в реальном коде:
  сырой шаблон не знает, какую периферию конкретная плата отведёт под это. С
  переездом к портам препятствие стало другим, чем было: `Board` наружу
  периферию не отдаёт вовсе (см. `docs/architecture.md`, «`Board` отдаёт рычаги платы, а не периферию и не протоколы»), так
  что транспорт пришлось бы собирать внутри `Board::new` — а какой именно
  USART подключён к переходнику на вашей плате, знаете только вы.
  Паттерн и обоснование, почему {% if has_usb == "true" %}все три turnkey-крейта{% else %}оба turnkey-крейта{% endif %} отпали (`defmt-bbq` и
  `defmt-serial` держат `defmt@0.3.x` при `defmt@1.x` у нас{% if has_usb == "true" %},
  `defmt-embassy-usbserial` требует `embassy-usb ^0.5`{% endif %}) — `docs/modules/app.md`,
  «defmt-транспорт для `release` без пробника». Дефолт в обоих профилях реального
  `main.rs` — `defmt-rtt`; при подключении паттерна не забыть сделать
  существующий `use defmt_rtt as _;` тоже `#[cfg(debug_assertions)]`.
- `-Tdefmt.x` линкуется статически из `crates-cross/.cargo/config.toml` (`rustflags`,
  рядом с `-Tlink.x`), не из `build.rs` — `defmt` используется в обоих профилях
  безусловно, в отличие от прежней схемы с `log`-only `release`, где это
  приходилось делать условно через `CARGO_FEATURE_DEFMT` в build-скрипте
  каждого бинарного крейта.
- `panic-abort` не использовать — не собирается на stable (требует nightly
  `#![feature(core_intrinsics)]`, не обновлялся с 2019). `panic-halt` тоже не
  подключён: остановка получается и без него — `panic-probe` под debug в
  обоих бинарниках, — а держать ради этого третью реализацию
  `#[panic_handler]` незачем.

## `lib.rs` только объявляет модули

В корне крейта (`lib.rs`) лежат только атрибуты крейта (`#![no_std]`,
`#![allow(..)]` с обоснованием), `//!`-документация, объявления `mod` и
`pub use`-реэкспорты. Публичный `mod` документирован — `///` над объявлением
либо `#![doc = include_str!(..)]` в самом модуле, как в `bsp`; у приватных и
тестовых{% if ota == "true" %} (`ota::fakes`){% endif %} — по необходимости. Определений — типов,
трейтов, функций, `impl` — в нём нет: они живут в модулях, названных по
предметной области ({% if ota == "true" %}`ports::ota`, `domain::ota::download`{% else %}`ports::cycles`, `domain::cpu_load::load`{% endif %}), а не по слою
(`types`, `utils`).

Реэкспорт в корне — часть правила, а не исключение из него: так устроены
`embedded-hal` и `embassy-*`, и так путь `ports::{% if ota == "true" %}FirmwareUpdate{% else %}CycleCounter{% endif %}` остаётся
коротким, а перестановка модулей внутри крейта не касается его пользователей.

Тестовые помощники, которые делят несколько модулей, — блок
`#[cfg(test)] mod fakes { .. }` в конце их общего родителя, а не отдельный
файл
{%- assign sep = ": " %}
{%- if ota == "true" %}{{ sep }}фейки портов OTA — `domain::ota::fakes` (их делят `ota`,
`ota::download` и `ota::update`), флеш в памяти под `embassy-boot` —
`adapters::ota::fakes` (модуль `ota` адаптеров){% assign sep = ", " %}{% endif %}
{%- if has_net == "true" %}{{ sep }}кабель между двумя стеками `embassy-net` —
`adapters::net::fakes` ({% if has_tcp == "true" %}`net::tcp::server`{% if has_udp == "true" %} и {% endif %}{% endif %}{% if has_udp == "true" %}`net::udp`{% endif %}){% endif %}. Отдельного файла и крейта
для фейков нет: в сборке их не видно, а с кодом, который они подменяют, они
рядом.

Фейк, который нужен одному модулю, живёт в его же `mod tests`
{%- if settings_port == "true" %}: так у адаптера
`settings` — свой асинхронный флеш в памяти ровно под свои тесты (под
`sequential-storage`){% if ota == "true" %}; так же и
`domain::ota::boot` — свой `MemFlash` в его `mod tests::fakes`, а не общий с
`adapters::ota::fakes` (крейты разные, и тянуть тестовый код через границу
крейта не стоит){% endif %}
{%- elsif ota == "true" %}: так у
`domain::ota::boot` — свой `MemFlash` в его `mod tests::fakes`, а не общий с
`adapters::ota::fakes` (крейты разные, и тянуть тестовый код через границу
крейта не стоит){% endif %}.{% if settings_port == "true" or ota == "true" %} Готового мока `NorFlash` в экосистеме нет —
`embedded-hal-mock` флеш не покрывает.{% endif %}

## Порядок объектов в модуле

Один порядок везде, чтобы нужное искалось глазами, а не поиском:

1. `mod` — объявления подмодулей;
2. `use` — одним блоком (его же сортирует `rustfmt`);
3. макросы;
4. `const` — числа и их `const`-assert'ы рядом с тем, что они проверяют;
5. типы: `type`-псевдонимы, затем `struct`/`enum`/`trait` и их `impl`;
6. `static` — память, которую модуль отдаёт `'static`, — после типов, под
   которые она заведена;
7. функции;
8. `#[cfg(test)] mod tests`.

Порядок групп 1–7 держит clippy — `arbitrary_source_item_ordering` в
`[workspace.lints.clippy]` обоих workspace, группы — `module-item-order-groupings`
в обоих `clippy.toml`. Безымянные `const _: () = assert!(..)` линт не трогает —
они остаются рядом с тем, что проверяют, — а модуль тестов он пропускает.

Внутри каждого вида (`mod` с `mod`, `const` с `const`, `type` с `type`,
`struct`, `enum`, `trait`, `static`, `fn` — каждый сам с собой) публичное стоит
выше приватного: `pub`, затем `pub(crate)`/`pub(super)`/`pub(in …)`, затем
приватное; в остальном порядок по смыслу. Этого clippy не проверяет: линт
сравнивает только группы. `use` не в счёт — его блок сортирует `rustfmt`.

С `mod` есть тонкость: `rustfmt` (`reorder_modules`) сортирует подряд идущие
объявления по алфавиту, не глядя на видимость, и `mod a;` встанет выше
`pub mod b;`. Порядок держится, только если публичные и приватные объявления —
разные группы: между ними пустая строка или строка-комментарий (doc-комментарий
`///` группу не разрывает). В `crates-cross` объявления стоят под Liquid, а тег
с дефисом слева съедает пустые строки перед собой, поэтому разделитель проверяют рендером
проекта, а не глазами. Исключение — `#[macro_use] mod resources;` в
`bsp/src/lib.rs`: макросы `#[macro_use]` видны только ниже по тексту, и
модуль обязан стоять раньше `board`, который ими пользуется.

Константе и статику документация нужна так же, как функции: почему это
число (что сломается, если его поменять) и почему оно именно здесь.

По решению пользователя

- **Тактирование шаблон не настраивает и настраивать не будет.**
  `init_peripherals` зовёт `embassy_stm32::init(config())` с умолчаниями, то есть
  чип стартует на внутреннем генераторе: у STM32F303 это 8 МГц при
  паспортных 72. Так и задумано — частоты выставляет пользователь под свою
  плату. Предложение генерировать `rcc::Config` (хотя бы «максимум от HSI»,
  без знания платы) рассматривалось и **отклонено**: у embassy одиннадцать
  семейных реализаций RCC со своими `Config`, а проверить их можно было бы
  ровно на том железе, что есть под рукой, — то есть шаблон раздавал бы
  1479 чипам арифметику, проверенную на одном.
  Что от этой темы остаётся и работает: дамп фактических частот в
  `Board::new` и `EXPECTED_SYS_HZ` в target-тесте (см. `docs/clocks.md`,
  «Тактирование: дамп и контракт»). Заполнил частоту — получил проверку на своей плате.
{%- if has_net == "true" and rng_irq != "" %}
  Единственное исключение, тоже по решению пользователя, — клок блока `RNG`
  (`config()` в `bsp/src/board.rs`): источник у каждой линии свой и выводится
  из метаданных и RM, а не из платы (`chip-data/rng.rhai`,
  `docs/modules/bsp-rng.md`). Частоты ядра и шин остаются умолчаниями: на
  F2/F4/F7 PLL включается только ради выхода Q.
{%- endif %}
- **Тулчейн запинен** — `rust-toolchain.toml` в корне (`channel`, компоненты
  `rustfmt`, `clippy` и цель прошивки; `llvm-tools` для покрытия ставят
  `cargo xtask setup` и джоб покрытия — тянуть его в каждый джоб CI незачем).
  Причина — воспроизводимый релиз: разные версии rustc дают разный код, и
  образ по тегу без той же версии побайтно не повторить. Версию поднимают
  руками и вместе с образами `rust:` в `.gitlab-ci.yml`; версию `flip-link`
  (`setup`, оба CI) — тоже везде разом. Расхождение ловит тест шаблона
  `pinned_versions_agree`. `rust-version = 1.96`
  в манифесте остаётся: это нижняя граница крейтов `rust-lib`, а не версия
  сборки. `rustfmt.toml` и `.editorconfig` нет — `cargo fmt` на умолчаниях.
- **Воспроизводимый релиз** — один коммит, собранный в том же окружении, что
  и релизный джоб CI (образ `rust:` — тот же путь проекта, `CARGO_HOME`,
  sysroot и каталог сборки), даёт побайтно один `app.bin` (и одну подпись).
  Окружение входит в образ дважды. Места паник (`файл:строка`) компилятор
  кладёт в `.rodata` абсолютными путями для всего вне `crates-cross` —
  `crates-host/*`, реестр и git в `CARGO_HOME`, `core` из sysroot, код
  build-скриптов в каталоге сборки; паникёр их при этом может и не читать —
  `Location` создаёт каждое место вызова, и LTO их не выбрасывает. А хеш
  `-C metadata` (из него имена символов, а от имён — порядок кода после LTO)
  cargo считает для path-зависимостей вне workspace от абсолютного пути.
  Поэтому образ у другого пользователя работает так же, но побайтно другой и
  на несколько килобайт больше или меньше — сознательно принято: срез
  префиксов (`--remap-path-prefix` под каждую машину) убран как не стоящий
  своего кода, а `trim-paths` профиля и `-Zlocation-detail=none` есть только
  на nightly. Кроме тулчейна и окружения, релиз держит `Cargo.lock`
  (релизные джобы зовут `cargo fetch --locked`). Релиз выкладывает
  `BUILD-ENV` (коммит, путь проекта, `rustc -vV`, `cargo -V`, `flip-link`) —
  по нему повторяют сборку в Docker и сверяют `SHA256SUMS`.
- **Kani убран целиком** — ни харнессов (`domain/src/kani_proofs.rs`), ни
  `check-cfg = ["cfg(kani)"]` в корневом `Cargo.toml`, ни джобов в обоих CI.
  Сначала ушли джобы: kani компилирует крейт вместе со ВСЕМИ зависимостями
  своим тулчейном (0.67.0 — `rustc 1.93.0-nightly`), а крейты из `rust-lib`
  объявляют `rust-version = 1.96`, и cargo отказывается резолвить ещё до
  верификации (`rustc 1.93.0-nightly is not supported by the following
  packages`). Когда `supervisor` стал прямой зависимостью `domain`, та же
  стена встала и на ручном запуске, а единственный харнесс доказывал
  монотонность `saturating_add` — не свойство домена, а заготовку конвенции.
  Под Windows kani к тому же не собирается (`kani-verifier` использует
  `std::os::unix`). Вернуть имеет смысл, когда тулчейн kani дорастёт до 1.96 и
  появится инвариант домена, который стоит доказывать, а не тестировать.

Отдельно, НЕ ограничение шаблона, а свойство окружения, но знать надо:
`domain` зависит от **приватного** `{{rust_lib}}`, поэтому сгенерированный
проект не собирается там, где нет доступа к нему — ни в CI (он будет красным), ни на чужой машине.
Локально это незаметно: креденшелы лежат в системном credential manager. Рецепт
выдачи доступа в CI (`git config --global url."https://x-access-token:$TOKEN@github.com/".insteadOf`
плюс `CARGO_NET_GIT_FETCH_WITH_CLI=true` — без него cargo не применяет
`insteadOf`, он ходит через libgit2) в шаблон по решению пользователя НЕ
вносится: шаблон и библиотека используются только автором.
