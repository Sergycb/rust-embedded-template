# Конвенции: фичи, зависимости, осознанные ограничения

## Правила добавления новых зависимостей

1. **Не верить кешу.** Компиляция на `{{target}}` с уже тёплым
   `crates-cross/target/` может «пройти», даже если чистая сборка не проходит.
   Перед тем как считать зависимость рабочей на ARM — обязательно
   `rm -rf crates-cross/target && cargo xtask build` из корня (прошивка
   собирается в `crates-cross/` со своим `.cargo/config.toml`, и корневой
   `target/` её кеша не держит). Прецедент:
   `firmware-controller` дважды казался рабочим на тёплом кеше, а на no_std ARM
   не собирается.
2. **Крейты из личной библиотеки** ([rust-lib]({{rust_lib}}))
   объявляются в том workspace'е, где реально используются, а не «про запас».
   В `crates-cross/Cargo.toml` это `supervisor` (спавнит
   `#[embassy_executor::task]`){% if graph == "true" %} и `watchdog` (драйвит аппаратный IWDG){% endif %}{% if ota == "true" and graph != "true" %} и `sync-request`
   (входы команд узла OTA){% endif %}, в корневом —
   тот же `supervisor` у `domain`: там лежат узлы{% if graph == "true" %} графа{% endif %} и их задачи, а сигнатуры
   называют контекст узла и `Heartbeat` (обоснование — `docs/architecture.md`).
   Обе строки `supervisor` — самостоятельные объявления одного крейта, и
   версия у них одна: cargo резолвит git-зависимость на одну ревизию для всей
   сборки прошивки.
   Все git-зависимости `rust-lib` запинены на одну ревизию — `rev` из
   генерации; поднимать её надо во всех строках обоих манифестов разом.
3. **Каждая новая библиотека в `cross`, для которой ещё нет компилируемого
   примера** (обычно потому, что примеру нужна реальная периферия платы, а
   `Board` её пока не отдаёт) — документируется как doc-комментарий с ```` ```ignore ```` блоком
   в `docs/modules/app.md` (крейт `app`) или
   `docs/buffers.md` (буферы/периферия), с обоснованием «почему
   именно эта библиотека».
4. **Если библиотека не подошла** (не собирается на ARM/требует alloc без
   альтернатив/дублирует уже используемую) — не удалять молча: короткий комментарий
   рядом с местом, где она могла бы быть объявлена: что не подошло и чем
   проверено, — чтобы никто не предлагал её повторно без контекста.
5. **Перед тем как исключить зависимость из-за `no_std`/`no-alloc` ограничения** —
   поискать альтернативы в экосистеме, а не просто убрать. Пример — `wg`:
   проверены `waitgroup`, `awaitgroup`, `async-wg`, `mea`, `compact-waitgroup` —
   все Arc-based, альтернативы без alloc нет, поэтому `wg` не взят.

`domain` не держит курируемый набор бизнес-логических библиотек «на
вырост» с компилируемым примером на каждую (`typestate`, `miniconf` и
т.п.): как пользоваться библиотекой, показывает её собственная
документация, а не шаблон{% if settings_port == "true" %}; единственное исключение — набросок подключения
`miniconf` поверх хранилища настроек в шапке `domain::settings`, потому что
хранилище (`u32`-ключ → байты) проектировалось под эту связку{% endif %}. Из `[dev-dependencies]` у `domain` (сверх того, что
нужно для линковки `supervisor`, — см. комментарий в манифесте) главная —
`tokio` (`rt` + `macros`, без
`default-features`) — исполнитель для `#[tokio::test]` над фейками портов{% if adapters_hw == "true" or adapters_logic == "true" %}; у
{% if adapters_hw == "true" %}`adapters-hw`{% if adapters_logic == "true" %} и {% endif %}{% endif %}{% if adapters_logic == "true" %}`adapters-logic`{% endif %} он же — для тестов над фейками драйверов и потоков{% endif %}. Своего `block_on` в тестах нет намеренно:
он был бы копией одних и тех же восьми строк в каждом крейте с async-тестами. Тест,
повисший на `Pending` (фейки не ждут), ловит `.config/nextest.toml`: тест
этих крейтов, не кончившийся за 20 с, nextest убивает, а не ждёт до
таймаута CI.

## Host-тесты — только через nextest

Host-тесты гоняются `cargo xtask test host` — то есть `cargo nextest`, — а не
`cargo test` и не кнопкой запуска тестов в IDE. Часы `embassy_time::MockDriver`

## Feature-flag конвенции

- `crates-cross/app`{% if ota == "true" %}, `crates-cross/boot`{% endif %} и `crates-cross/bsp` **не имеют фич `debug`/`release`,
  `log` и `defmt`**: `log` в прошивке не используется вовсе, `defmt` включён
  безусловно в обоих профилях, транспорт — `defmt-rtt` в обоих. Фич у
  `crates-cross/bsp`{% if ota == "true" %}/`crates-cross/boot`{% endif %} — {% if ota == "true" %}по одной, и обе{% else %}одна, и она{% endif %} не про профиль и не про
  чип: `time-driver` у `bsp` — драйвер времени, его включает `app`{% if ota == "true" %} (`boot` —
  нет, комментарий в манифесте `bsp`), `no-watchdog` у `boot` — bootloader под
  тесты на плате (`cargo xtask test target`){% endif %}. Выбор одно-/двухъядерной
  реализации делается Liquid-условием при генерации, а не Cargo-фичей
  (`init_peripherals` в `bsp/src/board.rs`).
- **У самой `embassy-stm32` фича `defmt` включена безусловно**, и это не
  «за компанию» с остальным defmt: без неё сгенерированная под чип структура
  `rcc::Clocks` не реализует `defmt::Format`, а перечислить её поля вручную
  шаблон не может — их состав различается по семействам. То есть дамп частот
  в `Board::new` без этой фичи нереализуем. Побочно включаются собственные
  логи embassy; flash это не занимает (строки defmt лежат в отдельной секции
  ELF).
- **Фичи `supervisor` включены точечно**, по словам DSL, которыми пишут
  фрагменты и граф (`crates-host/domain/Cargo.toml`, `crates-cross/Cargo.toml`), плюс
  `metadata-name`: она кладёт имя узла из DSL в `embassy_executor::Metadata` и
  занимает flash, по `&'static str` на узел. Фичи `defmt` у `supervisor`{% if graph == "true" %}/`watchdog`{% endif %}
  нет — библиотека сама ничего не
  печатает, и нужное прошивка логирует сама:
  {% if graph == "true" %}ошибку `spawn_all` — задача `start` в `main` бинарника приложения (через `Display`: `Debug` у ошибки графа нет),
  имя узла, переставшего кормить сторож, перед аппаратным сбросом —
  `before_reset` в `bsp::wdg`, застой узла — наблюдатель `observe:` в
  `graph.rs`{% else %}ошибку спавна задачи — `expect` в `tasks::spawn_all`{% endif %}. Перезапусков узлов в шаблоне нет
  (`docs/architecture.md`, «Узлы не падают»).
- **Паникёр и `#[global_logger]` — ровно по одному на бинарник**, развилка по
  профилю — `#[cfg(debug_assertions)]` на `use … as _;`, а не Cargo-фича: Cargo
  не умеет гейтить зависимости по профилю. Почему так, как проверено и чего
  не подключать (`panic-abort`, `panic-halt`) — `docs/diagnostics.md`, «Два
  паникёра, один на сборку».
- **`HardFault` перехватывает `app`** (`crates-cross/app/src/fault.rs`): фолт
  становится паникой с регистрами причины и дальше идёт штатным путём паники. У
  {% if ota == "true" %}`boot` и {% endif %}`target-tests` — дефолт `cortex-m-rt`; см. `docs/diagnostics.md`.
- {% if graph == "true" %}**Развилок по профилю в шаблоне две**{% else %}**Развилка по профилю в шаблоне ровно одна**{% endif %} — выбор паникёра (`app/src/panic.rs` под
  `cfg(debug_assertions)`) и чтение дампа при старте `app` под тем
  же `cfg`{% if graph == "true" %}; вторая — заморозка сторожа под отладчиком в dev-сборке
  (`freeze_on_halt` в `bsp::wdg`, тоже под `cfg(debug_assertions)`){% endif %}. Появится новая — держите её в той же форме (`docs/diagnostics.md`, «Два
  паникёра, один на сборку»).
- defmt-транспорт для `release` без пробника (UART) — не в реальном коде:
  шаблон не знает, какую периферию конкретная плата отведёт под это, а
  `Board` наружу периферию не отдаёт вовсе (см. `docs/architecture.md`, «`Board` отдаёт рычаги платы, а не периферию и не протоколы»), так
  что транспорт пришлось бы собирать внутри `Board::new` — а какой именно
  USART подключён к переходнику на вашей плате, знаете только вы.
  Паттерн и обоснование, почему {% if has_usb == "true" %}все три turnkey-крейта{% else %}оба turnkey-крейта{% endif %} отпали (`defmt-bbq` и
  `defmt-serial` держат `defmt@0.3.x` при `defmt@1.x` у нас{% if has_usb == "true" %},
  `defmt-embassy-usbserial` требует `embassy-usb ^0.5`{% endif %}) — `docs/modules/app.md`,
  «defmt-транспорт для `release` без пробника: UART». Дефолт в обоих профилях
  (`crates-cross/app/src/panic.rs`) — `defmt-rtt`; при подключении паттерна не забыть сделать
  существующий `use defmt_rtt as _;` тоже `#[cfg(debug_assertions)]`.
- `-Tdefmt.x` — в `rustflags` `crates-cross/.cargo/config.toml` рядом с
  `-Tlink.x`, а не в `build.rs`: `defmt` включён в обоих профилях безусловно, и
  подставлять скрипт линкера по условию незачем.

## `lib.rs` только объявляет модули

В корне крейта (`lib.rs`) лежат только атрибуты крейта (`#![no_std]`,
`#![allow(..)]` с обоснованием), `//!`-документация, объявления `mod` и
`pub use`-реэкспорты. Модуль без кода (одна `#![doc = include_str!(..)]`) не
заводится: такой документации место в `docs/`. Публичный `mod` документирован — `///` над объявлением
либо `#![doc = include_str!(..)]` в самом модуле, как в `bsp`; у приватных и
тестовых{% if ota == "true" %} (`ota::fake`){% endif %} — по необходимости. Определений — типов,
трейтов, функций, `impl` — в нём нет: они живут в модулях, названных по
предметной области ({% if ota == "true" %}`ports::ota`, `domain::ota::download`{% else %}`domain::cpu_load::load`{% endif %}), а не по слою
(`types`, `utils`).

Реэкспорт в корне — часть правила, а не исключение из него: так устроены
`embedded-hal` и `embassy-*`, и так путь `ports::{% if ota == "true" %}Partitions{% else %}<Трейт>{% endif %}` остаётся
коротким, а перестановка модулей внутри крейта не касается его пользователей.

## Порядок объектов в модуле

Один порядок везде, чтобы нужное искалось глазами, а не поиском:

1. `mod` — объявления подмодулей;
2. `use` — одним блоком (его же сортирует `rustfmt`);
3. макросы;
4. `const` — числа и их `const`-assert'ы рядом с тем, что они проверяют;
5. типы: `type`-псевдонимы, затем `struct`/`enum`/`trait` и их `impl`;
6. `static` — память, которую модуль отдаёт `'static`, — после типов, под
   которые она заведена;
7. функции;
8. `mod fake` — фейки модуля (раздел «Фейки»);
9. `#[cfg(test)] mod tests`.

Порядок групп 1–7 держит clippy — `arbitrary_source_item_ordering` в
`[workspace.lints.clippy]` обоих workspace, группы — `module-item-order-groupings`
в обоих `clippy.toml`. Безымянные `const _: () = assert!(..)` линт не трогает —
они остаются рядом с тем, что проверяют, — а модули под `#[cfg(test)]` (`tests`
и тестовый `fake`) он пропускает. Модуль `fake` под фичей
(`cfg(any(test, feature = "fake"))`) для линта обычный `mod` не на своём
месте, поэтому модуль, который его держит, снимает линт у себя:
`#![cfg_attr(any(test, feature = "fake"), expect(clippy::arbitrary_source_item_ordering, ..))]`.
Условие нужно, чтобы снять ровно там, где модуль есть: без фичи `expect` без
нарушения сам стал бы предупреждением.

Внутри каждого вида (`mod` с `mod`, `const` с `const`, `type` с `type`,
`struct`, `enum`, `trait`, `static`, `fn` — каждый сам с собой) публичное стоит
выше приватного: `pub`, затем `pub(crate)`/`pub(super)`/`pub(in …)`, затем
приватное; в остальном порядок по смыслу. Этого clippy не проверяет: линт
сравнивает только группы. `use` не в счёт — его блок сортирует `rustfmt`.

С `mod` есть тонкость: `rustfmt` (`reorder_modules`) сортирует подряд идущие
объявления по алфавиту, не глядя на видимость, и `mod a;` встанет выше
`pub mod b;`. Порядок держится, только если публичные и приватные объявления —
разные группы: между ними пустая строка или строка-комментарий (doc-комментарий
`///` группу не разрывает). В `crates-cross` объявления стоят под Liquid, а тег
с дефисом слева съедает пустые строки перед собой, поэтому разделитель проверяют рендером
проекта, а не глазами. Исключение — `#[macro_use] mod resources;` в
`bsp/src/lib.rs`: макросы `#[macro_use]` видны только ниже по тексту, и
модуль обязан стоять раньше `board`, который ими пользуется.

Константе и статику документация нужна так же, как функции: почему это
число (что сломается, если его поменять) и почему оно именно здесь.

## Известные, осознанные ограничения (не баги)
{%- if ota == "true" %}

Bootloader прыгает в `ACTIVE`, не проверяя вектор сброса и SP образа (подпись
нового образа перед обменом он проверяет — `docs/ota.md`), — осознанный
компромисс, описан в README, раздел «Bootloader»; не пытайтесь «исправить» без

Дополнительно — решения, у каждого из которых своя причина
{%- else %}

Решения, у каждого из которых своя причина
{%- endif %} (не менять без запроса):

- **Тактирование шаблон не настраивает и настраивать не будет.**
  `init_peripherals` зовёт `embassy_stm32::init(config())` с умолчаниями, то есть
  чип стартует на внутреннем генераторе: у STM32F303 это 8 МГц при
  паспортных 72. Так и задумано — частоты выставляет пользователь под свою
  плату. Генерировать `rcc::Config` (хотя бы «максимум от HSI», без знания
  платы) шаблон **не будет**: у embassy одиннадцать
  семейных реализаций RCC со своими `Config`, а проверить их можно было бы
  ровно на том железе, что есть под рукой, — то есть шаблон раздавал бы
  1479 чипам арифметику, проверенную на одном.
  Что от этой темы остаётся и работает: дамп фактических частот в
  `Board::new` и `EXPECTED_SYS_HZ` в target-тесте (см. `docs/clocks.md`,
  «Тактирование: дамп и контракт»). Заполнил частоту — получил проверку на своей плате.
{%- if has_net == "true" and rng_irq != "" %}
  Единственное исключение — клок блока `RNG` (`config()` в
  `bsp/src/board.rs`): источник у каждой линии свой и выводится из метаданных
  и RM, а не из платы, поэтому его выставила генерация
  (`docs/modules/bsp-rng.md`). Частоты ядра и шин остаются умолчаниями: на
  F2/F4/F7 PLL включается только ради выхода Q.

- **Тулчейн запинен** — `rust-toolchain.toml` в корне (`channel`, компоненты
  `rustfmt`, `clippy` и цель прошивки; `llvm-tools` для покрытия ставят
  `cargo xtask setup` и джоб покрытия — тянуть его в каждый джоб CI незачем).
  Причина — воспроизводимый релиз: разные версии rustc дают разный код, и
  образ по тегу без той же версии побайтно не повторить. Версию поднимают
  руками{% if ci == "gitlab" %} и вместе с образами `rust:` в `.gitlab-ci.yml`{% endif %}; версию `flip-link`
  (`setup`, CI) — тоже везде разом, как и `rust-version` в манифестах (корневой,
  `crates-cross`, `chip-info`): MSRV приложения — версия, которой его
  проверяют, а не меньшая, которую никто не собирает. `rustfmt.toml` и `.editorconfig` нет — `cargo fmt` на умолчаниях.
- **Воспроизводимый релиз** — один коммит, собранный в том же окружении, что
  и релизный джоб CI (образ `rust:` — тот же путь проекта, `CARGO_HOME`,
  sysroot и каталог сборки), даёт побайтно один `app.bin` (и одну подпись).
  Окружение входит в образ дважды. Места паник (`файл:строка`) компилятор
  кладёт в `.rodata` абсолютными путями для всего вне `crates-cross` —
  `crates-host/*`, реестр и git в `CARGO_HOME`, `core` из sysroot, код
  build-скриптов в каталоге сборки; паникёр их при этом может и не читать —
  `Location` создаёт каждое место вызова, и LTO их не выбрасывает. А хеш
  `-C metadata` (из него имена символов, а от имён — порядок кода после LTO)
  cargo считает для path-зависимостей вне workspace от абсолютного пути.
  Поэтому образ у другого пользователя работает так же, но побайтно другой и
  на несколько килобайт больше или меньше — сознательно принято: срез
  префиксов (`--remap-path-prefix` под каждую машину) не стоит своего кода,
  а `trim-paths` профиля и `-Zlocation-detail=none` есть только на nightly.
  Кроме тулчейна и окружения, релиз держит `Cargo.lock` (релизные джобы
  зовут `cargo fetch --locked`). Релиз выкладывает
  `BUILD-ENV` (коммит, путь проекта, `rustc -vV`, `cargo -V`, `flip-link`) —
  по нему повторяют сборку в Docker и сверяют `SHA256SUMS`.
- **Формальной верификации (Kani) нет** — ни харнессов, ни `cfg(kani)`, ни
  джобов CI. Kani компилирует крейт вместе со ВСЕМИ зависимостями своим
  тулчейном (0.67.0 — `rustc 1.93.0-nightly`), а `domain` зависит от
  `supervisor`: крейты `rust-lib` объявляют `rust-version = 1.96`, и cargo
  отказывается резолвить ещё до верификации (`rustc 1.93.0-nightly is not
  supported by the following packages`). Под Windows Kani к тому же не
  собирается (`kani-verifier` использует `std::os::unix`). Добавлять имеет
  смысл, когда тулчейн Kani дорастёт до 1.96 и появится инвариант домена,
  который стоит доказывать, а не тестировать.

Отдельно, НЕ ограничение шаблона, а свойство окружения, но знать надо:
`domain` зависит от **приватного** `{{rust_lib}}`, поэтому сгенерированный
проект не собирается там, где нет доступа к нему — ни в CI (он будет красным), ни на чужой машине.
Локально это незаметно: креденшелы лежат в системном credential manager. Рецепт
выдачи доступа в CI (`git config --global url."https://x-access-token:$TOKEN@<сервер>/".insteadOf`
плюс `CARGO_NET_GIT_FETCH_WITH_CLI=true` — без него cargo не применяет
`insteadOf`, он ходит через libgit2) в шаблоне нет: шаблоном и библиотекой
пользуется только автор, у которого доступ уже есть. Понадобится проекту
с чужим доступом — рецепт добавляют в CI вместе с секретом токена.
