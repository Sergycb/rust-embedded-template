# OTA: приём образа, подпись, полный цикл

## Команды: образ приходит через протокол

**Своего канала у OTA нет.** Образ приходит командами от узла протокола{% if has_protobuf == "true" %}
(protobuf){% elsif has_modbus == "true" %} (Modbus){% elsif has_canopen == "true" %} (CANopen){% endif %}: протокол переводит
свои сообщения в `domain::ota::Command` и отдаёт их узлу `OTA` (`domain::ota`)
через один из двух его входов.{% if graph == "true" %} `CMD` — `request:` графа, запрос с ответом
(`sync-request`): клиент ждёт исхода в вызове. `ASK` — `serves:` графа: клиент
объявляет ребро `asks:`, отправляет команду, не дожидаясь (`try_call`), и{% else %} `CMD` — `static` `RpcService` в `crate::tasks::ota`, запрос с
ответом (`sync-request`): клиент ждёт исхода в вызове. `ASK` — там же,
`sync_request::ask::AskService` (его очередь и рёбра задаются руками): клиент
отправляет команду, не дожидаясь (`try_call`), и{% endif %}
забирает исход из `reply()`, тем временем обслуживая свой канал; это вход для
узла протокола, которому нельзя молчать, пока узел OTA стирает раздел. Для
цикла узла входы одинаковы. На каждую команду узел отвечает
`domain::ota::Reply` — исходом именно её, и протокол передаёт его хосту как есть.

| Команда | Что делает узел | Ответ |
|---|---|---|
| `Start { len, signature }` | проверяет занятость, длину и подпись, стирает раздел | `Started` или код отказа |
| `Chunk` (до 128 байт) | пишет кусок вслед за принятыми | `Received(всего байт)` |
| `Finish` | сверяет длину, раскладку памяти и версию, применяет образ (`domain::ota::update::apply`); повтор после `Ready` ничего не пишет | `Ready` |
| `Reboot` | отвечает, ждёт `REBOOT_GRACE` (100 мс), сбрасывает МК портом `ports::Reboot` | `Rebooting` |

Почему так, а не «свой канал на образ»:

- **Канал общий с протоколом.** Хост уже говорит с устройством по протоколу,
  и второй транспорт ради прошивки ему не нужен. Каналом владеет узел
  протокола; будь у OTA свой вытягивающий порт, два
  узла делили бы один канал, и понадобился бы разборщик.
- **Узел один на все протоколы.** Протоколу остаётся перевод: {% if has_protobuf == "true" %}`Ota.Chunk`
  protobuf{% elsif has_modbus == "true" %}запись регистров
  Modbus{% elsif has_canopen == "true" %}запись SDO
  CANopen{% else %}кусок образа
  в его сообщении{% endif %} сводится к `Chunk`.
- **Ответ — исход, а не «принято».** Протокол отвечает хосту исходом команды:
  отказ куска виден на этом же куске. Ждать исход на месте нужно только тому,
  у кого ответ синхронный{% if has_modbus == "true" %} (Modbus slave){% endif %}: его ответ на `Start`
  ждёт стирания (секунды на F4).{% if has_protobuf == "true" %} Так же и protobuf: команда — на `CMD`,
  ответ — её исход.{% endif %}{% if has_canopen == "true" %} CANopen шлёт команду на `ASK` и
  обслуживает канал, пока узел OTA работает.{% endif %}
- **Сброс — команда хоста.** После `Finish` узел в состоянии `Ready` и ждёт
  `Reboot`: хост узнаёт исход образа до сброса, а не по факту перезагрузки.
  Новый `Start` в `Ready` — `Busy`: образ, ждущий обмена, затирать нельзя.
  `Finish` владельца в `Ready` снова отвечает `Ready`, ничего не записав и не
  стерев: его можно повторять, если ответ потерялся (`Finish` пишет запись для
  bootloader'а и стирает `STATE` — на F4 до секунды, ответ может не успеть к
  тайм-ауту хоста). Иначе повтор получил бы `NoSession`, хост счёл бы
  обновление проваленным и не прислал бы `Reboot`, а образ применился бы
  молча на первом сбросе.

Отказ хост получает кодом `domain::ota::command::Rejection`, полная причина уходит в лог
устройства. Отказ команде владельца приёма (`Length`, `Transfer`, `Busy`, `Rollback`,
`Signature`, `Device`, `Layout`) обрывает приём — хост начинает с `Start`;
`NoSession` владельцу идущего приёма не приходит — это ответ на `Chunk` или
`Finish` без приёма (ниже). `Busy` — одно имя
на три причины: приём ведёт другой клиент; принятый образ ждёт `Reboot` (`Ready`); раздел
занят образом, ждущим обмена или отката (`Updater::is_busy`, `UpdateError::Busy`). `Busy` другому
клиенту, пока приём идёт, приём владельца не трогает: тому хосту ждать и
повторить позже. `Chunk` или `Finish` без приёма — `NoSession`; исключение —
повтор `Finish` владельцем в `Ready` (см. выше), чужой там — `NoSession`. Хост замолчал посреди образа дольше `SESSION_TIMEOUT` (30 с) —
приём брошен: следующий кусок от другого хоста не ляжет в середину чужого
образа.

**Несколько транспортов — один владелец сессии.** Запрос на вход `CMD` —
`domain::ota::Request`: команда и номер клиента (`ClientId`). Клиент —
транспорт, а не удалённый хост: каждый узел протокола — свой клиент, номер
ему даёт генерация — порядковый номер транспорта с протоколом в `links`, с 0.
Узел, который ходит на `CMD`, держит клиента входа — {% if graph == "true" %}`ota_cmd_requester()`
графа{% else %}`crate::tasks::ota::CMD.requester()` (`static` в `crates-cross/app/src/tasks/ota.rs`){% endif %} —
обёрнутым в `domain::ota::Client::new(.., domain::ota::ClientId(n))`; узел,
который ходит на `ASK`{% if has_canopen == "true" %} (здесь — CANopen){% endif %}, держит во входе только номер
`domain::ota::ClientId(n)`. Принятый `Start` делает клиента
владельцем приёма; `Start`, `Chunk` и `Finish` другого клиента, пока приём
идёт, — `Busy`: кусок не пишется, раздел не стирается, срок молчания
владельца не продлевается. Свой `Start` владелец повторять может — приём
начинается заново (хост потерял ответ), а после `Ready` — свой `Finish`.
Владелец освобождается на `Finish`,
на отказе своей команды и по сроку `SESSION_TIMEOUT`; после срока чужой `Start`
начинает свою сессию. `Reboot` — от любого клиента. Два хоста на одном
транспорте (два соединения на одном порту, два хоста на одной шине) — один
клиент и делят одну сессию: различать их — дело протокола, а не узла.
{%- if graph != "true" %} Клиента
получает задача протокола.
{%- endif %}

Как команды ложатся на протокол:
{%- endif %}
{%- if has_protobuf == "true" %}

- **protobuf** — команда `ota` с вложенным `Ota.command`: `start`, `chunk`,
  `finish`, `reboot`; ответ `Ok` или `Error` с именем отказа
  (`crates-host/proto/proto/host.proto`).
  Обработчик `domain::ota::protobuf::Handler` шлёт команду на вход `CMD` и ждёт
  исхода, как Modbus: ответ с `request_id` запроса — её исход; пока узел OTA
  стирает раздел (секунды на F4), канал не обслуживается. Исход
  уходит тому, с кем канал говорит в этот момент{% if has_udp == "true" or has_tcp == "true" %}:{% if has_udp == "true" %} по UDP — отправителю
  последней датаграммы{% endif %}{% if has_udp == "true" and has_tcp == "true" %},{% endif %}{% if has_tcp == "true" %} по TCP — текущему соединению{% endif %}{% endif %}. Отсюда то же правило,
  что для сессии приёма: хост обновления на транспорте один. Числового кода
  исхода у protobuf нет: у него `Ok` или `Error` с текстом.
{%- if has_udp == "true" %}
  **UDP — только для доверенного сегмента.** Ответ уходит отправителю
  последней датаграммы, и адрес его ничем не проверяется. Подделанный адрес
  отправителя превращает устройство в отражатель: ответ (на `Info` — длиннее
  запроса) уходит жертве. А любой узел сегмента для узла OTA — тот же клиент,
  что и хост обновления: его `Start` начинает приём заново, его `Chunk` и
  `Finish` идут в чужую сессию, и подпись от этого не спасает — она защищает
  от чужого образа, а не от сорванного обновления.
{%- endif %}
{%- elsif has_modbus == "true" %}

- **Modbus** — одна запись FC16 в окно holding-регистров с `0xF000` — одна
  команда (`domain::modbus::OtaRegisters` вокруг карты проекта). Успех —
  обычный ответ FC16, отказ — исключение 04; точный код и принятая длина — во
  входных регистрах (FC04) с той же базы, код — из таблицы `domain::ota::command::reply_code`;
  карта окна — `crates-host/domain/src/modbus/ota.rs`.
  Узел OTA взял команду и не ответил — тоже 04 и код `Device`, как у
  protobuf и CANopen; запись не по форме — исключение 03 и код 0: в регистре
  не остаётся исход прошлой команды.
  Slave отвечает после исхода, поэтому тайм-аут опрашивающей стороны на
  `Start` должен быть длиннее стирания раздела (секунды на F2/F4/F7).
{%- elsif has_canopen == "true" %}

- **CANopen** — записи SDO в объект `0x4F00` (`domain::canopen::Object`,
  `application_callback` в `crates-host/canopen/device.toml`): sub 1 — `Start`, 2 — `Chunk`, 3 —
  `Finish`, 4 — `Reboot`; исход — sub 5, принятая длина — sub 6. Здесь
  протокол не ждёт исход: `zencan` отвечает на SDO синхронно, внутри обработки
  кадра, и отложить ответ нельзя. Запись только ставит команду, узел CANopen
  после обработки кадра шлёт её на вход `ASK` узла OTA, не дожидаясь исхода, и
  работает дальше: heartbeat, SDO и PDO идут и пока узел OTA стирает раздел.
  Исход узел забирает из `reply()` и кладёт в sub 5; хост перечитывает sub 5,
  пока там 0 (команда выполняется). Новая команда до исхода прежней —
  отказ SDO `0x0800_0022` (`CantStoreDeviceState`). Стирание страницы всё же
  останавливает весь МК (см. ниже), так что допуск потребителя heartbeat —
  не меньше стирания одной страницы `DFU`. Код исхода в sub 5 — из таблицы
  `domain::ota::command::reply_code`.
{%- endif %}

## Приём образа: стирание отдельно от записи

**Приём и применение крутит узел `OTA`, приложение не пишет во флеш само.**
Узел отказывает до стирания, если раздел занят или `Start` негодный, и ведёт
приём шагами `domain::ota::download::Transfer` — `start`, `chunk`, `finish`
над адаптером OTA `domain::ota::Updater`. Это данные состояния `Receiving`
узла, и делают они всё, что одинаково для любого протокола: сверяют
длину с `capacity()` ДО стирания, зовут `prepare` один раз, копят куски до
слова флеша (`write_granularity()`), ведут смещение и не дают образу вылезти за
обещанную длину. Заменять это ручным циклом `prepare`/`write` в проекте не
надо — там четыре независимые грабли, каждая из которых даёт молчаливо
испорченный образ, и все они закрыты host-тестами (`crates-host/domain/src/ota.rs`
и `crates-host/domain/src/ota/download.rs`).

`Updater` требует звать `prepare(len)` один раз перед передачей —
он стирает место под образ, — а `write()` не стирает.
Разделение не косметическое, и вернуть «умную» запись, которая стирает сама,
нельзя:

- `write_firmware` из `embassy-boot` стирает сектор, «если он не тот, что
  стирали в прошлый раз», и помнит это **полем в `FirmwareUpdater`**.
  А `domain::ota::Updater` создаёт апдейтер заново на каждый вызов — иначе
  структура вышла бы самоссылающейся (апдейтер держит и флеш, и выравненный
  буфер). У свежего объекта «в прошлый раз» пусто, поэтому стиралось при
  каждой записи.
- Цена ошибки: цикл приёма собирал в `DFU` только последний кусок каждого
  сектора, то есть OTA не работала вовсе — молча, потому что записи возвращали
  `Ok`. **Проверено на живой плате**: две записи по разным смещениям одного
  сектора, первая читается как `0xFF`.
- Стережёт это target-тест `dfu_partition_keeps_both_writes_into_one_sector`.
  Проверить на хосте нечем: подделка флеша ведёт себя не как настоящий, а вся
  суть именно в стирании.
- Явное `prepare(len)` заодно чинит второй случай, который «умная» запись не
  ловит в принципе: повторная передача, начатая с того же сектора, на котором
  закончилась прошлая, — там стирания не было бы, а память уже занята.

**Проверка занятости (`Swap`/`Revert`) в `write` — не дубль той, что внутри `prepare`.**
`write_firmware` начинался с `verify_booted()`, а прямая запись в раздел чужих
проверок не делает; `prepare` же может быть не вызван вовсе — кусок приходит из
недоверенного канала, и команды «начать» могло не быть. Без этой проверки
приложение затёрло бы образ, в который bootloader откатывается на ближайшем
сбросе, причём на F2/F4/F7 молча. Проверка запрещает `Swap` и `Revert` —
строже, чем `verify_booted`, который `Revert` разрешает: в `Revert` беречь в
`DFU` нечего (там отвергнутый образ), но держится он, только пока прежний образ
не подтвердил себя, и обновление на таком устройстве не принимается (см.
`Updater::is_busy` в `domain::ota::updater`). Вариантов у `State` четыре, а
неизвестная магия читается как `Boot`. Тестами это ловится —
`write_and_prepare_refuse_while_a_swap_is_pending_or_just_reverted` проверяет оба
магических значения, — поэтому снимать «как дубль» нельзя.
Занятость раздела отдаёт и сам адаптер (`is_busy`),
потому что логика применения обновления обязана отличать её от отката по
версии.

**`prepare(len)` стирает весь `DFU[..capacity]` и запасную страницу, а не
`ceil(len / ERASE_SIZE)` страниц под образ.** Подпись покрывает `len` байт, а
обмен `embassy-boot` копирует в `ACTIVE` раздел целиком — все `capacity`
байт. Сотри `prepare` только страницы под образ (ради
времени), хвост `DFU[round_up(len)..capacity]` с остатками прошлых загрузок
уезжал бы в `ACTIVE` непроверенным: например, байты чужого образа, который
прислал кто угодно (подпись приложение не проверяет) и который bootloader
отверг, — в исполняемой флеш за честно подписанным образом. Цена — время `Start`
короткого образа: оно такое же, как у образа во весь `ACTIVE` (на F4 — секунды на
сектор 128 KiB, на H7 с `ACTIVE` в семь секторов — около десяти секунд).
Худшее время то же — образ во весь раздел стирает столько же в любом случае,
поэтому ни тайм-аут хоста на `Start`, который обязан его покрывать{% if graph == "true" %}, ни
граница по сторожу (она — на одну страницу, см. ниже){% endif %}, от этого не сдвигаются.
Износ растёт на страницы за образом, но не вдвое: страницы `DFU` и так
стирает обмен. Альтернатива — проверка стёртого хвоста в bootloader'е —
отвергнута: после первого же чужого `Start` с длинным образом каждое честное
обновление короче него отвергалось бы до тех пор, пока хвост не сотрёт
кто-то другой, а bootloader'у пришлось бы ещё и знать стёртое значение флеша.
Длина `prepare` по-прежнему нужна — по ней отказ до стирания (ниже).

**Нулевая длина и длина сверх `capacity()` — ошибка, а не «сколько влезет».**
Стирание уничтожает образ, в который bootloader откатывается, поэтому узнать о
негодной длине надо ДО него; а `prepare(0)` не стёр бы ничего, и следующая
запись легла бы в нестёртую память — на F2/F4/F7 молча.

**`capacity()` отдаёт размер `ACTIVE`, а не `DFU`.** Раздел приёма по
построению больше активного (`assert_partitions` в `embassy-boot` требует
запасную страницу под обмен), а `swap` копирует ровно `ACTIVE`. Отдай плата
в `Partitions::capacity` размер `DFU` — образ, попавший в промежуток, прошёл бы и проверку длины, и
подпись, и пометку к обмену, а в `ACTIVE` приехал бы обрезанным: полный цикл
обновления с перезагрузкой и молчаливый откат.

**И это всё равно самый долгий вызов обновления.** Стирание идёт внутри
критической секции драйвера флеша, то есть исполнитель на это время
останавливается целиком{% if graph == "true" %} — вместе с тикером графа, который кормит IWDG{% endif %}.
Поэтому `prepare` стирает по странице раздела (`ERASE_SIZE` `DFU`) и после
каждой уступает исполнитель (`yield_now`): между страницами задачи прошивки{% if graph == "true" %} и
тикер{% endif %} успевают отработать. Неделима только одна страница — от десятков
миллисекунд на мелкой до нескольких секунд на секторе в четверть мегабайта.
{%- if graph == "true" %}
Отсюда граница, которую компилятор не проверит: максимальное время стирания
одной страницы `DFU` из datasheet обязано быть меньше `bsp::wdg::HW_TIMEOUT_MIN_US`
(таймаут сторожа на самом быстром LSI, `docs/watchdog.md`) минус `WATCHDOG_CHECK_EVERY` — иначе аппаратный сброс посреди подготовки
раздела. Страница дольше `domain::heartbeat::WATCHDOG` (7 с) сбросом не грозит,
но даёт ложное «узел HEARTBEAT перестал отмечаться»: узел объявлен `observe`,
это строка в логе, а не сброс (`docs/watchdog.md`).

Своего `watchdog:` у узла `OTA` нет по той же логике, по которой
`domain::heartbeat` отмечается только после реального прогресса: команды
может не быть всю жизнь платы, прогресса, о котором можно отметиться, у узла
нет, а отметка по таймеру сторожила бы исполнитель, а не работу (см. doc у
`task` в `domain::ota`).
{%- endif %}

## Подтверждение образа — в узле OTA, один раз за запуск

`mark_booted` зовёт стартовое действие узла `domain::ota` (`begin`), а не
`main` до исполнителя: там вызов пришлось бы опрашивать как future без
waker'а, а драйвер, ждущий `embassy_time::Timer`{% if ota_store == "external" %} (опрос
статуса стирания внешней флеши){% endif %}, паникует на чужом waker'е:
встроенная очередь таймеров требует waker исполнителя.

`begin` — самое раннее место, а не обязательное: появится критерий
«устройство работает» (подняли связь, отработали цикл измерений) —
переносите подтверждение туда, и откат застрахует и от образа, который
стартует, но не работает. Условия ниже переносятся вместе с вызовом{% if has_usb == "true" %}, и
готовность USB — тоже («USB встаёт на шину после подтверждения»){% endif %}.

Один раз за запуск — {% if graph == "true" %}слот `CONFIRMED` фрагмента{% else %}флаг `confirmed` контекста узла
(`crates-cross/app/src/tasks/ota.rs`){% endif %}. `STATE` сразу после обмена и
`STATE` с принятым, но ещё не применённым образом одинаковы (`Swap`,
различается только журнал), и подтверждение после `mark_updated` молча сняло
бы запрос, о котором хост услышал `Ready`. Поэтому принятый образ тоже
ставит флаг: подтверждать после него нечего. Не удалось подтвердить при
старте — узел работает и пробует снова на следующем `Start`, до проверок
образа. Не чаще: неудавшийся `mark_booted` может стоить стирания `STATE`
(`embassy-boot` стирает раздел перед записью магии), а на F2/F4/F7 стирание
сектора останавливает выборку из банка на доли секунды.
{%- if graph != "true" %}

Задачу узла спавнит `tasks::spawn_all` (`crates-cross/app/src/tasks/ota.rs`,
`domain::ota::task`), и узел подтверждает образ в стартовом действии так же.
Уберёте узел и станете применять образ своим кодом — `mark_booted` придётся
звать самому: без подтверждения bootloader откатит образ на следующем сбросе. Сторожа в этом
проекте нет ни в `boot`, ни в приложении: образ, повисший до `mark_booted`,
сам не откатится, пока не сбросят питание, — откат зависшего образа ручной.
{%- endif %}

### USB встаёт на шину после подтверждения

Первая загрузка нового образа (`Swap`) и откаченного (`Revert`) стирает
`STATE` в `mark_booted` — на обычной (`Boot`) стирания нет. Если `STATE` в
одном банке с кодом, ядро на время стирания стоит на выборке инструкций (у
H743 — около секунды на секторе 128K): прерывание USB не обслуживается, хост
не получает дескриптор и бракует устройство (`DEVICE_DESCRIPTOR_FAILURE` в
Windows) до переподключения или сброса МК. Поймано на плате: после отката в
`cargo xtask test host-target` устройство пропадало, а в эксплуатации так же
пропадало бы после каждого обновления — ровно когда хост должен убедиться,
что образ встал.

{% if graph == "true" %}Поэтому узел OTA объявляет `ready` и поднимает его в `begin` после попытки
подтверждения (удачной или нет), а узел `USB` ждёт его: `deps: [OTA ready]` в
`USB_FRAG`.{% else %}Поэтому узел OTA поднимает готовность в `begin` после попытки подтверждения
(удачной или нет) — сигнал `READY_<транспорт>` в
`crates-cross/app/src/tasks/ota.rs`, — а задача узла USB ждёт его
(`crates-cross/app/src/tasks/usb.rs`).{% endif %} Перенесёте
подтверждение из `begin` позже (туда, где устройство доказало
работоспособность, — см. doc у `begin` в `domain::ota`) — переносите и
готовность, иначе стирание снова встретится с перечислением.
{%- endif %}

## Bootloader и внешняя флеш

Раскладка — `docs/flash.md`. Bootloader не должен ни перестать загружаться из-за
отдельной детали платы, ни прыгнуть в наполовину переписанный `ACTIVE`; отсюда
решение по `STATE`, которое принимает проверка нового образа
(`screen_update`, `signature::screen` в `crates-cross/boot`):

- **не читается** — загружается текущий образ: был ли начат обмен, узнать
  нечем, и не начатый — частый случай (заглушка, не распаянная микросхема);
- **читается** — строгий `BootLoader::prepare` (`prepare` в
  `crates-cross/boot/src/external.rs`), без второго чтения `STATE`: отказ
  повторного чтения отправил бы bootloader в `ACTIVE` посреди обмена. Обмен
  запрошен или идёт, и его ошибка — паника, сброс, продолжение обмена по
  журналу с того же места. Прыжок в смесь старых и новых страниц — HardFault,
  а дойди такой образ до узла OTA — его подтверждение навсегда. Нестрогий
  `try_prepare` для читаемого `STATE` не используется.

Ошибка внешней флеши во время проверки подписи запрещает обмен: образ не
проверен, загружается текущий. Запрос на обмен до следующего сброса не
доживает: прежнее приложение в стартовом действии узла OTA (`begin`) зовёт
`mark_booted`, и магия `Swap` снимается. Разовая ошибка флеши у
bootloader'а — потерянное обновление; хост узнаёт об этом по прежней версии
и повторяет. Исключение — магия `Swap` прочитана, а журнал
прогресса нет (`Screening::JournalUnreadable`): обмен, может быть, уже идёт,
и bootloader паникует (сброс, повтор), а не прыгает в `ACTIVE`.{% if graph == "true" %} Сторожа во время обмена нет: bootloader запускает его
только перед прыжком в образ (в release), поэтому страница обмена до
128–256 KiB или весь `STATE` одним вызовом на NOR с сектором 4 KiB — десятки
команд по 45–400 мс — ему не мешают.{% endif %}
{%- endif %}

## Страница обмена во внутреннем flash

Во внутренней OTA страница обмена `embassy-boot` (плейсхолдер `page_size`, `SWAP_PAGE_SIZE`
в `boot` и `bsp::flash`) может быть крупнее физической страницы чипа: на чипе с
мелкой страницей журнал `STATE` (`(2 + 4*N) * WRITE_SIZE`) иначе разрастается и
съедает зону bootloader'а, а подписанный `boot` весит ≈23 KiB. У этого чипа
`ACTIVE` и `DFU` строятся над `ErasePage<_, SWAP_PAGE_SIZE>`; обмен, `prepare`
адаптера `Updater` и подпись работают в этих страницах. Прежний образ
после обмена лежит в `DFU[i + 1]` — со сдвигом на страницу обмена, а не
физическую. Подробности и
границы — `docs/flash.md`, «Страница раздела — не всегда страница чипа».
{%- endif %}

## Подпись OTA-образа

Подпись — часть OTA: отдельного вопроса при генерации нет, есть OTA — образы
подписываются, режима без подписи нет ни в шаблоне, ни в `domain`.
**Подпись проверяет bootloader, а не
приложение**: ключ зашит в `crates-cross/boot`, который обновлением не
перезаписывается, и проверяется ровно то, что сейчас станет `ACTIVE`. Ни
ошибка в OTA-коде приложения, ни запись в `DFU` в обход него не приведут к
запуску неподписанного образа.
{%- if ota_store == "external" %}

**С `ext_flash=yes` подпись не защищает от физического доступа к внешней
микросхеме.** Bootloader проверяет только новый запрос на обмен, а начатый
обмен продолжает без проверки (`screen_update` — см. ниже). Пока `STATE` во
внутреннем flash, подделать «начатый обмен» можно лишь через SWD; на внешней
SPI NOR — клипсой программатора: записать в `STATE` магию обмена с непустым
журналом, в `DFU` — свой образ. Тот же класс — подмена данных на шине между
проверкой и обменом. Нужна защита от этого — держите `STATE` внутри
(`ext_flash=no`) или храните признак «образ проверен» во внутреннем flash.
{%- endif %}

Путь образа:

1. Узел OTA в приложении принимает образ с подписью из
   команды `Start` (нет её — отказ `Signature` до стирания).
2. На `Finish` `domain::ota::update::apply` проверяет то, о чём можно
   сказать хосту сразу: длину, занятость раздела, раскладку памяти, версию
   (защита от отката). Не прошло — код отказа в ответе (`Length`, `Busy`,
   `Layout`, `Rollback`; ошибка флеша — `Device`).
3. Он же пишет подпись и длину (`ports::PendingImage`) записью адаптера
   (`Updater::write`) в запасную страницу `DFU` и помечает обмен; хост слышит `Ready`.
4. Хост шлёт `Reboot`, узел сбрасывает МК.
5. Bootloader{% if graph == "true" %} до запуска сторожа{% endif %} зовёт `domain::ota::boot::screen_update`: запись,
   длина, ключ, SHA-512 образа и подпись ed25519. Сошлось — обмен идёт как
   обычно. Нет — запрос на обмен снимается (`STATE` → `Boot`), загружается
   прежний образ. **Отправитель узнаёт об этом только по версии после
   перезагрузки** — кода отказа у bootloader'а нет, и это осознанная цена.

Что здесь нельзя нарушать:

- **Запись о подписи — в запасной странице `DFU`, по смещению `capacity`
  (размер `ACTIVE`).** `DFU` по построению на страницу больше `ACTIVE`
  (`assert_partitions` в `embassy-boot`), страница нужна только обмену как
  черновик: до него она свободна, а первый же шаг обмена (`ACTIVE[last]` →
  `DFU[last + 1]`) её затирает — к этому времени bootloader запись уже
  проверил. Отдельная запись (свой сектор, `STATE`) не годится: `STATE`
  `embassy-boot` стирает сам. Цена места — окно, в котором обновление
  теряется: первый шаг обмена стирает страницу с записью раньше, чем
  отмечает прогресс в журнале. Сбой питания между стиранием и отметкой —
  журнал пуст, записи нет, и `screen_update` видит новый запрос без записи
  (`NoRecord`): снимает его и грузит прежний образ (`ACTIVE` ещё не тронут).
  Обновление пропадает молча; хост узнаёт об этом по версии после
  перезагрузки и повторяет. Поэтому `prepare` адаптера (`domain::ota::Updater`) стирает
  вместе с `DFU[..capacity]` и запасную страницу (на F4 — сектор 128 KiB,
  секунда-две){% if graph == "true" %}; граница из раздела «Приём образа: стирание отдельно от записи» про таймаут сторожа —
  на одну страницу, и запасная её не меняет{% endif %}.
- **Bootloader проверяет только новый запрос, а не откат.** Магия `Swap` в
  `STATE` держится и после обмена, пока новый образ не подтвердился, — тогда
  `embassy-boot` откатывает его, а запись уже затёрта. Отличить «обмен ещё не
  начинался» `screen_update` может только по журналу прогресса: при `Swap`
  слово 1 всегда стёрто, и пустой журнал — это слово 2, побайтно равное слову
  1 (стёртое значение знать не нужно — у части чипов это `0x00`). Формат
  журнала внутренний у `embassy-boot`; привязку держит host-тест
  `after_the_swap_the_pending_revert_is_left_alone` с настоящим обменом
  `embassy-boot` на флеше в памяти. Обновили `embassy-boot` — этот тест первым
  скажет, если формат сменился. Вся логика проверки в bootloader'е (запись о
  подписи, отличие нового запроса от отката) стоит под host-тестами
  `domain::ota::boot` — с настоящими ключами и настоящим обменом
  `embassy-boot`. Обмен без записи (запрос мимо
  `apply`) — отказ `NoRecord`, а не «проверять нечего»:
  иначе неподписанный образ прошёл бы.
- **Проверка идёт без сторожа.** Это один неделимый вызов — сотня миллионов
  тактов в портируемой реализации, на частоте после сброса секунды (на L4 с
  MSI 4 МГц — около 25 с).{% if graph == "true" %} Программный сторож bootloader запускает только
  перед прыжком, так что проверке он не мешает.{% endif %} Поднимите частоту в
  bootloader'е под свою плату — проверка станет быстрой.
  **Аппаратный сторож (option bytes, `WDG_SW = 0`) с этим несовместим:** такой
  IWDG запущен с самого сброса с таймаутом около полсекунды, и проверка его не
  переживёт — сброс посреди неё, повтор, и так по кругу. Включаете его —
  поднимайте частоту в bootloader'е так, чтобы проверка укладывалась в его
  таймаут, или кормите его из хеширования (`screen_update` читает образ
  кусками) и разбейте проверку ed25519 — в шаблоне этого нет.
- **Размер bootloader'а.** Проверка добавляет ~12 KiB: на F4 release ~23 KiB при
  зоне {% if config == "true" %}32 KiB с разделом настроек{% else %}48 KiB (с разделом настроек — 32 KiB){% endif %}. Bootloader собирается только в release —
  debug-сборки у него нет (она с подписью в зону не влезала: на G4 ~28,5 KiB при
  зоне 28 KiB), поэтому голые `cargo build` его не трогают (`default-members`),
  а `cargo xtask build` и тесты на плате собирают его явно (`-p boot --release`).

- **Ключ и подпись — часть сборки, а не отдельные шаги.** `cargo xtask build`
  создаёт ключевую пару, делает сырой образ и подписывает его: выпуск
  обновления не зависит от того, вспомнил ли человек про отдельный шаг, и
  ключ не вставляется в исходник руками. `cargo xtask sign` подписывает уже
  собранный `app.bin` — так подписывает релиз, у которого ключ появляется
  после сборки.
- **Четыре состояния ключевой пары** (`ensure_signing_key` в `xtask`): нет обоих
  файлов — создаём пару; есть закрытый без открытого — выводим открытый (корень
  доверия тот же); есть оба — сверяем и отказываемся работать при расхождении;
  **есть открытый без закрытого — собираем, но не подписываем**. Последнее — это
  каждый CI-прогон и каждый свежий клон (закрытый в `.gitignore`, открытый
  коммитится), и ронять на нём сборку нельзя: для компиляции закрытый ключ не
  нужен вовсе. Но и создавать новый там нельзя — прошивка с ним не принималась
  бы уже прошитыми устройствами. Новый корень доверия выпускается только
  удалением обоих файлов. Все четыре состояния закреплены тестами `xtask`.
- **Открытый ключ приезжает файлом, а не правкой исходника.**
  `ota-public-key.bin` в корне проекта коммитится, `boot/build.rs` кладёт его в
  `OUT_DIR`, `boot/src/signature.rs` берёт через `include_bytes!` в статик
  `OTA_PUBLIC_KEY_IN_IMAGE`. Через промежуточный файл — чтобы `[u8; 32]`
  собирался и когда ключа ещё нет: `build.rs` пишет тогда 32 нуля.
- **Проводку ключа проверяет `cargo xtask build`.** Статик
  `OTA_PUBLIC_KEY_IN_IMAGE` имеет имя в ELF bootloader'а, и перед подписью
  `build` сверяет его байты (в release-ELF `boot`) с открытым ключом из
  закрытого, которым подписывает. Разошлись (нули, чужой файл, устаревшая
  сборка) — сборка падает, а не выпускает образ, который устройство отвергнет.
- **`cargo::rerun-if-changed` печатается только на СУЩЕСТВУЮЩИЙ файл ключа.**
  Отсутствующий по такому пути файл cargo считает вечно устаревшим, и скрипт
  перезапускался бы на каждой сборке. Цена решения: ключ, появившийся мимо
  `cargo xtask build`, требует `cargo clean -p boot`. По той же причине файл в
  `OUT_DIR` переписывается, только если содержимое изменилось.
- **Не найден и не прочитался — разные случаи.** Нули подставляются лишь при
  `NotFound`; любая другая ошибка чтения — паника сборки. Иначе права на файл
  или занятый файл дали бы молча собранный bootloader, отвергающий ЛЮБОЕ
  обновление.
- **Нулевой ключ отвергается отдельной проверкой** (`ScreenFailure::NoPublicKey` в
  `screen_update`). Убирать её нельзя: нулевой ключ ed25519 — валидная точка
  малого порядка, подпись для такой подделывается за считанные попытки, а
  `salty` (как и эталонная реализация) точки малого порядка не отсеивает.
  Цена переноса проверки в bootloader: приложение ключа не знает и отказать
  сразу не может — bootloader с нулевым ключом (собранный мимо `cargo xtask
  build`, до создания пары; `build.rs` об этом предупреждает) отвергает каждое
  обновление уже после перезагрузки, а отправитель видит успешную передачу и
  прежнюю версию. `cargo xtask build` создаёт пару до сборки, поэтому через
  него такой bootloader не получится.

- **Подписывается SHA-512 образа, а не образ.** Так считает
  `screen_update`, и так же — хостовая команда. Менять одну сторону, не меняя
  другую, нельзя.
- **`salty` на обеих сторонах — один и тот же крейт**, поэтому формат совпадает
  по построению; взят он, а не `ed25519-dalek`: меньше и написан под
  микроконтроллеры. Фича `slow-motion` (портируемая tweetnacl-реализация вместо
  ассемблерной под Cortex-M4/M33) выбрана осознанно: компактнее и работает на
  любом ядре, ценой скорости однократной проверки.
- **Длина образа проверяется дважды, и обе проверки нужны.** Приложение
  (`apply`, `UpdateError::TooLong`) — чтобы отказать отправителю сразу, а
  не после перезагрузки. Bootloader (`ScreenFailure::Length`) — потому что запись в
  `DFU` мог оставить и не тот код.
- **Порядок проверок в `apply` — ради различимых отказов.** Длина
  первой (`TooLong`), занятость раздела до версии (`Busy`: в `DFU` тогда лежит
  образ отката, версия у него заведомо старее, и «откат» соврал бы о причине),
  образ короче хвоста (раскладка и версия, 8 байт) — `Truncated`, чужая
  раскладка — `Layout` (до версии: у такого образа и версия — номер другой
  прошивки), версия — `Rollback`. Каждому
  отказу свой вариант `domain::ota::update::UpdateError`, и это проверяется host-тестами
  `domain::ota::update`.
- **Закрытый ключ (`ota-signing-key.bin`) в git не попадает** — он в
  `.gitignore`. Появится соблазн закоммитить «чтобы не потерялся» — значит
  подпись больше ничего не значит.
- **Хвост образа — `[образ][раскладка u32 LE][версия u32 LE]`.** Оба поля
  дописывает `cargo xtask build`, оба подписываются вместе с образом.
- **Версия образа лежит в его последних четырёх байтах** (защита от отката,
  `domain::ota::update::VERSION_BYTES`, проверка в `apply`). Место выбрано
  не из удобства: своя секция сразу за таблицей векторов накладывается на
  `.text` — линкер отказывается собирать (`section .fw_version virtual address
  range overlaps with .text`, проверено), а любое другое место внутри образа
  разъезжается от первой же правки кода. Хвост подписывается наравне с
  остальным и адресуется одним вычитанием из длины (`len - 4`). Сравнение со
  своей версией — `domain::ota::version::is_upgrade` (строго «новее»), отказ —
  `UpdateError::Rollback { current, incoming }`.
- **Версию проверяет приложение, а не bootloader.** Bootloader не знает версию
  текущего образа: запись о длине есть только у нового. Приложение знает свою
  (свойства образа своего бинарника; узлу OTA её отдаёт {% if graph == "true" %}граф —
  `running_version` во входе `OTA_FRAG`{% else %}задача — `running_version` контекста
  `OtaCtx`, `crates-cross/app/src/tasks/ota.rs`{% endif %}), а версию нового читает из хвоста `DFU` — из ещё не
  проверенных байтов, но подделать её нельзя: она внутри подписанного, и
  bootloader, проверяя подпись, проверит и её.
- **Bootloader версию не проверяет — защита от отката только в приложении.**
  Bootloader примет любой верно подписанный образ — и старый, с уже закрытой
  уязвимостью, тоже: версии он не сравнивает. Пока обмен запрашивает только
  `apply`, это не дыра — старый образ отвергнут на `Finish` (`Rollback`).
  {%- if ota_store == "external" %} С `ext_flash=yes` и физическим доступом к микросхеме — дыра: старый
  подписанный образ с его же записью `PendingImage` кладётся программатором в
  `DFU`, магия `Swap` с пустым журналом — в `STATE`, и bootloader подпись
  проверит и обмен пропустит. Откат так возможен; закрывает его только
  счётчик версии, который bootloader сверяет во внутреннем flash, — в шаблоне
  его нет.{% else %} Обойти приложение можно только через SWD, а с ним
  `ACTIVE` переписывается и без всякого обмена.{% endif %}
- **Версию дописывает `cargo xtask build`, читая её из символа
  `FW_VERSION_IN_IMAGE` в ELF, а не из `crates-cross/Cargo.toml`.** Символ
  определяет каждый бинарник `app` из своих свойств образа (`IMAGE.version`;
  у рабочего, `crates-cross/app/src/main.rs`, — из `version` манифеста), и `build` дописывает его до подписи — версия внутри подписанных
  байтов, соврать ею нельзя. В манифесте
  лежит то, что попросили, в образе — то, что получилось; разойтись они могут
  тихо (своя `version` у пакета вместо наследования от воркспейса), и тогда
  устройство сравнивало бы номер, которого в прошивке нет. По той же причине
  статику нужны и `#[used]`, и `#[unsafe(no_mangle)]`: первое просит оставить
  его, второе — сохранить имя для поиска. Гарантия тут не абсолютная (`#[used]`
  обязывает компилятор, но не линкер с `--gc-sections`; см. doc-комментарий
  статика), зато провал громкий: `build` не найдёт символ и остановится.
- **Перед версией — отпечаток раскладки памяти** (`LAYOUT_BYTES`, четыре
  байта на `len - 8`): FNV-1a 32 над шестью границами из `memory.x`, общими у
  приложения и bootloader'а, — `__bootloader_{state,active,dfu}_{start,end}`
  по порядку, каждая `u32` LE (`ports::LAYOUT_SYMBOLS`,
  `ports::layout_fingerprint`). `cargo xtask build` берёт значения этих
  символов из ELF приложения, сверяет с ELF bootloader'а (разошлись — ошибка
  сборки) и печатает `раскладка: 0x…`; прошивка считает тот же отпечаток по
  адресам символов в рантайме (`bsp::layout::fingerprint` →
  `ports::Partitions`, адаптер
  `Updater::layout`). На `Finish`, до
  `mark_updated`, узел сверяет отпечаток из хвоста со своим: не совпал —
  отказ `Layout` (`UpdateError::Layout`, код 17), обмен не запрашивается.
  Размеры страниц в отпечаток не входят: они у пары общие из генерации.
- **Изменилась раскладка — bootloader перешивается по проводу.** Bootloader
  обновлением не перезаписывается и ищет разделы по своей, старой раскладке:
  образ под новую он обменял бы не теми страницами, а сам образ, слинкованный
  под другой `ACTIVE`, не запустился бы. Поэтому такой образ приложение
  отвергает на `Finish` (`Layout`), а новую раскладку ставят `cargo flash -p
  boot --release` и прошивкой приложения по проводу.
- **target-тест `ota_rejects_an_older_image` готовит хвост `DFU` сам.** Проверка
  версии читает раздел, где лежат остатки прошлых прогонов, поэтому тест пишет
  в хвост известную версию, а готовить его можно только через `prepare(len)`:
  запись сама не стирает (см. «Приём образа: стирание отдельно от записи»).
  Сначала в хвосте версия `0.0.0` — с отпечатком раскладки самой платы перед
  ней, иначе отказ пришёл бы раньше, `Layout`, — и тест требует `Rollback`;
  следом — заведомо большая, и отказ обязан прийти уже не по версии. Вторая
  половина не для симметрии: без неё тест остался бы зелёным, даже если бы
  проверка отвергала вообще всё. Она доходит до записи для bootloader'а и
  пометки обмена — и сама снимает пометку (`mark_booted`), чтобы не оставлять
  запрос соседям по прогону.
- **`domain::ota::update::UpdateError` вместо `FirmwareUpdaterError`** — по правилу «разные
  отказы должны быть различимы»; ошибка адаптера (`domain::ota::UpdaterError`)
  приходит вариантом `Flash(_)`.
- **Без подписи защита от отката была бы видимостью.** Версия в образе
  правилась бы так же свободно, как и всё остальное, поэтому подпись у OTA
  обязательна. Обмен узел
  запрашивает только через `apply`, который перед `mark_updated()` кладёт
  запись о подписи.
  Сам адаптер обмен без записи не запрещает — его отклонит bootloader
  (`NoRecord`): `prepare` адаптера стирает запасную страницу,
  так что старая запись под новый образ не попадёт.
- **Хостовые зависимости `xtask`: `salty` — только с OTA, `getrandom` — с OTA
  или секретами служб, `object` — всегда** (сырой образ нужен и без OTA).
  Условие — Liquid в комментариях манифеста, как во всём корневом workspace
  (`docs/architecture.md`). Проверка подписи — `domain::ota::boot` под фичей `domain/boot`, которую
  включает `boot`, а `cargo xtask lint`/`test host`
  на хосте — через `--features domain/log,domain/boot`; сквозной тест «что
  пишет адаптер, то находит bootloader» — тоже в `domain` (`ota::updater`),
  под той же фичей.
- **Путь к ELF в `build` строится от `CARGO_TARGET_DIR`**, а не от
  `crates-cross/target`: с общим кешем (так устроены CI) жёсткий путь не
  находит ничего.
- **Пропуски в сыром образе заполняются `0xFF`** (`GAP_FILL` в
  `crates-host/xtask/src/image.rs`). Значение любое, лишь бы одно у хоста и в
  образе: пропуски уезжают в `DFU` вместе с образом, и хеш раздела на
  устройстве должен совпасть с посчитанным на хосте. «Стёртое состояние
  флеша» это значение называть нельзя — на L0/L1 оно нулевое.
- **Из ELF берётся физический адрес сегмента, а не виртуальный.** У `.data`
  они разные: секция исполняется из RAM, но лежит во флеше. Поэтому разбор
  идёт через `ElfFile32` и заголовки программы — общий `object::File` отдаёт
  только виртуальный, и в образе появилась бы дыра в сотни мегабайт.

## Тесты OTA по протоколу (host-target)

`cargo xtask test host-target` проверяет готовое устройство только так, как с
ним говорит настоящий хост: через транспорт и протокол проекта
(`crates-host/host-target-tests`: клиент — `src/lib.rs`, сценарии —
`tests/test.rs`). Ни чтения памяти, ни записи в `DFU`/`STATE` мимо
приложения, ни сброса пробником: пробник лишь необязательно прошивает плату
перед тестами (есть — шьются release-образы, нет — тесты идут против того, что
уже прошито), перепрошивки после тестов нет.
{%- if has_protobuf == "true" %} Адрес устройства —
`HOST_TARGET_ADDR` или `HOST_TARGET_PORT` (README, «Трёхэтапное
тестирование»); без него сценарии пропускаются, и `xtask` пишет это в сводке.
Первая итерация — protobuf; под остальные протоколы сценарии те же, встанут
вторым клиентом (`src/lib.rs`).

Сценарии (по одному, `--test-threads 1`: канал один, а `Reboot` одного
сценария рвёт связь другому):

- `info_answers` — устройство на связи, чип тот, версия — прошитая (если шили);
- `reboot_comes_back` — `Reboot` отвечает до сброса, устройство возвращается,
  причина сброса — `software`;
- `unsigned_start_is_rejected` — `Start` без подписи: `Signature` до стирания
  раздела, работает прежняя прошивка;
- `foreign_signature_is_not_swapped` — образ под чужим ключом: `Finish`
  проходит (приложение — `domain::ota::update::apply` — подпись не проверяет,
  это делает bootloader), после `Reboot` версия прежняя;
- `unconfirmed_image_is_swapped_and_rolled_back` — главный тест обмена:
  загрузка тестового образа, `Reboot` — работает он (`Info` называет метку
  `unconfirmed`, обмен состоялся), ещё `Reboot` — прежняя версия (откат);
- `same_version_is_rejected` — рабочий образ той же версии: `Rollback`.

Теста «новый образ подтвердился и остался» нет намеренно: он оставил бы
плату на тестовом образе.

`cargo xtask test host-target` говорит это и проходит пустым.

### Тестовый образ `app-unconfirmed`

Откат проверяется только на образе, который себя не подтверждает, — рабочая
прошивка подтверждает себя в `begin` узла OTA. Поэтому тестовый образ —
отдельный бинарник того же `app` (`[[bin]] app-unconfirmed`,
`crates-cross/app/Cargo.toml`) со своим запуском
(`crates-cross/app/src/bin/app-unconfirmed.rs`; всё, что не запуск, у обоих —
библиотека пакета) и своими свойствами образа — константой `IMAGE`
(`app::version::Image`), которую он отдаёт в `spawn_all`:

- узел OTA получает во входе `confirmed = IMAGE.confirmed` (`true`) — слот
  «уже подтверждён», и `mark_booted` не зовётся ни при старте, ни на
  `Start`; логика узла та же, что у рабочего образа;
- версия — рабочая + 1 (`app::version::PACKAGE_VERSION` + 1; свой символ
  `FW_VERSION_IN_IMAGE` у бинарника тоже свой):
  ровно настолько, чтобы устройство на рабочем образе приняло его (защита от
  отката — строго «новее»), и не больше. Не `u32::MAX`: подписанный ключом
  проекта образ «новее всего», встань он однажды насовсем (утечка, ошибка в
  подтверждении), закрыл бы устройству все обычные обновления; `+1` — самое
  большее одну версию;
- хосту (`Info`{% if has_modbus == "true" %}, Modbus FC43{% endif %}) и в баннере он называет себя меткой
  `unconfirmed` вместо версии: по ней тест видит, что обмен состоялся, не
  читая флеш;
- в логе старта — `warn!` «ТЕСТОВЫЙ образ app-unconfirmed».

Собирает его только `cargo xtask test host-target` (`cargo build -p app
--release --bin app-unconfirmed`, без фич): `cargo xtask build` собирает
только `--bin app`, так что в `app.bin` релиза он не попадает, а `cargo flash`
шьёт `--bin app`. Голый `cargo build` в `crates-cross/` собирает оба
бинарника, `cargo xtask lint cross` линтует оба. Образ OTA из него — та же
функция, что у `build` (`ota_image` в `crates-host/xtask/src/firmware.rs`:
сырой образ, хвост `[образ][раскладка][версия]`, сверка раскладки с
bootloader'ом). Подписей две: ключом проекта (`HOST_TARGET_UNCONFIRMED_SIG`) и
случайным ключом, которого нет ни в одном bootloader'е
(`HOST_TARGET_FOREIGN_SIG`). Закрытого ключа нет (CI, свежий клон) — тест
обмена пропускается, остальные идут.

Ключом проекта подписан образ, который устройство примет как настоящее
обновление, поэтому пережить прогон он не должен: образы и подписи `xtask`
пишет только в свежий временный каталог ОС (имя — 16 случайных байт;
существующий не берётся; на unix права 0700) и удаляет его в конце `test
host-target` — и после ошибки, и при панике; ни в `target/`, ни
рядом с `app.bin` их нет. Оборванный снаружи процесс (Ctrl+C) каталог
оставит — он во временных файлах ОС. ELF `app-unconfirmed` в `target/`
остаётся, но он не подписан. Сам образ на устройстве тоже не задерживается:
подтверждения нет, и первый же сброс возвращает прежний.

### Чего без пробника не проверить

Ключ в bootloader'е `xtask` сверяет с ключом подписи по собранному ELF
(`ensure_image_key`), но в уже прошитой плате может стоять bootloader другой
сборки. Без пробника этого не узнать: тест обмена при провале называет эту
причину сам. Ожидаемая версия (`HOST_TARGET_EXPECT_VERSION`) тоже передаётся
только после своей прошивки, и отказ той же версии пропускается, если
устройство старше собранного образа. Каждый такой пропуск сценарий пишет в
журнал (`host_target_tests::skip`, `HOST_TARGET_SKIP_LOG`), и `xtask` после
прогона печатает, сколько сценариев и почему прошли, ничего не проверив.

### Сроки

Медленные шаги — стирание `DFU` на `Start`, `Finish` (запись для
bootloader'а и стирание `STATE`) и сброс с обменом разделов — ждут по размеру
`ACTIVE` (`HOST_TARGET_ACTIVE_LEN`, `slow_timeout`): 20 с плюс 10 с на каждые
128 KiB переноса (худший случай — F0/F1 с записью полусловами), а переносится
вдвое больше `ACTIVE`. Предел ограничивает только провал: успех ждёт ответа
устройства. Сколько ушло на самом деле — `устройство ответило через …` в
выводе с `--no-capture`.
