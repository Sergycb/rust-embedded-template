# Диагностика падений: паникёр по профилю, регион `PANIC`, причина сброса

## Два паникёра, один на сборку

Выбирает профиль — `#[cfg(debug_assertions)]` в `crates-cross/app/src/panic.rs`.{% if ota == "true" %} Это
паникёр приложения; у bootloader'а свой — сброс МК без сообщения и без дампа
(`crates-cross/boot/src/main.rs`): на сбросе держится восстановление после сбоя флеша
(строгий `prepare` паникует, следующий старт продолжает обмен по журналу), а формат
причины стоил бы зоны bootloader'а.{% endif %}

| Профиль | Паникёр | Что делает | Почему |
|---|---|---|---|
| debug | `panic-probe` (`print-defmt`) | печатает причину через defmt, `udf()` | пробник ловит остановку там, где упало, со стеком |
| release | свой `#[panic_handler]` поверх `panic-persist` | пишет причину в регион `PANIC`, печатает её в defmt, сброс МК (`bsp::reset::Reboot`) | устройство возвращается в работу; причину печатает и следующий старт |

Release-обработчик свой, а не штатный из `panic-persist`, ради строки в RTT: с
подключённым пробником причина видна сразу, без `cargo xtask panic-info`. Крейт собран с
фичей `custom-panic-handler` — собственного `#[panic_handler]` у него нет, остаётся
`report_panic_info`. Порядок внутри — сначала дамп, потом печать: дамп ничто не
должно задержать. Печать не блокируется — `defmt-rtt` собран с
`disable-blocking-mode`, и строка, не влезшая в буфер без пробника, просто
теряется, а сброс всё равно происходит. Флаг повторного входа не даёт панике внутри самого defmt
затереть первую причину и уйти в рекурсию до конца стека.

Развилка по профилю — `#[cfg(debug_assertions)]` на `use … as _;`, а не Cargo-фича:

- `#[panic_handler]` и `#[global_logger]` требуют ровно одной активной реализации
  **на бинарник** — это ограничение rustc/линкера, а не Cargo, а `debug_assertions`
  уже даёт ровно одно значение на сборку (`dev`/`test` → `true`, `release` → `false`).
- Cargo гейтить сами зависимости по профилю не умеет:
  `[target.'cfg(debug_assertions)'.dependencies]` резолвится через
  `rustc --print=cfg` независимо от профиля (rust-lang/cargo#7634). Поэтому обе
  стороны развилки — обычные зависимости `app`, а выбор — только `cfg` на `use`.
- **Осторожно с `[profile.dev]`/`[profile.release]` в `crates-cross/Cargo.toml`**:
  `debug-assertions` там задан явно (ради `overflow-checks`), и правка этого поля
  по несвязанной причине молча переключит все развилки, без предупреждения
  компилятора.

Проверено эмпирически — два разных механизма, не путать:

- **Паникёр.** Крейт, на который в исходнике нет ни одной ссылки (`use` отсутствует
  вовсе, а не `cfg`-исключён), не линкуется и `#[panic_handler]` как lang item не
  регистрирует — поэтому `panic-probe` обычной зависимостью и `cfg` на `use` не
  конфликтует с release-обработчиком. Нарушение инварианта компилятор ловит
  ошибкой «duplicate lang item» (или «`#[panic_handler]` function required» — если
  не остался ни один).
- **Логгер.** `#[global_logger]` резолвится линковкой по имени символа
  (`_defmt_acquire` и т.п.), и два активных `use` разом дают жёсткое `error: Linking
  globals named '_defmt_acquire': symbol multiply defined!`. При правке
  `crates-cross/app/src/panic.rs` держите «ровно один `use <логгер> as _;` активен на
  сборку» (`docs/modules/app.md`, «defmt-транспорт для `release` без пробника: UART»).

Инвариант — на бинарник, а не на workspace: у `crates-cross/target-tests` паникёр
самого `embedded-test`, и паника там — способ сообщить раннеру про упавший тест.

`panic-abort` не использовать — не собирается на stable (требует nightly
`#![feature(core_intrinsics)]`, не обновлялся с 2019). `panic-halt` тоже не подключён:
остановка получается и без него — `panic-probe` под debug у `app`, — а держать ради
этого ещё одну реализацию `#[panic_handler]` незачем.

## Регион `PANIC`

Отрезан от конца RAM при генерации (регион `PANIC` в `crates-cross/app/memory.x`),
адресуется символами `_panic_dump_start`/`_panic_dump_end` из `memory.x`. Регион
обязателен: без этих символов release-образ не слинкуется. Секции у него нет, и это
ограничение, а не стиль: `flip-link` считает занятую часть RAM по адресам секций,
секция у верхней границы RAM убеждает его, что двигать стек некуда, `_stack_start`
остаётся в начале RAM, и первый же `push` уходит за границу — HardFault, `LOCKUP`.
Где держать свои данные, переживающие сброс, — `docs/modules/app.md`, «PANIC и
данные, переживающие сброс». Формат записи — `panic-persist`: магия
`0x0FACADE0` по смещению 0, длина по 4, байты сообщения с 8; его же читает
`cargo xtask panic-info` через `probe-rs read`.

Читается сообщение ровно один раз: `get_panic_message_utf8` стирает магию, чтобы одно
падение не всплывало после каждого сброса. Следствие для `cargo xtask panic-info`: если
release-приложение успело стартовать, дамп уже вычитан и ушёл в defmt-лог того запуска.
Читает её `panic::take()` (`crates-cross/app/src/panic.rs`) — один раз, в `main` до
`Board::new`, — и запоминает: сведения об устройстве берут ту же строку позже через
`panic::last()`. В dev обе — всегда `None`.

## Причина сброса

`main` приложения первым делом, до `Board::new`, читает флаги сброса `RCC`
(`bsp::reset::take_cause`) и снимает их битом `RMVF` — один раз за запуск и больше нигде{% if ota == "true" %}: bootloader флаги не трогает, и до
приложения они доходят как есть{% endif %}. Регистр и поля у семейств свои (`CSR`, `CSR2` у C0,
`RSR` у H5/H7; `WDGRSTF`/`PADRSTF` у F2/F4/F7, `IWDG1RSTF` у H7, `PWRRSTF` у G0/U0/C0) —
их выписывает генерация из `stm32-metapac`.{% if watchdog_peripheral == "IWDG2" %} У ядра CM4 двухъядерного H7 свои флаги
(`SFT2RSTF`, `IWDG2RSTF`, `WWDG2RSTF`, `LPWR2RSTF`): полей для них в `stm32-metapac` нет, и
`take_cause` читает их сырыми битами — первыми.{% endif %} Флагов бывает несколько сразу (любой
внутренний сброс ставит и флаг вывода `NRST`), поэтому причина — самая конкретная:
выход из low-power, оконный сторож, независимый сторож, программный сброс, option
bytes, питание, вывод; ни одного — `unknown`. Причина — строка в `snake_case`
(`low_power`, `window_watchdog`, `independent_watchdog`, `software`, `option_bytes`,
`power_on`, `pin`, `unknown`), её печатает строка старта `app: причина сброса …`.
Почему один раз и первым делом: второе чтение за запуск увидело бы пустой
регистр (`unknown`), а не снятые из-за повисшего старта флаги копились бы от
сброса к сбросу — после цикла сбросов по сторожу и кнопки плата назвала бы
причиной сторож.
{%- if has_protobuf == "true" or net_services != "" or has_cli == "true" %}

Обе вещи уходят наружу в сведениях об устройстве (`domain::device::DeviceInfo`:
`reset`, `last_panic`){% if has_protobuf == "true" %} — protobuf `Info.reset`/`Info.last_panic`{% endif %}{% if net_services contains "rest" %}, REST `/api/info`{% endif %}{% if net_services contains "mqtt" %}, тема MQTT `info`{% endif %}{% if net_services contains "ssh" %}, `info` в консоли SSH{% endif %}{% if has_cli == "true" %}, `info` в консоли `cli`{% endif %}.
Паника — коротко (`domain::device::panic_brief`, до `PANIC_BRIEF` = 96 байт): файл без
каталогов, строка, столбец и первая строка сообщения; нет паники — `null`{% if has_protobuf == "true" %} (в protobuf —
пустая строка){% endif %}. Так хост видит, что плата перезагрузилась сторожем или паникой, без
пробника и без `cargo xtask panic-info`.{% if has_protobuf == "true" %}

**protobuf `Info` отдаёт это без аутентификации** — любому, кто достучался до
транспорта протокола{% if has_udp == "true" %} (по UDP — любому отправителю датаграммы в сегменте){% endif %}: версию, коммит,
номер чипа, причину сброса и `last_panic` — место паники и первую строку её сообщения, а
в сообщении бывают значения (`assert!` с фактическими числами). Решение осознанное: протокол —
служебный канал наладки и обновления, и прятать от него диагностику незачем; кому это
лишнее, тот не кладёт секретов в тексты паник или убирает поле из ответа
(`domain::protobuf::info`, `host.proto`).{% endif %}
{%- endif %}

## Чего здесь нет
{%- if ota == "true" %}

- **`HardFault` и паника в bootloader'е не пишут причину.** В приложении фолт (мусорный
  указатель, прыжок по битому адресу) обработчик `app/src/fault.rs` превращает в панику с
  регистрами причины — она и попадает в `PANIC`. У `boot` обработчика нет (с LTO он
  занял бы около 14 KiB зоны), и `cortex-m-rt` подставляет туда бесконечный цикл:
  под пробником `probe-rs run` ловит отказ vector catch'ем и показывает место, а в
  поле плата так и останется в цикле{% if graph == "true" %} — сторож bootloader запускает только перед
  самым прыжком в образ{% endif %}. Паника bootloader'а — сброс МК без записи в `PANIC`;
  паника, которая повторяется на каждом старте, даёт молчаливый цикл сбросов —
  искать её пробником (`probe-rs attach`, точка останова на `rust_begin_unwind`).
{%- endif %}

- **Замера стека нет.** От переполнения защищает `flip-link` (фолт и `Lockup` ядра вместо
  тихой порчи статики: кадр исключения положить некуда, и обработчик `HardFault` не
  выполняется — `docs/clocks.md`, «Ядро: фолты и ловушка деления»); «сколько запаса
  осталось» шаблон не меряет.
